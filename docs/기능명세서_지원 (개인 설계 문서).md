## 1. 개요

누구나 회원가입 후 자기 블로그를 개설하고, 글을 발행하고, 다른 블로그를 구독·공감·댓글로 소통할 수 있는 멀티 유저 블로그 플랫폼을 만든다. 기준 모델은 티스토리이다.

통합 명세의 동작 규칙과 우선순위(P0 필수 · P1 권장 · P2 확장)는 그대로 따른다. 이 문서는 통합 명세에 있는 규칙을 반복하지 않고 ID로만 가리키며, 아래만 적는다.

1. 선택 항목에서 고른 방식 (2장)
2. 기술 스택 (3장)
3. 공통 구현 정책: 권한, 주소, 페이지네이션, 보안 (4장)
4. 기능 ID별 구현 방식과 자체 기능 (5장)
5. 화면 주소와 주요 흐름 (6장)
6. 일정, 자율로 정한 값, 통합 명세와 다른 점, 남은 일 (7\~10장)

## 4. 공통 구현 정책

### 4.1 권한 구현 (통합 3장)

1. **저장되는 역할**: member.role의 USER와 ADMIN 두 가지뿐이다. 비회원과 블로그 주인은 요청마다 토큰 유무와 blog.member\_id로 판단하는 상태다.
2. **부여**: 가입하면 항상 USER다. ADMIN은 화면이나 API로 얻을 수 없고 DB 초기 데이터로만 지정한다.
3. **검사 위치**: role은 Spring Security에서 URL 단위로(/api/admin/\*\*는 hasRole('ADMIN')), 블로그 주인 여부는 서비스 계층에서 대상 블로그를 조회한 뒤 검사한다. 수정·삭제 API는 서버에서 작성자·블로그 주인 여부를 반드시 검증한다.
4. **실패 응답**: 토큰이 없으면 401, 권한이 없으면 403. 남의 비공개 글은 존재를 숨기려고 404다.

### 4.2 블로그 주소·이사·삭제 (BLOG-01·06·07, 통합 4.2)

1. **주소 규칙 구현**: 정규식 `^[a-z0-9][a-z0-9-]{2,30}[a-z0-9]$`, 예약어(www, api, admin, static, mail, login 등) 거절.
2. **주소 해석**: 서버는 요청의 Host 헤더에서 서브도메인을 읽어 블로그를 찾는다(myblog.blog.com → myblog). 플랫폼 도메인(blog.com, www.blog.com)은 플랫폼 홈·로그인·글쓰기 화면이다. 로컬 개발은 myblog.localhost:8080으로 테스트한다.
3. **이사 대상**: 같은 회원의 활성 블로그만 지정할 수 있다. 자기 자신이나 삭제된 블로그는 안 된다.
4. **이사 후 동작**: 옛 블로그 홈 방문자는 새 블로그로 301 리다이렉트된다. 주인은 관리 화면으로 계속 들어갈 수 있다.
5. **글 이동과 이사는 별개**: 옮긴 글만 새 블로그로 리다이렉트되고, 옮기지 않은 글은 옛 블로그에 그대로 남는다. 옮긴 글의 카테고리는 '미분류', 태그는 이름으로 대상 블로그 태그에 다시 연결한다.
6. **연쇄 이사**: A → B 뒤 B → C로 이사하면 A의 대상도 C로 바꿔, 리다이렉트가 한 번만 일어나고 순환이 생기지 않게 한다.
7. **삭제는 소프트 삭제**: 사용자에게는 블로그가 사라지지만 내부적으로는 deleted\_at만 기록하고 행을 남긴다. 그래야 주소 재사용이 영구히 막히고 리다이렉트도 유지된다.
8. **개설 한도**: 5개는 활성 블로그만 센다. 삭제와 재개설을 반복해 주소를 선점하는 문제는 우선 허용하고, 필요하면 총 개설 수나 개설 간격 제한을 추가한다.
9. **이사 간 블로그 삭제**: 새 블로그(B)를 나중에 삭제하면 옛 블로그(A)의 리다이렉트도 끊기고 '존재하지 않는 블로그'가 된다.

| 요청 | 결과 |
| --- | --- |
| old.blog.com (이사함, 삭제 여부 무관) | 새 블로그 홈으로 301 |
| old.blog.com/15 (15번 글을 새 블로그로 옮김) | 글이 지금 속한 new.blog.com/15로 301 |
| old.blog.com/16 (옮기지 않은 글, 옛 블로그 삭제됨) | 404 |
| 삭제된 블로그의 주소로 새 블로그 개설 | 거절 (주소 영구 사용 불가) |

### 4.3 글 주소 (통합 4.3, 선택 7.5)

1. 사람용 글 주소는 `{address}.도메인/{post-id}`(예: myblog.blog.com/15)다. 서버는 Host에서 블로그를, 경로에서 글 번호를 읽어 확인이 끝나면 React 앱(index.html)을 돌려주고, React 라우터가 글 상세 화면을 띄운 뒤 API를 호출한다.
2. post-id는 전역 번호다. 글이 그 블로그 소속이 아닐 때, 글이 있고 볼 수 있으면 지금 소속 블로그 주소로 301 리다이렉트(블로그 이사 대비)하고, 없거나 볼 수 없으면 404다.

### 4.4 페이지네이션 (통합 4.4)

목록은 페이지 번호 방식(offset)을 기본으로 한다. 요청은 `?page=0&size=10`(page는 0부터), 응답은 content, page, size, totalElements, totalPages를 담는다. 짧은 목록은 페이지네이션 없이 고정 개수만 내려준다. 계속 쌓이는 피드는 커서 방식을 쓴다.

| 목록 | 방식 | 기본 크기 | 정렬 |
| --- | --- | --- | --- |
| 블로그 메인 글 목록 (카테고리별·태그별 포함) | 페이지 번호 | 10 | 최신순 |
| 블로그 내 검색 결과 | 페이지 번호 | 10 | 최신순 |
| 플랫폼 홈 최신 글, 구독 피드 | 더보기 (커서) | 20 | 최신순 |
| 내 글 관리 | 페이지 번호 | 20 | 최신순 |
| 댓글 | 더보기 | 20 (답글은 부모에 포함) | 작성순 |
| 방명록 | 페이지 번호 | 20 | 최신순 |
| 인기 글 순위 | 없음 | 상위 10 | 인기 점수순 |
| 주제별 글 | 없음 | 6 | 인기 점수순 |
| 사이드바 최근 글·최근 댓글 | 없음 | 각 5 | 최신순 |
| 카테고리·태그 목록 | 없음 | 전체 | 카테고리는 sort\_order, 태그는 글 수순 |

1. **정렬 기준**: '최신순'은 처음 발행한 시각(published\_at) 내림차순, 같으면 id 내림차순이다. 통합 4.4에 맞춰 created\_at에서 바꿨다. 임시저장 후 나중에 발행한 글도 발행 시각 기준으로 놓인다.
2. **커서 방식**: 홈 최신 글·구독 피드는 '마지막으로 받은 글의 (published\_at, id) 이후'를 요청한다. 더보기 중에 새 글이 들어와도 같은 글이 두 번 나오거나 빠지지 않아야 하기 때문이다(통합 4.4 ③).
3. **size 상한**: 1\~50만 허용한다. 50을 넘으면 50으로, 1 미만이면 기본 크기로 보정한다.
4. **범위 밖 요청**: page가 음수면 0으로 보정한다. 마지막 페이지를 넘으면 404가 아니라 빈 content를 돌려준다.
5. **페이지 번호 화면**: 티스토리처럼 번호를 10개씩 묶어 보여 주고(1\~10, 다음), 이전·다음 버튼을 둔다.
6. **개수에 포함되는 글**: 보는 사람이 볼 수 있는 글만 센다. 주인이 아니면 비공개 글과 삭제된 글은 목록과 totalElements 모두에서 빠진다.

### 4.5 보안·비기능 구현 (통합 8장)

1. **비밀번호**: bcrypt 해시 저장.
2. **XSS**: 에디터가 만든 본문 HTML을 저장하기 전에 서버에서 OWASP Java HTML Sanitizer로 정화한다. 허용 목록은 문단 제목, 굵게·기울임, 목록, 인용, 코드 블록, 링크(http/https만), 이미지(자체 업로드 경로)이고, script·이벤트 속성(onclick 등)·style은 제거한다. 출력할 때는 브라우저에서 DOMPurify로 한 번 더 정화한 뒤 넣는다(이중 방어). 클라이언트 정화만 믿지 않는 것은 API로 HTML을 직접 보내도 막기 위함이다. 본문 외 입력은 React 기본 출력(자동 이스케이프)으로만 표시하고, dangerouslySetInnerHTML은 DOMPurify를 거친 본문에만 쓴다, CSP 헤더로 인라인 스크립트 차단, 목록 요약은 서버에서 jsoup으로 태그 제거. Lucy XSS Filter·ESAPI는 쓰지 않는다.
3. **CSRF (통합 8.1 ③)**: Authorization 헤더로 토큰을 보내는 동안은 해당 없음. 블로그 간 로그인 공유를 쿠키로 하게 되면 SameSite 설정과 CSRF 토큰을 함께 정한다.
4. **반응형**: 모바일 화면(360px)부터 데스크톱까지 대응한다.
5. **SEO**: 글 상세 페이지에 제목·요약·대표 이미지 메타 태그(Open Graph).
6. **성능**: 목록은 페이지 단위, 이미지는 리사이즈·썸네일 생성, 홈의 무거운 섹션은 캐시(5.10).

### 4.6 계정·소셜 연동 정책 (AUTH-01·05·06, 선택 7.1)

원칙: 처음 가입한 방식이 그 회원의 기본 로그인 수단이다. 여러 로그인 수단을 한 회원에 묶는 길은 '로그인한 상태에서 마이페이지에서 소셜 연동' 하나뿐이고, 더할 수 있는 것은 소셜 계정뿐이다. 이메일이 같다는 이유로 합치지 않고, 충돌하면 거절만 한다. 계정 정리(계정 찾기·탈퇴 후 다시 연동)는 사용자가 직접 한다.

| 가입 방식 | 이메일 로그인 | 소셜 연동 |
| --- | --- | --- |
| 이메일 (인증 후 가입) | 기본 수단 | 가능 (카카오·구글, 제공사당 하나) |
| 소셜 | 불가 (추가 기능 없음) | 다른 제공사 소셜만 가능 |

| 상황 | 처리 |
| --- | --- |
| 소셜 로그인, 이미 연결된 소셜 계정 | 연결된 회원으로 로그인 (상태 확인 후) |
| 소셜 로그인, 처음 보는 소셜 계정 (이메일 가입 없이 소셜을 먼저 쓴 경우) | 닉네임 확인 후 신규 가입. 이메일·비밀번호는 NULL. 제공사 이메일과 기존 회원을 비교하지 않는다 |
| 이메일 가입, 같은 사람이 이미 소셜로 가입해 둔 경우 | 막지 않고 별도 회원으로 가입된다(소셜 회원은 이메일이 없으므로 중복이 아님). 정리는 사용자 몫 |
| 마이페이지 연동, 처음 보는 소셜 계정 | 연동 |
| 소셜로 먼저 가입한 후 다른 소셜 계정 연동 | 위와 같이 마이페이지에서 연동. 다른 제공사면 허용, 같은 제공사면 거절 |
| 마이페이지 연동, 이미 다른 회원에 연결된 소셜 계정 | 거절. "이미 다른 계정에 연결된 소셜 계정입니다" 안내. 그 계정에서 해제하거나 탈퇴하는 것은 사용자 몫 |
| 마이페이지 연동, 같은 제공사가 이미 연결됨 | 거절 (제공사당 하나) |
| 연동 해제, 해제 후 로그인 수단이 남지 않음 | 거절 (소셜로 가입한 회원은 소셜이 최소 하나 남아야 함) |
| 탈퇴 | 소셜 연동 삭제, 이메일·비밀번호 비우기, 회원 행은 남김 |

**세부 규칙**

1. **상태 확인**: 모든 로그인 경로에서 회원을 찾은 뒤 member.status를 먼저 본다. SUSPENDED면 로그인을 막고 사유·기한을 알리고(통합 ADMIN-02), WITHDRAWN이면 없는 계정으로 취급한다.
2. **소셜 요청 검증과 복귀**: 제공사로 보낼 때 state 값을 만들어 돌아온 요청이 우리가 시작한 것인지 확인하고, 로그인 전에 보던 주소도 함께 왕복시켜 돌려보낸다(통합 AUTH-01). 돌려보낼 주소는 우리 서비스 주소만 허용한다.
3. **실패 메시지**: 이메일 로그인 실패는 "이메일 또는 비밀번호가 맞지 않습니다"로 통일해 가입 여부를 드러내지 않는다.
4. **이메일 가입**: 인증 코드를 확인해야만 회원을 만든다. 그래서 이메일이 있는 회원은 모두 인증된 회원이고, 인증 시각을 따로 저장하지 않는다. 이메일 중복 확인은 이메일로 가입한 회원끼리만 해당된다.
5. **소셜 신규 가입**: 제공사 닉네임을 기본값으로 채운 닉네임 확인 화면을 거친다. member(이메일·비밀번호 NULL)와 social\_account는 한 트랜잭션으로 저장한다. 제공사가 준 이메일은 저장하지 않는다.
6. **마이페이지 연동**: 연동하기 → 제공사 인증 → state 확인 → 위 표의 거절 조건을 통과하면 social\_account에 추가한다. 연동 화면에 "다른 소셜 계정도 연결해 두면 로그인 수단을 잃었을 때 대비할 수 있어요" 안내를 둔다.
7. **연동 해제**: 해제 후에도 '이메일+비밀번호' 또는 '다른 소셜 연동'이 하나 이상 남을 때만 허용한다. 가능하면 제공사 쪽 연결도 끊는다.
8. **탈퇴**: 한 번 더 확인하고(통합 AUTH-06) 본인 확인(비밀번호 또는 소셜 재인증)을 받는다. 한 트랜잭션으로 status = WITHDRAWN과 withdrawn\_at을 기록하고, email·password\_hash를 비우고, social\_account 행을 서비스 코드에서 직접 삭제한다(상태만 바꾸면 ON DELETE CASCADE가 작동하지 않음). 그래야 같은 소셜 계정을 다른 회원에 다시 연동할 수 있다. 제공사 쪽 연결도 끊는다. member 행과 블로그·글·댓글은 통합 9.2가 정해질 때까지 남긴다.

**테이블 영향**: member는 email NULL 허용(UNIQUE 유지, 소셜 가입 회원은 항상 NULL)과 withdrawn\_at을 둔다. social\_account는 UNIQUE(provider, provider\_user\_id)와 UNIQUE(member\_id, provider)를 둔다.

| ADMIN-01 | 관리자 역할과 전용 영역 | P0 | role ADMIN은 DB 초기 데이터로만. /admin, /api/admin/\*\* 보호 |
| ADMIN-02 | 회원 이용 제한 | P1 | 회원 조회(이메일·닉네임 검색, 상태 필터, 상세에서 가입일·보유 블로그·받은 신고 수·제재 이력). 정지 기간 7일/30일/영구 + 사유, 기간이 끝나면 자동 해제. 정지 중에는 그 회원의 모든 블로그를 숨긴다(9장). 이미 발급된 토큰을 막는 방법(요청마다 회원 상태 확인 등)은 인증 방식과 함께 확정 |

**신고 처리 흐름**

1. 회원이 글·댓글·블로그를 신고한다(ADMIN-04).
2. 신고는 대상별로 묶여 '처리 대기' 목록에 쌓이고, 신고가 많은 대상이 위로 온다.
3. 관리자가 대상을 확인하고 결과를 고른다. 블라인드, 블로그 이용 제한, 작성자 정지, 기각 중 하나다.
4. 결과와 사유가 관리 이력(ADMIN-06)에 남고, 그 대상의 신고는 모두 '처리 완료'가 된다.
5. 작성자는 자기 글·블로그에서 제재 사유를 볼 수 있다. 알림(SUB-04)이 생기면 제재·해제 알림도 보낸다.

## 6. 화면 주소와 주요 흐름

블로그·글 주소로 들어온 요청은 두 단계로 처리된다. 서버가 주소를 확인한 뒤 React 앱(index.html)을 주고, React 라우터가 화면을 고른 뒤 API로 데이터를 받아 채운다. React 빌드 결과물은 Spring Boot가 함께 제공하므로 운영 서버는 1개다.

### ① 블로그 페이지 접근: 주소 → 화면 → API

1. 방문자가 myblog.blog.com/15를 연다. \*.blog.com은 모두 같은 서버 하나로 연결된다.
2. 서버는 Host 헤더에서 블로그 주소(myblog)를, 경로에서 글 번호(15)를 읽는다. 블로그가 없으면 404, 이사한 블로그면 새 블로그로, 글이 다른 블로그 소속이면 그 블로그로 301 리다이렉트한다. 리다이렉트는 검색엔진도 따라가도록 이 단계에서 서버가 직접 한다.
3. 문제가 없으면 서버는 React 앱(index.html)을 돌려준다. /api/로 시작하지 않는 화면 주소는 모두 같은 index.html이다.
4. React 라우터가 location.hostname(블로그 주소 myblog)과 경로(/15)를 보고 글 상세 화면을 띄운다. 플랫폼 도메인이면 홈·로그인·서비스 관리 라우트를, 블로그 서브도메인이면 블로그 라우트를 쓴다.
5. JS가 글 상세, 사이드바, 댓글 API를 동시에(Promise.all) 호출한다. API는 상대 경로 /api/...로 같은 서버를 부르므로 CORS 설정이 필요 없다.
6. 서버는 아래 ②의 판단을 거쳐 JSON을 돌려주고, JS는 본문 HTML을 DOMPurify로 한 번 더 정화한 뒤 화면에 채운다.

| 페이지 주소 | 서버 처리 | React 화면 | 화면이 부르는 API |
| --- | --- | --- | --- |
| blog.com/ | index.html | 홈 | 홈 섹션(최신 글, 인기 글, 주제별 글) |
| blog.com/login, blog.com/signup | index.html | 로그인, 회원가입 | 로그인, 회원가입 |
| blog.com/admin/... | index.html | 서비스 관리 | /api/admin/\*\* (ADMIN만) |
| myblog.blog.com/ | 블로그 확인(없으면 404, 이사했으면 301) 후 index.html | 블로그 메인 | 블로그 정보, 사이드바, 글 목록 |
| myblog.blog.com/category/{category-id} | 블로그 확인 후 index.html | 카테고리별 글 목록 | 글 목록(카테고리 조건) |
| myblog.blog.com/tag/{name} | 블로그 확인 후 index.html | 태그별 글 목록 | 글 목록(태그 조건) |
| myblog.blog.com/{post-id} | 블로그·글 확인(404, 다른 블로그 소속이면 301) 후 index.html | 글 상세 | 글 상세, 사이드바, 댓글 |
| myblog.blog.com/manage/... | 블로그 확인 후 index.html | 관리 화면 (주인만) | 글쓰기·글 관리·블로그 설정 |
| 어느 도메인이든 /api/\*\* | JSON 응답 | - | - |

### ② 글 조회 판단

&#91;embedded content: 글 조회 판단 · 질문 4개, 결과 6개\]

블로그 주인은 공개 범위와 상관없이 본문을 보고, 방문자에게 비공개 글은 없는 글처럼 404로 보인다.

### ③ 처음 사용자의 여정

1. 회원가입 후 로그인한다(AUTH-01).
2. 블로그를 개설한다(BLOG-01). 첫 블로그라 대표 블로그로 지정된다.
3. 관리 화면에서 카테고리를 만들고(CAT-01) 글을 쓴다(POST-01): 제목, 본문(WYSIWYG), 카테고리, 태그, 공개 범위.
4. 발행하면 myblog.blog.com/{post-id}로 이동하고, 공개 글이면 플랫폼 홈 최신 글(HOME-01)에도 나타난다.
5. 다른 회원이 글을 읽고 댓글(CMT-01)과 공감(SOC-01)을 남긴다.

### ④ 블로그 이사

1. 5개 한도 안에서 새 블로그를 개설한다.
2. 옛 블로그 관리 화면에서 옮길 글을 골라 새 블로그로 이동한다(BLOG-06). 옮긴 글의 옛 링크는 새 블로그로 301 리다이렉트된다.
3. 옛 블로그에 이사 대상을 지정한다. 옛 블로그 홈 방문자는 새 블로그로 301 리다이렉트된다.
4. 필요하면 대표 블로그를 새 블로그로 바꾸고(BLOG-08) 옛 블로그를 삭제한다(BLOG-07). 사용자에게는 사라지지만 내부적으로는 소프트 삭제라, 주소는 영구히 예약되고 리다이렉트도 유지된다.

| 조회수 중복 | 미결정(통합 9.2) | 일정 시간 안에 1회 | 통합 결정 대기 |
| 글자 수 | 기준안 제목 100 · 블로그 이름 40 · 카테고리 20 | 200 · 50 · 30 | 통합 9.2 확정 후 맞춘다 |
| 일정 앞당김 | 답글(CMT-05)은 P2 | 2주차에 구현 | 우선순위는 권장이라 허용 |

## 10. 남은 결정과 할 일

**통합 명세에 맞추려고 바꿔야 하는 것**

1. 목록 정렬 기준을 created\_at에서 published\_at으로 바꾼다(4.4).
2. 홈 최신 글·구독 피드를 처음부터 커서 방식으로 만든다(4.4).
3. 블로그 내 검색에 태그를 포함한다(SRCH-01).
4. 발행·댓글·공감·구독의 연타 방지 방식을 정한다(통합 8.3 ①).
5. ERD와 API 명세 탭을 통합 ID 기준으로 갱신한다(5.15 대응표 참고).

**결정 대기**

1. 에디터 라이브러리: Tiptap으로 확정(완료). React 공식 지원, MIT. 선정 기준: React에서 바로 쓸 수 있는지, 현재도 관리되는지, 이미지 업로드를 POST-05 API와 연결할 수 있는지, 만드는 HTML이 4.5 허용 목록에 들어맞는지.
2. 인증: 블로그 간 로그인 공유 방식, 로그인 유지(AUTH-03), 로그아웃 토큰 처리, 정지 회원 토큰 차단, 쿠키를 쓰면 CSRF 대책. 인증·인가 학습 후 함께 확정한다(따로 문서화).
3. 구독자 공개 글을 구독하지 않은 사람의 블로그 목록에서 '구독자 공개 글'로 보여 줄지 뺄지(선택 7.8).
4. 비회원 댓글 유지 여부(9장).
5. 글 삭제 방식(소프트/하드)과 조회수 중복 판정 시간.
6. 예전 '블로그 커스텀'(사이드바·홈 구성 변경)은 모든 블로그 같은 사이드바(BLOG-04)와 맞지 않아 빼 두었다. 다시 넣을지 정한다.
7. 프론트엔드: React로 확정(완료). React 빌드 결과물은 Spring Boot가 함께 제공하고(서버 1개), 6장 흐름을 React 앱 + 라우터 구조로 고쳤다.
