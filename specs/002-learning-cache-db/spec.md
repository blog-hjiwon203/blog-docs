## 사용자 시나리오와 확인 (User Scenarios & Testing)

### 유저 스토리 1 - 캐시 저장소를 스스로 고를 수 있다 (Priority: P1)

지원이 "인기 글 캐시를 Redis 말고 다른 것으로 해도 되나?"를 판단할 수 있도록, 캐시 저장소 선택지(서버 메모리 Map, Caffeine, Redis)의 차이와 고르는 기준을 이 프로젝트 코드에 맞춰 설명한다.

**Why this priority**: 지원이 먼저 물었고, 이미 만든 코드(스텝 8·9·20의 캐시)를 이해하는 데 바로 쓰인다.

**Independent Test**: 문서만 읽고 확인 문제에 답할 수 있다. 특히 "이 프로젝트에서 Redis를 빼면 무엇이 깨지나"에 코드 근거로 답할 수 있다.

**Acceptance Scenarios**:

1. **Given** 문서를 읽은 지원, **When** "꼭 Redis여야 하나?"를 받으면, **Then** "캐시만 보면 아니다. 저장소는 설정으로 바꾼다"와 그 근거(`@Cacheable`은 그대로, `spring.cache.type`만 바뀜)를 말할 수 있다.
2. **Given** 같은 지원, **When** "그런데 이 프로젝트는 왜 Redis를 계속 쓰나?"를 받으면, **Then** 캐시 말고 Redis를 쓰는 곳(로그인 토큰, 시도 횟수, 연타 방지, 인증 메일 재요청 간격, 소셜 로그인 state)을 들고, 서버 여러 대·재시작에서 무엇이 달라지는지 말할 수 있다.
3. **Given** 같은 지원, **When** 세 저장소 중 하나를 고르라는 상황(서버 1대 학습용 / 서버 여러 대 / 재시작해도 남아야 함)을 받으면, **Then** 상황마다 맞는 것과 이유를 말할 수 있다.

### 유저 스토리 2 - PostgreSQL과 MySQL의 차이와 DB 통합 판단 (Priority: P1)

지원이 두 DB의 차이를 알고, "DB 두 개(MySQL + PostgreSQL)를 하나로 합쳐도 되나, 설계상 가장 나은 건 무엇인가"를 이 프로젝트 기준으로 판단할 수 있도록 설명한다.

**Why this priority**: 지원이 "설계상 가장 나은 방안"을 직접 물었다. 지금 구조(스텝 10)의 약점(외래 키·트랜잭션·조인 없음)을 이해해야 답할 수 있다.

**Independent Test**: 문서만 읽고 "이 프로젝트에서 합친다면 어느 쪽으로, 무엇을 고쳐야 하나"에 답할 수 있다.

**Acceptance Scenarios**:

1. **Given** 문서를 읽은 지원, **When** 두 DB의 차이를 물으면, **Then** 공통점(관계형, JPA로 거의 같게 씀)과 이 프로젝트에 영향을 주는 차이(확장과 pgvector, 문법 차이)를 말할 수 있다.
2. **Given** 같은 지원, **When** "설계상 가장 나은 것"을 물으면, **Then** 선택지 셋(지금처럼 둘 / 전부 PostgreSQL / 전부 MySQL)의 장단점과, 설계만 보면 "PostgreSQL 하나 + pgvector"가 낫다는 결론과 이유(가시성 필터를 한 쿼리로, 외래 키, 한 트랜잭션)를 말할 수 있다.
3. **Given** 같은 지원, **When** "그럼 왜 지금 그렇게 안 했나 / 실제로 바꾸려면?"을 물으면, **Then** 운영 환경 제약(학교 서버가 주는 DB가 MySQL로 보임)과, 바꿀 때 고쳐야 하는 MySQL 전용 문법(INSERT IGNORE, UPDATE … JOIN, ON UPDATE, 계산 칸, 콜레이션)을 말할 수 있다.

### Edge Cases

- 지원이 이미 읽은 35·41·42와 내용이 겹치면? → 겹치는 부분은 링크로 넘기고 비교·판단만 새로 쓴다.
- 문서가 "사실"로 적은 것이 코드와 다르면? → 코드 저장소에서 확인한 것만 사실로 쓰고, 추측은 "추측"이라고 쓴다.
- 일반 지식(다른 DB 기능)이 버전마다 다르면? → 버전을 적거나 "확인 필요"로 둔다.

## 요구사항 (Requirements)

### Functional Requirements

- **FR-001**: 두 문서는 기존 개념 문서와 같은 순서를 따른다: 배우는 것 → 왜 필요한가 → 기본 개념 → 동작 원리 → 이 프로젝트에서는 → 자주 하는 실수 → 직접 해 보기 → 확인 문제 → 더 읽을거리.
- **FR-002**: 캐시 문서는 서버 메모리 Map(`ConcurrentMapCacheManager`), Caffeine, Redis를 같은 표로 비교한다(만료, 재시작, 서버 여러 대, 직렬화, 준비물).
- **FR-003**: 캐시 문서는 이 프로젝트에서 Redis를 쓰는 곳을 코드 경로와 키 접두어로 모두 적고, 캐시와 "캐시가 아닌 임시 데이터"를 구분한다.
- **FR-004**: 캐시 문서는 "캐시만 Caffeine으로 바꾸면" 무엇이 바뀌는지(설정·의존성·직렬화)를 보여 준다.
- **FR-005**: DB 문서는 PostgreSQL과 MySQL의 차이를 이 프로젝트에 영향 있는 것 중심으로 표로 정리한다.
- **FR-006**: DB 문서는 선택지 셋을 비교하고, "설계상 가장 나은 방안"과 그 근거를 분명히 적는다.
- **FR-007**: DB 문서는 이 프로젝트를 PostgreSQL로 옮길 때 고칠 곳을 실제 코드에서 센 개수와 함께 적는다.
- **FR-008**: 두 문서는 기존 문서(17, 35, 41, 42)로 이어지는 링크를 둔다.
- **FR-009**: 학습 자료 목차(`learning/README.md`)에 두 문서를 추가한다.
- **FR-010**: 코드를 바꾸지 않는다. "바꾸려면"은 설명과 예시 코드로만 보인다.

### Key Entities

- **개념 문서 65**: PostgreSQL vs MySQL, 하나로 합치기.

## 성공 기준 (Success Criteria)

- **SC-001**: 두 문서의 확인 문제 각 8개 이상, 모두 문서 본문만으로 답할 수 있다.
- **SC-002**: 문서에 적은 코드 경로·설정 키·개수가 코드 저장소 main(2026-10-12 커밋 `ab0b5dd`)과 모두 맞는다.
- **SC-003**: 지원의 질문 세 개(꼭 Redis? 차이와 통합? 설계상 최선?)에 대한 답이 각 문서 맨 앞 "한 줄 답"에 있다.

## 가정 (Assumptions)
