## R-02 운영 저장소 (2026-10-07 확정, 2026-10-13 PostgreSQL 하나로 바꿈)

- **지금 (2026-10-13부터, 스텝 23·24)**: 주 DB는 **PostgreSQL 17 + pgvector 하나**다. 회원·글·댓글과 글 임베딩이 같은 DB에 있다. 아래 "주 DB를 PostgreSQL로 합침"이 그 결정이고, 그 위의 MySQL 이야기는 스텝 22까지의 기록이다.
- **결정 (2026-10-07, 스텝 22까지)**: 주 DB는 MySQL. 개발도 docker compose의 MySQL 8을 쓴다(2026-10-08 변경, 아래 "개발 DB"). **Redis 사용**: Spring Cache 저장소(인기 글·주제별 글 TTL 5분), 연타 방지 Idempotency-Key 저장(R-09). 정지 회원 토큰 차단·로그아웃 토큰 처리도 R-03 확정 시 Redis 후보. **PostgreSQL + pgvector**: 비슷한 글 추천(OWN-06) 전용, 2주 안에 도전(도전 과제).
- **이유**: 개발에 AI를 쓰므로 2주 안에 벡터 검색까지 가능하다고 판단(지원). 단, 주 데이터는 MySQL 하나로 두고 PostgreSQL에는 글 id와 임베딩만 저장해 일정이 밀리면 기능째 뺄 수 있게 한다.
- **개발 DB (2026-10-08 변경)**: 원래 개발은 H2(MySQL 호환 모드)였는데, ERD에서 내보낸 `erd/schema.sql`이 H2에서 실행되지 않는다(`blog.primary_owner_id`의 `GENERATED ALWAYS AS … STORED`에서 문법 오류, H2 2.3.232로 확인). 스키마를 두 벌 관리하지 않으려고 개발·테스트도 MySQL 8로 맞춘다. 개발은 docker compose, 테스트는 Testcontainers. 스키마는 Flyway가 만든다.
- **로컬 개발**: PostgreSQL(pgvector), Redis, Ollama는 docker compose로 띄운다(스텝 22까지는 MySQL도). Redis가 없을 때 테스트는 embedded/Testcontainers 또는 ConcurrentMap 캐시로 대체.
- **임베딩 (2026-10-10 지원 결정, 스텝 10)**: 로컬 **Ollama + `bge-m3`**(다국어, 한국어 지원, 1024차원). 지원의 docker `ollama` 볼륨에 모델이 이미 있어 docker compose의 Ollama가 그 볼륨을 쓴다. API 키·비용이 없고 글이 외부로 나가지 않는다(외부 임베딩 API인 Voyage·OpenAI는 키·비용과 외부 전송 때문에 고르지 않음).
  - 넣는 글자: 제목 + 본문 글자(`content_text`) 앞 2,000자. **2026-10-13부터 `제목`, `태그: a, b`, `본문 글자`를 줄바꿈으로 이은 앞 2,000자**(지원 결정, 스텝 22). 넣는 글자 방식이 바뀌면 `post_embedding.text_version`을 올리고, 서버가 뜰 때 옛 방식 임베딩을 다시 만든다. 태그 이름을 바꾸거나 지우면 그 태그가 달린 글의 임베딩도 다시 만든다. 발행 글이면 공개 범위와 상관없이 모두 넣고(밖으로 나가지 않으므로), 볼 수 있는지는 추천할 때 거른다.
  - 갱신 시점: 발행·수정이 **커밋된 뒤 비동기**로 만든다(글 저장이 Ollama를 기다리지 않게). 글을 지우면 임베딩도 지운다. 서버가 뜰 때 임베딩이 없는 발행 글을 채운다(이미 있던 글).
  - Ollama가 꺼져 있거나 실패하면 경고만 남기고 넘어간다. 그 글의 추천은 빈 배열이다(contracts "추천이 준비 안 됐으면 빈 배열").
  - 추천: pgvector 코사인 거리(`<=>`) 가까운 순으로, 보는 사람 기준 가시성(`visibleTo`)을 같은 쿼리에서 걸고 자기 글을 빼고 `size`개(기본 5, 1~10, 다른 블로그 포함). 스텝 22까지는 후보 30개를 뽑은 뒤 MySQL에서 걸렀다.
  - 표: `post_embedding(post_id PK, embedding vector(1024), text_version, updated_at)`. 스텝 22까지는 두 번째 DB라 Flyway를 따로 하나 더 두었다(`db/recommend`). 스텝 23부터 주 DB의 V1에 있고 `post_id`는 `post` 외래 키(ON DELETE CASCADE)다.
  - **의미 검색 (2026-10-13 지원 결정, 스텝 22, OWN-07)**: 주 DB와 추천 DB를 합치지 않고 지금 구조로 한다. 검색어를 같은 모델로 임베딩(같은 검색어는 Redis 캐시 5분)해 `post_embedding`에서 코사인 유사도 0.40 이상인 글을 가까운 순 100개까지 뽑고, MySQL에서 글자 검색과 같은 가시성(전체: `visibleTo`, 블로그 안: `listedIn`)으로 거른 뒤 그 순서대로 10개씩 나눈다. 블로그 안 검색은 추천 DB가 블로그를 모르므로 MySQL에서 그 블로그의 볼 수 있는 글 번호를 먼저 읽어 그 안에서만 찾는다. 0.40은 bge-m3로 잰 값이다(관련 있는 글 0.42~0.58, 관련 없는 글 0.21~0.39, 2026-10-13 개발 Ollama로 측정). 설정값 `app.search.semantic.min-similarity`. 의미 검색은 앞쪽 결과만 쓸모가 있어 100개 제한을 둔다. 글자 검색과 점수를 섞는 방식(RRF)은 고르지 않았다(탭으로 나눠 차이를 보이기로, 지원 결정).
- **주 DB를 PostgreSQL로 합침 (2026-10-13 지원 결정, 스텝 23·24)**: 주 DB(MySQL)와 추천 DB(PostgreSQL)를 PostgreSQL 하나로 합친다. 운영 데이터가 아주 적은(발행 글 2개, 회원 몇 명) 지금이 옮기기 가장 싸고, 임베딩과 글이 한 DB에 있으면 의미 검색·추천의 가시성 조건을 SQL 한 번으로 쓰고 글을 지울 때 임베딩을 외래 키로 함께 지울 수 있다. DataSource·Flyway·테스트 컨테이너도 하나가 된다. 스텝 24에서 이 절과 plan·data-model·ERD를 PostgreSQL 기준으로 다시 쓴다.
  - 대소문자: MySQL `utf8mb4_0900_ai_ci`가 하던 대소문자 무시 비교(이메일·닉네임·블로그 주소·카테고리·태그·금칙어의 중복 막기와 찾기)는 `citext`로 한다. 글자 검색·관리자 회원 검색은 `ILIKE`. 악센트 무시(é = e)는 잃는다(한글에는 영향 없음, 지원 결정).
  - `updated_at`: MySQL의 `ON UPDATE CURRENT_TIMESTAMP`는 옮기지 않는다(트리거 없음). 엔티티 수정은 JPA `@LastModifiedDate`가 채우고, 네이티브 UPDATE 중 시각을 바꿔야 하는 곳만 직접 넣는다.
  - 운영: s2 서버에 이미 떠 있는 `aigj017-recommend-db`(pgvector pg17) 컨테이너 안에 `blog` DB를 새로 만들어 쓴다. 서버 포트는 열지 않고 docker 네트워크 안에서만 닿는다. 데이터는 docker 볼륨 `aigj017-recommend-data`.
  - 데이터 이전: 표는 Flyway로 만들고, s4 MySQL에서 표마다 `mysql -N -B --raw`로 꺼내(NULL·\·탭·줄바꿈은 SELECT에서 COPY 글자 형식으로 바꿈) `\copy`로 넣은 뒤 시퀀스를 `max(id)`에 맞춘다(코드 저장소 `deploy/migrate-from-mysql.sh`, 스텝 24). 임베딩은 옮기지 않고 서버가 뜰 때 다시 만든다. `pgloader`는 MySQL 8 기본 인증(`caching_sha2_password`)에 접속하지 못할 수 있어 쓰지 않는다. s4 MySQL은 되돌릴 길로 며칠 지우지 않는다.
  - 백업: 하지 않는다(과제 규모, 지원 결정). 볼륨을 지우는 명령(`docker volume rm`, `docker system prune --volumes`)을 쓰면 데이터를 잃는다.
  - 접속 설정: `stringtype=unspecified`(Hikari data-source-properties). JDBC가 글자 값을 `varchar`로 보내면 `citext = varchar`가 대소문자를 가리기 때문이다(스텝 23에서 확인). 연결마다 `hnsw.ef_search = 200`, `hnsw.iterative_scan = strict_order`.
  - 의미 검색·비슷한 글 (스텝 23): 글과 `post_embedding`을 JPA Criteria 한 쿼리로 묶어(hibernate-vector `cosine_distance`) 가시성 조건(`visibleTo`·`listedIn`)과 거리 순·페이지를 DB가 한 번에 한다. 블로그 안 검색의 글 번호 목록과 추천 후보 30개 거르기는 없앴다. 503 `SEMANTIC_SEARCH_UNAVAILABLE`은 임베딩 서버(Ollama)에 닿지 않을 때만이고, DB 오류는 다른 API처럼 500이다.
  - 운영 전환 순서 (스텝 24): 코드 PR 병합 → 자동 배포가 `blog` DB를 만들고 앱이 빈 DB로 뜸(Flyway V1·V2) → 지원이 서버에서 `migrate-from-mysql.sh` 실행(앱 정지, 표 비우기, 옮기기, 시퀀스, 행 수 비교, 앱 다시 띄움). 그 사이 몇 분은 사이트가 비어 보인다. 되돌리기는 이전 커밋으로 다시 배포(MySQL과 GitHub secrets `DB_*`는 며칠 남겨 둠). 옛 `recommend` DB(스텝 22까지의 임베딩)도 며칠 뒤 지운다.

## R-03 인증 (2026-10-07 확정, 2026-10-12 쿠키 Domain 없앰)

- **정해진 것**: JWT, 비밀번호 bcrypt. 로그인이 필요한 행동에 로그인 안 함 401, 권한 없음 403, 볼 수 없는 글·블로그 404(401보다 먼저).
- **문제** ([지원이 확인할 것](./review.md) 3): 원본 3장은 Access Token을 `Authorization: Bearer` 헤더로 보낸다. 토큰을 브라우저 저장소(localStorage)에 두면 출처(origin)마다 따로라서, 처음 정할 때의 서브도메인 주소(`myblog.blog.com`)에서는 `blog.com`에서 로그인해도 블로그 관리 화면에서 로그아웃 상태였다. 이건 P0 한 바퀴(로그인 → 내 블로그에서 글쓰기)를 막는다.
- **결정** (지원, Q6): 로그인하면 서버가 `HttpOnly; Secure; SameSite=Lax` 쿠키로 토큰을 준다. 쿠키를 쓰므로 상태를 바꾸는 요청에는 CSRF 대책(SameSite=Lax + 사용자 지정 헤더 확인 또는 CSRF 토큰)을 함께 둔다(원본 4.5 ③). 로그인 유지는 만료가 긴 Refresh Token 쿠키(14일), 로그아웃은 쿠키 삭제 + Redis에 남은 토큰 무효화, 정지 회원은 요청마다 회원 상태를 확인(짧은 캐시)한다.
- **쿠키 Domain** (2026-10-12 지원 결정, 스텝 21): 쿠키에 `Domain`을 두지 않는다(그 쿠키를 준 호스트에만 가는 host-only 쿠키). 로그인(access·refresh), 기기 확인(device), 비회원 방문자(visitor_id), 소셜 로그인 state(oauth_state) 쿠키 모두 같다. 처음에는 `Domain=.blog.com`으로 모든 서브도메인 블로그가 같은 쿠키를 보게 했지만, 블로그 주소가 `blog.com/@주소` 경로로 바뀌어(R-04) 플랫폼과 모든 블로그 화면이 한 호스트다. 같은 호스트라 Domain 없이도 로그인 상태가 저절로 공유되고, Domain을 넓게 열어 둘 이유가 없다.
- **로그인 유지를 고르지 않았을 때** (2026-10-08 지원 결정): 무활동 30분이면 로그아웃. Refresh 토큰은 항상 주되, 로그인 유지를 고르지 않으면 쿠키는 브라우저를 닫으면 사라지는 세션 쿠키이고 Redis의 TTL을 30분(`app.auth.idle-timeout`)으로 두어 요청마다 연장한다. Access 토큰(30분)이 끝나면 서버 필터가 살아 있는 Refresh 토큰으로 새로 준다. 고르지 않은 대안: Access 토큰만 주기(활동 중에도 30분이면 로그아웃), 세션 쿠키만(브라우저 탭 복원으로 사실상 기한이 없음).
- **고르지 않은 대안**: (a) 블로그 주소로 넘어갈 때마다 플랫폼 주소에서 토큰을 다시 받아 오는 방식(SSO 리다이렉트): 쿠키를 피할 수 있지만 화면 이동마다 왕복이 생기고 만들기 어렵다. (b) 상위 도메인 쿠키(`Domain=.blog.com`): 블로그 주소가 서브도메인일 때 쓰던 방식(2026-10-07~10-11). 경로 주소로 바뀐 뒤에는 필요 없다.
- **로컬 개발**: `/etc/hosts`에 `127.0.0.1 blog.test` 한 줄을 넣고 `http://blog.test:8080`으로 연다. 쿠키에 Domain이 없어서 `localhost:8080`에서도 로그인은 되지만, 메일·소셜 로그인 링크는 플랫폼 주소(`blog.test`)로 만들어지므로 `blog.test`를 권한다(빠른 시작).

## R-04 블로그 주소 해석 (4.2, 6장 ①, 2026-10-12 경로 주소로 바꿈)

- **결정**: 주소 규칙은 정규식 `^[a-z0-9][a-z0-9-]{2,30}[a-z0-9]$`, 예약어(www, api, admin, static, mail, login 등) 거절. 블로그 주소는 플랫폼 주소 아래 경로 `blog.com/@{주소}`다(2026-10-12 지원 결정, 스텝 21). 서브도메인 주소(`{주소}.blog.com`)는 없앴고 대신 받아 주지도 않는다.
  - **화면 주소**: `/@{주소}`, `/@{주소}/{글 번호}`, `/@{주소}/category/{번호}`, `/@{주소}/tag/{이름}`, `/@{주소}/search`, `/@{주소}/guestbook`, `/@{주소}/manage/...`. `/@`로 시작하지 않는 화면 주소는 플랫폼 화면이다. 블로그 첫 화면은 끝에 `/`를 붙이지 않은 `/@{주소}`다.
  - **API**: 주소는 그대로 둔다(`/api/posts/{id}` 등). 블로그 화면이 블로그 API를 부를 때 `X-Blog-Address: {주소}` 헤더로 어느 블로그인지 알린다(①안). 헤더가 없으면 플랫폼 요청, 헤더의 주소가 규칙에 어긋나거나 예약어면 없는 블로그와 같이 404다. 서버는 이 판단을 `BlogAddressResolver` 한 곳에서 한다.
  - **겹침 없음**: 블로그 주소 앞에 `@`가 붙으므로 `/login`, `/me`, `/admin` 같은 플랫폼 경로와 부딪히지 않는다. 주소 유일성(UNIQUE, 삭제된 블로그 주소도 영구 예약)은 그대로다.
- **바꾼 이유**: 배포 서버(학교 nginx, `now-log.java21.net`)는 도메인이 하나뿐이고 와일드카드 DNS(`*.도메인`)가 없어서 `{주소}.도메인` 블로그 주소를 열 수 없다. 원본 7.3의 서브도메인 선택은 이 환경에서 지킬 수 없어 경로로 바꿨다.
- **고르지 않은 대안**: (a) 서브도메인 유지(`{주소}.blog.com`): 와일드카드 DNS(https면 와일드카드 인증서도)가 있어야 하는데 배포 서버에 없다. 경로 주소와 둘 다 받는 방식도 쓰는 곳이 없어 두지 않았다. (b) API 경로에 블로그 주소 넣기(`/api/blogs/{주소}/…`, ②안): 주소만 보고 블로그를 알 수 있어 깔끔하지만, 블로그 API 59개의 주소와 계약·테스트가 모두 바뀐다. ①안은 API 주소를 그대로 두고 블로그를 정하는 곳(헤더 해석)만 바꾼다.
- 화면 주소는 서버가 먼저 확인(없으면 404, 이사했으면 301, 다른 블로그 소속 글이면 301)한 뒤 `index.html`을 준다. 리다이렉트를 서버가 하는 이유는 검색엔진도 따라가게 하기 위함. 301은 같은 블로그 안 경로를 새 주소로 옮긴다(`/@old/15` → `/@new/15`).
- 서버가 만드는 블로그 링크(알림 링크, 이사 301, 공유 미리보기 `og:url`, 글 저장 응답의 `url`)는 `http(s)://{플랫폼}/@{주소}/...` 전체 주소다.
- 프론트는 주소가 `/@{주소}`로 시작하면 React Router의 `basename`을 `/@{주소}`로 둔다. 그래서 블로그 화면 안의 링크(`/12`, `/manage/write`)는 서브도메인 때와 같은 모양으로 쓰고, API 클라이언트가 `X-Blog-Address`를 붙인다.
- `/api/**`는 같은 출처의 상대 경로라 CORS 설정이 필요 없다.

## R-07 계정·소셜 연동 (4.6)

- **결정**: 처음 가입한 방식이 기본 수단. 묶는 길은 "로그인 상태에서 마이페이지 소셜 연동" 하나뿐이고, 더할 수 있는 것은 소셜뿐. 이메일이 같다고 합치지 않고 충돌하면 거절.
- 소셜 신규 가입: 닉네임 확인 후 member(email·password NULL) + social_account를 한 트랜잭션. 제공사 이메일은 저장하지 않음.
- 연동 거절: 이미 다른 회원에 연결된 소셜 계정, 같은 제공사 중복. 해제 후 로그인 수단이 남지 않으면 거절.
- 모든 로그인 경로에서 member.status 먼저 확인(SUSPENDED → 사유·기한 안내, WITHDRAWN → 없는 계정).
- OAuth state 검증 + 복귀 주소는 우리 서비스 주소만 허용.
- 이메일 로그인 실패 문구는 가입 여부를 드러내지 않게 통일.
- 탈퇴: 본인 확인 후 한 트랜잭션으로 status=WITHDRAWN, withdrawn_at, email·password_hash 비우기, social_account 행 직접 삭제, 제공사 연결 해제. 블로그·글·댓글은 모두 소프트 삭제하고 그 회원의 공감·구독은 지운다(Q1, data-model 탈퇴 처리).
- **구현 메모 (스텝 20b, T099·T100, 2026-10-12)**: 인가 코드 흐름. `authorize`가 state(256비트 임의 값)를 Redis(10분)와 이 브라우저의 `oauth_state` 쿠키(Path=/api/auth/oauth, HttpOnly, SameSite=Lax)에 함께 두고, `callback`은 state를 한 번 쓰고 지운 뒤 code를 제공사 회원 번호로 바꿔 2분짜리 표를 만들어 시작한 플랫폼 주소의 `complete`로 보낸다. `complete`는 쿠키의 state와 표가 같아야 진행한다(로그인 CSRF 방지). 콜백과 쿠키 주는 곳을 나눈 이유: 콘솔에 등록한 콜백이 플랫폼 주소가 아닐 수 있고(개발에서 localhost로 등록한 경우. 처음 만들 때는 구글이 https가 아니면 localhost만 받아서였다), 로그인 쿠키는 플랫폼 주소의 쿠키여야 하는데 그런 응답으로 주면 그 주소에만 남는다(Domain 없음, R-03). 받는 정보는 제공사 회원 번호뿐(카카오 `/v2/user/me`의 id, 구글 userinfo의 `sub`). 탈퇴 본인 확인은 카카오 `prompt=login`, 구글 `max_age=0`으로 다시 로그인하게 하고, 10분짜리 표시를 한 번만 쓴다. 해제·탈퇴는 회원 행을 잠그고 남은 로그인 수단을 센다. **구글 로그인은 2026-10-12에 뺐다가 2026-10-13에 되살렸다(지원 결정)**: 구글은 리다이렉트 URI가 https여야 한다(localhost만 예외). 처음에는 학교 nginx 안내 예시(`listen 80`만)를 보고 운영이 http뿐이라고 판단해 뺐는데, 확인해 보니 `https://now-log.java21.net`이 Let's Encrypt 인증서로 열렸다. 그래서 운영 콜백은 카카오·구글 모두 `https://now-log.java21.net/api/auth/oauth/{provider}/callback`이고, 운영 쿠키는 Secure다. **제공사 쪽 연결 해제(카카오 unlink)는 하지 않는다(2026-10-12 지원 결정)**: 탈퇴·해제 때 우리 쪽 `social_account` 행만 지운다. 그래서 같은 카카오 계정은 다시 오면 처음 보는 계정으로 새로 가입하고, 다른 회원에 다시 연동할 수도 있다(서비스 동작에는 차이 없음). 카카오 계정 설정의 "연결된 서비스"에는 남아 있어 본인이 거기서 끊는다. 카카오 unlink는 모든 사용자를 다룰 수 있는 어드민 키가 필요해 학교 공용 서버에 두는 위험이 크다. 위 결정 줄의 "제공사 연결 해제"는 이 범위로 읽는다.

## R-08 블로그 이사·삭제 (4.2)

- 이사 대상은 같은 회원의 활성 블로그만(자기 자신·삭제된 블로그 불가). 옛 블로그 홈은 301, 주인은 관리 화면 접근 가능.

- 연쇄 이사 A→B→C면 A의 대상도 C로 갱신(리다이렉트 1회, 순환 없음).
- 삭제는 소프트 삭제(deleted_at). 개설 한도 5개는 활성 블로그만 셈.
- 이사 간 새 블로그(B)를 삭제하면 A의 리다이렉트도 끊기고 없는 블로그.

## R-13 랭킹 스냅숏과 블로그 점수 (2026-10-08)

- **이유**: 통합 명세 HOME-05가 "홈과 전체보기의 순위는 같은 기준, 같은 시점"을 요구한다. 매 요청마다 계산하면 홈과 전체보기의 시점이 어긋나고, 더보기 중에 순위가 바뀌어 중복·누락이 생긴다. 블로그 단위는 1시간 창이면 너무 출렁여서 7일로 늘렸다. 가중치·기간은 Claude 기본값이고 설정값으로 둔다.
- **대안**: MySQL에 순위 테이블을 두기(Redis가 이미 있어 불필요), 주제 맞춤 추천(2주 뒤 가산점으로 검토).
- **구현 메모 (스텝 20, T079)**: 인기 블로거는 1시간마다 도는 작업 대신 **정시 칸 캐시**로 만들었다. 순위는 [정시 − 7일, 정시) 동안의 활동으로 계산하고 기준 시각을 그 정시로 둔다. 그 시간의 첫 요청이 계산해 Redis에 키 = 정시로 둔다(`@Cacheable(sync = true)`). 끝을 정시로 고정하므로 같은 칸 안에서는 캐시가 비워져 다시 계산해도 같은 순위·같은 기준 시각이다. 작업이 없으니 "서버가 꺼져 있다 켜지면 순위가 비는" 일이 없고, 서버가 여러 대여도 같은 값을 계산한다. 결과(1시간마다 갱신, 상위 100, 기준 시각)는 결정과 같다. 인기 글(5분)은 스텝 7의 캐시를 그대로 쓰고 100위까지 읽게만 했다(T078). 조회 기록(`view_log`)은 블로그 점수에 7일까지 쓰므로, 새벽 작업이 7일 + 1시간보다 오래된 것을 지운다(정시 칸이 지금보다 최대 1시간 앞이라).

## R-14 방문 통계 (2026-10-08, MNG-03)

- **결정**: 방문할 때 `blog_visit`에 (블로그, 날짜, 방문자) 한 행을 UNIQUE로 넣어 하루 한 번만 센다. 매일 새벽 스케줄러가 전날 행을 `blog_daily_stat`(방문자·조회 수)과 `blog_referrer_daily`(유입 종류·사이트별 수)로 모으고 `blog.total_visitor_count`에 더한 뒤, 7일 지난 방문 기록을 지운다. 오늘 방문자는 `blog_visit`에서 바로 센다.
- **이유**: 방문 기록을 그대로 쌓으면 그래프·누적 계산이 매번 무거워진다. 일별로 모아 두면 일·주·월 그래프가 일별 행을 더하는 것으로 끝난다. 방문자 식별은 조회 기록(view_log)과 같은 visitor_key를 써서 회원·비회원을 같은 방식으로 센다.
- **대안**: Redis HyperLogLog로 하루 방문자를 세기(유입 경로를 따로 둬야 해서 테이블이 더 단순함), 외부 분석 도구(Google Analytics) 붙이기(블로그 주인별 화면을 따로 만들어야 함).

## R-17 비밀번호·인증 코드 시도 횟수 제한 (2026-10-09 지원 결정, T055a)

- **결정**: 로그인 비밀번호(이메일별), 이메일 인증 코드(이메일별), 비밀번호 변경의 지금 비밀번호(회원별)를 **15분 안에 5번** 틀리면 **다섯 번째로 틀린 때부터 15분 동안** 429 `TOO_MANY_REQUESTS`(`retryAfterSeconds`)로 막는다. 막힌 동안은 맞는 값도 받지 않는다. 성공하면 틀린 횟수를 지운다. 가입하지 않은 이메일로 로그인해도 똑같이 세서, 막히는지로 가입 여부를 알 수 없게 한다. 횟수와 시간은 설정값이다.
- **방법**: Redis에 키마다 시도 수를 둔다(`INCR`). 확인하기 **전에** 먼저 하나 올려 자리를 잡으므로, 동시에 많이 보내도 확인은 5번까지만 된다. 틀린 경우가 아닌 실패(정지 회원, 만료된 코드 등)는 올린 수를 되돌린다.
- **이유**: 없으면 무차별 대입에 열려 있다. 특히 6자리 인증 코드는 10분 안에 계속 넣어 보면 맞출 수 있다. bcrypt 비교는 일부러 느려서 대량 시도는 서버 부담도 된다. 이메일 인증 재발송 1분 제한과 같은 Redis 방식을 쓴다.
- **IP별 제한 (같은 날 지원 결정으로 추가)**: 같은 IP에서 위 셋의 실패를 **합쳐 15분 안에 20번** 틀리면 15분 동안 429. 이메일별 제한만으로는 비밀번호 하나를 여러 이메일에 돌려 보는 공격(비밀번호 스프레이)을 막지 못해서다. 20번은 회사·학교처럼 여러 사람이 IP 하나를 쓰는 경우를 생각한 Claude 기본값이고 설정값(`app.attempt-limit.ip-max-failures`)이다. 맞혀도 IP 횟수는 지우지 않는다(내 계정으로 한 번 로그인해 IP 횟수를 지우는 우회를 막으려고). IP는 요청의 접속 주소(`getRemoteAddr`)다. 운영에서 프록시·로드밸런서 뒤에 두면 모든 요청이 프록시 IP가 되므로, 그때는 믿을 수 있는 프록시의 `X-Forwarded-For`만 읽도록 `server.forward-headers-strategy`를 설정해야 한다.
- **남은 것**: 계정이 막혔다는 알림 메일은 하지 않는다. 다른 사람이 일부러 틀려서 내 로그인을 15분 막을 수 있다(계정 잠금의 일반적인 약점). IP별 제한은 그 사람의 IP도 막지만, IP를 바꿔 가며 하면 막지 못한다.
- **이어서 할 것 (2026-10-09 지원 결정, 백로그)**: ① 전에 로그인한 브라우저(기기 쿠키)는 이메일별 잠금에서 빼서 주인은 평소 쓰던 브라우저로 계속 들어온다(T055b, OWASP가 권하는 device cookie 방식). ② 새 기기에서 잠긴 주인은 메일 링크로 푼다. 실제 메일 발송이 필요해 비밀번호 재설정(OWN-02)과 함께 한다(T088). CAPTCHA는 외부 서비스가 필요해 고르지 않았다.
- **구현 메모 (스텝 20, T055b)**: 기기 쿠키 `device`는 `회원 번호.임의 값(128비트).서명`이고, 서명은 HMAC-SHA256(키 = 용도 이름 + JWT 비밀 키)이다. 로그인에 성공할 때마다 새로 주고(1년, HttpOnly, 로그아웃해도 남음), 로그인할 때 쿠키의 서명이 맞고 회원 번호가 그 이메일의 회원이면 틀린 횟수를 `login-device:{임의 값}`으로 센다. 기기도 15분에 5번 틀리면 막히고, IP별 제한은 그대로다. 쿠키가 없거나 다른 회원 것이면 지금처럼 이메일로 센다.
- **구현 메모 (스텝 20b, T088)**: ② 메일로 잠금 풀기는 비밀번호 재설정 링크를 그대로 쓴다. 로그인이 이메일별 횟수(`login:{이메일}`) 때문에 막히면, 가입한 이메일이면 그 메일함으로 "본인이면 이 링크로 비밀번호를 새로 정하면 바로 들어온다"는 메일을 보낸다(같은 이메일에 15분에 한 번, 응답은 메일과 상관없이 같음). 링크로 비밀번호를 바꾸면 그 이메일의 틀린 횟수를 지운다(IP 횟수는 그대로). 기기 쿠키로 세는 로그인(`login-device:`)이 막힌 것은 남이 막은 것이 아니라 그 브라우저에서 틀린 것이라 메일을 보내지 않는다. 재설정 링크 토큰은 256비트 임의 값이고 DB에는 SHA-256만 둔다. 메일은 커밋 뒤 다른 스레드에서 보낸다(요청이 SMTP를 기다리면 가입한 이메일만 응답이 느려져 응답 시간으로 가입 여부가 드러난다). 메일 발송은 `app.mail.sender`(log·smtp)로 고르고, 개발은 Mailpit(`docker compose`, http://localhost:8025)으로 받는다.

## R-18 이중화·무중단 배포 (2026-10-14~15 지원 결정, 스텝 25)

- **결정**: 같은 서버에 앱을 두 대(`aigj017-app` 8460, `aigj017-app-2` 8461, 배정 포트 8460~8469 안) 늘 띄우고, 학교 nginx 설정 파일(`~/nginx/now-log.java21.net.conf`)에 upstream(`now_log_java21_net`)을 두어 둘로 나눠 보낸다. 배포는 한 대씩 바꾸는 **롤링**이다. 이중화를 직접 해 보는 것도 목적이다.
- **블루·그린을 고르지 않은 이유**: 블루·그린은 배포 때만 두 벌이라 평소에는 한 대이고(이중화가 아님), 배포마다 nginx가 보내는 곳을 바꿔야 한다. 학교 nginx는 학생이 reload할 수 없고(sudo 없음), 서버가 10분마다 설정을 자동으로 다시 읽는다. 배포마다 보내는 곳을 바꾸면 언제 바뀌는지 알 수 없어, 옛 앱을 언제 꺼도 되는지 정할 수 없다. upstream은 한 번만 넣으면 이후 배포에서 nginx를 건드리지 않는다.
- **우리 nginx 컨테이너를 두지 않은 이유**: 다른 학생이 학교 nginx에 upstream 두 대를 이미 쓰고 있어 허용됨을 확인했다. 설정 파일을 한 번만 고치면 되고(10분 안에 자동 반영), 컨테이너를 하나 더 운영하지 않아도 된다. 대신 앱을 끄기 전에 upstream에서 미리 빼는 방식은 못 쓰고, 꺼진 앱을 nginx가 실패로 알아채 다른 앱으로 다시 보내는 방식이다(`max_fails=1 fail_timeout=10s`, `proxy_next_upstream error timeout http_502 http_503`, `proxy_next_upstream_tries 2`, `proxy_connect_timeout 3s`). POST처럼 이미 앱에 보낸 요청은 nginx가 다시 보내지 않으므로 두 번 저장되지 않는다.
- **앱 두 대에서 같이 도는 서버 작업**: 스케줄 작업을 한 앱에서만 켜지 않고 두 앱 모두 켠다. 같은 일을 한 앱만 하도록 DB가 가른다. 그래서 한 앱이 배포로 꺼져 있어도 다른 앱이 계속 한다.
  - 예약 발행(POST-13): 글을 엔티티로 읽어 고쳐 저장하던 것을, 번호만 읽고 글마다 `UPDATE … WHERE id = ? AND status = 'SCHEDULED'`(조건부 UPDATE)로 바꿨다. 바뀐 행이 1인 쪽만 발행 이벤트를 보낸다. 늦은 쪽은 행 잠금을 기다렸다가 커밋된 행으로 WHERE를 다시 보고 0행이 된다(READ COMMITTED). 발행 칸만 바꾸므로 그사이 고친 제목을 덮어쓰지 않고, `updated_at`도 바꾸지 않는다(벌크 UPDATE라 Auditing을 거치지 않음).
  - 새벽 통계(MNG-03): `pg_try_advisory_xact_lock`을 잡은 앱만 모으고 나머지는 건너뛴다. 지우고 다시 넣기가 겹치면 UNIQUE 위반으로 한쪽이 실패하기 때문이다. 연달아 다시 모으는 것은 결과가 같아 막지 않는다.
  - 글을 고치는 요청(지원 리뷰로 찾음): 예약 발행 작업이 UPDATE하고 커밋하기 전에 예약 취소·수정·공개 범위 변경 요청이 글을 읽으면 옛 상태로 "발행한 글은 되돌릴 수 없다" 검사를 통과하고, 변경 감지의 UPDATE(`WHERE id = ?`, 모든 칸)가 발행을 덮어썼다. 앱 한 대에서도 생긴다. 글을 고치는 요청은 엔티티를 읽기 전에 `SELECT … FOR UPDATE`로 행을 잠근다(`lockById`, 여러 글은 번호 순서로 `lockAllById`). 누가 먼저든 뒤쪽이 앞쪽 커밋을 보고 판단한다.
  - 비관적 락을 고르고 `@Version`(낙관적 락)을 고르지 않은 이유: 충돌해도 기다렸다가 최신 상태로 처리하면 대부분 둘 다 반영된다(발행 직후 내용만 고친 요청은 200). `@Version`이면 409 처리·화면 안내·재시도, 작업의 글마다 트랜잭션 나누기, version 칸 마이그레이션이 필요하다. 공감·댓글이 이미 `lockById`를 쓴다.
- **헬스체크**: `spring-boot-starter-actuator`로 `/actuator/health/readiness`(readinessState·db·redis)와 `/liveness`를 연다. health만 열고 details는 숨긴다(바깥에도 열리는 주소). 메일 서버 검사는 끈다(메일 비밀번호가 없으면 health 전체가 DOWN이 됨). 배포 스크립트가 새 앱이 요청을 받을 수 있는지 이 주소로 본다.
- **앱 끄기**: `docker stop -t 70`. Spring Boot는 graceful shutdown이 기본이라 새 연결을 거부하고 처리 중인 HTTP 요청을 마친다. 돌고 있는 `@Async` 작업(임베딩, 재설정 메일)도 종료 단계 제한(30초)까지 기다리고 DB는 그 뒤에 닫힌다(실험으로 확인). 두 기다림이 차례로 지나가므로 70초를 준다. `spring.task.execution.shutdown.await-termination=true`는 넣지 않는다. 켜면 종료 단계에서 기다리지 않고 DB부터 닫은 뒤에 기다려서 작업이 DB를 못 쓴다(실험으로 확인, `AsyncConfig` 주석).
- **배포 스크립트**(`deploy/deploy.sh`): app-2 → app 순서로 한 대씩 stop → 새 이미지로 띄움 → readiness UP까지 최대 3분 → 12초(nginx `fail_timeout`보다 길게) → 다음 앱. 처음 배포에는 app-2가 없으므로 app-2를 먼저 띄워 app을 바꾸는 동안에도 한 대가 받는다. 실패하면 배포 전 이미지 ID로 바꾼 앱을 거꾸로 되돌리고, 아직 안 바꾼 앱은 건드리지 않는다. 되돌리기가 실패하면 남은 새 버전 앱을 끄지 않는다(살아 있는 앱이 0대가 되지 않게). 옛 이미지는 두 대가 모두 바뀐 뒤에만 지운다. Redis는 지금 비밀번호로 PING이 되면 다시 만들지 않는다(다시 만들면 요청을 받는 앱이 로그인·캐시를 잃는다).
- **남은 것**: 서버 한 대 안의 이중화라 서버가 죽으면 둘 다 죽는다(DB·Redis도 한 대). 배포 중에는 옛 버전과 새 버전이 함께 떠 있으므로 DB 컬럼 삭제·이름 바꾸기는 "늘리기 → 옮기기 → 줄이기"로 배포를 나눈다(되돌리기도 이것을 전제로 한다). 화면 JS 파일 이름에 해시가 있어 섞인 동안 새 index.html이 옛 앱에서 JS 404를 받을 수 있다(새로고침하면 풀림, 받아들임). 두 기기에서 같은 글을 열어 두고 저장하는 긴 틈은 행 잠금으로 막지 못한다(필요하면 `@Version` + 화면이 version을 들고 다니기, 범위 밖). 앱 컨테이너에 메모리 상한이 없다(앱당 600MiB대 사용).
