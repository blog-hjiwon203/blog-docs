# 68. 운영 데이터 옮기기와 전환: 서버·컨테이너·DB가 어디 있는지부터

> 관련 스텝: [스텝 24](../step-24.md) (T129~T132) · 관련 개념: [67-mysql-to-postgresql](./67-mysql-to-postgresql.md), [65-postgresql-vs-mysql](./65-postgresql-vs-mysql.md), [03-flyway-migration](./03-flyway-migration.md), [42-second-db-async-events](./42-second-db-async-events.md)

> **한 줄 요약**: 운영 DB를 바꾸는 일은 코드보다 **순서**가 중요하다. 어디에 무엇이 도는지 그림을 먼저 그리고, "앱 멈춤 → 옮김 → 확인 → 다시 띄움"을 한 번에 하는 스크립트를 만들고, 되돌아갈 길(옛 DB, 옛 커밋)을 남겨 둔다.

## 1. 이 문서로 배우는 것

- 서버, Docker, 컨테이너, 포트, docker 네트워크의 관계. 개발용과 운영용이 왜 두 벌인가
- 이 프로젝트에서 무엇이 어느 컴퓨터에 있는가(스텝 24 전과 후)
- DB 사이에 데이터를 옮기는 법: PostgreSQL `COPY` 글자 형식, 이스케이프, 외래 키 순서, 번호 시퀀스
- 옮긴 뒤 확인하는 법: 행 수, 내용 대조
- 운영 전환과 되돌리기: 멈추는 시간, 옛 DB를 남겨 두는 이유
- 비밀번호를 명령줄에 쓰지 않는 법

## 2. 왜 필요한가

스텝 23에서 코드는 PostgreSQL로 바뀌었다. 그런데 운영 사이트의 회원·글은 아직 학교 MySQL(s4)에 있다. 새 코드만 배포하면 운영은 **빈 DB**로 뜬다. 데이터를 옮겨야 한다.

옮기는 일은 한 번뿐이고 운영 데이터를 다룬다. 손으로 SQL을 하나씩 치면 표 하나를 빠뜨리거나 번호를 안 맞추기 쉽다. 그래서 스크립트 하나로 만들고, 노트북에서 먼저 시험했다.

## 3. 기본 개념

### 3.1 서버와 Docker

- **서버**는 컴퓨터다. 이 프로젝트에는 컴퓨터가 셋 나온다: 지원 노트북, 학교 실습 서버 **s2**, 학교 DB 서버 **s4**.
- **Docker**는 컴퓨터 안에 **컨테이너**(상자)를 만들어 프로그램을 넣고 돌리는 도구다. 프로그램을 설치하지 않고 이미지(상자 틀)째 받아 띄운다.
- **Docker는 컴퓨터마다 따로 있다.** 노트북의 Docker Desktop 화면에는 노트북의 컨테이너만 보인다. s2의 컨테이너를 보려면 s2에 ssh로 들어가서 `docker ps`를 친다.

왜 서버에서도 Docker를 쓰나? s2는 학생들이 같이 쓰는 서버다. PostgreSQL을 직접 설치하려면 관리자 권한이 필요하고, 다른 학생과 버전·포트·설정이 부딪힌다. 컨테이너는 각자 따로라 이름(`aigj017-…`)만 다르면 겹치지 않고, `docker rm`이면 깨끗이 사라진다. 노트북도 운영과 **같은 이미지**(`pgvector/pgvector:pg17`)를 띄우므로 "내 컴퓨터에서는 되는데 서버에서는 안 된다"가 줄어든다.

### 3.2 포트와 docker 네트워크: 건물·방·현관문

비유: 컴퓨터는 **건물**, 컨테이너는 건물 안의 **방**이다.

- **방 안의 포트**(예: PostgreSQL 5432)는 같은 건물 안 복도에서 그 방을 찾아가는 번호다. 같은 docker 네트워크(복도)에 있는 컨테이너끼리는 이름과 이 번호로 바로 닿는다: `aigj017-recommend-db:5432`.
- **건물 현관문**(서버 포트)은 건물 **바깥**에서 들어오는 문이다. `-p 8460:8460`은 "현관문 8460을 이 방으로 연결"이라는 뜻이다. s2는 공용 건물이라 학교가 학생마다 현관문 번호를 나눠 줬다(지원은 8460~8469).

그래서 운영 PostgreSQL은 현관문(서버 포트)을 열지 않았다. 같은 s2 안의 앱만 복도로 들어가면 되고, 바깥 사람이 DB에 바로 들어오면 위험하기 때문이다. **포트를 열었는지와 어느 컴퓨터에 있는지는 상관이 없다.** 노트북의 개발 DB가 `5432:5432`로 현관문을 연 것은, 노트북에서 직접 실행한 개발 서버(컨테이너가 아님)가 `localhost:5432`로 들어가야 하기 때문이다.

### 3.3 개발용과 운영용은 두 벌이다

같은 프로그램을 두 컴퓨터에 하나씩 띄운다. 데이터도, 연결 정보도 따로다.

| 프로그램 | 개발용 (노트북) | 운영용 |
| --- | --- | --- |
| PostgreSQL | `blog-postgres`, `localhost:5432`, `blog`/`blog` (코드에 적힘) | `aigj017-recommend-db` (s2), 비밀번호는 GitHub secret `RECOMMEND_DB_PASSWORD` |
| Redis | `blog-redis` | `aigj017-redis` (s2) |
| Ollama | `blog-ollama` | `aigj017-ollama` (s2) |
| 블로그 앱 | `./mvnw spring-boot:run` (8080) | `aigj017-app` (s2, 8460) |
| MySQL (스텝 24 전) | `blog-mysql` (스텝 23부터 안 씀) | s4 학교 MySQL (우리가 띄운 것 아님) |

개발용 비밀번호(`blog`)는 공개돼도 상관없어서 `docker-compose.yml`·`application-dev.yml`에 적혀 있다. 운영 비밀번호는 GitHub secrets에만 있고, 배포할 때 `deploy.sh`가 꺼내 쓴다. 노트북 Docker를 꺼도 운영은 그대로다.

### 3.4 COPY 글자 형식

PostgreSQL `COPY … FROM STDIN`(psql에서는 `\copy`)은 표에 행을 빠르게 넣는다. 기본 글자 형식은:

- 한 줄이 한 행, 칸은 **탭**으로 나눈다
- NULL은 `\N`
- 값 안의 역슬래시·탭·줄바꿈은 `\\`, `\t`, `\n`(`\r`)로 쓴다

그래서 MySQL에서 꺼낼 때 이 모양으로 만들어 주면 그대로 흘려 넣을 수 있다. 조심할 점: `mysql -B`(탭 출력)는 기본으로 비슷한 이스케이프를 해 주지만, **NULL과 글자 'NULL'이 둘 다 `NULL`로 나와 구분이 안 된다.** 그래서 `--raw`(이스케이프 없음)로 받고, 이스케이프는 SELECT 식에서 직접 했다(5.2).

### 3.5 외래 키 순서와 번호 시퀀스

- **외래 키 순서**: 글(post)은 블로그(blog)를 가리킨다. 블로그보다 글을 먼저 넣으면 외래 키 확인에서 실패한다. 표 26개의 순서를 따지는 대신, 넣는 세션만 `session_replication_role = replica`로 두어 외래 키 트리거를 끈다. MySQL에서 이미 외래 키로 맞춰진 데이터라 괜찮다. 이 설정은 슈퍼유저만 쓸 수 있다(이 프로젝트의 `blog` 계정은 컨테이너를 만들 때의 슈퍼유저다).
- **번호 시퀀스**: id 칸이 `GENERATED BY DEFAULT AS IDENTITY`라 옛 번호를 그대로 넣을 수 있다. 하지만 번호를 직접 넣으면 시퀀스(다음 번호 장치)는 그대로 1에 머문다. 맞추지 않으면 **다음 가입이 id 1과 부딪혀 500**이다. 표마다 `setval(…, max(id) + 1, false)`로 맞춘다.

### 3.6 전환과 되돌리기

운영 전환에는 세 가지를 정해 둔다.

1. **멈추는 시간**: 옮기는 동안 새 글이 쓰이면 빠진다. 앱을 멈추고 옮긴다. 이 프로젝트는 데이터가 적어 몇 분이다.
2. **확인 기준**: 표마다 행 수가 같아야 앱을 다시 띄운다. 다르면 멈춘 채로 둔다.
3. **되돌릴 길**: 옛 DB(s4 MySQL)는 읽기만 하고 지우지 않는다. 이전 커밋으로 다시 배포하면 옛 `deploy.sh`가 MySQL로 앱을 띄운다. 그래서 GitHub secrets의 `DB_*`도 며칠 남긴다. 단, 되돌리면 그 사이 PostgreSQL에 새로 쓰인 글은 MySQL에 없다. 지켜보는 기간은 짧게 잡는다.

## 4. 동작 원리: 스텝 24 전과 후

```
스텝 24 전                                       스텝 24 후
s2: aigj017-app ──▶ s4 MySQL (회원·글)            s2: aigj017-app ──▶ aigj017-recommend-db
          └──────▶ aigj017-recommend-db                                 └ blog DB (회원·글·임베딩)
                     └ recommend DB (임베딩만)                          └ recommend DB (옛 임베딩, 며칠 뒤 지움)
```

전환 순서(research R-02):

```
① 코드 PR 병합 → GitHub Actions 배포
   deploy.sh: PostgreSQL 컨테이너 안에 blog DB가 없으면 만듦 → 앱을 blog DB로 띄움
   앱: Flyway V1·V2로 빈 표 + 초기 관리자 행 → 사이트가 빈 DB로 뜸 (몇 분)
② 지원이 s2에서 bash ~/now-log/deploy/migrate-from-mysql.sh
   앱 멈춤 → 표 비움 → 표마다 s4 MySQL → \copy → 시퀀스 → 행 수 비교 → 앱 다시 띄움
③ 앱이 뜨면서 발행 글 임베딩을 새로 만듦 (PostEmbeddingListener.onReady)
④ 며칠 지켜본 뒤: GitHub secrets DB_* 지우기, recommend DB 지우기
```

①과 ② 사이에 누가 가입하면 그 행은 ②에서 지워진다. 데이터가 적고 몇 분이라 받아들였다. 이 틈을 없애려면 배포 스크립트가 옮기기까지 하게 만들 수 있지만, 한 번뿐인 일에 배포를 복잡하게 만들지 않았다.

## 5. 이 프로젝트에서는

### 5.1 deploy.sh: 같은 컨테이너, 새 DB

`deploy/deploy.sh`:

```bash
# 주 DB(blog)가 없으면 만든다. 표는 앱이 뜰 때 Flyway가 만든다. 옛 recommend DB(스텝 22까지의 임베딩)는 건드리지 않는다
if [ -z "$(docker exec "$DB" psql -U blog -d recommend -tAc "SELECT 1 FROM pg_database WHERE datname = '$DB_NAME'")" ]; then
  docker exec "$DB" createdb -U blog "$DB_NAME"
  echo "   $DB_NAME DB를 새로 만들었습니다. 운영 데이터를 옮기려면 deploy/migrate-from-mysql.sh를 실행하세요"
fi
```

- 컨테이너(`aigj017-recommend-db`)는 2차 배포 때 만든 것을 그대로 쓴다. PostgreSQL 하나 안에 DB를 여러 개 둘 수 있어서, `blog` DB를 하나 더 만든다.
- 컨테이너 안에서 `psql`·`createdb`를 실행하면 비밀번호 없이 된다(같은 컨테이너 안의 접속은 믿는 설정).
- 앱에 넘기는 주소: `jdbc:postgresql://aigj017-recommend-db:5432/blog`. 컨테이너 이름이 곧 주소다(docker 네트워크).

비밀번호는 명령줄에 쓰지 않는다.

```bash
DB_PASSWORD="$RECOMMEND_DB_PASSWORD" docker run -d --name "$APP" … -e DB_PASSWORD …
```

`-e DB_PASSWORD=값`으로 쓰면 그 값이 명령줄에 들어가 서버의 다른 사용자도 `ps`로 볼 수 있다. 앞에 변수를 붙여 이 명령의 환경으로만 주고, `-e DB_PASSWORD`(값 없이)로 "이 환경 변수를 그대로 넘겨라"라고 한다.

### 5.2 migrate-from-mysql.sh: 칸 하나를 COPY 모양으로

```bash
read -r -d '' CELL <<'SQL' || true
IFNULL(REPLACE(REPLACE(REPLACE(REPLACE(CAST(`@` AS CHAR), CHAR(92 USING utf8mb4), CHAR(92, 92 USING utf8mb4)), CHAR(9 USING utf8mb4), CHAR(92, 116 USING utf8mb4)), CHAR(10 USING utf8mb4), CHAR(92, 110 USING utf8mb4)), CHAR(13 USING utf8mb4), CHAR(92, 114 USING utf8mb4)), CHAR(92, 78 USING utf8mb4))
SQL
```

- `<<'SQL'`(따옴표 친 here-doc): bash가 안의 글자를 건드리지 않고 그대로 둔다. 따옴표가 여러 겹인 sed 이스케이프보다 덜 틀린다.
- `CHAR(92 USING utf8mb4)`: 글자 번호 92(역슬래시)로 만든 글자. 9는 탭, 10은 줄바꿈, 13은 CR, 116·110·114·78은 `t`·`n`·`r`·`N`이다. 그러니 "역슬래시 → 둘, 탭 → `\t`, 줄바꿈 → `\n`, NULL → `\N`"이 된다.
- 왜 `'\t'` 같은 문자열 이스케이프를 쓰지 않나: MySQL은 `sql_mode`에 `NO_BACKSLASH_ESCAPES`가 있으면 문자열 안의 역슬래시를 그냥 글자로 본다. 학교 MySQL의 설정을 모르니, 설정과 상관없이 같은 글자 번호로 썼다. `USING utf8mb4`를 붙이지 않으면 `CHAR()`가 바이너리 문자열을 돌려줘서, 섞이는 글자의 문자셋이 흐려진다.
- 역슬래시를 **맨 먼저** 바꾼다. 나중에 바꾸면 방금 만든 `\t`의 역슬래시까지 두 배가 된다.
- `CAST(… AS CHAR)`: 숫자·시각·0/1도 글자로. 시각은 `2026-10-13 12:00:00.123456`처럼 나와 PostgreSQL TIMESTAMP가 그대로 받고, `TINYINT(1)`의 0/1은 BOOLEAN이 받는다.
- `IFNULL(…, \N)`: NULL이면 `\N` 두 글자.
- `@` 자리에 칸 이름을 끼운다: `${CELL//@/$c}`.

표 하나를 옮기는 줄:

```bash
mysql_q "SELECT $SELECT_COLS FROM \`$t\`" \
  | docker exec -i -e PGOPTIONS='-c session_replication_role=replica' "$PG" \
      psql -X -q -v ON_ERROR_STOP=1 -U blog -d "$PG_DB" -c "\\copy \"$t\" ($PG_COLS) FROM STDIN"
```

- 칸 목록은 PostgreSQL에서 읽는다(계산 칸 `is_generated = 'NEVER'`만). 같은 순서로 MySQL에서 SELECT하므로 칸 순서가 어긋나지 않는다.
- 파이프(`|`)로 바로 흘려서 중간 파일이 남지 않는다.
- `PGOPTIONS`로 이 psql 세션만 외래 키 확인을 끈다(3.5).
- `-v ON_ERROR_STOP=1`과 `set -o pipefail`: 한 표라도 실패하면 스크립트가 멈춘다.

MySQL 비밀번호는 `read -s`로 화면에 안 보이게 받고, 임시 폴더의 설정 파일(`[client] password=…`)로 mysql에 넘긴다. 끝나면 `trap`이 그 폴더를 지운다.

### 5.3 노트북에서 시험한 결과

같은 스크립트를 환경 변수만 바꿔 노트북의 개발 MySQL(`blog-mysql`) → 개발 PostgreSQL의 시험 DB(`migtest`)로 돌렸다.

```bash
MYSQL_HOST=blog-mysql MYSQL_PORT=3306 MYSQL_USER=blog MYSQL_DB=blog MYSQL_PASSWORD=blog \
NETWORK=blog_default PG=blog-postgres PG_DB=migtest APP=no-such-app \
bash deploy/migrate-from-mysql.sh --yes
```

- 표 26개 행 수가 모두 같았다(글 33, 회원 17, 조회 기록 73 …).
- 행 수만으로는 내용이 깨진 것을 모른다. 그래서 글마다 본문·본문 글자·제목의 MD5, 작성·발행 시각(마이크로초까지), 숨김 여부, 카테고리를 두 DB에서 뽑아 `diff`했다. 줄바꿈·탭·역슬래시가 든 글도 있었는데 모두 같았다. 회원(이메일·닉네임·비밀번호 해시·역할·상태·정지 기한)과 계산 칸 `blog.primary_owner_id`도 같았다.
- 다음 글 번호가 `max(id) + 1`(34)이었다.
- 그 DB로 앱을 띄우자 옛 비밀번호로 로그인이 되고, 발행 글 26개의 임베딩이 새로 만들어지고, 글자·의미 검색이 됐다.

## 6. 자주 하는 실수와 함정

- **노트북 Docker 화면에서 운영 컨테이너를 찾는다.** Docker는 컴퓨터마다 따로다. 운영은 s2에서 `docker ps`.
- **"포트를 안 열었으니 노트북 것"이라고 생각한다.** 포트를 여는 것은 바깥에서 들어올 문을 다는 것일 뿐이다. 운영 DB는 s2 안에 있고 일부러 문을 닫았다.
- **번호 시퀀스를 안 맞춘다.** 옮긴 직후에는 아무 문제가 없어 보이다가, 첫 가입에서 500이 난다.
- **NULL과 글자 'NULL'을 구분하지 않는다.** `mysql -B`의 기본 출력은 둘 다 `NULL`이다.
- **역슬래시를 나중에 바꾼다.** 이스케이프 순서가 틀리면 `\t`가 `\\t`가 되어 글자에 역슬래시가 남는다.
- **행 수만 보고 끝낸다.** 글자 인코딩이나 이스케이프가 틀리면 행 수는 같고 내용만 다르다. 몇 표는 내용까지 대조한다.
- **옛 DB를 바로 지운다.** 되돌릴 길이 없어진다. 며칠 지켜본다.
- **비밀번호를 명령줄에 쓴다.** `-p비밀번호`, `-e PASSWORD=값`은 `ps`와 셸 기록에 남는다.

## 7. 직접 해 보기

### 7.1 컨테이너가 어디 있는지

노트북에서 `docker ps --format '{{.Names}}'` → `blog-*`만 보인다. s2에 ssh로 들어가 같은 명령 → `aigj017-*`가 보인다.

### 7.2 COPY 형식 손으로 써 보기

```bash
docker exec -i blog-postgres psql -U blog -d blog <<'EOF'
CREATE TEMP TABLE t (a text, b int);
\copy t FROM STDIN
첫 줄\t바뀜	1
\N	2
역슬래시 \\ 하나	3
\.
SELECT a, a IS NULL AS is_null, b FROM t;
EOF
```

(가운데 칸 구분은 진짜 탭이다.) 첫 행의 `\t`는 탭 글자로, `\N`은 NULL로, `\\`는 역슬래시 하나로 들어간다.

### 7.3 시퀀스를 안 맞추면

```bash
docker exec -i blog-postgres psql -U blog -d blog <<'EOF'
CREATE TEMP TABLE s (id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, v text);
INSERT INTO s (id, v) VALUES (1, '옮긴 행');
INSERT INTO s (v) VALUES ('새 행');   -- 오류: id 1 중복
EOF
```

`SELECT setval(pg_get_serial_sequence('s', 'id'), 2, false);` 뒤에는 새 행이 2번으로 들어간다.

### 7.4 이전 스크립트 시험

5.3의 명령으로 노트북에서 돌려 본다. 그 전에 `CREATE DATABASE migtest`를 하고 V1·V2를 적용해 둔다(스텝 노트 24의 직접 해 보기). 끝나면 `DROP DATABASE migtest`.

## 8. 확인 문제

1. 노트북의 Docker Desktop에 운영 컨테이너가 보이지 않는 이유는?
<details><summary>답</summary>Docker는 컴퓨터마다 따로 돈다. 운영 컨테이너는 s2 서버의 Docker 안에 있고, Docker Desktop은 노트북의 Docker만 보여 준다.</details>

2. 운영 PostgreSQL에 서버 포트를 열지 않았는데도 앱이 접속할 수 있는 이유는?
<details><summary>답</summary>앱과 DB가 같은 s2의 같은 docker 네트워크(aigj017-net)에 있어서, 컨테이너 이름과 내부 포트(aigj017-recommend-db:5432)로 바로 닿는다. 서버 포트는 서버 바깥에서 들어올 때만 필요하다.</details>

3. 서버에서도 프로그램을 직접 설치하지 않고 Docker로 띄우는 이유 두 가지는?
<details><summary>답</summary>공용 서버라 관리자 권한 없이 띄울 수 있고 다른 학생과 버전·포트가 부딪히지 않는다. 개발·테스트·운영이 같은 이미지를 써서 환경 차이가 줄고, 지우거나 다시 띄우기 쉽다.</details>

4. MySQL에서 꺼낼 때 `mysql -B`의 기본 이스케이프를 쓰지 않고 `--raw` + SELECT에서 직접 이스케이프한 이유는?
<details><summary>답</summary>기본 출력은 NULL과 글자 'NULL'을 둘 다 NULL로 내서 구분할 수 없다. 직접 바꾸면 NULL은 \N, 글자는 그대로 나온다.</details>

5. 이스케이프에서 역슬래시를 가장 먼저 바꾸는 이유는?
<details><summary>답</summary>탭을 \t로 바꾼 뒤에 역슬래시를 두 배로 하면, 방금 만든 \t의 역슬래시까지 두 배가 되어 \\t(역슬래시 글자 + t)가 된다.</details>

6. 표 26개를 외래 키 순서대로 넣지 않아도 된 이유와 조건은?
<details><summary>답</summary>넣는 세션만 session_replication_role = replica로 외래 키 트리거를 껐다. MySQL에서 이미 외래 키로 맞던 데이터라 괜찮다. 슈퍼유저만 쓸 수 있는 설정이다.</details>

7. 옮긴 뒤 시퀀스를 맞추지 않으면 언제 어떤 문제가 생기나?
<details><summary>답</summary>옮긴 직후에는 멀쩡하다가, 처음으로 새 행을 넣을 때(가입·글쓰기) 시퀀스가 1을 줘서 이미 있는 id 1과 부딪혀 500이 난다.</details>

8. 행 수가 같은데도 내용을 대조한 이유는?
<details><summary>답</summary>이스케이프나 인코딩이 틀리면 행 수는 같고 본문만 달라진다. 줄바꿈·역슬래시가 든 글, 시각, NULL, 계산 칸을 두 DB에서 뽑아 비교했다.</details>

9. 되돌릴 길로 남겨 둔 것 두 가지와, 되돌릴 때 잃는 것은?
<details><summary>답</summary>s4 MySQL(지우지 않음)과 GitHub secrets DB_*(옛 deploy.sh가 씀). 이전 커밋으로 다시 배포하면 MySQL로 돌아간다. 그 사이 PostgreSQL에 새로 쓰인 데이터는 MySQL에 없어서 잃는다.</details>

10. `-e DB_PASSWORD="$값"` 대신 `DB_PASSWORD="$값" docker run … -e DB_PASSWORD`로 쓴 이유는?
<details><summary>답</summary>앞의 방법은 비밀번호가 docker 명령줄에 들어가 서버의 다른 사용자도 ps로 볼 수 있다. 뒤의 방법은 이 명령의 환경 변수로만 주고, docker에는 변수 이름만 넘긴다.</details>
