# 67. MySQL에서 PostgreSQL로 옮기기: 문법보다 무서운 조용한 차이

> 관련 스텝: [스텝 23](../step-23.md) (T123~T128) · 관련 개념: [65-postgresql-vs-mysql](./65-postgresql-vs-mysql.md), [03-flyway-migration](./03-flyway-migration.md), [32-search-like](./32-search-like.md), [33-isolation-deadlock](./33-isolation-deadlock.md), [41-embedding-vector-search](./41-embedding-vector-search.md), [42-second-db-async-events](./42-second-db-async-events.md), [66-semantic-search](./66-semantic-search.md)

> **한 줄 요약**: DB를 바꿀 때 문법 오류(`INSERT IGNORE`, `UPDATE … JOIN`)는 실행하자마자 드러나서 오히려 쉽다. 어려운 것은 **오류 없이 결과만 달라지는 차이**다. 대소문자 비교, 드라이버가 값을 보내는 타입, 기본 격리 수준, 시간대가 그렇다. 이 문서는 스텝 23에서 실제로 만난 것들을 순서대로 짚는다.

## 1. 이 문서로 배우는 것

- 스키마를 옮기는 법: 타입 대응표, `IDENTITY`, `COMMENT ON`, 이미 적용된 Flyway 파일을 새로 쓰는 경우
- 대소문자 무시 비교: `citext`, `ILIKE`, 그리고 **JDBC가 글자 값을 `varchar`로 보내면 citext가 대소문자를 가리는 함정**과 `stringtype=unspecified`
- MySQL 전용 SQL 바꾸기: `INSERT IGNORE` → `ON CONFLICT DO NOTHING`, `UPDATE … JOIN` → `UPDATE … FROM`, `DELETE x FROM … JOIN` → `DELETE … USING`
- `ON UPDATE CURRENT_TIMESTAMP`가 없을 때 `updated_at`을 누가 채우나
- 잠금과 격리 수준: REPEATABLE READ → READ COMMITTED, 외래 키 확인의 `FOR KEY SHARE`
- 벡터 검색과 가시성 조건을 **JPA Criteria 한 쿼리**로: hibernate-vector, 타입을 물려받는 값, `fetch`가 INNER JOIN이 되는 함정
- 테스트 SQL에서 자주 걸리는 차이(`INTERVAL`, 0/1, `NOW(6)`, `UPDATE … LIMIT`)

**먼저 알면 좋은 것**: 두 DB의 차이 표([65](./65-postgresql-vs-mysql.md) 3.2), Flyway([03](./03-flyway-migration.md)), 격리 수준과 데드락([33](./33-isolation-deadlock.md)), pgvector와 코사인 거리([41](./41-embedding-vector-search.md)).

## 2. 왜 필요한가

스텝 22까지 이 블로그는 DB를 두 개 썼다. 주 데이터는 MySQL, 글 임베딩은 PostgreSQL이다. 의미 검색을 만들고 보니 두 DB를 오가는 비용이 분명해졌다([66](./66-semantic-search.md) "뽑고 → 거르고 → 자르기"). 운영 데이터가 아주 적은(발행 글 2개) 지금이 옮기기 가장 싸서, 2026-10-13 지원이 PostgreSQL 하나로 합치기로 정했다(research R-02).

이 문서는 "어떻게 옮기나"를 다룬다. "합칠 만한가"는 [65](./65-postgresql-vs-mysql.md)에 있다.

## 3. 기본 개념

### 3.1 옮기기는 세 겹이다

| 겹 | 무엇 | 틀리면 |
| --- | --- | --- |
| ① 스키마 | 표 정의(Flyway SQL) | 서버가 안 뜬다(바로 보임) |
| ② 쿼리 | 네이티브 SQL, 테스트의 SQL | 그 기능을 부를 때 500(테스트가 있으면 보임) |
| ③ 의미 | 비교 규칙, 격리 수준, 시간대, 드라이버의 타입 | **오류 없이 결과가 다르다**(테스트가 그 경우를 짚어야 보임) |

①과 ②는 테스트를 돌리면 거의 다 드러난다. 이번에도 처음 돌린 409개 중 실패는 9개였다. ③은 테스트가 그 경우를 직접 확인하지 않으면 통과한 채로 남는다. 그래서 옮기기 전에 ③의 목록을 먼저 만들고, 항목마다 테스트가 있는지 본다.

### 3.2 타입 대응

| MySQL 8 | PostgreSQL 17 | 메모 |
| --- | --- | --- |
| `BIGINT AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `ALWAYS`면 번호를 직접 넣을 수 없다. 옛 데이터를 번호째 옮기려고 `BY DEFAULT`. 옮긴 뒤 `setval`로 다음 번호를 맞춘다 |
| `TINYINT(1)` | `BOOLEAN` | SQL에서 `= 0`/`= 1`은 오류. `= FALSE`, `NOT x` |
| `DATETIME` / `DATETIME(6)` | `TIMESTAMP(0)` / `TIMESTAMP(6)` | 시간대 없는 시각. `TIMESTAMPTZ`는 시간대가 있는 다른 타입 |
| `MEDIUMTEXT`, `TEXT` | `TEXT` | PostgreSQL `TEXT`는 길이 제한이 사실상 없다 |
| `VARCHAR(n)` + `ai_ci` 콜레이션 | `CITEXT` + `CHECK (char_length(x) <= n)` | 3.3 |
| `COMMENT '…'` (칸 정의 안) | `COMMENT ON TABLE/COLUMN … IS '…'` (따로) | |
| `IFNULL(a, b)` | `COALESCE(a, b)` | `COALESCE`는 둘 다에서 된다 |
| `ON UPDATE CURRENT_TIMESTAMP` | 없음 | 3.5 |

### 3.3 대소문자 무시 비교: citext

MySQL은 칸마다 **콜레이션**(글자를 비교·정렬하는 규칙)이 있고, 이 프로젝트의 `utf8mb4_0900_ai_ci`는 대소문자(ci)와 악센트(ai)를 무시한다. 그래서 `'Java' = 'java'`가 참이고, UNIQUE도 둘을 같은 값으로 본다.

PostgreSQL의 기본 비교는 대소문자를 가린다. 무시하는 방법은 넷이다.

| 방법 | 같음 비교 | UNIQUE | LIKE | 메모 |
| --- | --- | --- | --- | --- |
| `lower(x) = lower(y)` | 됨 | `lower(x)`에 UNIQUE 인덱스 | `lower(x) LIKE lower(p)` | 쿼리마다 잊지 않고 써야 한다 |
| `ILIKE` | (LIKE 전용) | | 됨 | 검색에만 |
| `citext` 확장 | 됨 | 그냥 UNIQUE | 됨 | 칸 타입만 바꾸면 쿼리는 그대로 |
| 비결정적 콜레이션(`deterministic = false`) | 됨 | 됨 | **PostgreSQL 17까지 LIKE 불가** | 악센트 무시도 가능하지만 LIKE가 막힘 |

이 프로젝트는 **이름 칸**(이메일, 닉네임, 블로그 주소, 카테고리, 태그, 금칙어)을 `citext`로, **검색**(글 제목·본문, 블로그 이름·소개)은 `ILIKE`로 했다. `citext`는 내부적으로 `lower()`로 바꿔 비교하므로 **악센트는 가린다**(Café ≠ cafe). 한글에는 대소문자도 악센트도 없어 영향이 없다. 지원이 이 차이를 받아들이기로 했다.

### 3.4 함정: 드라이버가 보내는 타입

`citext` 칸을 만들고 끝났다고 생각하기 쉽다. psql에서 직접 해 보면 이렇다(스텝 23에서 실제로 돌린 결과).

```sql
CREATE TEMP TABLE t (e citext UNIQUE);
INSERT INTO t VALUES ('Test@X.com');
SELECT e = 'test@x.com'::varchar AS v,   -- f  ← 대소문자를 가림!
       e = 'test@x.com'::text    AS t,   -- f
       e = 'test@x.com'          AS u,   -- t  (타입 없는 글자)
       e LIKE 'test%'::varchar   AS l    -- t
FROM t;
```

`e = '…'::varchar`가 **거짓**이다. PostgreSQL은 연산자를 고를 때 양쪽 타입을 본다. 오른쪽이 `varchar`면 citext를 text로 바꿔 `text = text`(대소문자 구분)를 고른다. 오른쪽이 **타입 없는 글자**(unknown)면 왼쪽 칸의 타입(citext)에 맞춰 `citext = citext`를 고른다.

그리고 JDBC 드라이버(PgJDBC)는 자바 `String` 값을 기본으로 **`varchar`로 보낸다.** 그러니 JPA가 `where m.nickname = ?`를 실행하면 대소문자를 가린다. 테스트가 없으면 "칸은 citext인데 중복 닉네임이 들어간다"는 일이 조용히 생긴다.

해결은 드라이버 설정 `stringtype=unspecified`다. 글자 값을 타입 없이 보내면 서버가 칸의 타입에 맞춰 정한다.

### 3.5 updated_at은 누가 채우나

MySQL의 `ON UPDATE CURRENT_TIMESTAMP`는 그 행의 **어떤 칸이든 바뀌면** DB가 수정 시각을 지금으로 바꾼다. PostgreSQL에는 이 기능이 없다(흉내 내려면 트리거).

이 프로젝트는 원래 두 군데서 채웠다.

1. 엔티티를 고칠 때: JPA Auditing의 `@LastModifiedDate`가 넣는다.
2. 그 밖: MySQL `ON UPDATE`가 넣는다. 그래서 "작성자가 고친 것이 아니면 수정 시각을 그대로 둔다"는 규칙(조회수, 댓글 수, 관리자 숨김)을 지키려고 쿼리마다 `updated_at = updated_at`을 일부러 써서 막았다(15곳).

PostgreSQL에서는 2가 없어지므로 **트리거를 두지 않으면** 이 규칙이 저절로 지켜진다. 벌크 UPDATE(JPQL `update … set`, 네이티브 SQL)는 `@LastModifiedDate`를 거치지 않기 때문이다. 그래서 `updated_at = updated_at`은 하는 일이 없어져 지웠다. 반대로 트리거를 만들었다면 이 15곳을 하나하나 다시 막아야 했다.

### 3.6 격리 수준과 잠금

| | MySQL InnoDB | PostgreSQL |
| --- | --- | --- |
| 기본 격리 | REPEATABLE READ: 트랜잭션의 첫 읽기 때 스냅샷을 계속 본다 | READ COMMITTED: **문장마다** 그때까지 커밋된 것을 본다 |
| 빈 자리(gap) 잠금 | 있음. 범위 조건으로 잠그면 아직 없는 행의 자리도 잠김 | 없음 |
| 외래 키 확인 | 부모 행에 공유 잠금(S) | 부모 행에 `FOR KEY SHARE`. 키가 아닌 칸의 UPDATE(`FOR NO KEY UPDATE`)와 부딪히지 않음 |
| "있으면 무시" 중 다른 트랜잭션이 같은 키를 넣는 중 | `INSERT IGNORE`가 그 행에 공유 잠금을 건다 | `ON CONFLICT DO NOTHING`이 상대 트랜잭션이 끝나기를 기다린 뒤 판단한다 |

이 프로젝트에는 MySQL 동작을 전제로 쓴 주석과 코드가 있었다([33](./33-isolation-deadlock.md)).

- "글 행을 먼저 잠그지 않으면 공감 INSERT(외래 키 공유 잠금)와 공감 수 UPDATE(배타 잠금)가 엇갈려 데드락": PostgreSQL에서는 외래 키 확인이 `FOR KEY SHARE`라 이 데드락은 생기지 않는다. 그래도 **글 행 잠금은 남겼다.** 같은 글의 공감·댓글·조회 기록을 차례로 처리해 "앞 요청이 넣은 것을 보고 판단"하게 하는 역할이 여전히 있기 때문이다.
- "잠그며 읽어야 다른 트랜잭션이 막 커밋한 값이 보인다(REPEATABLE READ 스냅샷)": READ COMMITTED에서는 평범한 SELECT도 새 값을 본다. 잠그며 읽기는 격리 수준을 올려도 맞도록 남겼다.

동시성 테스트(공감 연타, 같은 새 태그 동시 저장, 조회수 연타)는 그대로 통과했다.

## 4. 동작 원리

### 4.1 MySQL 전용 SQL 바꾸기

**있으면 무시하고 넣기**

```sql
-- MySQL
INSERT IGNORE INTO post_like (post_id, member_id) VALUES (?, ?);
-- PostgreSQL
INSERT INTO post_like (post_id, member_id) VALUES (?, ?) ON CONFLICT DO NOTHING;
```

둘 다 "넣은 행 수"를 0 또는 1로 돌려준다. 그 수로 "새로 눌렀나"를 판단하는 코드는 그대로 둔다. 차이 하나: `INSERT IGNORE`는 UNIQUE 말고 다른 오류(CHECK 위반, 글자 길이 초과 등)도 경고로 바꿔 삼킨다. `ON CONFLICT DO NOTHING`은 UNIQUE·기본 키 충돌만 넘긴다. 이 편이 더 안전하다.

**다른 표를 보며 고치기·지우기**

```sql
-- MySQL
UPDATE post p JOIN post_like l ON l.post_id = p.id
SET p.like_count = p.like_count - 1 WHERE l.member_id = ?;
DELETE l FROM post_like l JOIN post p ON p.id = l.post_id WHERE p.blog_id = ?;

-- PostgreSQL
UPDATE post p SET like_count = p.like_count - 1
FROM post_like l WHERE l.post_id = p.id AND l.member_id = ?;
DELETE FROM post_like l USING post p WHERE p.id = l.post_id AND p.blog_id = ?;
```

PostgreSQL에서는 `SET`의 왼쪽에 별칭을 붙이지 않는다(`SET p.like_count`는 오류). 오른쪽 식에서는 붙여도 된다. 조인 조건은 `WHERE`로 간다.

### 4.2 이미 적용된 마이그레이션을 새로 쓰기

Flyway의 규칙은 "이미 적용된 파일은 고치지 않는다"다([03](./03-flyway-migration.md)). 고치면 체크섬이 달라져 서버가 뜨지 않는다. 그런데 이번에는 **DB 자체가 새것**이다. 새 PostgreSQL DB에는 Flyway 이력 표가 비어 있으니, MySQL용 V1~V4를 고치는 것이 아니라 PostgreSQL용 V1·V2를 새로 시작한 것이다. MySQL 쪽 이력은 옛 DB(s4)에 그대로 남는다.

그래서 V3(본문 글자 칸 더하기)와 V4(사이드바 기본 행 채우기)는 지웠다. V3의 칸은 새 V1에 처음부터 넣었고, V4는 "이미 있던 블로그에 채우기"라 빈 DB에는 할 일이 없다. 운영 데이터는 이미 V4가 적용된 MySQL에서 옮겨 오므로 사이드바 행도 함께 온다(스텝 24).

### 4.3 벡터 검색과 가시성을 한 쿼리로

DB가 둘일 때는 이렇게 했다([66](./66-semantic-search.md)).

```
PostgreSQL: 가까운 글 번호 100개 → MySQL: 그중 볼 수 있는 글 → 자바에서 순서 맞춰 자르기
```

한 DB가 되면 조인 하나로 된다. 문제는 가시성 조건이 SQL이 아니라 **JPA Criteria**(`PostSpecifications.visibleTo`)로 짜여 있다는 것이다. 이 조건을 SQL로 한 벌 더 쓰면 두 벌을 같이 고쳐야 한다. 그래서 반대로 임베딩 표를 엔티티로 만들어 Criteria 쪽으로 데려왔다.

- `PostEmbedding` 엔티티: `@JdbcTypeCode(SqlTypes.VECTOR) float[] embedding`. hibernate-vector 모듈이 pgvector의 `vector` 칸을 `float[]`로 읽고, `cosine_distance` 같은 함수를 HQL·Criteria에 등록한다.
- 쿼리: `from Post p, PostEmbedding e where e.postId = p.id and (visibleTo 조건) order by cosine_distance(e.embedding, :query)`.

## 5. 이 프로젝트에서는

### 5.1 스키마: 변환 스크립트로 만든 V1

`V1__init.sql`(PostgreSQL)은 MySQL V1을 손으로 옮기지 않고 작은 스크립트로 바꿔 만들었다. 칸 200개 남짓을 손으로 옮기면 하나쯤 빠뜨리기 쉽다. 만든 뒤에는 개발 PostgreSQL에 실제로 적용해 오류가 없는지 먼저 봤다. 결과의 한 표:

```sql
CREATE TABLE member (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    profile_image_id BIGINT,
    email CITEXT,
    password_hash VARCHAR(100),
    nickname CITEXT NOT NULL,
    ...
    created_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    CONSTRAINT uk_member_email UNIQUE (email),
    CONSTRAINT uk_member_nickname UNIQUE (nickname),
    ...
    CONSTRAINT ck_member_email_length CHECK (char_length(email) <= 255),
    CONSTRAINT ck_member_nickname_length CHECK (char_length(nickname) <= 20)
);
```

- `email CITEXT` + `uk_member_email`: 대소문자만 다른 이메일은 UNIQUE 위반이다.
- `ck_member_nickname_length`: citext에는 길이가 없어서 원래의 `VARCHAR(20)` 제한을 CHECK로 옮겼다.
- `updated_at`에 `ON UPDATE`가 없다(3.5).

엔티티 쪽은 `ddl-auto=validate`가 칸 타입을 비교한다. 자바 `String`은 보통 `varchar`를 기대하므로 citext 칸에는 `columnDefinition`을 적어 알려 준다.

```java
@Column(name = "nickname", nullable = false, length = 20, columnDefinition = "citext")
private String nickname;
```

### 5.2 접속 설정: stringtype과 HNSW

`application.yml`:

```yaml
spring:
  datasource:
    hikari:
      data-source-properties:
        stringtype: unspecified
      connection-init-sql: "SET hnsw.ef_search = 200; SET hnsw.iterative_scan = strict_order"
```

- `stringtype: unspecified`: 3.4의 함정 막기. 개발·운영·테스트가 모두 이 설정 파일을 읽으므로 접속 주소마다 붙이지 않아도 된다.
- `hnsw.ef_search = 200`: HNSW 인덱스가 한 번에 보는 후보 수. 기본 40이면 의미 검색이 가까운 순 100개를 다 못 본다([66](./66-semantic-search.md)).
- `hnsw.iterative_scan = strict_order`(pgvector 0.8부터): 이제 가시성 조건을 **같은 쿼리**에서 거른다. 인덱스가 찾은 후보가 조건에 많이 걸러져 LIMIT를 못 채우면, 인덱스를 더 읽어 채운다. 가까운 순서는 지킨다.

### 5.3 대소문자 무시 검색: ILIKE를 Criteria로

표준 JPA `CriteriaBuilder`에는 `ilike`가 없다. Spring Data가 넘겨주는 `cb`는 실제로 Hibernate 구현이라, `HibernateCriteriaBuilder`로 바꿔 부른다. `global/web/LikePatterns.java`:

```java
public static Predicate containsIgnoreCase(CriteriaBuilder cb, Expression<String> column, String pattern) {
    return ((HibernateCriteriaBuilder) cb).ilike(column, pattern, ESCAPE);
}
```

- `pattern`은 `%검색어%`로, `%`·`_`를 이스케이프한 것이다([32](./32-search-like.md)).
- 검색(`SearchService`), 내 글 관리 검색(`ManagePostService`), 관리자 회원 검색(`AdminMemberService`)이 모두 이 한 곳을 쓴다.

태그 이름을 합치는 자바 코드(`TagNames.nameComparator`)도 DB와 같은 규칙이어야 한다. 전에는 MySQL `ai_ci`를 흉내 내려고 `Collator`의 1차 비교(악센트까지 무시)를 썼다. 이제는 소문자 비교다. 둘이 다르면 "자바는 같다고 보고 하나로 합쳤는데 DB는 다르다고 본다"는 어긋남이 생긴다.

### 5.4 MySQL 전용 SQL

| 무엇 | 곳 | 바꾼 것 |
| --- | --- | --- |
| `INSERT IGNORE` | 공감·저장·신고·구독·차단·금칙어·태그·방문 기록 (8곳) | `ON CONFLICT DO NOTHING` |
| `UPDATE … JOIN` | `MemberTraceCleaner`(2), `BlogContentCleaner`(1), `BlogStatsRepository.refreshTotals`(1) | `UPDATE … FROM` |
| `DELETE x FROM … JOIN` | `BlogContentCleaner`(3) | `DELETE … USING` |
| `is_blinded = 0` | 인기 점수·블로그 점수 SQL | `= FALSE` |
| `updated_at = updated_at` | JPQL 8곳, 네이티브 SQL 7곳 | 지움(3.5) |

`member/domain/MemberTraceCleaner.java` (탈퇴한 회원이 쓴 댓글 수만큼 글마다 댓글 수 줄이기):

```java
jdbcTemplate.update("""
        UPDATE post p SET comment_count = p.comment_count - c.n
        FROM (SELECT post_id, COUNT(*) AS n FROM comment
              WHERE member_id = ? AND deleted_at IS NULL GROUP BY post_id) c
        WHERE c.post_id = p.id""", memberId);
```

- `FROM (부분 쿼리) c`: 글마다 지울 댓글 수를 먼저 세어 표처럼 쓴다.
- `WHERE c.post_id = p.id`: MySQL의 `JOIN … ON`이 하던 일이다.
- `SET comment_count`: 왼쪽에 `p.`를 붙이지 않는다.

### 5.5 한 쿼리로 가까운 글 찾기

`recommend/domain/PostEmbeddingRepository.java`:

```java
public List<NearPost> findNear(float[] query, Specification<Post> visible, Double minSimilarity, Long excludePostId,
                               int offset, int limit, String... fetch) {
    CriteriaBuilder cb = entityManager.getCriteriaBuilder();
    CriteriaQuery<Tuple> criteria = cb.createTupleQuery();
    Root<Post> post = criteria.from(Post.class);
    for (String path : fetch) {
        // 미분류 글(category 없음)도 나오게 LEFT. 그냥 fetch하면 INNER JOIN이라 빠진다
        post.fetch(path, JoinType.LEFT);
    }
    Root<PostEmbedding> embedding = criteria.from(PostEmbedding.class);
    Expression<Double> distance = distance(cb, embedding, query);
    criteria.multiselect(post, distance)
            .where(conditions(cb, criteria, post, embedding, distance, visible, minSimilarity, excludePostId))
            .orderBy(cb.asc(distance), cb.desc(post.get("id")));
    ...
}
```

- `criteria.from`을 두 번: 글과 임베딩을 함께 읽고, `conditions`에서 `e.postId = p.id`로 잇는다.
- `visible.toPredicate(post, criteria, cb)`(`conditions` 안): 글 목록과 **같은** 가시성 코드를 그대로 건다. 의미 검색 전체는 `visibleTo`, 블로그 안은 `listedIn`, 비슷한 글은 `visibleTo`.
- `multiselect(post, distance)`: 글과 거리를 같이 받아 유사도(`1 - 거리`)를 만든다.
- `orderBy(거리, 글 번호 내림차순)`: 가까운 순, 같으면 나중 글.
- `setFirstResult/setMaxResults`(생략한 부분): DB가 페이지를 자른다. 전에는 자바가 잘랐다.

거리 식:

```java
private static Expression<Double> distance(CriteriaBuilder cb, Root<PostEmbedding> embedding, float[] query) {
    SqmExpression<float[]> column = (SqmExpression<float[]>) embedding.<float[]>get("embedding");
    return cb.function("cosine_distance", Double.class, column, ((SqmCriteriaNodeBuilder) cb).value(query, column));
}
```

- `cb.literal(query)`로 넘기면 Hibernate가 `float[]`를 **배열 타입**으로 보고, hibernate-vector가 "cosine_distance의 인자는 vector여야 한다"며 쿼리를 만들지 않는다.
- `value(query, column)`: "이 값의 타입은 저 칸(vector)을 따른다"고 알려 주는 값이다. 그러면 SQL에 `cast(? as vector)`로 들어가고 벡터로 묶여 나간다. 표준 JPA와 공개 API(`HibernateCriteriaBuilder`)에는 이 기능이 없어 Hibernate 구현 클래스를 쓴다. Hibernate를 올릴 때 다시 확인할 자리다.

이렇게 바뀌면서 없어진 것: 블로그 안 검색이 볼 수 있는 글 번호를 모두 모아 `IN (…)`으로 넘기던 일(`PostCountRepository.findIds`), 비슷한 글이 후보 30개를 넉넉히 뽑던 일(`CANDIDATES`), 두 번째 DataSource와 Flyway(`RecommendDataSourceConfig`, `db/recommend`).

### 5.6 테스트에서 만난 차이

| MySQL | PostgreSQL | 메모 |
| --- | --- | --- |
| `NOW() - INTERVAL 2 HOUR` | `NOW() - INTERVAL '2 hour'` | 숫자와 단위를 따옴표 안에 |
| `NOW(6) - INTERVAL ? MINUTE` | `NOW() - ? * INTERVAL '1 minute'` | 자리표시자는 곱하기로 |
| `UPDATE … LIMIT 1` | `WHERE id = (SELECT MIN(id) …)` | UPDATE에 LIMIT 없음 |
| `CAST(x AS CHAR)` | `CAST(x AS TEXT)` | PostgreSQL `CHAR`는 **한 글자**(`char(1)`)라 잘린다 |
| `table_schema = DATABASE()` | `table_schema = current_schema()` | |

`NOW()`의 시간대도 달라졌다. 테스트용 MySQL 컨테이너는 UTC였다. PgJDBC는 접속할 때 JVM 시간대(테스트는 Asia/Seoul)를 세션 시간대로 보내므로, PostgreSQL의 `NOW()`는 한국 시간으로 `TIMESTAMP` 칸에 들어간다. 앱이 넣는 시각(`LocalDateTime`, 한국 시간)과 같은 기준이 되었다.

## 6. 자주 하는 실수와 함정

- **칸만 citext로 바꾸고 드라이버 타입을 잊는다.** JDBC가 `varchar`로 보내면 `citext = varchar`가 대소문자를 가린다(3.4). 대소문자만 다른 값으로 가입·검색하는 테스트로 확인한다.
- **`fetch`를 그냥 쓴다.** Criteria의 `fetch("category")`는 INNER JOIN이다. 카테고리가 없는 글이 결과에서 사라진다. 이번에도 의미 검색이 0개를 돌려줘서 생성된 SQL을 보고 찾았다. 없을 수 있는 연관은 `JoinType.LEFT`.
- **트리거로 `ON UPDATE`를 흉내 낸다.** "수정 시각 그대로" 규칙이 있는 곳마다 다시 막아야 한다. JPA Auditing만 쓰면 벌크 UPDATE는 저절로 시각을 건드리지 않는다.
- **`INSERT IGNORE`를 `ON CONFLICT DO NOTHING`과 똑같다고 믿는다.** MySQL은 다른 오류도 삼킨다. 옮긴 뒤 CHECK 위반이 오류로 드러날 수 있다(그게 맞는 동작이다).
- **같은 쿼리 안의 조건과 근사 인덱스.** HNSW는 후보를 `ef_search`개까지만 보고, 조건으로 거른 뒤 모자라면 결과가 적게 나온다. pgvector 0.8의 `iterative_scan`을 켠다.
- **자바와 DB의 "같은 이름" 규칙이 어긋난다.** DB가 citext(소문자 비교)인데 자바가 악센트까지 무시하면, 자바는 Café와 cafe를 하나로 합치고 DB는 둘을 다르게 저장한다.
- **빌드 폴더에 지운 마이그레이션이 남는다.** `src`에서 V3를 지워도 `target/classes`에 남아 있으면 Flyway가 그것을 실행한다. 파일을 지운 뒤에는 `./mvnw clean`.

### 7.5 격리 수준

psql 창 두 개를 열고 [33](./33-isolation-deadlock.md) 7절의 실습을 PostgreSQL에서 해 본다. 창 A에서 `BEGIN; SELECT like_count FROM post WHERE id = 1;`, 창 B에서 `UPDATE post SET like_count = like_count + 1 WHERE id = 1;`, 창 A에서 다시 SELECT하면 **바뀐 값**이 보인다(READ COMMITTED). `BEGIN ISOLATION LEVEL REPEATABLE READ;`로 시작하면 옛 값이 보인다.

## 8. 확인 문제

1. 옮기기의 세 겹(스키마·쿼리·의미) 중 테스트를 돌려도 드러나지 않을 수 있는 것은? 왜?
<details><summary>답</summary>의미(비교 규칙, 격리 수준, 시간대, 드라이버 타입). 문법 오류가 없어 실행은 되고 결과만 다르다. 테스트가 그 경우(대소문자만 다른 값 등)를 직접 확인할 때만 드러난다.</details>

2. 칸이 citext인데 JPA로 `where nickname = ?`를 하면 대소문자를 가리는 이유와 이 프로젝트의 해결은?
<details><summary>답</summary>PgJDBC가 String을 varchar로 보내서 PostgreSQL이 citext를 text로 바꿔 text = text(대소문자 구분)를 고른다. 접속 설정 <code>stringtype=unspecified</code>로 타입 없이 보내면 칸의 타입(citext)을 따른다.</details>

3. 이 프로젝트가 비결정적 콜레이션 대신 citext를 고른 이유는?
<details><summary>답</summary>PostgreSQL 17까지 비결정적 콜레이션 칸에는 LIKE를 쓸 수 없다. citext는 같음 비교·UNIQUE·LIKE가 모두 된다(악센트는 가림).</details>

4. MySQL에서 `updated_at = updated_at`을 쓴 이유와 PostgreSQL에서 지운 이유는?
<details><summary>답</summary>MySQL의 ON UPDATE CURRENT_TIMESTAMP가 어떤 칸이든 바뀌면 수정 시각을 바꾸므로 일부러 같은 값을 넣어 막았다. PostgreSQL에는 그 기능이 없고 트리거도 두지 않아, 벌크 UPDATE는 원래 수정 시각을 건드리지 않는다.</details>

5. `INSERT IGNORE`와 `ON CONFLICT DO NOTHING`의 공통점과 차이는?
<details><summary>답</summary>공통: 이미 있으면 넣지 않고 0행을 돌려준다. 차이: INSERT IGNORE는 CHECK 위반·길이 초과 같은 다른 오류도 경고로 삼키고, ON CONFLICT DO NOTHING은 UNIQUE·기본 키 충돌만 넘긴다.</details>

6. MySQL에서 "공감 INSERT와 공감 수 UPDATE가 엇갈려 데드락"이 났는데 PostgreSQL에서는 왜 안 나나? 그런데도 글 행 잠금을 남긴 이유는?
<details><summary>답</summary>PostgreSQL의 외래 키 확인은 부모 행에 FOR KEY SHARE를 걸고, 키가 아닌 칸의 UPDATE는 FOR NO KEY UPDATE라 서로 부딪히지 않는다. 글 행 잠금은 같은 글의 요청을 차례로 처리해 뒤 요청이 앞 요청의 결과를 보고 판단하게 하는 역할(줄 세우기)이 있어서 남겼다.</details>

7. 의미 검색에서 가시성 조건을 SQL로 새로 쓰지 않고 Criteria로 한 쿼리를 만든 이유는?
<details><summary>답</summary>가시성 조건이 이미 PostSpecifications(Criteria)로 있어서, SQL로 한 벌 더 쓰면 두 벌을 같이 고쳐야 한다. 임베딩 표를 엔티티로 만들어 같은 Specification을 그대로 건다.</details>

8. `cb.function("cosine_distance", …, cb.literal(query))`가 실패한 이유는?
<details><summary>답</summary>Hibernate가 float[] 값을 배열 타입으로 보고, hibernate-vector가 cosine_distance의 인자가 vector인지 확인해 거절한다. 임베딩 칸의 타입을 물려받는 값(<code>value(query, column)</code>)으로 넘겨야 <code>cast(? as vector)</code>가 된다.</details>

9. Criteria로 글을 읽으며 `post.fetch("category")`를 했더니 결과가 0개였다. 왜?
<details><summary>답</summary>fetch는 기본이 INNER JOIN이라 카테고리가 없는(미분류) 글이 모두 빠진다. 테스트 글이 모두 미분류였다. <code>fetch("category", JoinType.LEFT)</code>로 고쳤다.</details>

10. 이미 적용된 Flyway 파일은 고치지 않는 것이 원칙인데, 이번에 V1을 새로 쓰고 V3·V4를 지워도 된 이유는?
<details><summary>답</summary>DB 자체가 새 PostgreSQL이라 Flyway 이력이 비어 있다. 옛 MySQL의 이력은 옛 DB에 남는다. 새 DB에서는 처음부터 지금 스키마를 V1으로 만들면 된다. V4(이미 있던 블로그 채우기)는 빈 DB에 할 일이 없고, 운영 데이터는 V4가 적용된 MySQL에서 그대로 옮겨 온다.</details>
