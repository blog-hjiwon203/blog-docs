## 자세히

### 1. 이메일 인증

- **원본**: 4.6 ④는 "인증 코드를 확인해야만 회원을 만든다"고 하고, 5.14는 "가입 시 인증 메일 발송, 인증 전에는 글 발행 제한"이라고 한다. 앞의 방식이면 인증하지 않은 회원이 없으므로 "인증 전 발행 제한"이 성립하지 않는다. 또 이메일 인증은 P1인데, P0인 가입(AUTH-01)이 이 인증을 거쳐야만 끝나고, 7장 일정 어디에도 이메일 인증이 없다.
- **처리**: 4.6 ④(코드 확인 후 회원 생성)를 따르고 "인증 전 발행 제한"은 뺐다. OWN-01은 등급은 P1 그대로 두되 1주차 가입과 함께 만든다(작업 목록 T017).
- **확인할 것**: 메일 발송까지 1주차에 넣기 부담스러우면, 1주차에는 개발용으로 코드를 로그에 찍고 실제 메일 발송은 2주차로 미루는 방법도 있다.

### 2. 글쓰기 화면 위치

- **원본**: 4.2 ②는 플랫폼 주소(`blog.com`)가 "홈·로그인·글쓰기 화면"이라고 하고, 6장 표는 글쓰기를 `myblog.blog.com/manage/...` 관리 화면에 둔다.
- **처리**: 6장을 따랐다. 블로그를 여러 개 가질 수 있어서 글쓰기는 어느 블로그에 쓰는지가 주소에 드러나는 편이 맞다. 플랫폼 홈의 글쓰기 버튼은 대표 블로그의 글쓰기로 보낸다(AUTH-04).

### 3. 블로그 주소 사이 로그인 공유 (가장 급함)

- **원본**: 3장은 "Access Token을 Authorization 헤더로 보낸다"고 하면서 "블로그 간 로그인 공유 방식은 인증 학습 후 확정"이라고 미뤘다. 하지만 `blog.com/login`에서 로그인하고 `myblog.blog.com/manage`에서 글을 쓰는 것이 P0 한 바퀴다. 브라우저 저장소(localStorage)는 주소(출처)마다 따로라서, 헤더 방식만으로는 블로그 주소로 넘어가는 순간 로그아웃 상태가 된다.
- **처리**: 1주차 시작 전에 정할 질문 Q6으로 올렸다. 로그아웃(AUTH-02), 로그인 유지(AUTH-03), 정지 회원 차단(ADMIN-02)도 같은 결정에 묶인다.
- **추천**: 로그인하면 `.blog.com` 상위 도메인에 HttpOnly 쿠키를 굽는 방식. 모든 블로그 주소에서 같은 쿠키가 보이므로 공유가 저절로 되고, 쿠키를 쓰게 되므로 원본 4.5 ③대로 SameSite와 CSRF 대책을 함께 둔다. 자세한 비교는 [조사](./research.md) R-03.

### 4. "볼 수 없는 글"의 범위

- **원본**: 4.1 ④는 "남의 비공개 글은 404", 4.4 ⑥은 "비공개 글과 삭제된 글은 목록에서 빠짐", BLOG-04는 "비공개 글과 그 글의 댓글은 주인에게만"이라고 한다. 셋 다 구독자 공개(7.8), 숨긴 글(ADMIN-03), 제한 블로그(ADMIN-05), 정지 회원의 블로그(9장)를 빠뜨렸다.
- **처리**: 기능 명세 권한 절에 "볼 수 없는 글" 정의를 하나 두고 모든 목록·개수·사이드바·검색이 그 정의를 쓰게 했다.

### 5. 401과 404의 순서

- **원본**: 4.1 ④는 "토큰이 없으면 401, 권한이 없으면 403, 남의 비공개 글은 404"라고만 한다. 비회원이 비공개 글 주소를 열면 401(로그인 안내)이 먼저인지 404가 먼저인지 정해져 있지 않다. 401이 나오면 "로그인하면 볼 수 있는 글이 있다"는 사실이 드러난다.
- **처리**: 볼 수 없는 글·블로그를 여는 경우는 로그인 여부와 상관없이 404, 401은 로그인이 필요한 행동·화면에만 쓴다고 적었다.

### 6. 사이드바 카테고리 트리와 하위 카테고리 일정

- **원본**: BLOG-04(P0, 1주차)는 "카테고리 2단계 트리", CAT-02(P0, 1주차)는 "상위 클릭 시 하위 글 포함"을 요구한다. 그런데 2단계를 만드는 CAT-03(P1)과 순서 변경 CAT-04(P1)는 7장 일정 어디에도 없다.
- **처리**: 1주차에는 카테고리가 한 단계로 보이고, CAT-03을 2주차 후반에 넣었다(작업 목록). CAT-04는 2주 뒤로 둔다.
- **확인할 것**: 2주차 후반이 빠듯하면 CAT-03도 2주 뒤로 미루고, 그동안 사이드바는 한 단계로 둔다.

### 7. 구독자 공개와 구독 일정

- **원본**: 7.8은 구독자 공개를 골랐고 POST-06(P0)은 세 가지 공개 범위를 말하지만, 7장은 구독(SUB-01~06)과 구독자 공개(POST-12)를 범위 밖에 둔다.
- **처리**: POST-06에 "구독이 생기기 전에는 공개·비공개만"이라고 적었다. 원본 7장의 의도와 같다.

### 8. 주제별 글의 '인기' 기준

- **원본**: HOME-03은 "그 주제의 최근 인기 글 6개"인데, '최근'과 '인기'가 무엇인지 없다. 인기 글(7.6)은 "최근 1시간 조회수"인데, 주제마다 1시간 안 조회는 적어서 탭이 자주 빌 수 있다.
- **처리**: 질문 Q7로 올렸다. 정하기 전 기본값은 인기 글과 같은 최근 1시간 조회수이고, 6개가 안 되면 그 주제의 최신 글로 채운다.

### 9. 글 조회 판단 그림

- **원본**: 6장 ②가 "&#91;embedded content: 글 조회 판단 · 질문 4개, 결과 6개&#93;"로만 남아 있다. 문서를 내보낼 때 그림이 빠진 것으로 보인다.
- **처리**: 원본 4.2, 4.3, 7.8, ADMIN-03, ADMIN-05, 9장을 모아 [데이터 모델](./data-model.md)의 "글 가시성 판단"으로 다시 만들었다. 질문 4개(글이 있나 → 이 블로그 소속인가 → 보는 사람이 주인인가 → 공개 범위·숨김·제한상 볼 수 있나), 결과 6개(404, 301, 주인에게 보임, 보임, 404로 숨김, 숨김 사유와 함께 작성자에게 보임)다.
- **확인할 것**: 원래 그림과 같은지 지원이 확인해야 한다.

### 10. 원본에 내용이 없는 참조

원본 1장은 "통합 명세의 규칙을 반복하지 않고 ID로만 가리킨다"고 해서, 몇 군데는 원본만으로 동작이 정해지지 않는다. 이 저장소는 원본만 기준으로 하므로 꼭 필요한 값만 채우고 기능 명세에 (채움) 표시를 했다.

| 원본 위치 | 원본 문장 | 채운 값 |
| --- | --- | --- |
| POST-03 | "함께 처리되는 것은 통합 4.7" | 그 글의 댓글·공감·알림도 함께 사라진다 |
| 5.12 머리말 | "운영 원칙은 통합 6.12 공통 원칙" | 관리자는 고치거나 지우지 않고 숨기거나 제한만 한다, 모든 제재에 사유를 남긴다 (헌법 원칙 V) |

### 12. 저장소 쓰임

- **원본**: 3장 DB에 "운영: MySQL, Redis, PostgreSQL"만 있고 각각의 쓰임이 없다.
- **처리**: 2026-10-07 지원 결정을 반영했다. MySQL은 주 저장소, Redis는 홈 캐시와 연타 방지 키 저장, PostgreSQL+pgvector는 비슷한 글 추천(OWN-06)에만 쓴다. [조사](./research.md) R-02.

### 13. 연타 방지

- **원본**: 10장 ④ "발행·댓글·공감·구독의 연타 방지 방식을 정한다."
- **처리**: 2026-10-07 지원 결정을 반영했다. 공감·구독은 DB의 회원-대상 쌍 중복 금지로, 발행·댓글은 요청마다 붙이는 키(Idempotency-Key)를 Redis에 잠시 저장해 두 번째 요청을 첫 결과로 돌려준다. [조사](./research.md) R-09.

### 14. 비슷한 글 추천 일정

- **원본**: 7장은 비슷한 글 추천을 범위 밖에 둔다.
- **처리**: 지원이 "2주 안에 해 볼 수 있으면 한다"고 해서 2주차 후반 도전 과제로 넣었다. 밀리면 그대로 2주 뒤로 간다.

### 15. 자체 기능 코드

- **원본**: 5.14 자체 기능 표에 기능 코드가 없다.
- **처리**: 작업과 커밋에서 가리킬 수 있게 `OWN-01` 이메일 인증, `OWN-02` 비밀번호 재설정, `OWN-03` 소셜 계정 연동·해제, `OWN-04` 비회원 댓글(보류), `OWN-05` 같은 카테고리의 다른 글, `OWN-06` 비슷한 글 추천을 붙였다.
- **확인할 것**: 다른 코드를 원하면 바꾼다.

### 16. 예전 ID와 ERD·API 갱신

- **원본**: 5.15 예전 ID 대응표, 10장 ⑤ "ERD와 API 명세 탭을 통합 ID 기준으로 갱신한다."
- **처리**: 이 저장소의 [데이터 모델](./data-model.md)과 [REST API 초안](./contracts/rest-api.md)은 처음부터 지금 기능 코드로 썼다. 대응표는 원본에만 남긴다.

## 고치지 않은 것

- 원본의 기능 코드, 기능 이름, 등급, 2주 일정의 큰 틀은 그대로 썼다.
- 원본 파일(`docs/`)은 기록으로 그대로 둔다.
