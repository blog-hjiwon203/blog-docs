# 블로그 주소: 서브도메인과 Host 헤더에서 경로 `blog.com/@주소`로

> **스텝 21에서 바뀜 (2026-10-12 지원 결정)**: 배포 서버(학교 nginx, `now-log.java21.net`)에 와일드카드 DNS가 없어 블로그 주소를 서브도메인(`alpha.blog.com`)에서 경로(`blog.com/@alpha`)로 바꿨다. API는 Host 대신 `X-Blog-Address` 헤더로 블로그를 정하고, `BlogHostResolver`·`RequestHost`는 `BlogAddressResolver`·`RequestBlog`가 되었으며, `DomainProperties.cookieDomain()`·`blogHost()`는 없어졌다. 이 문서의 3.1~3.10, 4장 앞부분과 4.1, 5.1~5.7, 7장 실습 1~6은 스텝 3~20의 구조로 남겨 둔다. DNS·Host 헤더·가상 호스트·멀티테넌시·인자 해석기 설명은 그대로 유효하고, 지금 코드는 3.11부터, 4.2, 5.8부터, 실습 7부터를 본다. 개발에도 dnsmasq나 블로그마다의 hosts 줄은 더 필요 없다(`127.0.0.1 blog.test` 한 줄).

| --- | --- | --- |

처음에는 서브도메인과 Host 헤더로 블로그를 찾았고(1~10절 대부분), 스텝 21에서 배포 환경 때문에 경로 주소로 바꿨다(각 장의 뒤쪽). 바꾼 이유를 이해하려면 서브도메인 방식이 DNS·Host에 무엇을 요구했는지 먼저 알아야 하므로 이 순서로 읽는다.

## 1. 이 문서로 배우는 것

**처음 구조: 서브도메인과 Host 헤더 (스텝 3~20)**

- 도메인 이름이 어떤 부분으로 이루어지는지(최상위 도메인, 서브도메인)
- 브라우저가 `alpha.blog.com`을 열 때 DNS가 이름을 IP 주소로 바꾸는 과정
- 블로그가 수천 개여도 DNS 설정은 한 줄이면 되는 이유(와일드카드 DNS)
- 로컬 개발에서 `/etc/hosts`를 고치는 이유와 `*.localhost`를 쓰지 않는 이유
- `/etc/hosts`의 한계(블로그마다 한 줄)와, dnsmasq + `/etc/resolver`로 `*.blog.test` 전체를 한 번에 내 컴퓨터로 보내는 법
- 실제 배포에서 DNS 와일드카드 레코드와 와일드카드 HTTPS 인증서를 설정하는 법
- 한 서버가 여러 주소의 요청을 받고 구분하는 방법(HTTP `Host` 헤더, 가상 호스트)
- 멀티테넌시: 하나의 서비스 안에 블로그(테넌트)가 여럿 사는 구조
- 서브도메인 방식과 경로 방식(`blog.com/@alpha`)의 장단점
- 이 프로젝트의 `BlogHostResolver`, `BlogAddressRule`, `DomainProperties`, `@CurrentBlog`가 각각 하는 일

**바꾼 구조: 경로 주소 `blog.com/@주소` (스텝 21부터)**

- 서브도메인 주소(`alpha.blog.com`)와 경로 주소(`blog.com/@alpha`)가 DNS·인증서·웹 서버(nginx `server_name`)에서 각각 무엇을 요구하는지, 그리고 배포 환경 때문에 바꿀 수밖에 없었던 이유
- API가 "어느 블로그에 대한 요청인지"를 아는 세 방법: **Host 헤더**, **사용자 지정 헤더**, **경로 한 칸**. 이 프로젝트가 고른 ①안(`X-Blog-Address` 헤더)과 고르지 않은 ②안(`/api/blogs/{주소}/…`)의 저울질
- 사용자 지정 요청 헤더가 CORS·CSRF와 어떻게 얽히는지(같은 출처라서 문제가 없는 이유)
- 쿠키 `Domain` 속성: **host-only 쿠키**와 **도메인 쿠키**, 예전에는 `Domain`이 꼭 필요했고 지금은 필요 없는 이유
- `/@주소/…` 화면 주소를 서버가 먼저 확인하기(404, 이사 301, 공유 미리보기)
- React Router `basename`으로 블로그 화면 안의 링크를 그대로 두기
- 같은 출처 기준으로 열린 리다이렉트 막기
- Spring 경로 패턴(`{이름:정규식}`)에 `/`를 넣으면 서버가 뜨지 않는 함정

**먼저 알면 좋은 것**: HTTP 요청이 메서드·경로·헤더·본문으로 이루어진다는 것, Spring MVC 컨트롤러의 기본(`@GetMapping`), Java의 `record`. 몰라도 이 문서에서 필요한 만큼은 설명한다. 뒤쪽(경로 주소)은 [쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md)의 Domain 속성, [SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md)의 `SpaForwardController`, [React 화면 나누기와 API 클라이언트](./08-React-화면-나누기와-API-클라이언트.md)의 `BrowserRouter`·`api()`도 알면 좋다. 뒤쪽은 앞쪽(DNS·Host 헤더·`@CurrentBlog`) 위에서 "무엇이 바뀌었고 왜"를 다룬다.

## 2. 왜 필요한가

**어느 블로그를 향한 요청인지 알아야 한다.** 티스토리처럼 회원마다 자기 블로그 주소를 갖는 서비스를 생각해 보자. A의 블로그는 `alpha.blog.com`, B의 블로그는 `beta.blog.com`이다.

서버를 블로그마다 하나씩 띄울 수는 없다. 블로그가 만 개면 서버도 만 대가 된다. 그래서 **서버 한 대(또는 같은 서버 여러 대)가 모든 블로그 주소의 요청을 받고, 요청이 어느 블로그를 향하는지 알아내야** 한다.

이걸 알아내지 못하면 이런 일이 생긴다.

- `alpha.blog.com/15`와 `beta.blog.com/15`를 구분하지 못한다. 경로는 둘 다 `/15`다.
- 블로그 A의 관리 화면에 B가 들어와도, 서버는 "어느 블로그의 관리 화면인지" 모르니 주인 검사를 할 수 없다.
- 삭제된 블로그나 없는 주소로 와도 막을 기준이 없다.

처음(스텝 3)에 이 프로젝트는 요청의 **Host 헤더**에서 서브도메인(`alpha`)을 읽어 블로그를 찾았다(research.md R-04). 3~5장 앞쪽이 그 바탕이 되는 개념과 코드다.

**배포할 곳에서는 서브도메인을 쓸 수 없었다.** 스텝 3부터 블로그 주소는 티스토리처럼 서브도메인이었다(`alpha.blog.com`). 개발 컴퓨터에서는 `/etc/hosts`나 dnsmasq로 `*.blog.test`를 모두 내 컴퓨터로 보내서 잘 돌았다.

배포할 곳은 학교 서버다. 학교 nginx가 `now-log.java21.net` **한 이름**을 받아 우리 앱(포트 8460)으로 넘겨 준다. 여기서 문제가 드러났다.

```
now-log.java21.net          → DNS에 있음 → 학교 nginx → 우리 앱      ✔
alpha.now-log.java21.net    → DNS에 없음 → 브라우저가 "그런 이름 없음"  ✘ (서버까지 오지도 않음)
```

서브도메인 블로그를 열려면 DNS에 와일드카드 레코드(`*.now-log.java21.net`)가 있어야 하고, 학교 nginx도 그 이름들을 우리 앱으로 넘기게 설정돼 있어야 하며, HTTPS라면 와일드카드 인증서까지 필요하다. 셋 다 우리가 손댈 수 없는 학교 쪽 설정이다. 아래 3.6에서 볼 것처럼 DNS에서 실패한 요청은 서버 코드로 고칠 수 없다.

그래서 스텝 21에서 블로그 주소를 **플랫폼 주소 아래의 경로**로 바꿨다(research.md R-04, 2026-10-12 지원 결정).

```
전: http://alpha.blog.com/12          http://alpha.blog.com/manage/write
후: http://blog.com/@alpha/12         http://blog.com/@alpha/manage/write
```

이름이 하나뿐이니 DNS·nginx·인증서는 지금 그대로 충분하다. 대신 코드에서 "어느 블로그인가"를 Host로 알던 곳을 모두 바꿔야 했다. 각 장의 뒤쪽이 그 바꾼 자리들과, 각 자리에서 고른 방법의 이유다.

## 3. 기본 개념

3.1~3.10은 처음 구조(서브도메인과 Host 헤더), 3.11~3.18은 스텝 21에서 바꾼 경로 주소다.

### 3.1 도메인 이름의 구조

도메인 이름은 점(`.`)으로 나뉜 **라벨**들이고, **오른쪽으로 갈수록 상위**다.

```
        alpha  .  blog  .  com
        ─────    ─────    ───
        서브도메인  2단계    최상위 도메인(TLD)
                 도메인
        └────────── 전체를 FQDN이라고도 부른다 ──────────┘
```

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| TLD(Top-Level Domain, 최상위 도메인) | 가장 오른쪽 라벨 | `com`, `net`, `kr`, `test` |
| 2단계 도메인 | TLD 바로 왼쪽. 보통 돈을 내고 등록하는 이름 | `blog.com`의 `blog` |
| 서브도메인 | 등록한 도메인 왼쪽에 붙이는 이름. 등록한 사람이 마음대로 만든다 | `alpha.blog.com`, `www.blog.com` |
| 호스트 이름(hostname) | 특정 컴퓨터(또는 서비스)를 가리키는 전체 이름 | `alpha.blog.com` |

`blog.com`을 가진 사람은 `alpha.blog.com`, `beta.blog.com`, `www.blog.com`을 추가 비용 없이 원하는 만큼 만들 수 있다. 서브도메인은 "등록"하는 것이 아니라 내 DNS 설정에 **이름을 적는** 것이기 때문이다.

> `test` TLD는 테스트용으로 예약된 이름이라 인터넷의 실제 DNS에는 존재하지 않는다(RFC 2606). 그래서 로컬 개발용 `blog.test`가 실제 사이트와 겹칠 걱정이 없다.

### 3.2 DNS: 이름을 IP 주소로 바꾸는 전화번호부

컴퓨터끼리는 IP 주소(`203.0.113.10` 같은 숫자)로 통신한다. 사람이 쓰는 이름을 IP로 바꿔 주는 것이 **DNS(Domain Name System)**다.

브라우저 주소창에 `http://alpha.blog.com/15`를 치면:

```
1. 브라우저 캐시, 운영체제 캐시에 alpha.blog.com의 IP가 있나?   → 있으면 바로 사용
2. 운영체제가 hosts 파일(/etc/hosts)을 본다                     → 적혀 있으면 그 IP 사용
3. 없으면 DNS 리졸버(보통 통신사나 8.8.8.8)에 묻는다
4. 리졸버가 루트 서버 → .com 서버 → blog.com의 네임서버 순으로 물어 답을 얻는다
5. "alpha.blog.com = 203.0.113.10" 을 받아 캐시에 저장(TTL 동안)
6. 브라우저가 203.0.113.10의 80번 포트로 TCP 연결을 열고 HTTP 요청을 보낸다
```

중요한 점: **DNS는 IP만 알려 준다.** 어느 블로그인지는 DNS가 아니라 이후 HTTP 요청 안의 정보(Host 헤더)로 구분한다.

DNS에 적는 기록(레코드)의 대표적인 종류:

| 레코드 | 뜻 | 예 |
| --- | --- | --- |
| A | 이름 → IPv4 주소 | `blog.com. A 203.0.113.10` |
| AAAA | 이름 → IPv6 주소 | |
| CNAME | 이름 → 다른 이름(별칭) | `www.blog.com. CNAME blog.com.` |

### 3.3 와일드카드 DNS

블로그가 생길 때마다 DNS에 `alpha.blog.com A ...`, `beta.blog.com A ...`를 추가할 수는 없다. 그래서 **와일드카드 레코드**를 한 줄 둔다.

```
*.blog.com.   A   203.0.113.10
```

이러면 `alpha.blog.com`, `beta.blog.com`, `아무거나.blog.com`이 모두 같은 IP로 간다. 블로그가 존재하는지는 DNS가 아니라 **서버가 DB를 보고** 판단한다. 그래서 `nobody-here.blog.com`도 DNS 단계에서는 우리 서버로 오고, 서버가 404를 준다.

> 와일드카드 `*`는 라벨 하나에만 대응한다. `*.blog.com`은 `a.b.blog.com`(라벨 두 개)을 덮지 않는다. 이 프로젝트도 서브도메인이 두 단계인 주소는 블로그로 보지 않는다(아래 5.1).

HTTPS를 쓰려면 인증서도 와일드카드 인증서(`*.blog.com`)가 필요하다. 이것도 한 단계만 덮는다.

**실제로 설정하는 곳.** 도메인(`blog.com`)을 산 곳(가비아, Cloudflare, AWS Route 53 등)의 DNS 관리 화면에서 레코드를 더한다. 화면 모양은 달라도 넣는 값은 같다.

| 타입 | 이름(호스트) | 값 | TTL | 뜻 |
| --- | --- | --- | --- | --- |
| A | `@` (도메인 자신) | 서버 IP | 300 등 | 플랫폼 주소 `blog.com` |
| A | `*` | 서버 IP | 300 등 | 모든 블로그 주소 `{주소}.blog.com` |
| A 또는 CNAME | `www` | 서버 IP 또는 `blog.com` | | `www.blog.com`도 플랫폼 (`*`가 덮지만 따로 두면 의도가 분명하다) |

- **TTL**은 다른 DNS 서버가 이 답을 몇 초 동안 기억해도 되는지다. 처음 설정할 때는 짧게(300초) 두면 잘못 넣었을 때 빨리 바로잡힌다.
- 레코드는 바로 퍼지지 않는다. 몇 분에서 길게는 TTL만큼 걸린다.
- **와일드카드 인증서**: 무료 인증서인 Let's Encrypt는 `*.blog.com` 인증서를 **DNS-01 방식**으로만 준다. "이 도메인의 주인이 맞다"를 DNS에 `_acme-challenge.blog.com` TXT 레코드를 넣어 증명하는 방식이다. DNS 회사가 API를 주면 certbot 같은 도구가 자동으로 넣고 갱신한다.
- 앱 쪽은 설정값 하나만 바꾼다. `app.domain.platform`(운영은 환경 변수 `APP_PLATFORM_DOMAIN`)을 실제 도메인으로 두면, 블로그 주소 해석과 로그인 쿠키 도메인(`Domain=.blog.com`)이 모두 그 값을 따른다(5.3).

### 3.4 /etc/hosts: 내 컴퓨터만의 DNS

`/etc/hosts`(Windows는 `C:\Windows\System32\drivers\etc\hosts`)는 운영체제가 DNS보다 먼저 보는 파일이다. 한 줄에 "IP 이름 이름 ..."을 적는다.

```
127.0.0.1   blog.test alpha.blog.test beta.blog.test gamma.blog.test
```

이렇게 적으면 내 컴퓨터에서만 `alpha.blog.test`가 `127.0.0.1`(내 컴퓨터 자신)을 가리킨다. 그래서 로컬에서 돌리는 Spring Boot(8080)에 `http://alpha.blog.test:8080`으로 접속할 수 있다.

- **와일드카드를 쓸 수 없다.** hosts 파일은 `*.blog.test`를 지원하지 않아서, 테스트할 블로그 주소를 하나씩 적어야 한다. quickstart.md가 `alpha`, `beta`, `gamma`를 적게 하는 이유다.
- 관리자 권한이 필요하다(`sudo vi /etc/hosts`).

- **새 블로그를 만들 때마다 한 줄씩 더해야 한다.** 화면에서 블로그를 개설하면 바로 그 주소(`myfirst.blog.test`)로 이동하는데, hosts에 없으면 브라우저가 `DNS_PROBE_FINISHED_NXDOMAIN`(그런 이름 없음) 오류를 낸다. 서버까지 요청이 가지도 않은 것이라 서버 로그에는 아무것도 없다.

**왜 `*.localhost`를 쓰지 않나**: 요즘 브라우저는 `alpha.localhost`처럼 `.localhost`로 끝나는 이름을 hosts 없이도 127.0.0.1로 보내 준다. 편해 보이지만, 이 프로젝트는 **모든 블로그 주소가 로그인 쿠키를 같이 써야** 한다(`Domain=.blog.test`, [쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md)). `localhost`에 대한 쿠키 도메인 처리는 브라우저마다 달라서, `Domain=.localhost` 쿠키가 하위 주소에 공유되지 않는 경우가 있다(research.md R-03 "로컬 개발"). 그래서 실제 운영과 같은 구조(`blog.test` + 하위 주소)를 hosts로 흉내 낸다.

### 3.5 dnsmasq와 /etc/resolver: 내 컴퓨터의 와일드카드 DNS

hosts는 와일드카드가 안 되니, 내 컴퓨터 안에 **작은 DNS 서버**를 띄워 와일드카드 규칙을 주는 방법이 있다. 그 DNS 서버 프로그램이 **dnsmasq**다.

```
address=/blog.test/127.0.0.1
```

dnsmasq 설정에 이 한 줄을 두면 `blog.test`와 그 아래 모든 이름(`alpha.blog.test`, `아무거나.blog.test`)을 127.0.0.1로 답한다. 3.3의 `*.blog.com A ...` 레코드와 같은 일을 내 컴퓨터 안에서 하는 셈이다.

그런데 운영체제는 평소에 통신사·공유기 DNS에 묻지, 내 컴퓨터의 dnsmasq에 묻지 않는다. macOS는 **`/etc/resolver/{도메인}` 파일**로 "이 도메인과 그 아래 이름은 이 DNS 서버에 물어라"를 정할 수 있다. 파일 이름이 곧 도메인이다.

```
/etc/resolver/blog.test 의 내용:
nameserver 127.0.0.1
```

**판단은 두 단계로 나뉜다.**

| 단계 | 누가 | 무엇을 보고 | 범위 |
| --- | --- | --- | --- |
| ① 누구에게 물을지 | macOS | `/etc/resolver/` 파일 이름 | `blog.test`면 `*.blog.test`만 dnsmasq로, 나머지(`naver.com` 등)는 원래 DNS |
| ② 뭐라고 답할지 | dnsmasq | `address=/blog.test/127.0.0.1` 규칙 | 규칙에 맞는 이름은 127.0.0.1, 안 맞으면 원래 DNS에 대신 물음 |

와일드카드 역할은 ② dnsmasq 규칙이 하고, ①은 "이 질문을 dnsmasq에 넘길지"만 정한다.

```
"xyz.blog.test의 IP는?"
  → /etc/hosts에 없음
  → ① 끝이 blog.test → /etc/resolver/blog.test → 127.0.0.1의 dnsmasq에 물음
  → ② dnsmasq: address=/blog.test/127.0.0.1 규칙에 맞음 → 127.0.0.1
  → 브라우저가 127.0.0.1:8080에 연결, Host: xyz.blog.test로 요청 → BlogHostResolver(5.1)
```

파일 이름을 `test`로 하면(`/etc/resolver/test`) ①이 `.test`로 끝나는 이름을 **전부** dnsmasq로 보낸다. 다른 프로젝트에서 `myapp.test`를 쓸 때 dnsmasq 규칙만 한 줄 더하면 되는 대신, 이 프로젝트에 필요한 것보다 범위가 넓다. 규칙이 없는 `foo.test`는 ②에서 원래 DNS로 넘어가 결국 "없음"이 되므로 어느 쪽이든 동작은 같다. 이 문서는 범위가 좁은 `blog.test`를 쓴다.

**dnsmasq는 내 컴퓨터에서 온 질문만 받게 한다.** dnsmasq는 기본으로 모든 네트워크 연결(와이파이 등)에서 질문을 받는다. 같은 와이파이의 다른 기기가 내 dnsmasq에 DNS를 물을 수 있다는 뜻이다. 필요 없으니 닫는다.

```
listen-address=127.0.0.1    # 내 컴퓨터 자신으로 온 질문만
bind-interfaces             # 그 주소에만 붙어서 다른 연결에서는 듣지 않음
```

**dnsmasq와 블로그 서버는 별개 프로그램이다.** dnsmasq는 `brew services`로 켜 두면 컴퓨터를 켤 때 자동으로 켜지고, Spring 서버를 켜든 끄든 계속 돈다. 그래서 브라우저 오류로 어디가 꺼졌는지 알 수 있다.

| 상태 | 브라우저 오류 | 어디서 실패했나 |
| --- | --- | --- |
| dnsmasq 꺼짐, hosts에도 없음 | `DNS_PROBE_FINISHED_NXDOMAIN` | 이름 찾기(DNS) |
| dnsmasq 켜짐, Spring 서버 꺼짐 | `ERR_CONNECTION_REFUSED` | 127.0.0.1:8080에 받는 프로그램이 없음 |
| 서버 켜짐, Docker(MySQL) 꺼짐 | 서버가 뜨지 않음 | 서버가 DB에 연결 못 함 |

개발이 끝난 뒤 dnsmasq를 꼭 되돌릴 필요는 없다. `*.blog.test`에만 영향이 있고 가볍다. 다른 프로그램(일부 VPN, 다른 DNS 도구)이 53번 포트를 써야 해서 부딪히거나, 다시 쓸 일이 없을 때 7장의 되돌리기를 한다. (스텝 21에서 경로 주소로 바꾼 뒤로는 개발에 dnsmasq가 필요 없다.)

`.test`는 실제 인터넷에서 쓰지 않기로 예약된 끝 이름이라(RFC 2606) 진짜 사이트와 겹칠 걱정이 없다.

| | /etc/hosts | dnsmasq + /etc/resolver |
| --- | --- | --- |
| 와일드카드 | 안 됨, 이름마다 한 줄 | `address=/blog.test/127.0.0.1` 한 줄 |
| 설치 | 필요 없음 | `brew install dnsmasq` |
| 새 블로그 | 매번 추가 | 할 일 없음 |
| 운영과 닮은 정도 | 낮음 | 운영의 와일드카드 레코드와 같은 구조 |

명령 모음은 7장 실습 6에 있다.

### 3.6 DNS 오류와 서버의 주소 해석은 다른 단계

"블로그 주소 라우팅 기능이 있으면 이 오류도 해결되지 않나?" 아니다. 요청은 두 단계를 지난다.

```
① 이름 찾기(DNS)         내 컴퓨터가 함: alpha.blog.test → 127.0.0.1    ← NXDOMAIN은 여기서 실패
② 블로그 고르기(Host)     서버가 함: Host: alpha.blog.test → alpha 블로그  ← BlogHostResolver
```

①이 실패하면 요청이 서버에 닿지 않으니 서버 코드로는 고칠 수 없다. 개발에서는 hosts나 dnsmasq가, 운영에서는 DNS 와일드카드 레코드가 ①을 맡는다. 스텝 21에서 배포 서버에 이 ①을 맡을 와일드카드 레코드가 없다는 것이 경로 주소로 바꾼 이유가 되었다(2장).

### 3.7 HTTP Host 헤더

HTTP/1.1 요청에는 **Host 헤더가 반드시** 들어간다. 브라우저가 주소창의 호스트 이름(과 포트)을 그대로 넣는다.

```http
GET /15 HTTP/1.1
Host: alpha.blog.test:8080
Cookie: access_token=...
Accept: text/html
```

- 포트가 기본값(http 80, https 443)이면 생략되고, 아니면 `:8080`처럼 붙는다.
- 같은 IP로 온 요청이라도 Host가 다르면 "다른 사이트를 향한 요청"이다.
- HTTP/2에서는 `:authority`라는 의사 헤더가 같은 역할을 하고, 서블릿 API에서는 똑같이 `getServerName()`으로 읽힌다.

서블릿(`HttpServletRequest`)에서 읽는 법:

| 메서드 | `Host: alpha.blog.test:8080`일 때 |
| --- | --- |
| `getServerName()` | `alpha.blog.test` (포트를 뺀 이름) |
| `getServerPort()` | `8080` |
| `getHeader("Host")` | `alpha.blog.test:8080` (원문) |

> 운영에서 앞에 로드밸런서나 리버스 프록시(Nginx)를 두면, 프록시가 Host를 바꿔 넘기거나 `X-Forwarded-Host`에 원래 값을 담는다. 그때는 Spring Boot의 `server.forward-headers-strategy` 설정이 필요할 수 있다. 스텝 20까지 프로젝트는 프록시 없이 직접 받는 구조였다. (학교 nginx 뒤에 배포하면서 `server.forward-headers-strategy: native`를 두었다, 5.8.)

### 3.8 가상 호스트: 한 서버, 여러 사이트

**가상 호스트(virtual host)**는 서버 하나가 Host 헤더를 보고 여러 사이트를 나눠 서빙하는 방식이다. Nginx의 `server_name`, Apache의 `<VirtualHost>`가 대표적이다.

```
            ┌─────────────────────────────┐
요청 ──────▶│ 서버 (IP 203.0.113.10:80)    │
Host: a.com │  Host == a.com → 사이트 A    │
Host: b.com │  Host == b.com → 사이트 B    │
            └─────────────────────────────┘
```

이 프로젝트는 처음에 같은 생각을 **애플리케이션 안에서** 했다. Spring Boot 앱 하나가 모든 Host를 받고, 코드(`BlogHostResolver`)가 Host를 보고 플랫폼 화면인지, 어느 블로그인지 정했다.

### 3.9 멀티테넌시

**테넌트(tenant)**는 "세입자"라는 뜻이다. 하나의 서비스(건물)에 여러 고객(세입자)이 각자의 공간을 갖는 구조를 **멀티테넌시**라고 한다. 이 프로젝트에서 테넌트는 **블로그**다.

| 멀티테넌시 방식 | 데이터 분리 | 이 프로젝트 |
| --- | --- | --- |
| 테넌트마다 DB 따로 | 가장 강함, 비용 큼 | 아님 |
| 테넌트마다 스키마 따로 | 중간 | 아님 |
| **테이블 공유 + 테넌트 id 컬럼** | 코드가 조건을 빠뜨리지 않아야 함 | **이 방식**: `post.blog_id`, `category.blog_id` |

테이블을 공유하는 방식에서는 "모든 조회에 `blog_id` 조건이 붙었나"가 생명이다. 그래서 요청이 들어오는 입구에서 **현재 블로그를 한 번 정해 두고**(`@CurrentBlog`), 모든 기능이 그 블로그를 기준으로 일하게 만든다. 이 구조는 경로 주소로 바꾼 뒤에도 그대로다(5.9).

### 3.10 서브도메인 방식 vs 경로 방식

블로그를 구분하는 방법은 크게 두 가지다.

| | 서브도메인 방식 `alpha.blog.com/15` | 경로 방식 `blog.com/@alpha/15` |
| --- | --- | --- |
| 쓰는 곳 | 티스토리, 기존 블로그 서비스 | 미디엄, 벨로그 |
| 주소 느낌 | 블로그가 독립된 사이트처럼 보임 | 플랫폼 안의 페이지처럼 보임 |
| DNS | `*.blog.com` 와일드카드 레코드 | `blog.com` 레코드 하나 |
| 웹 서버(nginx) | `server_name`에 `*.blog.com`(또는 `.blog.com`)도 받게 | `server_name blog.com` 하나 |
| HTTPS 인증서 | `*.blog.com` 와일드카드 인증서(Let's Encrypt는 DNS-01로만) | `blog.com` 인증서 하나 |
| 출처(origin) | 블로그마다 다른 출처 | 모든 블로그가 **한 출처** |
| 로그인 쿠키 공유 | 상위 도메인 쿠키(`Domain=.blog.com`)가 필요 | 같은 출처라 저절로 됨(host-only 쿠키로) |
| 보안 | 다른 블로그와 출처가 달라 어느 정도 분리됨. 그러나 같은 사이트(same-site)라 CSRF는 더 신경 써야 함([CSRF SameSite CORS](../3-보안/05-CSRF-SameSite-CORS.md)) | 모든 블로그가 같은 출처라 한 블로그의 XSS가 전체에 영향 |
| 로컬 개발 | hosts에 블로그마다 한 줄, 또는 dnsmasq | hosts에 `blog.test` 한 줄 |
| 서버가 블로그를 아는 곳·구현 | Host 헤더. Host 해석 장치 필요(5.1) | 화면은 경로, API는 따로 정해야 함(3.13) |

plan.md "복잡도 기록"에 적힌 대로, 이 프로젝트는 처음에 티스토리와 같은 경험을 위해 서브도메인을 골랐고, 그 대가로 상위 도메인 쿠키와 CSRF 대책을 떠안았다. 그리고 스텝 21에서 배포 환경 때문에 경로 방식으로 바꿨다(아래 3.11부터).

### 3.11 서브도메인 주소와 경로 주소가 각각 요구하는 것

(3.11부터는 스텝 21에서 바꾼 경로 주소 이야기다.)

두 방식이 DNS·웹 서버·인증서·로컬 개발·출처·쿠키에서 무엇을 요구하는지는 위 3.10 표에 모았다. 여기서는 웹 서버 쪽을 더 본다.

**가상 호스트와 `server_name`.** nginx는 한 IP·포트로 온 요청을 Host 헤더로 나눠 다른 사이트로 보낸다(3.8). 그 기준이 `server` 블록의 `server_name`이다.

```nginx
server {
    listen 80;
    server_name now-log.java21.net;          # 이 이름으로 온 요청만
    location / { proxy_pass http://127.0.0.1:8460; }
}
```

서브도메인 블로그를 받으려면 `server_name now-log.java21.net *.now-log.java21.net;`처럼 와일드카드 이름도 적어야 한다(nginx 설명서의 "Server names": `*.example.org`, 또는 `example.org`와 그 아래를 함께 뜻하는 `.example.org`). 학교 nginx는 학생마다 이름 하나를 정해 넘겨 주는 구조라 이것을 기대할 수 없었다. 그리고 nginx가 받아 주더라도 DNS에 와일드카드 레코드가 없으면 요청이 nginx까지 오지도 않는다.

**경로 방식에서 `@`를 붙이는 이유.** 플랫폼 화면에는 이미 `/login`, `/me`, `/admin`, `/search` 같은 경로가 있다. 블로그 주소를 그냥 첫 칸에 두면(`blog.com/alpha`) `login`이라는 블로그와 로그인 화면을 구분할 수 없고, 나중에 플랫폼 화면을 더할 때마다 이미 있는 블로그 주소와 부딪힐 수 있다. 블로그 주소는 영문 소문자·숫자·하이픈만 쓰므로 `@`로 시작하는 첫 칸은 **블로그만** 쓸 수 있다. 미디엄·벨로그처럼 `@`를 쓰는 서비스가 흔한 것도 같은 이유다.

### 3.12 화면 주소와 API 주소는 따로 생각한다

SPA에서 요청은 두 종류다([SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md)).

| 요청 | 누가 보내나 | 예 |
| --- | --- | --- |
| 화면 주소 | 브라우저 주소창(새로고침, 링크, 북마크) | `GET /@alpha/12` (HTML) |
| API | 화면의 자바스크립트(`fetch`) | `GET /api/posts/12` (JSON) |

화면 주소는 사람이 보고 공유하는 주소라서 `/@alpha/12`로 바꾸는 것이 이번 일의 목적이다. API 주소는 사람이 보지 않는다. 예전에는 화면과 API가 같은 호스트(`alpha.blog.com`)였으니 API도 Host로 블로그를 알았다. 이제 API의 호스트는 언제나 `blog.com`이라 Host에는 블로그 정보가 없다. **API에게 블로그를 알려 줄 다른 길**이 필요하다.

### 3.13 "어느 블로그"를 API에 알리는 세 방법

| 방법 | 예 | 장점 | 단점 |
| --- | --- | --- | --- |
| Host 헤더 | `Host: alpha.blog.com` + `GET /api/posts/12` | 주소에 드러나지 않음, 화면과 같은 기준 | 서브도메인이 있어야 함. 이번에 쓸 수 없게 됨 |
| **사용자 지정 헤더 (①안)** | `X-Blog-Address: alpha` + `GET /api/posts/12` | API 경로가 그대로, 바꿀 곳이 "헤더를 읽는 곳" 하나 | 주소만 보고는 어느 블로그인지 모름(로그, 캐시에서 헷갈릴 수 있음) |
| 경로 한 칸 (②안) | `GET /api/blogs/alpha/posts/12` | 주소만 보고 블로그를 앎, REST 교과서에 가까움 | 블로그 API 59개의 경로·계약·테스트·프론트 호출을 모두 바꿈 |

①안을 고른 이유는 **바꾸는 범위**다. 이 프로젝트의 블로그 API는 모두 `@CurrentBlog Blog blog` 인자 하나로 블로그를 받는다(5.4). 그 인자를 만드는 곳이 Host 대신 헤더를 읽게 바꾸면, 59개 API의 컨트롤러·계약(rest-api.md)·테스트 경로가 그대로다. ②안은 더 "정석"처럼 보이지만, 같은 기능을 하는 코드를 바꾸는 양이 훨씬 많고 계약 문서 전체를 고쳐야 한다. 이것이 지원이 정한 저울질이다(research.md R-04 "고르지 않은 대안").

①안에서 지킨 규칙:

- 헤더가 **없으면 플랫폼** 요청이다(`GET /api/home/posts` 같은 플랫폼 API는 아무것도 붙이지 않는다).
- 헤더의 주소가 규칙에 맞지 않거나 예약어면, 없는 블로그와 같이 **404**다.
- 같은 경로가 플랫폼과 블로그에서 다른 일을 하는 `GET /api/search`(5.7)는 이제 Host가 아니라 **헤더가 있는지**로 나눈다.

**헤더는 "어느 블로그"를 고르는 값이지 권한이 아니다.** 누구나 curl로 `X-Blog-Address: 아무거나`를 붙일 수 있다. 괜찮다. 예전 Host도 마찬가지로 아무나 바꿀 수 있는 값이었다. 블로그를 고른 **다음에** 서버가 그 블로그를 볼 수 있는지(가시성, [인가와 가시성](../3-보안/07-인가와-가시성.md)), 주인인지(`BlogOwnerGuard`)를 로그인 쿠키로 따로 검사한다. "주소창에 다른 블로그 주소를 치는 것"과 같은 일이라 새로운 위험이 생기지 않는다.

### 3.14 사용자 지정 헤더와 CORS·CSRF

[CSRF SameSite CORS](../3-보안/05-CSRF-SameSite-CORS.md) 3.7에서 본 대로, **다른 출처**로 보내는 `fetch`에 사용자 지정 헤더(`X-Blog-Address`, `X-Requested-With`)를 넣으면 브라우저가 먼저 OPTIONS 사전 요청(preflight)을 보내고, 서버가 허락하지 않으면 본 요청을 보내지 않는다.

이 프로젝트에서는 문제가 되지 않는다. 화면과 API가 **같은 출처**이기 때문이다.

| 환경 | 화면 | API | 출처 |
| --- | --- | --- | --- |
| 운영 | `http://now-log.java21.net/@alpha/12` | `http://now-log.java21.net/api/posts/12` | 같음 |
| 개발(서버만) | `http://blog.test:8080/@alpha/12` | `http://blog.test:8080/api/...` | 같음 |
| 개발(Vite) | `http://blog.test:5173/@alpha/12` | `http://blog.test:5173/api/...` → Vite가 8080으로 넘김 | 브라우저 입장에서 같음 |

같은 출처 요청에는 CORS 규칙이 아예 적용되지 않으므로 사전 요청도 없다. 이미 상태를 바꾸는 요청마다 `X-Requested-With`를 붙이고 있었던 것과 같은 상황이다.

오히려 경로 방식이 되면서 출처 관계가 **더 단순**해졌다.

```
전: blog.test:8080 / alpha.blog.test:8080 / beta.blog.test:8080  → 서로 다른 출처, 같은 사이트
후: blog.test:8080 (/, /@alpha, /@beta 모두)                     → 한 출처
```

- **CSRF 대책은 그대로 필요하다.** 다른 사이트의 숨은 폼은 여전히 우리 주소로 POST를 보낼 수 있다. `X-Requested-With` 검사(`CsrfHeaderFilter`)와 `SameSite=Lax`는 바뀌지 않는다. 다른 사이트의 스크립트는 다른 출처라 `X-Requested-With`를 붙이면 사전 요청에서 막힌다.
- **대신 한 출처라서 XSS의 영향이 넓어진다.** 예전에는 `evil.blog.com`의 스크립트가 `alpha.blog.com`의 API 응답을 읽을 수 없었다(다른 출처). 이제는 `/@evil/12`에서 돈 스크립트도 같은 출처라서 `X-Requested-With`를 붙여 어떤 API든 로그인한 사람의 이름으로 부를 수 있다. 본문 정화(OWASP Sanitizer + DOMPurify)와 CSP([XSS 방어 본문 정화와 CSP](../3-보안/06-XSS-방어-본문-정화와-CSP.md))가 지금은 더 중요한 방어선이다. 3.10 표의 "모든 블로그가 같은 출처라 한 블로그의 XSS가 전체에 영향"이 바로 이것이다.

### 3.15 쿠키 Domain: host-only 쿠키와 도메인 쿠키

[쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md) 3.4의 요약:

| `Set-Cookie`에 | 이름 | 어디로 보내나 |
| --- | --- | --- |
| `Domain` 없음 | host-only 쿠키 | 쿠키를 준 그 호스트에만(`blog.test`에만, `alpha.blog.test`에는 안 감) |
| `Domain=blog.test` | 도메인 쿠키 | `blog.test`와 그 아래 모든 호스트 |

둘 다 **포트와 경로의 앞부분**은 따로 따진다(포트는 보지 않고, 경로는 `Path` 속성으로).

**예전에는 Domain이 꼭 필요했다.** 로그인은 플랫폼(`blog.test`)에서 하고, 글쓰기는 내 블로그(`alpha.blog.test`)에서 한다. host-only 쿠키면 `alpha.blog.test`로 가는 순간 로그아웃 상태가 된다. 그래서 `Domain=.blog.test`로 줘서 모든 블로그 주소가 같은 로그인 쿠키를 받게 했다(5.3의 `cookieDomain()`).

**지금은 Domain이 필요 없다.** 플랫폼과 모든 블로그 화면이 한 호스트(`blog.test`)라서, host-only 쿠키도 `/`, `/@alpha/manage`, `/@beta/12` 어디서든 같이 간다(`Path=/`). 그리고 필요 없는 범위를 열어 두지 않는 것이 안전하다. 도메인 쿠키는 그 아래 **모든** 호스트로 가므로, 같은 도메인 아래에 다른 서비스가 생기면 그 서비스에도 로그인 쿠키가 간다.

그래서 로그인(access·refresh), 기기(device), 비회원 방문자(visitor_id), 소셜 state(oauth_state) 쿠키 모두 `Domain`을 뺐다(research.md R-03).

> **Path로 블로그마다 쿠키를 나누면?** `Path=/@alpha`로 주면 그 쿠키는 `/@alpha/…` 요청에만 간다. 하지만 RFC 6265(8.6절)가 밝히듯 Path는 **보안 경계가 아니다**. 같은 출처의 다른 경로에서 돈 스크립트가 그 경로의 페이지를 열어 접근할 수 있다. 블로그 사이의 분리를 쿠키 경로에 기대지 않는다.

덤으로, 쿠키에 Domain이 없으니 `http://localhost:8080`으로 열어도 로그인이 된다(예전에는 `localhost` 응답의 `Domain=.blog.test` 쿠키를 브라우저가 버렸다, [쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md) 3.4, 위 3.4의 "왜 `*.localhost`를 쓰지 않나"). 다만 메일·소셜 로그인 링크는 설정된 플랫폼 주소(`blog.test`)로 만들어지므로 개발은 여전히 `blog.test`로 연다.

### 3.16 SPA 서버 라우팅: `/@주소/…`

[SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md)의 원칙은 그대로다. 서버가 화면 주소를 먼저 확인하고 `index.html`을 준다.

| 요청 | 전(서브도메인) | 후(경로) |
| --- | --- | --- |
| 블로그 첫 화면 | `alpha.blog.com/` | `blog.com/@alpha` |
| 없는 블로그 | `nobody.blog.com/` → 404 | `blog.com/@nobody` → 404 |
| 예약어 | `admin.blog.com/` → 404 | `blog.com/@admin` → 404 |
| 이사한 블로그 | `old.blog.com/category/3` → 301 `new.blog.com/category/3` | `/@old/category/3` → 301 `/@new/category/3` |
| 다른 블로그 소속 글 | `beta.blog.com/15` → 301 `alpha.blog.com/15` | `/@beta/15` → 301 `/@alpha/15` |
| 공유 미리보기 `og:url` | `http://alpha.blog.com/15` | `http://blog.com/@alpha/15` |
| 공유 미리보기 `og:image` | `http://alpha.blog.com/uploads/…` | `http://blog.com/uploads/…` (`/@alpha`를 붙이지 않음) |
| 플랫폼 화면 | Host가 `blog.com` | `/@`로 시작하지 않는 모든 경로 |

바뀐 것은 "블로그를 어디서 읽나"(Host → 경로 첫 칸)와 "블로그 안 경로가 무엇인가"(전체 경로 → `@주소` 뒤 나머지)뿐이다. 301은 **블로그 안 경로를 그대로 두고 앞의 `@주소`만 바꾼다**.

서버가 만드는 블로그 링크(알림 링크, 301 `Location`, `og:url`, 글 저장 응답의 `url`)는 모두 `http(s)://{플랫폼}/@{주소}/…` 전체 주소다.

**블로그 화면 주소와 파일 주소는 다르다.** 서브도메인 때는 `alpha.blog.com/15`(화면)와 `alpha.blog.com/uploads/a.png`(사진)가 같은 호스트 아래 있어서 "블로그 주소 + 경로"로 둘 다 만들 수 있었다. 경로 방식에서 `/@alpha`는 **화면에만** 붙는다. 사진(`/uploads/…`), 빌드 파일(`/assets/…`), API(`/api/…`)는 블로그와 관계없이 플랫폼 바로 아래에서 나간다. `/@alpha/uploads/a.png`는 `SpaForwardController`가 블로그 화면으로 받으려 하다 점(`.`) 때문에 맞지 않아 404가 된다. 공유 미리보기를 가져가는 봇은 자바스크립트를 돌리지 않으므로([Open Graph 공유 미리보기](./12-Open-Graph-공유-미리보기.md)) 서버가 만든 이 HTML의 주소가 그대로 쓰인다.

### 3.17 React Router `basename`

블로그 화면의 링크는 그동안 `<Link to="/manage/write">`, `navigate('/12')`처럼 블로그 안 경로로 쓰여 있었다. 경로 방식에서는 이것이 `/@alpha/manage/write`가 되어야 한다. 모든 링크에 `/@alpha`를 붙여 고치는 대신 **라우터의 기준 경로**를 바꿨다.

`<BrowserRouter basename="/@alpha">`는 React Router에게 "이 앱은 `/@alpha` 아래에 산다"고 알린다.

| 앱 코드 | 실제 주소창 |
| --- | --- |
| `<Link to="/manage/write">` | `/@alpha/manage/write` |
| `navigate('/12')` | `/@alpha/12` |
| 주소창 `/@alpha/category/3` | 라우트는 `/category/3`으로 맞춤 |

- 라우터는 주소창 경로에서 basename을 떼고 라우트를 고르고, 링크를 만들 때는 앞에 붙인다. 그래서 `BlogRoutes`의 `path="/category/:categoryId"`, `path="/:postId"`는 한 글자도 바꾸지 않았다.
- basename 비교는 대소문자를 가리지 않는다. 설치된 React Router 7.18.4의 `stripBasename`은 `pathname.toLowerCase().startsWith(basename.toLowerCase())`로 비교한다(`node_modules/react-router/dist/development/chunk-*.mjs`에서 확인). 그래서 `/@Alpha/12`로 들어와도 화면이 그려진다.
- **basename 밖으로 가는 이동은 라우터로 하지 않는다.** 블로그 화면에서 `<Link to="/login">`을 쓰면 `/@alpha/login`이 된다. 플랫폼 화면(로그인, 마이페이지)이나 다른 블로그로 갈 때는 `platformUrl()`·`blogUrl()`로 만든 전체 주소를 `<a href>`나 `location.assign`으로 연다. 페이지를 새로 여는 것이고, 새로 연 페이지에서 `App`이 다시 플랫폼/블로그를 고른다.

Thymeleaf로 비유하면, 앱을 `server.servlet.context-path=/@alpha`로 띄운 것과 비슷하다. 템플릿의 `@{/manage}`가 `/@alpha/manage`가 되듯, 링크는 앱 안의 경로로 쓰고 앞부분은 틀이 붙인다.

### 3.18 같은 출처 기준의 열린 리다이렉트 막기

로그인 화면은 `?redirect=`의 주소로 돌아간다. 아무 주소나 받으면 `?redirect=https://evil.example`로 피싱 사이트에 보내는 **열린 리다이렉트**가 된다([가입 로그인 로그아웃](../3-보안/08-가입-로그인-로그아웃.md), [OAuth 소셜 로그인](../3-보안/12-OAuth-소셜-로그인.md)).

- **전**: "플랫폼 주소이거나 `*.blog.test` 블로그 주소"를 받아야 했다. 호스트 이름 끝을 비교하는 규칙이 필요했다(`endsWith(".blog.test")`, 점을 빼먹으면 `evilblog.test`가 통과하는 함정, 6장 함정 1).
- **후**: 블로그도 같은 출처 아래 경로라 **지금 페이지와 출처(스킴+호스트+포트)가 같은가** 하나만 보면 된다. 브라우저의 `URL` 객체가 `origin`을 계산해 주므로 문자열을 직접 자를 필요가 없다.

서버 쪽(소셜 로그인 뒤 돌아갈 곳)도 "호스트가 플랫폼 주소와 같은가"로 줄었다.

## 4. 동작 원리

**처음 구조(스텝 3~20).** 로컬에서 로그인한 사용자가 `http://alpha.blog.test:8080/api/test/blog`(블로그 API, 테스트 전용)를 부를 때 일어나는 일을 단계별로 보자.

```
① 운영체제: /etc/hosts에서 alpha.blog.test → 127.0.0.1
② 브라우저: 127.0.0.1:8080으로 연결, 요청에 Host: alpha.blog.test:8080
③ 톰캣: 요청을 받아 HttpServletRequest를 만든다. getServerName() = "alpha.blog.test"
④ 보안 필터: 쿠키로 로그인 회원을 정해 SecurityContext에 둔다 ([Spring Security 필터 체인](../3-보안/04-Spring-Security-필터-체인.md))
⑤ DispatcherServlet: 경로로 컨트롤러 메서드를 찾는다
⑥ 인자 준비: 메서드 인자에 @CurrentBlog Blog가 있다
      → CurrentBlogArgumentResolver.resolveArgument()
         → BlogHostResolver.resolve("alpha.blog.test")
              플랫폼("blog.test")인가? 아니오
              ".blog.test"로 끝나나? 예 → 앞부분 "alpha"
              주소 규칙에 맞나, 예약어가 아닌가? 예 → BlogAddress("alpha")
         → blogRepository.findByAddress("alpha")  (DB 조회)
         → 볼 수 있는 블로그인가(BlogVisibilityPolicy) / 이사했나
         → 통과하면 Blog 객체를 인자로 넘김, 아니면 404 예외
⑦ 컨트롤러 메서드 실행: 이미 "어느 블로그인지"가 정해진 상태
```

핵심은 ⑥이다. 컨트롤러마다 Host를 읽고 블로그를 찾는 코드를 반복하지 않고, **인자 해석기(HandlerMethodArgumentResolver)** 한 곳에 모았다. 스텝 21에서 경로 주소로 바꿀 때 컨트롤러를 한 줄도 고치지 않아도 된 것이 이 덕분이다(4.2, 5.9).

### 4.1 HandlerMethodArgumentResolver

Spring MVC는 컨트롤러 메서드를 부르기 전에, 인자 하나하나를 **인자 해석기 목록**에 물어 채운다.

```
@GetMapping("/api/posts/{id}")
public PostResponse get(@PathVariable Long id,          ← PathVariableMethodArgumentResolver
                        @RequestParam int page,          ← RequestParamMethodArgumentResolver
                        @AuthenticationPrincipal LoginMember me,  ← AuthenticationPrincipalArgumentResolver
                        @CurrentBlog Blog blog)          ← 우리가 만든 CurrentBlogArgumentResolver
```

각 해석기는 두 메서드를 가진다.
- `supportsParameter(parameter)`: "이 인자는 내가 맡는다"를 true/false로 답한다.
- `resolveArgument(...)`: 실제 값을 만들어 돌려준다. 예외를 던지면 컨트롤러는 실행되지 않고, 그 예외가 `@RestControllerAdvice`로 간다([Spring MVC 요청과 예외 처리](./01-Spring-MVC-요청과-예외-처리.md)).

직접 만든 해석기는 `WebMvcConfigurer.addArgumentResolvers`로 등록한다. Spring은 직접 등록한 해석기를 기본 해석기들 뒤, 그러나 "무엇이든 받는" 마지막 해석기(애노테이션 없는 객체를 `@ModelAttribute`로 보는 것)보다는 앞에서 물어본다.

### 4.2 지금(스텝 21부터): 경로 주소와 헤더

로그인한 주인이 `http://blog.test:8080/@alpha/manage/write`를 새로고침하고 글을 발행하는 흐름이다.

```
[화면 주소] GET /@alpha/manage/write     Host: blog.test:8080   Cookie: access_token=…(host-only)
  → SpaForwardController.page
      경로 "/@alpha/manage/write" → "/@"로 시작 → 주소 "alpha", 블로그 안 경로 "/manage/write"
      findBlog("alpha") → 있음 → 볼 수 있나·이사했나 → 관리 화면 → 200 index.html
[브라우저] App: parseLocation("/@alpha/manage/write") → { blog, alpha }
      <BrowserRouter basename="/@alpha"> → 라우트 "/manage/*" → 글쓰기 화면
[API] POST /api/posts     Host: blog.test:8080
        X-Blog-Address: alpha          ← api()가 지금 경로에서 읽어 붙임
        X-Requested-With: XMLHttpRequest
        Cookie: access_token=…          ← 같은 호스트라 그대로 감
  → CsrfHeaderFilter 통과 → 로그인 회원
  → @CurrentBlog: BlogAddressResolver.resolve → 헤더 "alpha" → BlogAddress("alpha") → DB → 볼 수 있나 → Blog
  → 주인인가(BlogOwnerGuard) → 저장
  ← 201 { id: 33, url: "http://blog.test:8080/@alpha/33" }
[브라우저] navigate("/33") → 주소창 /@alpha/33 (basename이 붙음)
```

헤더가 없는 경우:

```
GET /api/blog                    (X-Blog-Address 없음)  → resolve = Platform → findBlog 빈 값 → 404
GET /api/blog  X-Blog-Address: alpha                    → 200
GET /api/blog  X-Blog-Address: admin                    → Unknown(예약어) → 404
```

위의 처음 구조와 비교하면 ⑥의 "어느 블로그인가"를 Host 대신 헤더(API)와 경로 첫 칸(화면)에서 읽는 것만 다르다. 인자 해석기 구조(4.1)는 그대로다.

### 5.1 BlogHostResolver: Host를 세 종류로 나누기

`src/main/java/com/nhnacademy/blog/global/host/RequestHost.java`

```java
public sealed interface RequestHost {
    record Platform() implements RequestHost { }
    record BlogAddress(String address) implements RequestHost { }
    record Unknown() implements RequestHost { }
}
```

- `sealed interface`: 이 인터페이스를 구현할 수 있는 타입을 **정해 둔** 인터페이스다. 여기서는 같은 파일 안의 세 record만 구현할 수 있다. 그래서 `switch`에서 세 경우를 모두 다뤘는지 컴파일러가 확인해 준다([인가와 가시성](../3-보안/07-인가와-가시성.md)에서 자세히).
- `record`: 값을 담는 불변 클래스를 짧게 쓰는 문법이다. `BlogAddress("alpha")`는 생성자, `address()` 접근자, `equals`/`hashCode`/`toString`이 자동으로 생긴다. 그래서 테스트에서 `isEqualTo(new RequestHost.BlogAddress("alpha"))`로 비교할 수 있다.

`src/main/java/com/nhnacademy/blog/global/host/BlogHostResolver.java`

```java
public RequestHost resolve(String serverName) {
    if (serverName == null) {
        return new RequestHost.Unknown();                       // (1)
    }
    String host = serverName.toLowerCase(Locale.ROOT);          // (2)
    String platform = domainProperties.platform();              // (3) "blog.test" 또는 "blog.com"
    if (host.equals(platform) || host.equals("www." + platform)) {
        return new RequestHost.Platform();                      // (4)
    }
    String suffix = "." + platform;
    if (!host.endsWith(suffix)) {
        return new RequestHost.Unknown();                       // (5)
    }
    String address = host.substring(0, host.length() - suffix.length());  // (6)
    if (!BlogAddressRule.isUsable(address)) {
        return new RequestHost.Unknown();                       // (7)
    }
    return new RequestHost.BlogAddress(address);                // (8)
}
```

1. Host가 없으면(테스트 등) 알 수 없는 주소다.
2. 도메인 이름은 대소문자를 구분하지 않는다. `ALPHA.Blog.Test`도 같은 주소라 소문자로 맞춘다. `Locale.ROOT`를 주는 이유는 터키어 로케일 같은 환경에서 `I`의 소문자가 `i`가 아닌 문자로 바뀌는 문제를 피하기 위해서다.
3. 플랫폼 주소는 설정값이다(아래 5.3). 코드에 `blog.com`을 박지 않아서 개발(`blog.test`)과 운영(`blog.com`)이 같은 코드로 돈다.
4. `blog.test`, `www.blog.test`는 플랫폼(홈, 로그인, 가입 화면).
5. `.blog.test`로 끝나지 않으면 이 서비스의 주소가 아니다. 예: `other.com`, `evilblog.test`(점이 없어서 `.blog.test`로 끝나지 않는다). `endsWith("blog.test")`가 아니라 앞에 점을 붙인 `endsWith(".blog.test")`로 검사하는 것이 핵심이다. 점이 없으면 `evilblog.test`가 통과해 버린다.
6. 뒷부분을 잘라 서브도메인만 남긴다. `alpha.blog.test` → `alpha`, `a.b.blog.test` → `a.b`.
7. 주소 규칙(아래 5.2)에 맞지 않으면 블로그 주소가 아니다. `a.b`는 점이 규칙에 없어 여기서 걸린다. 그래서 두 단계 서브도메인은 자연스럽게 막힌다.
8. 통과하면 블로그 주소. 아직 **DB에 그 블로그가 있는지는 모른다**(주석: "블로그가 실제로 있는지는 아직 모른다").

DB 조회는 따로 한다.

```java
public Optional<Blog> findBlog(HttpServletRequest request) {
    if (resolve(request) instanceof RequestHost.BlogAddress(String address)) {
        return blogRepository.findByAddress(address);
    }
    return Optional.empty();
}
```

`instanceof RequestHost.BlogAddress(String address)`는 Java 21의 **record 패턴**이다. "BlogAddress이면, 그 안의 `address` 값을 꺼내 `address` 변수에 넣어라"를 한 줄로 쓴 것이다. 예전 방식으로 쓰면 이렇다.

```java
RequestHost host = resolve(request);
if (host instanceof RequestHost.BlogAddress) {
    String address = ((RequestHost.BlogAddress) host).address();
    ...
}
```

`findByAddress`는 삭제된 블로그도 돌려준다(주소는 삭제돼도 영구 예약, R-08). 볼 수 있는지는 부르는 쪽에서 판단한다. 이렇게 "주소 해석"과 "볼 수 있나 판단"을 나눠 둔 덕에 API(`@CurrentBlog`)와 화면 주소 처리([SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md))가 같은 해석기를 쓰면서 각자 다르게 대응한다.

(스텝 21에서 이 클래스는 `BlogAddressResolver`, `RequestHost`는 `RequestBlog`가 되었다. 5.8.)

### 5.2 BlogAddressRule: 정규식과 예약어

`src/main/java/com/nhnacademy/blog/blog/domain/BlogAddressRule.java`

```java
private static final Pattern FORMAT = Pattern.compile("^[a-z0-9][a-z0-9-]{2,30}[a-z0-9]$");
```

정규식을 조각내 읽어 보자.

| 조각 | 뜻 |
| --- | --- |
| `^` | 문자열 시작 |
| `[a-z0-9]` | 첫 글자: 영문 소문자나 숫자 **한 글자**(하이픈 불가) |
| `[a-z0-9-]{2,30}` | 가운데: 소문자·숫자·하이픈 **2~30글자** |
| `[a-z0-9]` | 마지막 글자: 소문자나 숫자 한 글자(하이픈 불가) |
| `$` | 문자열 끝 |

전체 길이는 1 + (2~30) + 1 = **4~32자**다. 블로그 주소 규칙(spec: 영문 소문자·숫자·하이픈 4~32자)과 같다.

| 입력 | 결과 | 이유 |
| --- | --- | --- |
| `alpha` | 통과 | |
| `my-blog` | 통과 | 하이픈은 가운데만 |
| `abc` | 실패 | 3자. 가운데가 최소 2자라 최소 4자 |
| `-alpha`, `alpha-` | 실패 | 처음·끝 하이픈 |
| `Alpha` | 실패 | 대문자. 단, Host는 소문자로 바꾼 뒤 검사하므로 `Alpha.blog.test`는 `alpha`로 통과 |
| `al_pha`, `al.pha` | 실패 | 밑줄·점은 허용 문자가 아님 |

처음과 끝을 하이픈 불가로 둔 이유는 DNS 라벨 규칙 때문이기도 하다. DNS 라벨(호스트 이름의 한 칸)은 하이픈으로 시작하거나 끝날 수 없다(RFC 1123 호스트 이름 규칙).

`Pattern.compile`을 `static final`로 한 번만 만드는 이유: 정규식을 컴파일하는 비용이 있어서, 요청마다 새로 만들지 않는다.

**예약어**:

```java
private static final Set<String> RESERVED = Set.of(
        "www", "api", "admin", "static", "mail", "login", "logout", "signup", "manage", "assets", "uploads",
        "blog", "help", "support", "notice", "cdn", "smtp", "imap", "ftp", "test", "dev", "root", "system");
```

누가 `admin`이라는 블로그를 만들면 `admin.blog.com`이 관리자 화면처럼 보여 피싱에 쓰일 수 있고, 나중에 플랫폼이 `api.blog.com`, `cdn.blog.com` 같은 서브도메인을 쓰고 싶어도 이미 남의 블로그가 된다. 그래서 미리 막아 둔다. 이 목록은 블로그 개설(스텝 4, T022)에서도 같이 쓴다. 규칙이 한 곳에 있으니 "개설할 때는 막았는데 주소 해석에서는 통과" 같은 불일치가 생기지 않는다.

`www`는 예약어이면서 동시에 `BlogHostResolver`의 (4)에서 플랫폼으로 먼저 처리된다.

이 규칙은 스텝 21 뒤에도 그대로이고, 헤더 값과 화면 경로의 주소를 함께 검사한다(5.8).

### 5.3 DomainProperties: 설정값으로 플랫폼 주소 받기

`src/main/java/com/nhnacademy/blog/global/host/DomainProperties.java` (스텝 20까지의 모양. 지금 모양은 5.8)

```java
@ConfigurationProperties(prefix = "app.domain")
public record DomainProperties(String platform) {
    public String cookieDomain() { return "." + platform; }
    public String blogHost(String address) { return address + "." + platform; }
}
```

- `@ConfigurationProperties(prefix = "app.domain")`: 설정 파일의 `app.domain.platform` 값을 이 record의 `platform`에 넣는다. `BlogApplication`의 `@ConfigurationPropertiesScan`이 이런 클래스를 찾아 빈으로 만든다([설정과 프로필](../1-개발-환경과-배포/02-설정과-프로필.md)).
- 값: `application.yml`은 `blog.com`, `application-dev.yml`은 `blog.test`, `application-prod.yml`은 `${APP_PLATFORM_DOMAIN:blog.com}`.
- `cookieDomain()`: 로그인 쿠키를 `.blog.test`에 둬서 모든 블로그 주소가 함께 받는다([쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md)). 주소 해석과 쿠키 도메인이 **같은 설정값**에서 나오므로 둘이 어긋날 일이 없다.
- `blogHost("gamma")` → `gamma.blog.test`. 301 리다이렉트 주소를 만들 때 쓴다.

### 5.4 @CurrentBlog: 블로그 API의 입구

`src/main/java/com/nhnacademy/blog/global/host/CurrentBlogArgumentResolver.java`

```java
@Override
public boolean supportsParameter(MethodParameter parameter) {
    return parameter.hasParameterAnnotation(CurrentBlog.class) && Blog.class.equals(parameter.getParameterType());
}
```

`@CurrentBlog`가 붙어 있고 타입이 `Blog`인 인자만 맡는다.

```java
@Override
public Blog resolveArgument(...) {
    HttpServletRequest request = webRequest.getNativeRequest(HttpServletRequest.class);  // (1)
    Long viewerId = LoginMembers.currentId();                                             // (2)
    Blog blog = blogHostResolver.findBlog(request)                                        // (3)
            .filter(found -> blogVisibilityPolicy.canView(found, viewerId))               // (4)
            .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND));               // (5)
    // 이사한 블로그는 주인만 옛 주소의 API를 쓴다 (BLOG-06)
    if (blog.isMoved() && !blog.isOwnedBy(viewerId)) {                                    // (6)
        throw new BusinessException(ErrorCode.NOT_FOUND);
    }
    return blog;
}
```

1. Spring의 요청 추상화(`NativeWebRequest`)에서 서블릿 요청을 꺼낸다.
2. 보안 필터가 SecurityContext에 넣어 둔 로그인 회원 id. 비회원이면 null.
3. Host → 블로그(없으면 빈 `Optional`).
4. 볼 수 있는 블로그만 남긴다. 삭제된 블로그는 아무도, 이용 제한·주인 정지 블로그는 주인만 본다([인가와 가시성](../3-보안/07-인가와-가시성.md)).
5. 남은 게 없으면 404. **없는 블로그와 볼 수 없는 블로그를 같은 404로** 돌려준다. 응답만 보고 "이 주소에 블로그가 있긴 하구나"를 알 수 없게 한다.
6. 이사한 블로그(`moved_to_blog_id`가 있음)의 옛 주소로 부르는 API는 주인만 쓸 수 있다. 주인은 옛 블로그 관리 화면을 계속 쓰고(BLOG-06), 다른 사람은 화면 단계에서 이미 새 주소로 301을 받으므로 이 404를 볼 일이 거의 없다(rest-api.md "주소와 Host 범위").

컨트롤러는 이렇게 쓴다(테스트 전용 API `src/test/.../support/TestApiController.java`).

```java
@PutMapping("/api/test/blog/settings")
public Map<String, String> ownerOnly(@CurrentBlog Blog blog, @AuthenticationPrincipal LoginMember member) {
    blogOwnerGuard.requireOwner(blog, member);   // 비회원 401, 남 403
    return Map.of("result", "ok");
}
```

인자 해석이 컨트롤러 실행 **전에** 일어나므로, 없는 블로그면 로그인 검사(401)보다 404가 먼저 나간다. rest-api.md의 상태 코드 순서(404 → 401 → 403)가 구조적으로 지켜진다.

등록은 `src/main/java/com/nhnacademy/blog/global/config/WebConfig.java`:

```java
@Override
public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
    resolvers.add(currentBlogArgumentResolver);
}
```

### 5.5 이사한 블로그

블로그 A가 C로 이사하면 `blog.moved_to_blog_id = C`가 된다(R-08, 연쇄 이사도 최종 대상으로 갱신).

| 요청 | 처리하는 곳 | 결과 |
| --- | --- | --- |
| 화면 `a.blog.com/category/3` | `SpaForwardController` | 301 → `c.blog.com/category/3` |
| 화면 `a.blog.com/manage/...`(주인) | `SpaForwardController` | 200 (옛 블로그 관리) |
| API `a.blog.com/api/...`(주인 아님) | `@CurrentBlog` | 404 |
| API `a.blog.com/api/...`(주인) | `@CurrentBlog` | 통과 |
| 화면 `a.blog.com/15`(A에 남은 글) | `SpaForwardController` | 200 ([SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md) "글 확인이 먼저") |

301 주소는 `BlogHostResolver.blogUrl`이 만든다.

```java
StringBuilder url = new StringBuilder()
        .append(request.getScheme()).append("://")                 // http 또는 https
        .append(domainProperties.blogHost(blog.getAddress()));     // c.blog.test
int port = request.getServerPort();
boolean defaultPort = ("http".equals(request.getScheme()) && port == 80)
        || ("https".equals(request.getScheme()) && port == 443);
if (!defaultPort && port > 0) {
    url.append(':').append(port);                                  // 개발에서는 :8080 또는 :5173
}
return url.append(pathAndQuery).toString();                        // 경로와 쿼리는 그대로
```

요청이 들어온 스킴과 포트를 그대로 쓰기 때문에, 개발(`http://...:8080`)과 운영(`https://...`, 포트 생략)에서 같은 코드가 맞는 주소를 만든다. (경로 주소에서 같은 표가 어떻게 바뀌었는지는 3.16, 코드는 5.10.)

### 5.6 프론트: Vite 개발 서버의 allowedHosts와 Host 전달

`frontend/vite.config.ts`

```ts
server: {
  allowedHosts: ['.blog.test'],
  proxy: {
    '/api': 'http://localhost:8080',
    '/uploads': 'http://localhost:8080',
  },
},
```

- **allowedHosts**: Vite 개발 서버는 보안상(DNS 리바인딩 공격 방지) 처음 보는 Host로 온 요청을 403으로 거절한다. `'.blog.test'`처럼 점으로 시작하면 `blog.test`와 그 모든 하위 주소를 허용한다. 실제로 확인한 결과: `Host: alpha.blog.test:5173` → 200, `Host: evil.example:5173` → 403.
- **proxy**: 브라우저가 `alpha.blog.test:5173/api/...`로 보낸 요청을 Vite가 8080으로 넘긴다. `changeOrigin` 옵션을 켜지 않았으므로(기본값 false) **원래 Host 헤더(`alpha.blog.test:5173`)를 그대로** 넘긴다. 그래서 백엔드의 `BlogHostResolver`가 `alpha`를 찾을 수 있다. `changeOrigin: true`로 바꾸면 Host가 `localhost:8080`으로 바뀌어 모든 블로그 API가 404가 된다.

프론트에도 같은 판단이 있다. `frontend/src/app/host.ts`의 `parseHost`는 `window.location.hostname`으로 플랫폼/블로그를 나눠 다른 라우트를 그린다([React 화면 나누기와 API 클라이언트](./08-React-화면-나누기와-API-클라이언트.md)). 프론트는 주소 규칙(정규식, 예약어)을 검사하지 않는다. 없는 블로그는 서버가 화면을 주기 전에 404로 막기 때문이다. (스텝 21에서 `parseHost`는 경로를 보는 `parseLocation`으로 바뀌었다, 5.13.)

### 5.7 (스텝 15) 같은 경로, 다른 호스트: `GET /api/search`

API 명세에서 `/api/search`는 두 번 나온다. 블로그 주소(**B**)에서는 그 블로그 안 검색(SRCH-01), 플랫폼 주소(**P**)에서는 전체 검색(SRCH-02)이다. 사용자가 보기에는 자연스럽다: 블로그 머리글의 검색창은 그 블로그를, 플랫폼 머리글의 검색창은 전체를 찾는다.

문제는 Spring MVC가 **Host로 컨트롤러 메서드를 고르지 못한다**는 것이다. `@GetMapping`은 경로·메서드·파라미터·헤더 조건을 볼 수 있지만, 헤더 조건(`headers = "Host=…"`)은 값이 정확히 같은지를 볼 뿐 "어느 블로그 주소든"이나 "플랫폼 주소"를 나타낼 수 없다. 같은 경로에 메서드 두 개를 두면 시작할 때 "Ambiguous mapping" 오류다.

그래서 메서드 하나에서 나눈다.

```java
// search/presentation/SearchController.java
@GetMapping("/api/search")
public PageResponse<?> search(HttpServletRequest request, @RequestParam(required = false) String q, ...) {
    ...
    if (!(blogHostResolver.resolve(request) instanceof RequestHost.Platform)) {
        Blog blog = currentBlog.resolve(request);
        return posts(searchService.search(blog, viewerId, q, pageQuery), blog);
    }
    // 플랫폼: type=post(기본) 또는 blog
```

- `blogHostResolver.resolve(request)`: 5.1의 Host 세 갈래(`Platform`, `BlogAddress`, `Unknown`) 그대로다. `instanceof`로 플랫폼인지 본다(sealed 인터페이스라 갈래가 셋뿐이다).
- 플랫폼이 아니면 `@CurrentBlog`와 **똑같은 판단**이 필요하다(없거나 볼 수 없으면 404, 이사한 블로그는 주인만). 인자에 `@CurrentBlog Blog blog`를 쓰면 플랫폼 주소에서도 그 판단이 돌아 404가 나므로 쓸 수 없다. 대신 `CurrentBlogArgumentResolver`의 몸통을 `public Blog resolve(HttpServletRequest request)`로 꺼내, 인자 해석기와 이 컨트롤러가 같이 부른다.

```java

                            NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
    return resolve(webRequest.getNativeRequest(HttpServletRequest.class));
}

public Blog resolve(HttpServletRequest request) {
    Long viewerId = LoginMembers.currentId();
    Blog blog = blogHostResolver.findBlog(request)
            .filter(found -> blogVisibilityPolicy.canView(found, viewerId))
            .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND));
    ...
```

- 고르지 않은 대안: (1) 경로를 나눈다(`/api/blogs/search`처럼). 명세의 API를 바꾸는 것이라 고르지 않았다. (2) 서블릿 필터에서 Host를 보고 경로를 바꿔 넘긴다(`/api/search` → `/api/platform/search`). 동작은 하지만 코드를 읽는 사람이 경로가 바뀌는 것을 알아채기 어렵다.
- 반환 타입이 `PageResponse<?>`: 글이면 `PostSummary`, 블로그면 `{ blog, owner, subscriberCount }`라 내용 타입이 갈래마다 다르다. JSON으로 바꿀 때는 실제 값의 타입으로 쓰이므로 문제없다.

### 5.8 `BlogAddressResolver`: 블로그를 정하는 한 곳

(5.8부터는 스텝 21부터의 지금 코드다.)

`src/main/java/com/nhnacademy/blog/global/host/BlogAddressResolver.java` (스텝 21에서 `BlogHostResolver`를 바꿔 만든 것)

```java
/** 블로그 화면이 블로그 API를 부를 때 붙이는 헤더. 값은 블로그 주소(alpha). */
public static final String HEADER = "X-Blog-Address";
/** 화면 주소에서 블로그 주소 앞에 붙는 글자: /@alpha. */
public static final String PATH_PREFIX = "/@";
```

- 헤더 이름과 경로 앞글자를 상수로 둔다. 서버 코드와 테스트(`TestBlogs.HEADER`)가 같은 상수를 쓰므로 글자가 어긋날 일이 없다.

```java
/** API 요청이 가리키는 곳. X-Blog-Address가 없으면 플랫폼이다. */
public RequestBlog resolve(HttpServletRequest request) {
    String address = request.getHeader(HEADER);
    return address == null ? new RequestBlog.Platform() : resolveAddress(address);
}

/** 블로그 주소 값을 규칙으로 확인한다. 대소문자는 가리지 않는다. */
public RequestBlog resolveAddress(String rawAddress) {
    String address = rawAddress.trim().toLowerCase(Locale.ROOT);
    return BlogAddressRule.isUsable(address) ? new RequestBlog.BlogAddress(address) : new RequestBlog.Unknown();
}
```

- `request.getHeader(HEADER)`: 헤더 이름은 대소문자를 가리지 않는다(서블릿 `getHeader`가 그렇게 찾는다). `x-blog-address`로 와도 같다.
- 헤더가 없으면(`null`) 플랫폼. 예전 `BlogHostResolver.resolve(serverName)`(5.1)에서 Host를 플랫폼·블로그·알 수 없음으로 나누던 자리를 그대로 이어받았다.
- `resolveAddress`는 **화면 경로에서 꺼낸 주소에도** 쓴다(5.10). 헤더든 경로든 같은 규칙(`BlogAddressRule`: 4~32자, 예약어 거절, 5.2)을 한 곳에서 본다. `trim()`은 헤더 값 앞뒤의 공백을 지운다.
- 소문자로 바꾸는 이유도 그대로다. 주소는 소문자로만 저장되므로 `My-Blog`로 와도 `my-blog`를 찾는다. `Locale.ROOT`는 터키어 로케일의 `I` 문제를 피한다(5.1).

`src/main/java/com/nhnacademy/blog/global/host/RequestBlog.java`

```java
public sealed interface RequestBlog {
    record Platform() implements RequestBlog { }
    record BlogAddress(String address) implements RequestBlog { }
    record Unknown() implements RequestBlog { }
}
```

- 예전 `RequestHost`(5.1)와 모양이 같고 이름만 바뀌었다. 이제 Host를 해석한 결과가 아니라 "요청이 가리키는 블로그"라서 이름을 바꿨다.

```java
/** API 요청이 가리키는 블로그. 플랫폼·규칙에 맞지 않는 주소면 빈 값. … */
public Optional<Blog> findBlog(HttpServletRequest request) {
    return resolve(request) instanceof RequestBlog.BlogAddress(String address)
            ? blogRepository.findByAddress(address) : Optional.empty();
}

/** 화면 주소의 블로그 주소(/@alpha/… 의 alpha)로 찾는다. */
public Optional<Blog> findBlog(String rawAddress) {
    return resolveAddress(rawAddress) instanceof RequestBlog.BlogAddress(String address)
            ? blogRepository.findByAddress(address) : Optional.empty();
}
```

- 같은 이름의 메서드가 둘이다(오버로딩). 요청을 주면 헤더에서, 문자열을 주면 그 문자열에서 주소를 읽는다. 앞은 API(`@CurrentBlog`)가, 뒤는 화면 주소(`SpaForwardController`)가 쓴다.
- `instanceof RequestBlog.BlogAddress(String address)`: Java 21 record 패턴(5.1).

```java
/** 블로그 화면의 경로. path가 "/"면 블로그 첫 화면(/@alpha), 아니면 /@alpha/12 꼴. */
public static String blogPath(String address, String pathAndQuery) {
    return PATH_PREFIX + address + ("/".equals(pathAndQuery) ? "" : pathAndQuery);
}

public String blogUrl(HttpServletRequest request, Blog blog, String pathAndQuery) {
    return platformUrl(request, blogPath(blog.getAddress(), pathAndQuery));
}

public String platformUrl(HttpServletRequest request, String pathAndQuery) {
    return url(request, platform(), pathAndQuery);
}
```

- `blogPath("alpha", "/")` → `/@alpha`, `blogPath("alpha", "/12")` → `/@alpha/12`. 첫 화면은 끝에 `/`를 붙이지 않는다(R-04 "블로그 첫 화면은 끝에 `/`를 붙이지 않은 `/@{주소}`").
- **블로그 주소 = 플랫폼 주소 + 블로그 경로**가 되었다. 예전에는 `blogHost("gamma")` → `gamma.blog.test`처럼 호스트를 만들었는데(5.3, 5.5), 이제 호스트는 언제나 플랫폼이고 경로만 다르다. 그래서 `blogUrl`이 `platformUrl`을 부르는 한 줄이 됐다.
- `url(...)`(파일 아래쪽)은 그대로다(5.5의 스킴·포트 코드). 요청의 스킴과 포트를 따라가므로 개발(`http://blog.test:8080`)과 운영(`http://now-log.java21.net`)에서 같은 코드가 맞는 주소를 만든다. 운영은 nginx 뒤라서 `application-prod.yml`에 `server.forward-headers-strategy: native`를 두었다. nginx가 넘기는 `X-Forwarded-*` 헤더로 원래 스킴·포트를 알게 하는 설정이다(3.7). 학교 nginx 설정(`~/nginx/now-log.java21.net.conf`)은 `proxy_set_header Host $host`, `X-Forwarded-For`, `X-Forwarded-Proto`를 넘긴다. `$host`에는 포트가 없어서 서버가 만드는 링크는 `http://now-log.java21.net/@…`(포트 없음)이 된다. 배포 뒤 실제 응답으로 한 번 더 본다(7장 실습 12).

### 5.10 `SpaForwardController`: `/@주소/…`를 먼저 확인하기

`src/main/java/com/nhnacademy/blog/global/config/SpaForwardController.java`

```java
private static final String FIRST = "{s1:(?!api$|uploads$|assets$)[^.]+}";
/** 디코딩한 경로(%40 → @). Spring MVC가 주소를 맞출 때 쓰는 것과 같은 방식이다. */
private static final UrlPathHelper PATH_HELPER = new UrlPathHelper();

@GetMapping({
        "/",
        "/" + FIRST,
        "/" + FIRST + "/{s2:[^.]+}",
        "/" + FIRST + "/{s2:[^.]+}/{s3:[^.]+}",
        "/" + FIRST + "/{s2:[^.]+}/{s3:[^.]+}/{s4:[^.]+}",
        "/" + FIRST + "/{s2:[^.]+}/{s3:[^.]+}/{s4:[^.]+}/{s5:[^.]+}",
        // 태그 이름에는 점이 들어갈 수 있다(node.js). 확장자로 보지 않는다 (TAG-02)
        "/{s1:@[^.]+}/tag/{name:.+}"})
```

- 1~5칸 패턴은 [SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md) 5.1과 같다. `@alpha`도 점이 없는 한 칸이라 `FIRST`에 맞는다. 따로 블로그용 패턴을 만들 필요가 없었다.
- **칸 하나를 블로그 주소가 쓴다.** 예전에는 블로그 안 경로가 5칸까지 됐지만 이제 `@alpha`가 첫 칸이라 블로그 안 경로는 4칸까지다. 가장 깊은 블로그 화면 `/@alpha/manage/posts/12/edit`이 정확히 5칸이라 들어맞는다. 더 깊은 블로그 화면을 만들면 패턴을 늘려야 한다.
- **태그 줄만 바뀌었다.** 예전 `"/tag/{name:.+}"`(서브도메인에서는 블로그 안 경로가 곧 전체 경로)를 `"/{s1:@[^.]+}/tag/{name:.+}"`로 바꿨다. 첫 칸이 `@`로 시작해야 하고, 태그 이름 칸은 `.+`라서 `node.js`처럼 점이 있어도 된다. 다른 줄은 모든 칸에 점이 없어야 해서 `/@alpha/tag/node.js`는 이 줄만 맞는다.
- 이 줄을 처음 쓸 때 서버가 뜨지 않은 일은 6장 함정 17에 있다.

```java
public ResponseEntity<Resource> page(HttpServletRequest request, HttpServletResponse response) {
    String path = PATH_HELPER.getPathWithinApplication(request);
    if (!path.startsWith(BlogAddressResolver.PATH_PREFIX)) {
        return app(HttpStatus.OK);
    }
    // /@alpha/12 → 주소 alpha, 블로그 안 경로 /12. 블로그 안 경로가 없으면 첫 화면(/)
    String rest = path.substring(BlogAddressResolver.PATH_PREFIX.length());
    int slash = rest.indexOf('/');
    String address = slash < 0 ? rest : rest.substring(0, slash);
    String blogPath = slash < 0 ? "/" : rest.substring(slash);
    return blogPage(request, response, address, blogPath);
}
```

1. `getPathWithinApplication`: 요청 경로를 **디코딩해서** 준다(`UrlPathHelper`는 기본으로 디코딩한다). `@`는 경로에 그대로 써도 되는 글자라 브라우저는 보통 `/@alpha`로 보내지만, 어떤 도구가 `/%40alpha`로 바꿔 보내도 같은 주소로 읽기 위해서다. `request.getRequestURI()`는 디코딩하지 않은 원문이라 `%40`이 그대로 남는다.
2. `/@`로 시작하지 않으면 플랫폼 화면이다. 예전에는 Host가 이상하면(`a.b.blog.test`) 404, 이 서비스 주소가 아니면(`localhost`) 200으로 갈렸는데([SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md) 5.2, 7장 실습 2), 이제 Host를 보지 않으므로 그 구분(`isUnderPlatform`)이 사라졌다. 없는 플랫폼 경로(`/nothing`)는 예전처럼 React의 `NotFoundPage`가 그린다.
3. `rest`: `@`까지 뗀 나머지. `alpha/manage/write`.
4. 첫 `/` 앞이 주소, 그 뒤가 블로그 안 경로. `/` 가 없으면(`/@alpha`) 블로그 첫 화면 `/`.
5. `blogPage`는 예전과 같은 판단(없음·볼 수 없음 404, 이사 301, 다른 블로그 소속 글 301, 관리 화면, 방문 기록)을 **블로그 안 경로** 기준으로 한다. 예전에는 `request.getRequestURI()`가 곧 블로그 안 경로였는데, 이제는 인자로 받은 `path`를 쓴다.

```java
private ResponseEntity<Resource> blogPage(HttpServletRequest request, HttpServletResponse response,
                                          String address, String path) {
    Optional<Blog> found = blogAddressResolver.findBlog(address);
    if (found.isEmpty()) {
        return app(HttpStatus.NOT_FOUND);
    }
```

- `findBlog(address)`가 규칙 검사와 DB 조회를 한 번에 한다. `@admin`(예약어), `@ab`(3자), `@nobody-here-x`(없음) 모두 여기서 빈 값 → 404.

```java
/** 같은 블로그 안 경로(path)를 새 블로그 주소로 301. */
private ResponseEntity<Resource> redirect(HttpServletRequest request, Blog target, String path) {
    String query = request.getQueryString();
    String pathAndQuery = path + (query == null ? "" : "?" + query);
    return ResponseEntity.status(HttpStatus.MOVED_PERMANENTLY)
            .location(URI.create(blogAddressResolver.blogUrl(request, target, pathAndQuery)))
            .build();
}
```

- 예전에는 `request.getRequestURI()`(전체 경로)를 새 호스트에 붙였다(5.5). 지금 전체 경로는 `/@old/category/3`이라 그대로 붙이면 `/@new/@old/category/3`이 된다. 그래서 **블로그 안 경로 `path`**(`/category/3`)를 받아 `blogUrl`이 `/@new`를 앞에 붙인다. 이 실수를 막는 것이 테스트 `movedBlogRedirectsWithSamePathExceptOwnersManagePages`다(5.14).

공유 미리보기의 두 주소는 서로 다른 함수로 만든다.


### 5.11 소셜 로그인 뒤 돌아갈 곳: `SocialAuthService.safeRedirect`

`src/main/java/com/nhnacademy/blog/auth/application/SocialAuthService.java`

```java
/** 로그인 뒤 돌아갈 곳. 우리 서비스 주소(플랫폼 호스트, 블로그는 그 아래 /@주소)나 경로만, 아니면 홈. */
private String safeRedirect(String redirect) {
    if (redirect == null || redirect.isBlank()) {
        return "/";
    }
    if (redirect.startsWith("/") && !redirect.startsWith("//") && !redirect.startsWith("/\\")) {
        return redirect;
    }
    try {
        URI uri = URI.create(redirect);
        boolean web = "http".equals(uri.getScheme()) || "https".equals(uri.getScheme());
        if (web && hostResolver.platform().equalsIgnoreCase(uri.getHost())) {
            return redirect;
        }
    } catch (IllegalArgumentException e) {
        // 주소 모양이 아니면 홈으로
    }
    return "/";
}
```

- 바뀐 줄은 `if (web && …)` 하나다. 예전에는 "호스트를 블로그 주소 해석기에 넣어 `Unknown`이 아니면"(플랫폼이나 `*.blog.test`)이었고, 지금은 "호스트가 플랫폼 주소와 같으면"이다. 블로그 화면도 플랫폼 호스트 아래라 이것으로 충분하다.
- `//evil.com`(스킴 없이 호스트로 가는 주소)과 `/\evil.com`(일부 브라우저가 `//`처럼 읽음)을 경로로 보지 않는 검사는 그대로다([OAuth 소셜 로그인](../3-보안/12-OAuth-소셜-로그인.md)).
- 이 검사는 호스트만 본다. 포트나 스킴이 달라도(`http://blog.test:9999/`) 통과한다. 같은 호스트 이름이라 다른 사람의 사이트로 보내는 일은 아니어서 그대로 두었다. 프론트의 `safeRedirect`(5.13)는 포트까지 같은 출처를 요구해 더 좁다.

### 5.13 프론트: `host.ts`, `App.tsx`, `client.ts`

`frontend/src/app/host.ts`

```ts
/** /@alpha 또는 /@alpha/… 의 alpha. 주소 규칙(영문 소문자·숫자·하이픈)은 서버가 다시 본다 */
const BLOG_PATH = /^\/@([A-Za-z0-9-]+)(?=\/|$)/

/** 경로(location.pathname)로 플랫폼·블로그를 나눈다 */
export function parseLocation(pathname: string): Host {
  const match = BLOG_PATH.exec(pathname)
  return match ? { kind: 'blog', address: match[1].toLowerCase() } : { kind: 'platform' }
}
```

- 정규식 조각: `^\/@`(경로가 `/@`로 시작), `([A-Za-z0-9-]+)`(주소에 쓸 수 있는 글자를 잡아 둠, 대문자도 받고 아래에서 소문자로), `(?=\/|$)`(바로 뒤가 `/`이거나 끝. **전방 탐색**이라 그 `/`는 잡지 않는다). 그래서 `/@a.b/1`은 `a` 뒤가 `.`이라 맞지 않아 플랫폼이 된다.
- 예전 `parseHost(hostname)`(5.6)는 호스트 이름을 보고, 플랫폼 주소를 `VITE_PLATFORM_DOMAIN` 설정(없으면 `'blog.test'`)에서 읽었다. 이제 경로만 보므로 플랫폼 주소를 알 필요가 없다.
- 길이·예약어 같은 규칙은 검사하지 않는다. `/@admin`은 서버가 먼저 404를 주므로 프론트가 그 경로로 블로그 화면을 그릴 일이 없다.

```ts
export function safeRedirect(target: string | null, location: Location = window.location): string | null {
  if (!target) {
    return null
  }
  let url: URL
  try {
    url = new URL(target)
  } catch {
    return null
  }
  return (url.protocol === 'http:' || url.protocol === 'https:') && url.origin === location.origin ? url.href : null
}
```

- `new URL(target)`: 주소를 해석한다. 상대 주소(`/relative`)는 기준 없이 해석할 수 없어 예외 → `null`. 로그인 화면에 오는 `redirect`는 언제나 전체 주소로 만들기 때문이다.

## 6. 자주 하는 실수와 함정

**서브도메인과 Host 헤더 (스텝 3~20)**

1. **`endsWith(platform)`에서 점 빼먹기**: `host.endsWith("blog.test")`로 쓰면 `evilblog.test`가 통과한다. 반드시 `"." + platform`.
2. **`getHeader("Host")`를 그대로 쓰기**: 포트(`:8080`)가 붙어 있어 비교가 틀어진다. `getServerName()`을 쓴다.
3. **대소문자**: 도메인은 대소문자를 구분하지 않는다. 소문자로 맞추지 않으면 `Alpha.blog.test`가 다른 블로그 취급된다.
4. **hosts에 와일드카드 적기**: `127.0.0.1 *.blog.test`는 동작하지 않는다. 주소를 하나씩 적는다.
5. **새 블로그를 만들고 hosts에 안 적기**: 스텝 4에서 `mytest`라는 블로그를 만들면, `mytest.blog.test`도 hosts에 추가해야 브라우저로 열린다.
6. **"없음"과 "볼 수 없음"을 다른 응답으로 주기**: 403을 주면 "있긴 있다"는 정보가 샌다. 둘 다 404.
7. **테넌트 조건 빠뜨리기**: 블로그 API에서 글을 찾을 때 `postRepository.findById(id)`만 쓰면 다른 블로그의 글이 나온다. `@CurrentBlog`로 받은 블로그와 글의 소속을 꼭 비교한다(가시성 판단 ②).
8. (스텝 15) **같은 경로를 Host로 나누려고 메서드를 두 개 만들기**: 시작할 때 Ambiguous mapping. 한 메서드에서 `RequestHost`로 나누고, 블로그 쪽은 `@CurrentBlog`와 같은 `resolve`를 부른다.
9. **Vite 프록시에 `changeOrigin: true`**: 위 5.6. 백엔드가 블로그를 못 찾는다.
10. **운영에서 리버스 프록시 뒤에 둘 때 Host가 바뀜**: 프록시가 원래 Host를 넘기도록 설정해야 한다.
11. **dnsmasq만 켜고 `/etc/resolver/blog.test`를 안 만듦**: macOS가 dnsmasq에 묻지 않아 여전히 NXDOMAIN이다.
12. **`dig`·`nslookup`으로 확인**: 이 둘은 macOS의 `/etc/resolver`를 거치지 않고 DNS 서버에 바로 물어서, 설정이 맞아도 "없음"이 나올 수 있다. `ping`이나 `dscacheutil -q host -a name xyz.blog.test`로 확인한다.
13. **설정을 바꿨는데 그대로**: 운영체제가 예전 답을 기억(캐시)하고 있다. `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`로 비우고, 브라우저는 새로 연다.
14. **dnsmasq를 쓰면서 hosts에 옛 줄을 남김**: hosts가 먼저라 그 이름은 hosts 값을 쓴다. 지금은 둘 다 127.0.0.1이라 문제없지만, 헷갈리지 않게 지운다.
15. **와일드카드 레코드만 두고 인증서는 `blog.com`용 하나만**: 블로그 주소에서 HTTPS 오류가 난다. `*.blog.com` 인증서가 따로 필요하다.
16. **dnsmasq를 모든 네트워크에 열어 둠**: 기본 설정은 와이파이 등 모든 연결에서 질문을 받는다. `listen-address=127.0.0.1`과 `bind-interfaces`로 내 컴퓨터만 받게 한다.

**경로 주소 (스텝 21부터)**

17. **경로 패턴 `{이름:정규식}` 안에 `/`를 쓰기.** 태그 줄을 처음에는 정규식 안에 `/`가 들어간 모양으로 썼다(첫 칸에 `/`가 없다는 뜻을 담으려고). 서버가 시작하다가 `Expected close capture character after variable name }` 오류로 멈췄다. Spring의 경로 패턴 해석기는 패턴을 `/`로 칸을 나누며 읽기 때문에, 중괄호 안의 `/`도 칸 나눔으로 읽혀 변수가 닫히지 않은 것으로 본다. `{…}` 하나는 원래 한 칸만 맞추므로 "`/`가 없다"를 따로 쓸 필요가 없다. `{s1:@[^.]+}`로 고쳤다. 테스트가 아니라 **시작할 때** 깨지므로, 패턴을 고친 뒤에는 서버(또는 통합 테스트 하나)를 꼭 띄워 본다.
18. **`location.origin`이나 `request.getRequestURI()`에 경로를 그대로 붙이기.** 서브도메인에서는 "호스트 = 블로그"라서 맞던 코드가 경로 방식에서 조용히 틀린다. 공유 주소(`origin + /12`), 이사 301(`새 주소 + getRequestURI()`)이 그랬다. 블로그 주소는 늘 `blogUrl`·`blogPath`로 만든다. **반대로 파일 주소에는 `/@주소`를 붙이지 않는다.** 서브도메인 때는 "블로그 주소 + `/uploads/…`"가 맞았지만 경로 방식에서는 `/@alpha/uploads/…`가 404다. 공유 미리보기 `og:image`가 실제로 이렇게 틀렸다가 고쳐졌다(5.10). 화면이면 `blogUrl`, 사진·`/assets`·API면 `platformUrl`.
19. **블로그 화면에서 `<Link to="/login">`.** basename이 붙어 `/@alpha/login`이 되고, 블로그 라우터에는 그런 라우트가 없어 `NotFoundPage`가 뜬다. 플랫폼 화면으로는 `platformUrl()` + `<a href>`.
20. **API 호출마다 헤더를 직접 붙이기.** 하나만 빠뜨려도 그 요청이 플랫폼 요청이 되어 404. `api()`·`uploadFile()` 한 곳에서 붙인다. `fetch`를 새로 직접 쓰는 곳이 생기면 그곳도 `blogHeader()`가 필요하다.
21. **헤더를 권한으로 착각하기.** `X-Blog-Address`는 누구나 아무 값으로 보낼 수 있다. 권한은 언제나 로그인 쿠키와 `BlogOwnerGuard`·가시성 판단으로 본다.
22. **헤더에 따라 응답이 다른 GET을 캐시하기.** 같은 `/api/blog`가 헤더마다 다른 블로그를 돌려준다. 브라우저나 중간 서버(CDN)가 주소만 보고 캐시하면 다른 블로그의 응답이 섞인다. 지금은 API 응답을 HTTP 캐시하지 않지만(Spring Security가 기본으로 `Cache-Control: no-cache, no-store …`를 붙인다), 캐시를 켜게 되면 응답에 `Vary: X-Blog-Address`를 붙여야 한다. ②안(경로에 주소)이었다면 생기지 않는 문제다.
23. **브라우저에 남은 예전 Domain 쿠키.** 스텝 21 전에 `blog.test`에서 로그인했던 브라우저에는 `Domain=.blog.test`인 `access_token`이 남아 있을 수 있다. 새 서버는 Domain 없는 `access_token`을 준다. 쿠키는 (이름, Domain, Path)가 모두 같아야 같은 쿠키라서([쿠키와 로그인 유지](../3-보안/02-쿠키와-로그인-유지.md) 4.1) 브라우저에 **같은 이름의 쿠키가 둘** 생기고 둘 다 보낸다. 경로가 같으면 브라우저는 먼저 만든(옛) 쿠키를 앞에 보낸다(RFC 6265 5.4). 처음에는 서버가 첫 번째 값을 읽고 로그아웃은 Domain 없는 쪽만 지워서, 옛 Refresh 쿠키로 "로그아웃했는데 다시 로그인되는" 일이 생길 수 있었다. 그래서 같은 이름이 둘 오면 **뒤(새) 값을 읽고**, 옛 `Domain=.{플랫폼}` 쿠키는 지우라고 응답하게 했다(`AuthCookieManager.readCookie`·`expireLegacyDomainCookies`, `LogoutIntegrationTest.legacyDomainCookieIsIgnoredAndExpired`). 배포된 사이트도 스텝 21 전에는 `Domain=.now-log.java21.net` 쿠키를 줬으므로 같은 일이 생긴다. 쿠키를 바꿀 때는 이미 나간 쿠키가 어떻게 남는지까지 생각해야 한다.
24. **5칸 패턴을 잊고 깊은 블로그 화면 만들기.** 블로그 안 경로는 이제 4칸까지다(5.10). `/@alpha/manage/a/b/c/d`처럼 깊은 화면을 만들면 새로고침에서 JSON 404가 난다([SPA와 서버 라우팅](./06-SPA와-서버-라우팅.md) 6장의 6칸 함정과 같다).
25. **Vite 개발 서버의 `/@` 경로와 겹치는 블로그 이름.** Vite 개발 서버는 `/@`로 시작하는 몇몇 경로를 자기 것으로 쓴다. 설치된 Vite 8.3.3 코드에서 `/@vite/client`, `/@vite/env`, `/@fs/`, `/@id/`를, `@vitejs/plugin-react`에서 `/@react-refresh`를 확인했다. `fs`, `id`는 4자보다 짧아 블로그 주소가 될 수 없지만, `vite`와 `react-refresh`는 주소 규칙에 맞고 예약어도 아니다. 그런 블로그를 **Vite 개발 서버(5173)에서** 열면 그 정확한 경로(예: 블로그 `react-refresh`의 첫 화면 `/@react-refresh`)는 Vite가 가져가 블로그 화면 대신 자바스크립트 파일이 나올 수 있다. 운영과 `:8080`(Spring이 직접 줌)에는 이런 일이 없다. 개발에서 불편하면 예약어에 넣는 방법이 있다(지금은 넣지 않았다).
26. **경로 방식이면 보안이 그대로라고 생각하기.** 쿠키·CSRF는 더 단순해졌지만, 모든 블로그가 한 출처가 되어 XSS 한 번의 피해가 전체로 커졌다(3.14).

**실습 6. dnsmasq로 바꾸기 (명령 모음)**

`/etc/hosts`에 블로그 주소를 하나씩 넣던 방식을 dnsmasq로 바꾸고, 옛 hosts 줄을 지운다. 위에서부터 차례로 실행한다.

```bash
# ── 1. dnsmasq 설치와 규칙 ─────────────────────────────
brew install dnsmasq
echo 'address=/blog.test/127.0.0.1' >> "$(brew --prefix)/etc/dnsmasq.conf"
printf 'listen-address=127.0.0.1\nbind-interfaces\n' >> "$(brew --prefix)/etc/dnsmasq.conf"   # 내 컴퓨터만
grep -E 'blog.test|listen-address|bind-interfaces' "$(brew --prefix)/etc/dnsmasq.conf"   # 세 줄이 보이면 됨

# ── 2. dnsmasq 켜기 (53번 포트를 쓰므로 sudo, 컴퓨터를 켤 때 자동 시작) ──
sudo brew services start dnsmasq
sudo brew services list | grep dnsmasq                  # started 이면 성공

# ── 3. *.blog.test 이름은 dnsmasq에 묻게 하기 ─────────
sudo mkdir -p /etc/resolver
echo 'nameserver 127.0.0.1' | sudo tee /etc/resolver/blog.test
scutil --dns | grep -A3 'domain   : blog.test'          # resolver 등록 확인
# 예전에 /etc/resolver/test로 만들었다면 둘 중 하나만 남긴다: sudo rm /etc/resolver/test

# ── 4. 기존 /etc/hosts의 blog.test 줄 되돌리기 ─────────
sudo cp /etc/hosts /etc/hosts.backup-$(date +%Y%m%d)    # 혹시 몰라 백업
grep -n 'blog\.test' /etc/hosts                         # 지울 줄 미리 보기
sudo sed -i '' '/blog\.test/d' /etc/hosts                # blog.test가 들어간 줄만 삭제
grep -c 'blog\.test' /etc/hosts                         # 0 이면 다 지워짐

# ── 5. 캐시 비우고 확인 ───────────────────────────────
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
ping -c 1 alpha.blog.test                              # 127.0.0.1에서 응답
ping -c 1 xyz-anything.blog.test                       # 처음 보는 이름도 127.0.0.1
dscacheutil -q host -a name myfirst.blog.test          # ip_address: 127.0.0.1
```

브라우저는 완전히 껐다 켜거나 시크릿 창으로 `http://{아무 블로그}.blog.test:8080`을 연다. `ERR_CONNECTION_REFUSED`가 나오면 DNS는 된 것이고 Spring 서버가 꺼져 있는 것이다(3.5 표).

**되돌리기 (dnsmasq를 그만 쓰고 hosts로 돌아갈 때)**

```bash
sudo brew services stop dnsmasq
sudo rm -f /etc/resolver/blog.test /etc/resolver/test
sudo sed -i '' -e '/address=\/blog.test\//d' -e '/^listen-address=127.0.0.1$/d' -e '/^bind-interfaces$/d' "$(brew --prefix)/etc/dnsmasq.conf"
sudo cp /etc/hosts.backup-YYYYMMDD /etc/hosts           # 4단계에서 만든 백업 날짜로
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
# brew uninstall dnsmasq                                # 아예 지우려면
```

(실습 7부터는 스텝 21의 경로 주소다.) 준비: `/etc/hosts`에 `127.0.0.1 blog.test` 한 줄(블로그마다 줄을 더할 필요가 없다), `docker compose up -d`, `./mvnw spring-boot:run`. 아래 `alpha`는 내가 가진 블로그 주소로 바꾼다.

**실습 9. 쿠키에 Domain이 없는지**

브라우저로 `http://blog.test:8080/login`에서 로그인 → 개발자 도구 → Application → Cookies → `http://blog.test:8080`. `access_token`의 Domain 칸이 `.blog.test`가 아니라 `blog.test`(앞 점 없음, host-only)인지 본다. Network 탭에서 로그인 응답의 `Set-Cookie`에 `Domain=`이 없는 것도 본다. 그다음 `/@alpha/manage`로 가서 로그인 상태가 이어지는지 본다. 6장 함정 23의 옛 쿠키가 보이면 지운다.

**실습 10. basename 링크 따라가기 (브라우저)**

이번 스텝에서 **브라우저로 눌러 보는 확인은 아직 하지 못했다**(서버 응답과 테스트로만 확인). 직접 해 본다.

1. `http://blog.test:8080/@alpha`를 연다. 글 제목, 카테고리, 태그, 방명록 링크를 차례로 누르며 주소창이 `/@alpha/…`로 바뀌는지, 새로고침해도 같은 화면인지 본다.
2. 관리 → 글쓰기 → 발행. 주소창이 `/@alpha/{새 번호}`가 되는지 본다.
3. 개발자 도구 Network에서 아무 `/api/…` 요청을 눌러 Request Headers에 `X-Blog-Address: alpha`가 있는지, 플랫폼 홈(`/`)의 `/api/home/posts`에는 없는지 본다.
4. 블로그 머리글의 "마이페이지"·로고(플랫폼 홈)를 눌러 `/me`, `/`로 가는지(`/@alpha/me`가 아닌지) 본다.
5. 글 상세의 "주소 복사"가 `http://blog.test:8080/@alpha/{번호}`를 복사하는지 본다.
6. 로그아웃 상태로 `/@alpha/manage`를 열어 로그인 화면으로 갔다가, 로그인 뒤 `/@alpha/manage`로 돌아오는지 본다(`safeRedirect`).

**실습 11. 공유 미리보기와 이사 301**

```bash
curl -s http://blog.test:8080/@alpha/{공개 글 번호} | grep -o '<meta property="og:\(url\|image\)"[^>]*>'
# <meta property="og:url" content="http://blog.test:8080/@alpha/{번호}">
# <meta property="og:image" content="http://blog.test:8080/uploads/….">   (사진이 있는 글이면, /@alpha 없음)
```

블로그 이사를 해 봤다면 `curl -sI 'http://blog.test:8080/@옛주소/category/3?page=2' | grep -i '^location'` → `http://blog.test:8080/@새주소/category/3?page=2`.

**실습 12. 운영 주소 확인 (배포 뒤)**

`http://now-log.java21.net/@{주소}`를 열고, 글 저장 응답의 `url`과 알림 링크가 `http://now-log.java21.net/@…`인지(포트 `:8460`이 붙지 않았는지) 본다. 붙어 있다면 학교 nginx가 `X-Forwarded-*` 헤더를 넘기지 않는 것이다(5.8).

**실습 13. 패턴 함정 재현**

`SpaForwardController`의 태그 줄 `"/{s1:@[^.]+}/tag/{name:.+}"`를 `"/{s1:@[^/.]+}/tag/{name:.+}"`로 바꾸고 `./mvnw test -Dtest=SpaForwardIntegrationTest`를 돌린다. 컨텍스트가 뜨지 않으며 원인에 패턴 오류가 보인다. 되돌린다.

## 8. 확인 문제

1. `alpha.blog.com`에서 TLD, 2단계 도메인, 서브도메인은 각각 무엇인가?
<details><summary>답 보기</summary>TLD는 <code>com</code>, 2단계 도메인은 <code>blog</code>(<code>blog.com</code>), 서브도메인은 <code>alpha</code>다.</details>

2. 블로그가 1만 개인데 DNS 레코드는 몇 개면 되나? 어떻게?
<details><summary>답 보기</summary>와일드카드 레코드 <code>*.blog.com A {서버 IP}</code> 한 줄(플랫폼용 <code>blog.com</code> 레코드까지 두 줄)이면 된다. 블로그가 실제로 있는지는 서버가 DB로 판단한다.</details>

3. DNS는 `alpha.blog.com`과 `beta.blog.com`의 요청을 구분해 주나? 서버는 무엇으로 구분하나?
<details><summary>답 보기</summary>DNS는 둘 다 같은 IP를 알려 줄 뿐 구분하지 않는다. 서버는 HTTP 요청의 Host 헤더(서블릿의 <code>getServerName()</code>)로 구분한다.</details>

4. `host.endsWith("blog.com")`으로 검사하면 어떤 문제가 생기나?
<details><summary>답 보기</summary><code>evilblog.com</code>처럼 남의 도메인도 <code>blog.com</code>으로 끝나서 통과한다. 앞에 점을 붙여 <code>".blog.com"</code>으로 검사해야 한다.</details>

5. 정규식 `^[a-z0-9][a-z0-9-]{2,30}[a-z0-9]$`가 받는 길이는? `abc`와 `ab-`는 통과하나?
<details><summary>답 보기</summary>4~32자다. <code>abc</code>는 3자라 실패, <code>ab-</code>는 3자이고 하이픈으로 끝나서 실패한다.</details>

6. 없는 블로그와 이용 제한된 블로그(남이 볼 때)에 각각 몇을 주나? 왜 같게 주나?
<details><summary>답 보기</summary>둘 다 404다. 403을 주면 "그 주소에 블로그가 있다"는 정보가 새므로, 존재를 숨기기 위해 같은 응답을 준다(헌법 II).</details>

7. 로컬 개발에서 `alpha.localhost` 대신 hosts에 `alpha.blog.test`를 적는 이유는?
<details><summary>답 보기</summary>모든 블로그 주소가 <code>Domain=.blog.test</code> 로그인 쿠키를 공유해야 하는데, <code>localhost</code>의 하위 도메인 쿠키 공유는 브라우저마다 동작이 달라 운영과 같은 구조로 확인할 수 없기 때문이다.</details>

8. Vite 프록시에서 `changeOrigin: true`를 켜면 블로그 API가 왜 깨지나?
<details><summary>답 보기</summary>프록시가 Host 헤더를 대상 서버 주소(<code>localhost:8080</code>)로 바꿔 보내서, 백엔드가 서브도메인을 읽지 못해 플랫폼이나 알 수 없는 주소로 판단하기 때문이다.</details>

9. 브라우저가 `DNS_PROBE_FINISHED_NXDOMAIN`을 낼 때 서버 로그에 아무것도 없는 이유는?
<details><summary>답 보기</summary>이름을 IP로 바꾸는 단계(DNS)에서 실패해 요청이 서버에 닿지도 않았기 때문이다. 서버의 Host 해석(BlogHostResolver)은 그다음 단계라 이 오류와 관계없다.</details>

10. dnsmasq를 설치하고 규칙을 넣었는데도 `alpha.blog.test`가 열리지 않는다. 무엇을 빠뜨렸을 가능성이 큰가?
<details><summary>답 보기</summary><code>/etc/resolver/blog.test</code>(내용 <code>nameserver 127.0.0.1</code>)를 만들지 않아 macOS가 <code>*.blog.test</code> 이름을 dnsmasq에 묻지 않는 경우다. 또는 dnsmasq가 켜지지 않았거나(<code>sudo brew services list</code>), 예전 답이 캐시에 남아 있는 경우다.</details>

11. 실제 배포에서 블로그 1만 개를 HTTPS로 열려면 DNS와 인증서에 각각 무엇이 필요한가?
<details><summary>답 보기</summary>DNS에는 <code>*</code> A 레코드 한 줄(플랫폼용 <code>@</code> 포함), 인증서는 <code>*.blog.com</code> 와일드카드 인증서 하나다. Let's Encrypt라면 DNS-01 방식(TXT 레코드로 소유 증명)으로 받는다.</details>

12. `/etc/resolver/blog.test`와 dnsmasq의 `address=/blog.test/127.0.0.1`은 각각 무엇을 정하나?
<details><summary>답 보기</summary><code>/etc/resolver/blog.test</code>는 macOS가 어떤 이름을 dnsmasq에 물을지(<code>*.blog.test</code>만)를 정하고, dnsmasq 규칙은 물어 온 이름에 뭐라고 답할지(127.0.0.1)를 정한다. 와일드카드 답은 dnsmasq 규칙이 한다.</details>

13. dnsmasq를 켜 둔 채 Spring 서버를 끄고 블로그 주소를 열면 어떤 오류가 나고, NXDOMAIN과 무엇이 다른가?
<details><summary>답 보기</summary><code>ERR_CONNECTION_REFUSED</code>다. 이름은 127.0.0.1로 찾았지만 8080번에서 받는 프로그램이 없다는 뜻이다. NXDOMAIN은 이름 찾기 자체가 실패한 것이다.</details>

14. (스텝 15) `GET /api/search` 메서드에 `@CurrentBlog Blog blog` 인자를 쓰지 못한 이유는?
<details><summary>답 보기</summary>같은 경로가 플랫폼 주소에서는 전체 검색이다. @CurrentBlog는 인자를 만들 때 Host의 블로그를 찾고 없으면 404를 던지므로, 플랫폼 주소의 요청까지 404가 된다. 그래서 Host를 먼저 보고, 블로그 주소일 때만 같은 판단(resolve)을 직접 부른다.</details>

15. 서브도메인 블로그 주소를 배포 서버에서 쓸 수 없었던 이유는? 서버 코드로 해결할 수 없는 이유는?
<details><summary>답 보기</summary>배포 서버(학교 nginx, <code>now-log.java21.net</code>)는 이름이 하나뿐이고 와일드카드 DNS(<code>*.now-log.java21.net</code>)가 없다. <code>alpha.now-log.java21.net</code>은 DNS에서 이름을 찾지 못해 요청이 서버에 닿지도 않으므로, 서버 코드로는 고칠 수 없다(nginx의 <code>server_name</code>과 HTTPS 와일드카드 인증서도 학교 쪽 설정이다).</details>

16. 블로그 경로에 `@`를 붙인 이유는?
<details><summary>답 보기</summary>블로그 주소는 영문 소문자·숫자·하이픈만 쓰므로 <code>@</code>로 시작하는 첫 칸은 블로그만 쓴다. 그래서 <code>/login</code>, <code>/me</code> 같은 플랫폼 경로와, 앞으로 더할 플랫폼 경로와도 부딪히지 않는다.</details>

17. API에 블로그를 알리는 방법으로 `X-Blog-Address` 헤더(①안)를 고르고 `/api/blogs/{주소}/…`(②안)를 고르지 않은 이유는? ①안이 대신 떠안은 단점 하나는?
<details><summary>답 보기</summary>블로그 API는 모두 <code>@CurrentBlog</code> 인자 해석기 한 곳에서 블로그를 받으므로, 그곳이 Host 대신 헤더를 읽게 하면 59개 API의 경로·계약·테스트가 그대로다. ②안은 그 모두를 바꿔야 한다. 대신 주소만 보고는 어느 블로그인지 알 수 없어서, 로그를 볼 때 헷갈리거나 HTTP 캐시를 쓰면 <code>Vary: X-Blog-Address</code>가 필요하다.</details>

18. 누구나 `X-Blog-Address`를 마음대로 붙일 수 있는데 괜찮은 이유는?
<details><summary>답 보기</summary>헤더는 어느 블로그에 대한 요청인지 고르는 값일 뿐 권한이 아니다. 주소창에 다른 블로그 주소를 치는 것과 같다. 고른 뒤에 서버가 로그인 쿠키로 가시성(볼 수 있나)과 주인 여부를 따로 검사한다. 예전 Host 헤더도 마찬가지로 아무나 바꿀 수 있었다.</details>

19. 화면이 API에 `X-Blog-Address`·`X-Requested-With` 같은 사용자 지정 헤더를 붙여도 사전 요청(preflight)이 생기지 않는 이유는?
<details><summary>답 보기</summary>화면과 API가 같은 출처(같은 스킴·호스트·포트)이기 때문이다. 사전 요청은 다른 출처로 보내는 요청에만 있는 CORS 규칙이다. 개발에서 Vite를 써도 브라우저는 <code>blog.test:5173</code>의 <code>/api</code>를 부르고, Vite가 8080으로 넘기므로 브라우저 입장에서는 같은 출처다.</details>

20. 예전에는 로그인 쿠키에 `Domain=.blog.test`가 꼭 필요했고 지금은 필요 없는 이유는? 필요 없는데 남겨 두면 안 되는 이유는?
<details><summary>답 보기</summary>예전에는 로그인하는 플랫폼(<code>blog.test</code>)과 블로그(<code>alpha.blog.test</code>)가 다른 호스트라, host-only 쿠키면 블로그로 가는 순간 로그아웃 상태였다. 지금은 모두 한 호스트 아래 경로라 host-only 쿠키(<code>Path=/</code>)가 모든 화면에 간다. 도메인 쿠키는 그 아래 모든 호스트로 가므로, 같은 도메인 아래 다른 서비스가 생기면 로그인 쿠키가 거기에도 간다. 필요 없는 범위는 열지 않는다.</details>

21. 경로 방식으로 바뀌면서 XSS의 위험은 어떻게 달라졌나?
<details><summary>답 보기</summary>모든 블로그가 한 출처가 되었다. 한 블로그 글에서 스크립트가 돌면 같은 출처라서 <code>X-Requested-With</code>를 붙여 어떤 API든 로그인한 사람의 이름으로 부를 수 있다. 예전에는 블로그마다 출처가 달라 다른 블로그 API의 응답을 읽을 수 없었다. 그래서 본문 정화와 CSP가 더 중요해졌다.</details>

22. `<BrowserRouter basename="/@alpha">`에서 `<Link to="/manage">`는 어떤 주소가 되나? 블로그 화면에서 로그인 화면으로 갈 때 `<Link to="/login">`을 쓰면 안 되는 이유는?
<details><summary>답 보기</summary><code>/@alpha/manage</code>가 된다. 같은 이유로 <code>/login</code>도 <code>/@alpha/login</code>이 되어 블로그 라우터의 "없는 화면"이 뜬다. 플랫폼 화면은 다른 라우터라서 <code>platformUrl('/login')</code>로 만든 전체 주소를 <code>&lt;a href&gt;</code>로 열어 페이지를 새로 읽게 한다.</details>

23. 이사한 블로그의 301 주소를 `blogUrl(…, request.getRequestURI())`로 만들면 어떤 주소가 되나?
<details><summary>답 보기</summary><code>getRequestURI()</code>는 <code>/@old/category/3</code> 전체라서 <code>/@new/@old/category/3</code>이 된다. <code>@주소</code> 뒤의 블로그 안 경로(<code>/category/3</code>)만 넘겨야 <code>/@new/category/3</code>이 된다.</details>

24. 프론트의 `safeRedirect`가 `http://alpha.blog.test:5173/`과 `http://blog.test:8080/`(지금 페이지는 `http://blog.test:5173`)을 모두 막는 이유는?
<details><summary>답 보기</summary>같은 출처(스킴+호스트+포트)만 받기 때문이다. 앞의 것은 호스트가, 뒤의 것은 포트가 다르다. 블로그도 같은 출처 아래 경로라 "출처가 같은가" 하나로 충분하고, 호스트 이름 끝을 자르는 규칙이 필요 없어졌다.</details>

25. 경로 패턴의 `{이름:정규식}` 안에 `/`를 넣으면(실습 13의 `"/{s1:@[^/.]+}/tag/{name:.+}"`처럼) 서버가 뜨지 않는 이유와 고친 모양은?
<details><summary>답 보기</summary>Spring 경로 패턴 해석기는 <code>/</code>를 칸 나눔으로 읽어서, 중괄호 안의 <code>/</code> 때문에 변수가 닫히지 않은 것으로 보고 "Expected close capture character after variable name }" 오류를 낸다. <code>{…}</code>는 원래 한 칸만 맞추므로 <code>/</code>를 뺀 <code>{s1:@[^.]+}</code>로 충분하다.</details>

26. 글의 대표 사진 `/uploads/a.png`로 공유 미리보기 `og:image`를 만들 때 `blogUrl`이 아니라 `platformUrl`을 쓰는 이유는?
<details><summary>답 보기</summary><code>/@주소</code>는 블로그 화면 주소에만 붙는다. 사진은 블로그와 관계없이 플랫폼 아래 <code>/uploads/…</code>에서 나가므로, <code>blogUrl</code>로 만들면 <code>/@alpha/uploads/a.png</code>가 되어 404다. 서브도메인 때는 호스트만 바뀌어서 둘 다 맞았던 것이 경로 방식에서 갈라졌다.</details>

27. 예전 프론트의 `VITE_PLATFORM_DOMAIN ?? 'blog.test'`가 운영에서 어떤 문제를 일으켰을까? 지금은 왜 생기지 않나?
<details><summary>답 보기</summary>Vite는 <code>VITE_</code> 환경 변수를 빌드할 때 코드에 박는데, 배포용 Docker 빌드에서 이 값을 정하지 않아 기본값 <code>blog.test</code>가 들어갔을 것이다. 운영 화면의 로그인·블로그 링크가 모두 <code>http://blog.test/…</code>로 가서 깨진다. 지금은 모든 주소를 <code>location.origin</code>(지금 출처) 기준으로 만들어 설정이 필요 없고, 변수도 없앴다.</details>
