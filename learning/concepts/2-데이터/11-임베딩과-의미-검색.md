# 임베딩과 의미 검색: 비슷한 글 추천, 커밋 뒤 비동기 처리, 뜻으로 찾기

> 관련 스텝: [스텝 10](../../스텝-10.md) (T069a, T069b, T069c, T069d), [스텝 22](../../스텝-22.md) (T120, T121, T122), [스텝 23](../../스텝-23.md)(한 DB로 합침, T126) · 관련 개념: [Spring Boot 기초](../1-개발-환경과-배포/01-Spring-Boot-기초.md), [Flyway 마이그레이션](./02-Flyway-마이그레이션.md), [Docker와 서버](../1-개발-환경과-배포/03-Docker와-서버.md), [Spring 테스트](../1-개발-환경과-배포/04-Spring-테스트.md), [인가와 가시성](../3-보안/07-인가와-가시성.md), [트랜잭션과 동시성](./05-트랜잭션과-동시성.md), [블로그 안 검색 LIKE](./09-블로그-안-검색-LIKE.md), [캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md), [PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md), [Docker와 서버](../1-개발-환경과-배포/03-Docker와-서버.md)

이 문서는 세 문서를 합친 것이다. 순서대로 **비슷한 글 추천**(스텝 10, 임베딩·pgvector·Ollama) → **두 번째 DB와 커밋 뒤 비동기 처리**(스텝 10, 임베딩을 언제·어디에 저장하나) → **의미 검색**(스텝 22, 같은 임베딩을 검색에 쓰기)이다. 각 부분에 있던 안내를 그대로 둔다.

> **(비슷한 글 부분)** 스텝 10에서는 임베딩을 MySQL과 따로 떨어진 추천 전용 PostgreSQL에 두었다. 스텝 23부터는 주 DB가 PostgreSQL + pgvector 하나라서, 글과 임베딩이 같은 DB에 있고 가시성까지 한 쿼리로 거른다. 이 문서는 지금(한 DB) 코드 기준이고, 두 DB였던 때 이야기는 따로 표시했다.

> **(두 번째 DB와 비동기 부분, 3.8~3.13·5.8~5.14) 스텝 23 이후**: 두 번째 DB(추천용 PostgreSQL)는 주 DB에 합쳐져 없어졌다([PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md)). `@Bean(defaultCandidate = false)` DataSource와 DB별 Flyway는 이 문서로 공부하되, 지금 코드에는 없다. 커밋 뒤 비동기로 임베딩을 만드는 부분(이벤트, `@TransactionalEventListener`, `@Async`)은 그대로 쓴다.

> **(의미 검색 부분) 스텝 23 이후**: 주 DB를 PostgreSQL 하나로 합치면서(2026-10-13 지원 결정) 스텝 22의 "두 DB에서 뽑고 → 거르고 → 자르기"는 **글과 임베딩을 묶은 쿼리 한 번**(가시성 조건 + 기준값 + 거리 순 + 페이지)으로 바뀌었다. 블로그 안 검색의 "글 번호 목록 먼저 읽기"도 없어졌다. 기준값, 캐시, `text_version`은 그대로이고, `ef_search`는 주 DB 연결에서 `iterative_scan`과 함께 켠다. Ollama가 안 되면 503인 것은 같고, DB 오류는 다른 API처럼 500이 됐다. 이 부분은 지금(한 DB) 코드 기준이고, 스텝 22 때의 구조는 "스텝 22까지"로 표시해 남겼다. Criteria로 거리 함수를 부르는 요령은 [PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md) 5.6.

## 1. 이 문서로 배우는 것

**비슷한 글 추천(임베딩과 벡터 검색)**

- **임베딩(embedding)**: 글을 "뜻을 담은 숫자 벡터"로 바꾸는 것. 낱말이 달라도 뜻이 비슷하면 벡터가 가깝다
- 벡터가 "가깝다"를 재는 법: **코사인 유사도**와 **코사인 거리**, 정규화(길이 1)
- 낱말 검색(LIKE, [블로그 안 검색 LIKE](./09-블로그-안-검색-LIKE.md))과 벡터 검색의 차이
- **pgvector**: PostgreSQL에서 벡터를 저장하고 가까운 순으로 찾기(`vector(1024)`, `<=>`), **HNSW** 근사 최근접 이웃 인덱스
- **pgvector 이미지**: 컨테이너 이미지가 `postgres`가 아니라 `pgvector/pgvector:pg17`인 이유, 확장의 "설치"와 "켜기"
- **Ollama + bge-m3**: 내 컴퓨터에서 임베딩 모델 돌리기, `/api/embed` 호출
- **Ollama는 기다리는 서버다**: 모델 받기·서버 띄우기·메모리에 올리기·계산 요청이 각각 따로이고, 계산은 **앱이 API를 불러야** 일어난다. 이 프로젝트가 언제 부르나
- 임베딩을 만드는 **다른 방법들**(라이브러리, DB가 부르기, 앱 안에서 모델 실행, 외부 API)과 무엇이 다른가
- 추천 결과에서 **볼 수 없는 글 거르기**: 가시성 조건을 벡터 검색과 같은 쿼리에 건다
- 진짜 모델 없이 **가짜 임베딩으로 테스트**하는 법
- 화면: 비슷한 글 카드, 빈 배열이면 숨기기

**두 번째 DB와 커밋 뒤 비동기 처리**

- 한 애플리케이션이 **DB 두 개**(MySQL + PostgreSQL)를 쓰는 법: 자동 설정이 멈추지 않게 두 번째 `DataSource` 만들기(`@Bean(defaultCandidate = false)`, `@Qualifier`) (스텝 22까지)
- 두 번째 DB의 표를 **따로 된 Flyway**로 만들기(이력 표가 DB마다 따로) (스텝 22까지)
- 두 DB 사이에는 외래 키도, 한 트랜잭션도 없다는 것과 그 결과
- **도메인 이벤트**: 글 쓰기 기능이 추천 기능을 모르게 하면서 알리기(`ApplicationEventPublisher`)
- **`@TransactionalEventListener`**: 트랜잭션이 **커밋된 뒤에만** 이벤트를 받기
- **`@Async`**: 요청 스레드와 따로 돌리기, `@EnableAsync`, 프록시라서 생기는 함정
- 부가 기능이 실패해도 본 기능을 막지 않기, 서버가 뜰 때 빠진 것 채우기
- 테스트: 컨테이너를 하나 더 띄우고 설정값으로 이어 주기(`DynamicPropertyRegistrar`), 비동기 결과 기다리기

**의미 검색**

- **의미 검색**(semantic search)이 글자 검색(`LIKE`)과 무엇이 다른가
- 검색어도 글과 **같은 모델로** 임베딩해야 하는 이유
- **유사도 기준값**(threshold)을 왜 두고, 어떻게 정했나(실제로 재 본 숫자)
- 가시성 조건을 벡터 검색과 **같은 쿼리**에 거는 법, 그리고 스텝 22의 두 DB 방식(**뽑고 → 거르고 → 자르기**)과 비교
- 블로그 안 검색: 블로그 조건도 같은 쿼리에(스텝 22에서는 "범위를 먼저 정하고 그 안에서 찾기")
- pgvector HNSW 인덱스의 **`hnsw.ef_search`**와 **`hnsw.iterative_scan`**: 결과가 40개에서 끊기거나, 걸러져서 모자라는 함정
- 검색어 임베딩을 **캐시**하는 이유와 `@Cacheable`을 따로 된 부품에 두는 이유
- 임베딩에 넣는 글자를 바꿨을 때 **옛 임베딩을 다시 만드는 법**(`text_version`)
- 의미 검색이 안 될 때 몰래 글자 검색으로 바꾸지 않는 이유(503)
- 검색어를 바꿀 때 Ollama를 **요청 안에서** 부르는 이유(글 임베딩은 커밋 뒤 비동기, 아래 5.11)

**먼저 알면 좋은 것**: 글 가시성 조건 `visibleTo`([인가와 가시성](../3-보안/07-인가와-가시성.md)), 블로그 안 검색의 LIKE와 가시성([블로그 안 검색 LIKE](./09-블로그-안-검색-LIKE.md)), "후보를 넉넉히 두고 읽을 때 가시성 확인"이라는 인기 글의 방식([캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md) 5.4), 빈과 자동 설정([Spring Boot 기초](../1-개발-환경과-배포/01-Spring-Boot-기초.md)), Flyway([Flyway 마이그레이션](./02-Flyway-마이그레이션.md)), docker compose([Docker와 서버](../1-개발-환경과-배포/03-Docker와-서버.md)), Testcontainers([Spring 테스트](../1-개발-환경과-배포/04-Spring-테스트.md)), `@Transactional`과 커밋([트랜잭션과 동시성](./05-트랜잭션과-동시성.md)), 프록시로 동작하는 어노테이션([캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md) 3.5), 한 DB로 합친 이유([PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md)).

## 2. 왜 필요한가

**비슷한 글 추천.** OWN-06 "글 상세 아래에 내용이 비슷한 글을 추천한다."

"비슷하다"를 낱말로 판단하면 한계가 뚜렷하다. "Spring Security 필터 체인"과 "스프링 시큐리티로 로그인 토큰 검증"은 겹치는 낱말이 거의 없다(영어·한국어 표기도 다르다). LIKE나 태그로는 둘을 이을 수 없다.

임베딩 모델은 글을 수백~수천 개의 숫자로 바꾸는데, 이 숫자들이 **뜻**을 담도록 학습되어 있다. 뜻이 비슷한 글은 숫자 벡터도 비슷한 방향을 가리킨다. 스텝 10을 만들며 실제로 재 본 값(bge-m3, 1에 가까울수록 비슷):

| 비교 | 코사인 유사도 |
| --- | --- |
| "Spring Security 필터 체인과 JWT 인증 정리" ↔ "스프링 시큐리티로 로그인 토큰 검증하기" | 0.580 |
| "Spring Security 필터 체인과 JWT 인증 정리" ↔ "제주도 3박 4일 여행 맛집 코스" | 0.353 |

겹치는 낱말이 없는데도 보안 글끼리 더 가깝다.

**임베딩을 어디에, 언제 만드나.** 스텝 10에서 비슷한 글 추천은 글 임베딩을 PostgreSQL(pgvector)에 두었고, 주 데이터는 MySQL이었다. 그래서 두 가지 문제가 생겼다.

1. **DB 두 개**: Spring Boot는 `spring.datasource.*`로 DB 하나를 자동으로 만들어 준다. 그런데 `DataSource` 빈을 하나 더 만들면 "사용자가 직접 만들었구나" 하고 **자동 설정을 멈춘다.** 그러면 MySQL·JPA·Flyway가 모두 흔들린다. (스텝 23에서 DB를 하나로 합치며 이 문제는 없어졌다.)
2. **언제 임베딩을 만드나**: 글을 저장할 때 바로 Ollama를 부르면, 글 저장 응답이 모델 계산(첫 호출 2초)을 기다린다. Ollama가 꺼져 있으면 글 저장까지 실패한다. 그리고 글 쓰기 코드(`post/`)가 추천(`recommend/`)을 직접 부르면, 추천을 빼고 싶을 때 글 쓰기 코드를 고쳐야 한다(명세는 "통째로 빼도 됨"). 이 문제는 지금도 그대로라서, 커밋 뒤 비동기 처리를 지금도 쓴다.

**의미 검색.** 글자 검색은 **낱말이 들어 있는 글**만 찾는다. "자바 공부"로 찾으면 제목이나 본문에 "자바"와 "공부"가 그대로 있어야 한다. 그런데 사람이 찾고 싶은 건 낱말이 아니라 **주제**인 경우가 많다.

| 검색어 | 찾고 싶은 글 | 글자 검색 | 의미 검색 |
| --- | --- | --- | --- |
| 자바 공부 | "스프링 부트 입문기" | 못 찾음(낱말 없음) | 찾음 |
| 데이터베이스 성능 | "MySQL 인덱스 공부" | 못 찾음 | 찾음 |
| 반려동물 | "강아지 산책 일기" | 못 찾음 | 찾음 |
| JPA N+1 | "JPA N+1과 fetch join" | 찾음 | 찾음 |

비슷한 글 추천(스텝 10, OWN-06)을 만들면서 글마다 **임베딩**(뜻을 숫자 1,024개로 나타낸 것)을 이미 만들어 두었다. 의미 검색은 같은 임베딩을 다시 쓴다. "이 글과 가까운 글"을 찾던 것을 "**이 검색어와** 가까운 글"로 바꾸는 것이다.

반대로 의미 검색이 약한 곳도 있다. 정확한 낱말(예: 에러 메시지, 사람 이름, 버전 번호)은 글자 검색이 낫다. 그래서 이 프로젝트는 둘을 **탭으로 나눠** 사용자가 고르게 했다(2026-10-13 지원 결정).

## 3. 기본 개념

3.1~3.7은 임베딩과 벡터 검색, 3.8~3.13은 두 번째 DB와 커밋 뒤 비동기 처리, 3.14~3.23은 의미 검색이다.

### 3.1 벡터와 임베딩

**벡터**는 숫자를 줄지어 놓은 것이다. `[0.12, -0.03, 0.88, …]`. 칸 수를 **차원**이라 한다. bge-m3는 글 하나를 **1024차원** 벡터로 바꾼다.

**임베딩 모델**은 글 → 벡터 함수다. 같은 모델이면 같은 글은 늘 같은 벡터가 된다. 다른 모델의 벡터끼리는 비교할 수 없다(칸마다 뜻이 다르다). 그래서 모델을 바꾸면 모든 글의 임베딩을 다시 만들어야 한다.

### 3.2 가까움 재기: 코사인

두 벡터 `a`, `b`가 얼마나 같은 방향인지는 **코사인 유사도**로 잰다.

```
cos(a, b) = (a · b) / (|a| × |b|)        a · b = Σ aᵢ × bᵢ (내적), |a| = √(Σ aᵢ²) (길이)
```

- 1이면 같은 방향(아주 비슷), 0이면 직각(관계없음), -1이면 반대.
- 벡터의 **길이를 1로 맞춰 두면**(정규화) 분모가 1이라 코사인 유사도 = 내적이다. bge-m3가 돌려주는 벡터는 이미 길이가 1이었다(직접 확인: `1.0`).

pgvector는 "작을수록 가까운" **거리**로 정렬한다. 코사인 거리 = `1 - 코사인 유사도`. 0이면 같고, 2면 정반대다.

| pgvector 연산자 | 뜻 |
| --- | --- |
| `<->` | 유클리드(L2) 거리 |
| `<#>` | 내적의 음수(정렬용) |
| `<=>` | **코사인 거리** (이 프로젝트) |

### 3.3 낱말 검색과 벡터 검색

| | LIKE·태그 ([블로그 안 검색 LIKE](./09-블로그-안-검색-LIKE.md)) | 벡터 검색 |
| --- | --- | --- |
| 무엇을 보나 | 글자가 들어 있나 | 뜻이 가까운가 |
| "스프링"으로 "Spring" 찾기 | 못 함 | 됨 |
| 결과 | 맞다/아니다 | 가까운 순서 |
| 비용 | 싸다 | 글마다 모델 계산이 필요(저장할 때 한 번) |
| 쓰임 | 사용자가 친 검색어 찾기 | 추천, "이런 글은 어때요" |

검색창은 사용자가 원하는 낱말이 정확히 들어간 글을 찾는 게 맞아 LIKE를 그대로 둔다. 추천은 뜻이 비슷한 글이 필요해 임베딩을 쓴다. (스텝 22부터는 검색창에도 "의미로 찾기" 탭을 더했다. 3.14부터.)

### 3.4 pgvector와 HNSW

**pgvector**는 PostgreSQL 확장이다. `CREATE EXTENSION vector`로 켜면 `vector(n)` 칸 타입과 거리 연산자가 생긴다.

```sql
SELECT post_id FROM post_embedding ORDER BY embedding <=> :나의벡터 LIMIT 30;
```

행이 많아지면 모든 행과 거리를 재는 것이 느리다. **HNSW**(Hierarchical Navigable Small World)는 가까운 벡터끼리 여러 층의 그래프로 이어 두고, 위층에서 크게 건너뛰다 아래층에서 좁혀 가며 찾는 인덱스다. **근사**(approximate)라서 아주 드물게 진짜 가장 가까운 것을 놓칠 수 있지만, 훨씬 빠르다. 추천에는 그 정도 오차가 문제되지 않는다.

```sql
CREATE INDEX ... ON post_embedding USING hnsw (embedding vector_cosine_ops);
```

`vector_cosine_ops`는 "코사인 거리로 찾는 인덱스"라는 뜻이다. 쿼리의 연산자(`<=>`)와 맞아야 인덱스를 쓴다. 행이 적으면 PostgreSQL이 인덱스 대신 전부 읽는 편을 고르기도 한다.

**확장은 "설치"와 "켜기"가 따로다.**

| 단계 | 무엇 | 이 프로젝트에서 누가 |
| --- | --- | --- |
| 설치 | 확장 파일(프로그램)이 DB 서버에 들어 있다 | 컨테이너 이미지 `pgvector/pgvector:pg17` |
| 켜기 | 그 DB 안에서 쓰겠다고 등록한다. 그때 `vector` 타입·연산자가 생긴다 | Flyway가 처음 돌 때 `V1__init.sql`의 `CREATE EXTENSION IF NOT EXISTS vector` |

공식 `postgres:17` 이미지에는 pgvector가 **설치돼 있지 않아서** `CREATE EXTENSION vector`가 "확장을 찾을 수 없다"며 실패한다. 직접 설치하려면 Dockerfile로 이미지를 새로 만들어 패키지를 넣어야 한다. `pgvector/pgvector:pg17`은 pgvector 프로젝트가 **공식 PostgreSQL 17 이미지 위에 pgvector를 설치해 둔 이미지**다. 그래서 `docker ps`의 IMAGE 칸이 `postgres`가 아니라 `pgvector/...`로 보여도 안에서 도는 것은 PostgreSQL 17 그대로다. 접속(`psql`), 환경 변수(`POSTGRES_USER` 등), 데이터 폴더도 공식 이미지와 같다. `citext`는 PostgreSQL에 딸려 오는 확장이라 공식 이미지에도 설치돼 있고, 같은 `V1__init.sql`에서 켠다.

왜 MySQL이 아니라 PostgreSQL인가: 처음 설계(research R-02)에서 벡터 검색은 pgvector로 하기로 정했다. 스텝 22까지는 주 데이터를 MySQL에 두고 PostgreSQL에는 글 번호와 임베딩만 두었다(추천은 도전 과제라 일정이 밀리면 기능째 뺄 수 있게 떼어 둠, 두 DB를 함께 쓰는 법은 아래 3.8~3.10). 스텝 23에서 주 DB를 PostgreSQL 하나로 합쳤다. 이유와 옮긴 방법은 [PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md).

### 3.5 Ollama와 bge-m3

**Ollama**는 언어·임베딩 모델을 내 컴퓨터에서 돌려 HTTP API로 내주는 프로그램이다. 이 프로젝트는 docker compose의 `ollama` 서비스로 띄우고, 지원이 이미 받아 둔 docker 볼륨(`ollama`)의 모델을 쓴다.

**bge-m3**: 100개가 넘는 언어를 다루는 다국어 임베딩 모델. 한국어·영어가 섞인 글도 같은 공간의 벡터로 바꾼다. 1024차원.

외부 API(Voyage, OpenAI)를 고르지 않은 이유(지원 결정, R-02): API 키와 비용이 없고, **글 내용이 밖으로 나가지 않는다**. 비공개 글도 임베딩을 만들어 둘 수 있다(추천할 때 거른다).

```
POST http://localhost:11434/api/embed
{ "model": "bge-m3", "input": "스프링 시큐리티 필터 체인 정리" }
→ { "embeddings": [[0.0123, -0.0456, ...1024개...]], ... }
```

첫 호출은 모델을 메모리에 올리느라 2초쯤 걸렸고, 그다음은 짧은 글이면 금방이다.

**Ollama는 스스로 아무것도 하지 않는다.** DB 서버가 쿼리를 받아야 일하듯, Ollama도 요청을 받아야 계산한다. "모델이 있다"와 "임베딩이 만들어진다" 사이에는 네 단계가 따로 있다.

| 단계 | 하는 일 | 이 프로젝트에서 누가·언제 |
| --- | --- | --- |
| ① 모델 받기 | 모델 파일(bge-m3 약 1.2GB)을 내려받아 볼륨에 둔다. **실행은 아니다** | 운영: `deploy.sh`의 `ollama pull bge-m3`(이미 있으면 바로 끝남). 개발: 지원이 받아 둔 docker 볼륨 `ollama` |
| ② 서버 띄우기 | `ollama serve`가 11434 포트에서 요청을 기다린다 | 컨테이너가 뜰 때(이미지의 기본 명령, `docker ps`의 COMMAND 칸 `/bin/ollama serve`) |
| ③ 모델 올리기 | 요청이 오면 그 모델을 메모리에 올린다. 한동안 요청이 없으면 다시 내린다(Ollama 기본 5분, 요청의 `keep_alive`로 바꿀 수 있다. 이 프로젝트는 기본값) | Ollama가 알아서. 첫 호출이나 오래 쉰 뒤 호출이 느린 이유 |
| ④ 계산 | 글자를 받아 벡터를 돌려준다 | **앱이 `POST /api/embed`를 부를 때만** |

그래서 "Ollama를 띄워 두면 글이 알아서 임베딩된다"는 틀린 생각이다. **언제 무엇을 보낼지는 앱이 정해야 한다.** 이 프로젝트가 정한 때는 4장과 5.11.

### 3.6 추천에서 볼 수 없는 글 빼기

임베딩 표에는 **모든 발행 글**(비공개·숨긴 글 포함)이 있다. 그래서 가장 가까운 글이 비공개일 수 있다. 헌법 원칙 II(볼 수 없는 글은 추천에서도 빠짐, spec "볼 수 없는 글" 표)를 지키려면 가시성으로 걸러야 한다.

- **지금(스텝 23부터, 한 DB)**: 글(`post`)과 임베딩(`post_embedding`)이 같은 DB에 있다. 그래서 "가까운 순"과 "보는 사람이 볼 수 있는 글(`visibleTo(viewerId)`)"을 **한 쿼리**에 건다(`PostEmbeddingRepository.findNear`, 5.17). 걸러진 다음에 `LIMIT size`를 하므로 볼 수 없는 글이 빠져도 늘 `size`개(기본 5)를 채운다.
- **스텝 22까지(두 DB)**: 두 DB는 서로 다른 서버라 조인할 수 없었다. 그래서 PostgreSQL에서 가까운 순 후보 30개를 넉넉히 뽑고(인기 글과 같은 요령, [캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md) 4.3), MySQL에서 그중 볼 수 있는 글만 읽어 후보 순서대로 `size`개를 잘랐다. 볼 수 없는 글이 30개 넘게 몰려 있으면 모자랄 수 있었다.

### 3.7 임베딩을 만드는 다른 방법

어느 방법이든 **누군가는 모델을 불러야** 한다. 방법마다 "누가, 어디서 부르나"가 다르다.

| 방법 | 누가 부르나 | 좋은 점 | 대가 |
| --- | --- | --- | --- |
| **이 프로젝트: 앱이 HTTP로 직접** (`RestClient` → Ollama `/api/embed`) | 앱 | 코드가 짧고 동작이 다 보인다. 언제 부를지(커밋 뒤, 서버 시작 때)를 앱이 정확히 정한다 | 모델 서버를 따로 띄워야 한다 |
| **라이브러리가 대신** (Spring AI, LangChain4j의 임베딩 모델) | 앱(라이브러리 속에서 같은 HTTP 호출) | `EmbeddingModel` 같은 인터페이스 하나로 Ollama·OpenAI 등을 바꿔 끼운다 | 의존성이 늘고, Spring Boot 버전과 맞는 판을 골라야 한다. 이 프로젝트의 `EmbeddingClient` 인터페이스가 이미 같은 역할을 작게 한다 |
| **DB가 부르기** (예: Timescale의 pgai vectorizer) | DB 쪽 작업자 | 표의 행이 바뀌면 임베딩을 "알아서" 만든다 | 확장과 작업자를 더 띄워야 하고, 넣는 글자(제목·태그·본문)나 실패 처리를 앱 규칙대로 다루기 어렵다 |
| **앱 안에서 모델 실행** (ONNX Runtime 등) | 앱 JVM 안 | 모델 서버 컨테이너가 필요 없다 | 앱 메모리와 시작 시간이 크게 는다. bge-m3처럼 큰 모델은 부담이 크다 |
| **다른 모델 서버** (예: Hugging Face Text Embeddings Inference) | 앱 | 여러 글을 묶어 빠르게 처리한다 | Ollama 자리를 바꿀 뿐 여전히 API 호출이다 |
| **외부 API** (OpenAI, Voyage) | 앱 | 모델 서버를 운영하지 않는다 | API 키·비용, 글 내용이 밖으로 나간다. R-02에서 이 이유로 고르지 않았다 |

"자동으로" 되는 방법(DB가 부르기)도 결국 누군가 모델 API를 부르는 것이고, 그 "누군가"가 앱 밖으로 옮겨 갈 뿐이다. 이 프로젝트는 글이 적고, 넣는 글자와 실패 처리를 앱 규칙대로 하고 싶어서 앱이 직접 부른다.

### 3.8 DataSource와 자동 설정

(3.8~3.10은 스텝 22까지의 두 DB 구조 이야기다. 지금 코드에는 없다.)

**DataSource**는 DB 연결을 내주는 객체다(보통 연결 풀, 이 프로젝트는 HikariCP). JPA, `JdbcTemplate`, Flyway가 모두 이것을 주입받아 DB에 닿는다.

Spring Boot의 `DataSourceAutoConfiguration`은 "DataSource 빈이 **없으면** `spring.datasource.*`로 하나 만든다"(`@ConditionalOnMissingBean`)이다. 내가 하나 만들면 "있다"가 되어 자동 설정이 물러난다. 예전에는 그래서 DB 두 개를 쓰려면 주 DB까지 직접 만들고 `@Primary`를 붙여야 했다.

### 3.9 `@Bean(defaultCandidate = false)`

Spring Framework 6.2부터 `@Bean`에 `defaultCandidate = false`를 줄 수 있다. 이 빈은 **"타입만으로 고를 때의 후보"에서 빠진다.**

- `DataSource`를 타입으로 찾는 곳(JPA, Flyway, 자동 설정의 "있나?" 검사)에는 보이지 않는다. 그래서 주 DB 자동 설정이 그대로 돈다.
- 이 빈은 **이름표(`@Qualifier`)를 짚어야만** 주입된다.

```java
@Bean(defaultCandidate = false)
@Qualifier("recommend")
public HikariDataSource recommendDataSource(...) { ... }

// 쓰는 쪽
public PostEmbeddingRepository(@Qualifier("recommend") NamedParameterJdbcTemplate jdbc) { ... }
```

스텝 10에서 이렇게 만든 뒤 테스트를 돌려 보니, MySQL 마이그레이션 3개와 추천 DB 마이그레이션 1개가 따로 적용되고 JPA도 그대로 MySQL을 썼다.

### 3.10 DB 두 개 사이에 없는 것

- **외래 키**: `post_embedding.post_id`는 MySQL `post.id`를 가리키지만, 다른 DB라 외래 키를 걸 수 없다. 글을 지우면 **애플리케이션이** 임베딩도 지워야 한다. 지우다 실패해 남은 행은 나중에 정리한다(5.13 `sync`). (지금은 같은 DB라 외래 키를 건다, 5.1.)
- **한 트랜잭션**: MySQL 커밋과 PostgreSQL 쓰기를 하나로 묶을 수 없다(분산 트랜잭션은 이 규모에선 과하다). 그래서 "글 저장이 먼저 확실히 끝나고(커밋), 그다음 임베딩"으로 순서를 정한다. 임베딩이 실패해도 글은 저장돼 있고, 다음 기회(수정, 서버 시작)에 다시 만든다. 이렇게 "결국에는 맞춰지는" 방식을 **최종 일관성**(eventual consistency)이라 한다.
- **조인**: 두 DB의 표를 SQL 하나로 조인할 수 없다. 추천은 PostgreSQL에서 번호를 뽑고 MySQL에서 그 번호로 읽는 두 단계다(위 3.6의 "스텝 22까지").

### 3.11 도메인 이벤트

**이벤트**는 "이런 일이 일어났다"는 알림 객체다. 알리는 쪽은 **누가 듣는지 모른다.**

```java
// 글 쓰기 쪽 (post)
events.publishEvent(new PostContentChangedEvent(saved.getId()));

// 추천 쪽 (recommend)
@TransactionalEventListener
public void onContentChanged(PostContentChangedEvent event) { ... }
```

- `post` 패키지는 `recommend`를 import하지 않는다. 의존 방향이 `recommend → post`(추천이 글 이벤트를 안다) 하나뿐이다.
- 추천을 통째로 빼면 듣는 쪽만 사라지고 글 쓰기 코드는 그대로다.
- 이벤트는 레코드 하나(`PostContentChangedEvent(Long postId)`)다. 글 전체가 아니라 번호만 담는다. 받는 쪽이 필요할 때 최신 상태를 읽는다.

### 3.12 `@TransactionalEventListener`: 커밋된 뒤에만

평범한 `@EventListener`는 `publishEvent`를 부른 **그 자리에서 바로** 실행된다. 글 저장 트랜잭션이 아직 커밋되지 않은 상태다. 그러면:

- 그 뒤에 글 저장이 실패해 롤백되면, 없는 글의 임베딩을 만들어 버린다.
- 다른 스레드에서 글을 읽으면 아직 커밋 전이라 옛 내용(또는 없음)이 보인다(격리 수준, [트랜잭션과 동시성](./05-트랜잭션과-동시성.md)).

`@TransactionalEventListener`는 이벤트를 **트랜잭션이 끝날 때까지 미뤘다가** 정한 단계에 실행한다. 기본 단계가 `AFTER_COMMIT`이다. 커밋에 성공했을 때만 실행되고, 롤백되면 실행되지 않는다.

| 단계 | 언제 |
| --- | --- |
| `AFTER_COMMIT` (기본) | 커밋 성공 뒤 |
| `AFTER_ROLLBACK` | 롤백 뒤 |
| `AFTER_COMPLETION` | 어느 쪽이든 끝난 뒤 |
| `BEFORE_COMMIT` | 커밋 직전(아직 같은 트랜잭션) |

주의: 트랜잭션 **밖에서** 발행한 이벤트는 기본적으로 **아예 실행되지 않는다**(기다릴 커밋이 없어서). 그래서 이벤트는 `@Transactional` 메서드(`PostService.publish/edit/delete`) 안에서 발행한다. 트랜잭션 밖에서도 받고 싶으면 `fallbackExecution = true`를 준다.

일괄 삭제(`ManagePostService.delete`)는 바깥 트랜잭션 하나에서 `PostService.delete`를 여러 번 부른다([조건 목록과 일괄 처리](./10-조건-목록과-일괄-처리.md)). 이벤트도 여러 개 나가고, 바깥 트랜잭션이 커밋된 뒤 한꺼번에 처리된다.

### 3.13 `@Async`

`@Async`가 붙은 메서드는 **다른 스레드에서** 실행되고, 부른 쪽은 기다리지 않는다. `@EnableAsync`로 켜고, 스레드는 Spring Boot가 만들어 주는 실행기(`applicationTaskExecutor`, 스레드 풀)에서 나온다.

`@TransactionalEventListener` + `@Async`를 함께 쓰면: 커밋된 뒤, 요청 스레드가 아니라 다른 스레드에서 임베딩을 만든다. 글 저장 응답은 임베딩을 기다리지 않는다.

`@Async`도 `@Transactional`·`@Cacheable`처럼 **프록시**로 동작한다([캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md) 3.5). 같은 클래스 안에서 `this.method()`로 부르면 비동기가 되지 않는다. 그래서 이벤트 받기(`PostEmbeddingListener`)와 실제 일(`PostEmbeddingService`)을 다른 클래스로 나눴다.

비동기 메서드에서 난 예외는 부른 쪽에 전달되지 않는다(이미 응답이 나갔다). 그냥 두면 로그에만 남는다. 그래서 서비스 안에서 잡아 **경고로 남기고 넘어간다**(5.13).

### 3.14 검색어도 같은 모델로 임베딩한다

(3.14부터는 스텝 22의 의미 검색이다.)

임베딩은 모델마다 "숫자 공간"이 다르다. bge-m3로 만든 글 벡터와 다른 모델로 만든 검색어 벡터는 거리를 재도 뜻이 없다. 축(차원)의 의미가 서로 다르기 때문이다. 그래서 검색어도 **글과 같은 모델(bge-m3)**, 같은 방법(Ollama `/api/embed`)으로 바꾼다.

```
글   "스프링 부트 입문기\n태그: 자바\n…"  ──bge-m3──▶ [0.012, -0.031, …] (1024개, 길이 1)
검색어 "자바 공부"                         ──bge-m3──▶ [0.020, -0.015, …] (1024개, 길이 1)
                                       코사인 유사도 = 두 벡터의 내적 = 0.58
```

어떤 모델은 검색어 앞에 `query: ` 같은 표시를 붙이라고 한다(검색어용·문서용을 나눠 학습한 모델). bge-m3는 검색어에 표시를 붙이지 않고 그대로 넣는다.

### 3.15 코사인 유사도와 거리

위 3.2에서 본 것처럼, 길이가 1인 벡터 둘의 코사인 유사도는 내적이고, pgvector의 `<=>`는 **코사인 거리** = `1 - 코사인 유사도`다.

| | 같은 뜻 | 관계없음 | 반대 |
| --- | --- | --- | --- |
| 코사인 유사도 | 1 | 0 근처 | -1 |
| 코사인 거리 `<=>` | 0 | 1 근처 | 2 |

그래서 "유사도 0.40 이상"은 SQL에서 "거리 0.60 이하"(`<=> ... <= 0.60`)로 쓴다.

### 3.16 기준값(threshold): 의미 검색은 늘 무언가를 돌려준다

글자 검색은 낱말이 없으면 결과가 0개다. 의미 검색은 다르다. **가장 가까운 글은 언제나 있다.** "양자역학"으로 찾아도 이 블로그에서 그나마 가까운 글이 1등으로 나온다. 그대로 보여 주면 관계없는 글이 "검색 결과"처럼 보인다.

그래서 유사도가 기준값보다 낮은 글은 뺀다. 기준값은 모델마다 다르므로 **재 봐야** 한다. 2026-10-13 개발 Ollama(bge-m3)로 글 6개와 검색어 9개를 재 보니 이랬다.

| 검색어 | 스프링 입문기 | 객체지향 정리 | 제주 여행 | 김치찌개 | MySQL 인덱스 | 강아지 산책 |
| --- | --- | --- | --- | --- | --- | --- |
| 자바 공부 | **0.58** | **0.44** | 0.34 | 0.28 | 0.41 | 0.38 |
| 데이터베이스 성능 | 0.36 | 0.39 | 0.32 | 0.21 | **0.53** | 0.31 |
| 맛집 | 0.31 | 0.32 | **0.52** | **0.41** | 0.27 | 0.38 |
| 반려동물 | 0.26 | 0.28 | 0.34 | 0.31 | 0.27 | **0.50** |
| 양자역학 | 0.27 | 0.34 | 0.23 | 0.27 | 0.28 | 0.30 |

관련 있는 글은 0.42~0.58, 관련 없는 글은 0.21~0.39였다. 그 사이인 **0.40**을 기준값으로 정했다. 보이듯이 경계는 깔끔하지 않다("자바 공부"와 "MySQL 인덱스"가 0.41). bge-m3의 유사도는 0.2~0.6 사이에 몰려 있어서 숫자 차이가 작다. 기준값은 설정(`app.search.semantic.min-similarity`)으로 두고, 글이 쌓이면 다시 재서 고친다.

### 3.17 앞쪽만 쓸모 있다: 최대 결과 수

의미 검색 결과는 뒤로 갈수록 "덜 비슷한" 글이다. 50등, 100등 결과를 보는 사람은 거의 없다. 그래서 **가까운 순 100개까지만** 보고 그 안에서 10개씩 페이지를 나눈다(`max-results: 100`). 전체 수도 100을 넘지 않는다(조건에 맞는 글이 300개여도 "글 100개", 10쪽까지).

### 3.18 가시성은 같은 쿼리에서 건다

임베딩 표에는 **비공개·숨긴 글도** 들어 있다(글이 밖으로 나가지 않으니 모두 만들어 두고, 보여 줄 때 거른다). 거르지 않으면 남의 비공개 글 제목이 검색 결과로 새어 나간다. 이 프로젝트의 가장 중요한 규칙(볼 수 없는 글은 어디에도 안 보임, 헌법 II)이 깨진다.

**지금(스텝 23부터)**: 글과 임베딩이 같은 PostgreSQL에 있다. 그래서 한 쿼리에 모든 조건을 건다.

```
글 ⨝ 임베딩
  WHERE 보는 사람이 볼 수 있는 글(visibleTo)          ← 글 목록과 같은 조건 코드
    AND 거리 <= 0.60 (유사도 0.40 이상)
  ORDER BY 거리, 글 번호 DESC
  OFFSET (쪽-1)×10 LIMIT 10                            → [(12, 0.58), (31, 0.43), …]
```

걸러진 다음에 자르므로, 가까운 글 중 남의 비공개 글이 많아도 볼 수 있는 글로 쪽이 채워진다. 전체 수는 같은 조건의 `count`를 100과 비교해 작은 쪽이다(3.17).

**스텝 22까지(두 DB)**: 글은 MySQL, 임베딩은 PostgreSQL이라(위 3.8~3.10) 한 쿼리로 묶을 수 없었다. 그래서 순서를 셋으로 나눴다.

```
① 뽑기   PostgreSQL: 유사도 0.40 이상, 가까운 순 100개   → [(12, 0.58), (7, 0.44), (31, 0.43), …]
② 거르기  MySQL: 그중 보는 사람이 볼 수 있는 글만         → 12, 31 (7은 남의 비공개 글)
③ 자르기  ①의 순서를 지키며 page번째 10개                 → [(12, 0.58), (31, 0.43)]
```

②에서 빠진 글이 많으면 결과가 100개보다 적어졌다(가까운 100개 중 70개가 남의 비공개 글이면 30개). 의미 검색은 앞쪽만 보면 되므로 받아들인 한계였고, 한 DB가 되면서 없어졌다.

### 3.19 블로그 안 검색: 블로그 조건도 같은 쿼리에

임베딩 표는 **어느 블로그의 글인지 모른다**(`post_id`와 벡터뿐). 전체에서 가까운 100개를 뽑은 뒤 "이 블로그 것만" 거르면, 다른 블로그 글이 100개를 다 차지해 이 블로그 글이 하나도 안 남을 수 있다.

**지금**: 3.18의 가시성 조건 자리에 블로그 화면 목록과 같은 조건(`listedIn(blog, 보는 사람)`)을 넣는다. 글 표와 묶은 쿼리라 "이 블로그의 글"이 처음부터 조건에 들어 있어 위 문제가 생기지 않는다. 주인에게는 자기 비공개 글도 나온다(글자 검색과 같은 조건).

**스텝 22까지**: 임베딩 DB가 블로그를 몰라서 순서를 바꿨다. MySQL에서 **이 블로그의 볼 수 있는 글 번호를 먼저** 읽고, PostgreSQL에는 "이 번호들 안에서만 찾아라"(`post_id IN (…)`)라고 보냈다.

```
① 범위   MySQL: 이 블로그에서 보는 사람이 볼 수 있는 글 번호   → [3, 5, 8, 12, …]
② 뽑기   PostgreSQL: 그 번호 안에서 유사도 0.40 이상 가까운 순 100개
③ 다시 거르기·자르기 (①과 ③ 사이에 글이 비공개로 바뀌었을 수 있으니 한 번 더 본다)
```

글이 아주 많은 블로그라면 번호 목록이 길어지는 약점이 있었고, 한 DB가 되면서 없어졌다.

### 3.20 HNSW와 `hnsw.ef_search`: 40개에서 끊기는 함정

pgvector의 HNSW 인덱스는 **근사** 최근접 이웃 검색이다(3.4). 모든 벡터와 거리를 재지 않고, 그래프를 따라가며 "가까울 것 같은" 후보를 모은다. 이때 모으는 후보 목록의 크기가 `hnsw.ef_search`이고 **기본값은 40**이다.

함정은 이것이다. `LIMIT 100`으로 물어도 인덱스가 쓰이면 **최대 40개**만 돌아온다. 오류도 나지 않는다. 비슷한 글 추천은 30개만 뽑아서 문제가 없었지만, 의미 검색은 100개까지 본다. 그래서 DB 연결을 열 때마다 `SET hnsw.ef_search = 200`을 실행한다(`connection-init-sql`, 5.17). 스텝 22까지는 추천 DB 연결에만, 지금은 주 DB 연결에 건다.

글이 적을 때는 PostgreSQL이 인덱스를 쓰지 않고 표 전체를 읽기도 한다(그러면 40개 제한도 없다). 그래서 개발에서 잘 되다가 글이 많아진 운영에서만 결과가 줄어드는 식으로 드러나기 쉽다.

**같은 쿼리에서 거르면 생기는 두 번째 함정**: 인덱스는 먼저 가까운 후보를 `ef_search`개 모으고, 그다음에 가시성·기준값 조건으로 거른다. 후보 200개 중 상당수가 남의 비공개 글이면 걸러진 뒤 `LIMIT`을 못 채운다. pgvector 0.8부터 있는 `hnsw.iterative_scan`을 켜면 이때 인덱스를 **더 읽어** 채운다. `strict_order`는 더 읽어도 가까운 순서를 지키는 방식이다. 끝없이 읽지는 않고, 한도(`hnsw.max_scan_tuples`)까지 읽어도 모자라면 그만큼만 돌려준다. 스텝 22까지는 거르기를 다른 DB에서 해서 `ef_search` 하나로 충분했지만, 같은 쿼리에서 거르게 된 스텝 23부터 둘 다 켠다.

### 3.21 검색어 임베딩 캐시

검색어를 임베딩하는 데 개발 PC에서 처음엔 약 0.86초가 걸렸다. 같은 검색어로 2쪽, 3쪽을 누를 때마다 다시 계산할 이유가 없다. 그래서 Redis 캐시(5분, [캐시와 저장소 고르기](./12-캐시와-저장소-고르기.md))에 둔다. 두 번째부터는 0.03초였다.

`@Cacheable`은 **프록시**가 거는 것이다([예약 작업과 프록시](./14-예약-작업과-프록시.md), 위 3.13의 `@Async`와 같다). 같은 클래스 안의 메서드를 `this.embed()`로 부르면 프록시를 거치지 않아 캐시가 걸리지 않는다. 그래서 캐시를 거는 메서드를 따로 된 부품(`QueryEmbeddings`)에 둔다. 예외는 캐시하지 않는다. 임베딩 서버가 잠깐 꺼졌다 켜지면 다음 요청에서 다시 계산한다.

### 3.22 넣는 글자를 바꿨을 때: 버전 번호

임베딩은 "무엇을 넣었나"에 따라 달라진다. 이번에 넣는 글자를 `제목 + 본문`에서 `제목 + 태그 + 본문`으로 바꿨다. 이미 만든 임베딩은 옛 방식이라 그대로 두면 태그가 반영되지 않는다.

그래서 표에 `text_version`(넣는 글자 방식 번호)을 두었다. 코드의 `TEXT_VERSION`(지금 2)과 다른 행은 서버가 뜰 때 다시 만든다. 넣는 글자를 또 바꾸면 번호만 올리면 된다. 모델을 바꿀 때도 같은 생각을 쓸 수 있다(그때는 차원이 달라질 수 있어 표를 새로 만드는 편이 낫다).

태그는 글 저장 말고도 바뀐다. 태그 관리 화면에서 이름을 바꾸거나 지우면 그 태그가 달린 글들의 넣는 글자가 바뀐다. 그래서 그때도 "글 내용이 바뀌었다"는 이벤트를 글마다 보낸다.

### 3.23 안 될 때는 안 된다고 말한다

추천 기능을 꺼 둔 서버(1차 배포)나 Ollama가 꺼졌거나 실패한 경우, 의미 검색은 **503 `SEMANTIC_SEARCH_UNAVAILABLE`**("지금은 의미 검색을 쓸 수 없습니다. 글자로 찾기를 이용해 주세요.")을 돌려준다. 스텝 22까지는 추천 DB 오류도 503이었다. 지금은 임베딩이 주 DB에 있어서 DB 오류는 다른 API와 같은 500이다(주 DB가 죽으면 글자 검색도 안 되므로 "글자로 찾기를 이용해 주세요"가 맞지 않다). 몰래 글자 검색 결과를 돌려주지 않는 이유는, 사용자가 "의미로 찾기" 탭에서 본 결과를 의미 검색 결과로 믿기 때문이다. 결과의 순서도, "가까움" 점수도 달라서 섞으면 틀린 정보가 된다.

비슷한 글 추천은 반대로 빈 목록을 준다. 추천은 글 화면의 덧붙은 칸이라 비어 있어도 되지만, 검색은 사용자가 직접 요청한 일이라 실패를 알려야 한다.

```

[Ollama를 부르는 때 ③] 의미 검색 (요청 안에서)                                 [아래 의미 검색 흐름]
```

비슷한 글을 **보여 줄 때는 Ollama를 부르지 않는다.** 이미 저장해 둔 12번 글의 벡터를 꺼내 DB 안에서 거리만 잰다. 모델 계산은 글을 저장할 때 한 번이고, 그래서 추천 요청은 빠르다.

### 5.1 표: `src/main/resources/db/migration/V1__init.sql`

스텝 22까지는 추천 DB 전용 파일(`db/recommend/V1__post_embedding.sql`)에 있었다. 스텝 23에서 주 DB의 `V1__init.sql`(= 문서 저장소 `erd/schema.sql`) 하나로 합쳤다.

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS vector;
...
-- 글 임베딩 (비슷한 글 OWN-06, 의미 검색 OWN-07). 발행 글이면 공개 범위와 상관없이 두고, 볼 수 있는지는 찾을 때 거른다.
-- 글을 지우는 것은 소프트 삭제라 애플리케이션이 이 행도 지운다. 글 행이 정말 지워지면 외래 키가 함께 지운다.

    post_id      BIGINT PRIMARY KEY REFERENCES post (id) ON DELETE CASCADE,
    embedding    vector(1024) NOT NULL,
    text_version SMALLINT     NOT NULL,
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);
...
-- 코사인 거리(<=>)로 가까운 글을 찾는 근사 최근접 이웃 인덱스(HNSW)
CREATE INDEX idx_post_embedding_embedding ON post_embedding USING hnsw (embedding vector_cosine_ops);
```

- `CREATE EXTENSION ... vector`: 이미지에 설치된 pgvector를 이 DB에서 켠다(3.4). 이 줄이 표보다 먼저 와야 `vector(1024)` 타입을 쓸 수 있다.
- `post_id`는 `post.id`를 가리키는 **외래 키**다. 두 DB였을 때는 걸 수 없었지만(3.10) 지금은 같은 DB라 건다. 없는 글의 임베딩은 들어갈 수 없다. 다만 이 프로젝트의 글 삭제는 행을 지우지 않는 소프트 삭제라, `ON DELETE CASCADE`가 아니라 애플리케이션이 임베딩을 지운다(4장의 `onDeleted`).
- `vector(1024)`: 차원을 정해 둔다. 다른 차원의 벡터를 넣으면 오류다. 모델을 바꾸면 이 숫자도 바뀐다.
- `text_version`: 임베딩에 넣은 글자의 방식 번호(1 = 제목 + 본문, 2 = 제목 + 태그 + 본문). 지금 방식과 다르면 서버가 뜰 때 다시 만든다(3.22).

- 요청에 `keep_alive`를 넣지 않으므로 모델을 메모리에 두는 시간은 Ollama 기본값을 따른다(3.5 ③).
- `EmbeddingClient`는 인터페이스다. 테스트는 이 자리에 가짜를 넣는다(5.7). 나중에 외부 API나 Spring AI로 바꿔도 이 클래스만 바꾸면 된다(3.7).
- 이 클래스는 **어떻게** 부르는지만 안다. **언제** 부르는지는 5.11.

- 쓰기(`save`)는 JDBC로 SQL을 그대로 쓴다(`NamedParameterJdbcTemplate`, [통계와 순위](../5-기능-설계/07-통계와-순위.md) 3.5와 같은 방식). 벡터를 `'[0.1,0.2,…]'` 글자로 보내고 `CAST(... AS vector)`로 바꾼다(`toLiteral`).
- `ON CONFLICT (post_id) DO UPDATE`: PostgreSQL의 "있으면 바꾸고 없으면 넣기"(upsert). 글을 고쳐 다시 만들 때 같은 메서드를 쓴다. `EXCLUDED`는 넣으려던 새 값이다.
- 읽기(`findEmbedding`, `findNear`)는 JPA로 한다. 스텝 23에서 임베딩 표에도 엔티티(`PostEmbedding`)를 두었다. 그래야 글 목록과 **같은 가시성 코드**(`PostSpecifications.visibleTo`)를 벡터 검색 쿼리 안에 그대로 끼울 수 있다.
- `findNear`: 글(`post`)과 임베딩을 `embedding.postId = post.id`로 묶고, 가시성·자기 글 빼기 조건을 건 뒤 코사인 거리 순으로 `limit`개. 같은 거리면 최근 글(번호 큰 것)을 먼저 둬서 순서를 하나로 정한다. **비슷한 글과 의미 검색이 같이 쓴다.** Criteria에서 pgvector 거리 함수를 부르는 요령은 [PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md) 5.6.

### 5.4 `recommend/application/SimilarPostService.java`

```java
@Transactional(readOnly = true)
public List<Post> similar(Blog blog, Long postId, Long viewerId, int size) {
    postReadService.readable(blog, postId, viewerId);
    return postEmbeddingRepository.findEmbedding(postId)
            .map(embedding -> postEmbeddingRepository.findNear(embedding,
                    PostSpecifications.visibleTo(viewerId, LocalDateTime.now(clock)), null, postId,
                    0, size, "blog", "category"))
            .orElse(List.of())
            .stream()
            .map(NearPost::post)
            .toList();
}
```

- `readable`: 원래 글을 볼 수 없으면 추천도 404·403(글 상세와 같은 판단). 남의 비공개 글 번호로 "비슷한 글"을 물어 그 글이 무엇에 관한 것인지 짐작하는 길을 막는다.
- `findEmbedding(postId)`: 이 글의 저장된 벡터를 꺼낸다. **Ollama를 부르지 않는다.** 아직 없으면(방금 쓴 글이라 만드는 중, Ollama가 꺼져 있었음) 빈 목록이다(contracts "추천이 준비 안 됐으면 빈 배열").
- `findNear(벡터, visibleTo, null, postId, 0, size, ...)`: 유사도 기준 없이(`null`), 자기 글(`postId`)을 빼고, 볼 수 있는 글만 가까운 순 `size`개. `"blog", "category"`는 목록 한 줄에 나가는 연관을 같이 읽어 N+1을 막는다.
- `visibleTo(viewerId)`: **보는 사람 기준**이다. 구독자 공개 글은 구독자에게만 추천된다. 인기 글(모두에게 같은 공개 글, 비회원 기준)과 다른 점이다. 추천은 캐시하지 않으므로 사람마다 달라도 된다.
- 블로그 조건이 없다. **다른 블로그의 글도** 추천한다(contracts "다른 블로그 포함").
- 스텝 22까지는 후보 30개를 뽑아 `Map`에 넣고 후보 순서대로 다시 꺼내는 코드였다(3.6). 한 쿼리가 되면서 그 요령이 필요 없어졌다.

### 5.7 가짜 임베딩으로 테스트: `TestRecommendConfiguration`

진짜 모델로 테스트하면 Ollama를 띄워야 하고, 느리고, 결과가 모델에 따라 조금씩 다르다. 테스트에는 **뜻이 아니라 낱말로 가까워지는** 가짜를 쓴다.

```java
public static float[] bagOfWords(String text) {
    float[] vector = new float[DIMENSIONS];
    for (String word : text.toLowerCase(Locale.ROOT).split("[^\\p{L}\\p{N}]+")) {
        if (!word.isEmpty()) {
            vector[Math.floorMod(word.hashCode(), DIMENSIONS)] += 1;
        }
    }
    ... 길이 1로 맞춤
}
```

- **낱말 주머니(bag of words)**: 낱말마다 해시로 칸 하나를 골라 1을 더한다. 겹치는 낱말이 많을수록 같은 칸이 커져 코사인이 커진다. 1024차원이라 표(`vector(1024)`)에 그대로 들어간다.
- `@Primary`로 등록해 진짜 `OllamaEmbeddingClient` 대신 주입된다. 테스트는 "가까운 순, 비공개 제외, 다른 블로그 포함" 같은 **우리 코드의 규칙**을 확인하는 것이지, 모델의 품질을 시험하는 게 아니다. 모델 품질은 2장처럼 직접 재 봤다.
- `SimilarPostIntegrationTest`는 낱말에 테스트마다 다른 표식(`mark`)을 붙인다. 테스트끼리 DB를 같이 쓰므로([Spring 테스트](../1-개발-환경과-배포/04-Spring-테스트.md) 5.7) 다른 테스트의 글과 가까워지지 않게 하려는 것이다.

| 테스트 | 확인하는 것 |
| --- | --- |
| `closestVisiblePostsFirstIncludingOtherBlogs` | 가장 비슷한 비공개 글과 자기 글은 빠짐, 다른 블로그 글 포함, 가까운 글이 먼 글보다 앞, `size=1`이면 1개 |
| `sizeMustBeOneToTen` | `size` 0·11은 400 |
| `invisibleSourcePostIsNotFoundAndMissingEmbeddingGivesEmptyList` | 비공개 원글 404, 임베딩이 없으면 빈 배열 |

### 5.11 누가 언제 Ollama를 부르나(이벤트 받기): `recommend/application/PostEmbeddingListener.java`, `PostEmbeddingService.sync`

3.5에서 본 대로 Ollama는 요청을 받아야 일한다. 이 프로젝트에서 그 요청을 보내는 곳은 `EmbeddingClient.embed`를 부르는 **두 군데**뿐이다: 글 임베딩(`PostEmbeddingService.refresh`)과 검색어 임베딩(`QueryEmbeddings.embed`). 그리고 `refresh`를 부르는 때를 리스너가 정한다.

```java
@ConditionalOnProperty(name = "app.recommend.enabled", havingValue = "true", matchIfMissing = true)
@Component
public class PostEmbeddingListener {
    ...
    @Async
    @TransactionalEventListener
    public void onContentChanged(PostContentChangedEvent event) {
        postEmbeddingService.refresh(event.postId());
    }

    @Async
    @TransactionalEventListener
    public void onDeleted(PostDeletedEvent event) {
        postEmbeddingService.remove(event.postId());
    }

    /** 서버가 다 뜬 뒤 한 번, 임베딩이 없는 발행 글을 채운다. */
    @Async
    @EventListener(ApplicationReadyEvent.class)
    public void onReady() {
        postEmbeddingService.sync();
    }
}
```

- 이 클래스는 "언제"만 정하고, "무엇을"은 `PostEmbeddingService`에 맡긴다(프록시 함정 피하기, 3.13).
- `onContentChanged`: 글 서비스가 발행·수정 때 이벤트를 내고, **커밋된 뒤**(`@TransactionalEventListener` 기본 AFTER_COMMIT) **다른 스레드에서**(`@Async`, Spring Boot의 `applicationTaskExecutor`) 받는다. 글 저장 응답은 Ollama를 기다리지 않고, 저장이 롤백되면 임베딩도 만들지 않는다(3.12, 3.13).
- `onDeleted`: 임베딩 행만 지운다. Ollama는 부르지 않는다.
- `onReady`: 서버가 요청을 받을 준비를 마쳤을 때(`ApplicationReadyEvent`) 한 번 `sync()`를 돈다. 이것도 `@Async`라 서버 시작을 늦추지 않는다. 아래 경우가 모두 여기서 메워진다. 배포하고 나서 따로 할 일이 없는 이유다.
  - 이미 있던 글(처음 추천을 켰을 때, 스텝 24에서 데이터를 옮긴 뒤처럼 임베딩 없이 글만 들어온 때)
  - Ollama가 꺼져 있던 사이에 쓴 글(`refresh`가 경고만 남기고 넘어간 글)
  - 넣는 글자 방식을 바꾼 뒤(`text_version`이 옛 번호인 글)
- 운영에서 `deploy.sh`가 **앱보다 먼저** `ollama pull bge-m3`를 하는 것도 이 때문이다. 앱이 뜨자마자 `sync()`가 Ollama를 부르는데, 그때 모델이 없으면 모두 실패하고 다음 재시작까지 비어 있다.
- `sync()`도 실패를 밖으로 던지지 않는다(`catch (RuntimeException e)` → `log.warn`). Ollama가 없어도 서버는 뜬다.


- 여기서 `embeddingClient.embed(text)`가 Ollama `/api/embed`로 가는 실제 호출이다(5.2).
- 초안·예약 글처럼 발행 글이 아니면 만들지 않고, 있던 임베딩도 지운다. 발행 글이면 공개 범위와 상관없이 만든다(모델이 로컬이라 글이 밖으로 나가지 않음, 볼 수 있는지는 찾을 때 거름).
- 검색어 쪽(`QueryEmbeddings.embed`)은 **요청 안에서** 부른다. 사용자가 결과를 기다리고 있어서다. 다음 페이지를 누를 때마다 다시 계산하지 않게 Redis에 5분 캐시한다(`@Cacheable`, 실패는 캐시하지 않음, 3.21).
- `app.recommend.enabled=false`이면 리스너, `PostEmbeddingService`, `OllamaEmbeddingClient`, `QueryEmbeddings`가 아예 만들어지지 않는다(`@ConditionalOnProperty`). Ollama를 한 번도 부르지 않고, 추천은 늘 빈 배열이며 의미 검색은 쓸 수 없다고 알린다(글자 검색은 그대로, `RecommendDisabledIntegrationTest`).

### 5.17 가까운 글 찾기: `recommend/domain/PostEmbeddingRepository.java`

비슷한 글(5.3, 5.4)과 같은 메서드를 쓴다. 의미 검색은 기준값과 페이지를 넘긴다.

```java
public List<NearPost> findNear(float[] query, Specification<Post> visible, Double minSimilarity, Long excludePostId,
                               int offset, int limit, String... fetch) {
    CriteriaBuilder cb = entityManager.getCriteriaBuilder();
    CriteriaQuery<Tuple> criteria = cb.createTupleQuery();
    Root<Post> post = criteria.from(Post.class);
    for (String path : fetch) {
        // 미분류 글(category 없음)도 나오게 LEFT. 그냥 fetch하면 INNER JOIN이라 빠진다
        post.fetch(path, JoinType.LEFT);
    }
    Root<PostEmbedding> embedding = criteria.from(PostEmbedding.class);
    Expression<Double> distance = distance(cb, embedding, query);
    criteria.multiselect(post, distance)
            .where(conditions(cb, criteria, post, embedding, distance, visible, minSimilarity, excludePostId))
            .orderBy(cb.asc(distance), cb.desc(post.get("id")));
    List<NearPost> result = new ArrayList<>();
    for (Tuple row : entityManager.createQuery(criteria).setFirstResult(offset).setMaxResults(limit).getResultList()) {
        result.add(new NearPost(row.get(0, Post.class), 1 - row.get(1, Double.class)));
    }
    return result;
}

/** findNear와 같은 조건에 맞는 글 수. */
public long countNear(float[] query, Specification<Post> visible, Double minSimilarity, Long excludePostId) { ... }

private static Predicate[] conditions(...) {
    List<Predicate> conditions = new ArrayList<>();
    conditions.add(cb.equal(embedding.get("postId"), post.get("id")));
    conditions.add(visible.toPredicate(post, criteria, cb));
    if (minSimilarity != null) {
        conditions.add(cb.le(distance, 1 - minSimilarity));
    }
    ...
}
```

- `criteria.from(Post.class)`와 `criteria.from(PostEmbedding.class)`를 둘 다 두고 `embedding.postId = post.id`를 조건으로 건다. 글과 임베딩을 묶는(조인) 쿼리다. 스텝 22에서는 서로 다른 DB라 이것이 불가능했다(3.18).
- `visible.toPredicate(...)`: 글 목록·글자 검색과 **같은 가시성 코드**(`PostSpecifications.visibleTo`/`listedIn`)를 그대로 끼운다. 두 탭의 "볼 수 있는 글"이 어긋날 수 없다.
- `cb.le(distance, 1 - minSimilarity)`: 유사도 0.40 → 거리 0.60 이하(3.15). 비슷한 글은 `minSimilarity`에 `null`을 넘겨 이 조건이 없다.
- `orderBy(거리 오름차순, 글 번호 내림차순)`: 거리가 같으면 새 글 먼저. 순서가 늘 같아야 페이지를 넘겨도 결과가 흔들리지 않는다.
- `setFirstResult(offset).setMaxResults(limit)`: SQL의 `OFFSET … LIMIT …`. 걸러진 뒤에 자른다.
- `1 - 거리`를 유사도로 돌려준다. 화면의 "가까움 0.58"이 이 값이다.
- `distance(...)`는 Hibernate의 pgvector 함수 `cosine_distance`(= `<=>`)를 부른다. 검색어 벡터를 `vector` 타입으로 넘기는 요령은 [PostgreSQL vs MySQL](./03-PostgreSQL-vs-MySQL.md) 5.6.

연결마다 `ef_search`와 `iterative_scan`을 켜는 곳(`src/main/resources/application.yml`, 주 DB의 Hikari 설정):

```yaml
      # pgvector HNSW 인덱스 검색은 기본으로 가까운 40개까지만 후보로 본다. 의미 검색은 가까운 순 100개까지 보고(max-results),
      # 가시성 조건을 같은 쿼리에서 거르므로 후보를 넉넉히 보고(ef_search), 조건에 맞는 글이 모자라면 인덱스를 더 읽는다(iterative_scan).
      # 이름에 점이 있는 설정은 vector 확장이 아직 없을 때(처음 Flyway 전)에도 SET할 수 있다
      connection-init-sql: "SET hnsw.ef_search = 200; SET hnsw.iterative_scan = strict_order"
```

- Hikari는 연결을 새로 만들 때마다 이 SQL을 실행한다. 연결은 풀에 남아 다시 쓰이므로 요청마다 SET하지 않아도 된다.
- 처음 서버가 뜰 때는 확장(`CREATE EXTENSION vector`)을 Flyway가 켜기 전이다. PostgreSQL은 이름에 점이 있는 설정(`hnsw.ef_search`)을 확장이 없어도 SET할 수 있게 해 준다(나중에 확장이 올라오면 그 값을 쓴다). 테스트(Testcontainers, 빈 DB에서 시작)가 이 경우를 지나간다.
- 스텝 22까지는 추천 DB 전용 설정 클래스(`recommend/config/RecommendDataSourceConfig.java`, 5.9)가 `dataSource.setConnectionInitSql("SET hnsw.ef_search = 200")`으로 추천 DB 연결에만 걸었다. 그 클래스는 DB를 합치며 없어졌다.

### 5.18 쿼리 한 번에 묻기: `search/application/SemanticSearchService.java`

```java
/** 블로그 안 의미 검색. 결과의 글은 모두 이 블로그 것이라 블로그를 함께 읽지 않는다. */
@Transactional(readOnly = true)
public Page<SemanticHit> search(Blog blog, Long viewerId, String rawQuery, PageQuery page) {
    String query = SearchService.normalize(rawQuery);
    return search(query, PostSpecifications.listedIn(blog, viewerId, LocalDateTime.now(clock)), page, "category");
}

/** 전체 의미 검색. 목록 한 줄에 블로그 이름과 카테고리가 나가므로 함께 읽는다. */
@Transactional(readOnly = true)
public Page<SemanticHit> searchAll(Long viewerId, String rawQuery, PageQuery page) {
    String query = SearchService.normalize(rawQuery);
    return search(query, PostSpecifications.visibleTo(viewerId, LocalDateTime.now(clock)), page,
            "blog", "category");
}
```

- 검색어 검사(`normalize`)를 맨 먼저 한다. 빈 검색어는 의미 검색을 쓸 수 있든 없든 400 `q`다.
- 블로그 안과 전체는 **넘기는 조건만** 다르다. `listedIn`은 블로그 화면 목록과 같은 조건이라 주인에게는 자기 비공개 글도 들어간다. 글자 검색(`SearchService`)과 같은 조건을 써야 두 탭의 "볼 수 있는 글"이 같다.
- `fetch`: 전체 검색은 줄마다 블로그 이름이 필요해 `blog`, `category`를 함께 읽고, 블로그 안 검색은 블로그가 하나라 `category`만 읽는다(N+1 막기).

```java
/** 가까운 순 max-results개 안에서 이 페이지 몫. 전체 수도 max-results를 넘지 않는다. */
private Page<SemanticHit> search(String query, Specification<Post> visible, PageQuery page, String... fetch) {
    float[] vector = embed(query);
    Pageable pageable = page.toPageable(Sort.unsorted());
    long total = Math.min(postEmbeddingRepository.countNear(vector, visible, properties.minSimilarity(), null),
            properties.maxResults());
    int offset = (int) Math.min(pageable.getOffset(), total);
    int limit = (int) Math.min(pageable.getPageSize(), total - offset);
    if (limit == 0) {
        return new PageImpl<>(List.of(), pageable, total);
    }
    List<SemanticHit> hits = postEmbeddingRepository
            .findNear(vector, visible, properties.minSimilarity(), null, offset, limit, fetch).stream()
            .map(near -> new SemanticHit(near.post(), near.similarity()))
            .toList();
    return new PageImpl<>(hits, pageable, total);
}
```

- `page.toPageable(...)`: 이 프로젝트의 페이지는 **1부터**다(`PageQuery`). Spring Data는 0부터라 `toPageable`이 하나 뺀다. 처음에 `PageRequest.of(page.page(), …)`로 썼다가 2쪽이 비는 실수를 테스트가 잡았다(아래 6장).
- `total`: 조건에 맞는 글 수와 100(`max-results`) 중 작은 쪽. 화면의 "글 N개"와 쪽수가 이 값으로 나온다.
- `limit = min(10, total - offset)`: 100개 경계를 넘지 않게 마지막 쪽을 줄인다. 100개를 넘는 쪽이면 0이 되어 쿼리 없이 빈 쪽을 준다.
- 결과의 순서는 DB가 `ORDER BY 거리`로 정해 준 그대로다. 스텝 22에서는 MySQL의 `id IN (…)` 결과가 순서를 지키지 않아 `Map`에 담고 PostgreSQL이 준 순서대로 다시 늘어놓았는데, 그 요령이 필요 없어졌다.

```java
private float[] embed(String query) {
    if (queryEmbeddings.isEmpty()) {
        throw new BusinessException(ErrorCode.SEMANTIC_SEARCH_UNAVAILABLE);
    }
    try {
        return queryEmbeddings.get().embed(query);
    } catch (RuntimeException e) {
        log.warn("검색어를 임베딩하지 못했습니다(임베딩 서버): {}", e.toString());
        throw new BusinessException(ErrorCode.SEMANTIC_SEARCH_UNAVAILABLE);
    }
}
```

- `Optional<QueryEmbeddings>`: 추천을 끄면(`app.recommend.enabled=false`) 이 부품이 없다(`@ConditionalOnProperty`). 비슷한 글 추천과 같은 방식이다.
- **Ollama 호출만** `try`로 감싸 503으로 바꾼다(연결 실패 `ResourceAccessException` 등). 원인은 로그에 남기고, 화면에는 정해진 문장만 보낸다.
- DB 쿼리(`countNear`, `findNear`)는 감싸지 않는다. 주 DB 오류는 다른 API처럼 500으로 나간다(3.23). 스텝 22에서는 추천 DB 오류도 같은 `catch`에서 503으로 바꿨다.
- 검색어 임베딩은 사용자가 결과를 기다리는 **요청 안에서** 부른다. 글 임베딩은 커밋 뒤 다른 스레드에서 부르는 것과 다르다(5.11). 그래서 같은 검색어를 다시 계산하지 않게 캐시한다(5.19).

### 5.22 테스트: `search/SemanticSearchIntegrationTest`

가짜 임베딩(낱말 주머니, 5.7)은 같은 낱말이 많이 겹칠수록 가깝다. 그래서 유사도를 손으로 계산해 정확히 맞출 수 있다. 글 본문을 제목과 같게 넣으므로 넣는 글자는 "제목\n제목"이고, 제목 낱말이 두 번씩 들어간다.

| 검색어 | 글 제목 | 글 벡터(낱말별 수) | 계산 | 유사도 |
| --- | --- | --- | --- | --- |
| A B | A B | A2 B2 | (2+2) / (√2 × √8) | 1.00 |
| A B | A B C | A2 B2 C2 | (2+2) / (√2 × √12) | 0.82 |
| A B | C | C2 | 0 | 0 → 빠짐 |
| A T | A (태그 T) | A2 태그1 T1 | (2+1) / (√2 × √6) | 0.87 |

| 테스트 | 확인하는 것 |
| --- | --- |
| `searchAllGivesVisibleCloseOnesInOrderWithSimilarity` | 가까운 순(1.00 → 0.82), 먼 글 빠짐, 비공개 글은 주인이 봐도 전체 검색에 없음, 다른 블로그 글 포함 |
| `pagesAreCutInSimilarityOrder` | `page=2&size=1`이 두 번째로 가까운 글, 전체 2개·2쪽 |
| `blogSearchStaysInTheBlogAndShowsOwnPrivatePostsToTheOwner` | 블로그 안에서는 다른 블로그 글 없음, 주인에게만 자기 비공개 글 |
| `tagNamesAreEmbeddedAndRenamingATagRemakesTheEmbedding` | 태그가 임베딩에 들어감(`text_version` 2), 태그 이름을 바꾸면 임베딩이 다시 만들어짐 |
| `wrongModeOrBlogTypeIsRejected` | `mode=vector` 400, `type=blog&mode=semantic` 400, 빈 검색어 400 `q` |
| `RecommendDisabledIntegrationTest.semanticSearchIsUnavailableButKeywordSearchWorks` | 추천을 끈 서버: 의미 검색 503, 글자 검색은 200 |

가짜 임베딩은 낱말을 해시로 1,024칸 중 하나에 넣는다. 서로 다른 낱말이 같은 칸에 들어가면(충돌) 계산이 어긋난다. 그래서 테스트 낱말끼리 칸이 겹치지 않는 표식을 고르고(`distinctMark`), 다른 테스트 글과 섞일 수 있는 전체 검색은 이 테스트의 글만 골라 순서를 본다.

## 6. 자주 하는 실수와 함정

**임베딩과 비슷한 글**

- **Ollama를 띄우면 임베딩이 알아서 생긴다고 생각한다.** Ollama는 요청을 기다리는 서버다. 앱이 `/api/embed`를 불러야 만들어진다(3.5, 5.11).
- **`ollama pull`만 하고 끝났다고 생각한다.** pull은 모델 파일을 받기만 한다. 서버(`ollama serve`)가 떠 있고 앱이 불러야 계산한다. 반대로 서버만 있고 모델을 받지 않았으면 호출이 "모델이 없다"며 실패한다.
- **공식 `postgres` 이미지에서 `CREATE EXTENSION vector`를 한다.** 설치돼 있지 않아 실패한다. pgvector가 든 이미지를 쓰거나 직접 설치한다(3.4).
- **임베딩 표의 결과를 그대로 보여 준다.** 비공개·숨긴 글이 추천에 나오고, 검색 결과로 제목이 샌다. 가시성으로 거른다. 같은 DB면 같은 쿼리에 거는 것이 가장 확실하고(3.6, 3.18), 글 목록과 같은 조건 코드를 쓰면 두 곳이 어긋나지 않는다.
- **(두 DB일 때) 후보를 딱 size개만 뽑는다.** 다른 DB에서 몇 개가 걸러지면 모자란다. 넉넉히 뽑는다. 한 쿼리로 거를 수 있으면 이 문제가 없다.
- **모델을 바꾸고 예전 임베딩을 그대로 둔다.** 다른 모델의 벡터끼리는 비교가 안 된다. 모두 다시 만든다(차원도 바뀔 수 있다).
- **거리 연산자와 인덱스 종류가 다르다.** `<=>`(코사인)로 찾는데 인덱스는 `vector_l2_ops`면 인덱스를 못 쓴다.
- **정규화를 생각하지 않는다.** 길이가 다른 벡터에 내적을 쓰면 긴 글이 무조건 가깝게 나올 수 있다. 코사인을 쓰거나 길이를 1로 맞춘다.
- **임베딩을 요청 안에서 만든다.** 글 저장이 모델 계산(수백 ms~수 초)을 기다린다. 커밋 뒤 비동기로(3.12, 3.13).
- **추천 실패가 글 상세를 깨뜨린다.** 추천 DB·모델이 꺼져도 빈 배열로 넘어간다.
- **테스트에 진짜 모델을 쓴다.** 느리고 결과가 흔들린다. 우리 규칙은 가짜로, 모델 품질은 따로 잰다.
- **글 전체를 통째로 넣는다.** 모델 입력 길이를 넘거나 느려진다. 앞부분(제목 + 2,000자)만 넣는다.

**두 번째 DB와 커밋 뒤 비동기**

- **두 번째 `DataSource`를 평범한 `@Bean`으로 만든다.** 주 DB 자동 설정이 멈추고, JPA·Flyway가 엉뚱한 DB를 쓰거나 "DataSource가 둘"이라며 뜨지 않는다. `defaultCandidate = false` + `@Qualifier`, 또는 주 DB를 직접 만들고 `@Primary`.
- **테스트 컨테이너에 `@ServiceConnection`을 붙인다.** 두 번째 DB가 주 DB 자리를 차지한다.
- **Flyway 위치를 같은 폴더로 둔다.** MySQL 스크립트가 PostgreSQL에 돌거나 반대가 된다. 폴더(`db/migration`, `db/recommend`)를 나눈다.
- **두 DB를 한 트랜잭션처럼 믿는다.** MySQL이 롤백돼도 PostgreSQL 쓰기는 남는다. 커밋 뒤에 쓰고, 어긋남은 정리 작업으로 맞춘다.
- **`@EventListener`로 받는다.** 커밋 전에 실행되어 롤백된 글의 임베딩이 생기거나, 다른 스레드에서 옛 내용을 읽는다.
- **`@TransactionalEventListener`인데 트랜잭션 밖에서 발행한다.** 아무 일도 안 일어난다(`fallbackExecution` 없이는).
- **`@EnableAsync`를 빠뜨린다.** 같은 스레드에서 돌아 글 저장이 느려진다. 오류가 없어 알아차리기 어렵다.
- **같은 클래스 안에서 `@Async` 메서드를 부른다.** 프록시를 거치지 않아 비동기가 아니다.
- **비동기 작업의 예외를 그냥 둔다.** 아무도 모르게 사라진다. 잡아서 남기고, 정리 작업으로 다시 맞출 길을 둔다.
- **비동기 결과를 `Thread.sleep`으로 기다리는 테스트.** 느린 컴퓨터에서 깨지고, 빠른 컴퓨터에서는 쓸데없이 느리다. 조건이 맞을 때까지 짧게 돌며 기다린다.

**의미 검색**

- **블로그 안 검색을 "전체에서 뽑고 거르기"로**: 다른 블로그 글이 앞자리를 다 차지해 이 블로그 결과가 0개가 될 수 있다. 블로그 조건을 처음부터 쿼리에 넣는다(3.19).
- **`LIMIT 100`인데 40개만**: HNSW `ef_search` 기본 40(3.20). 오류가 안 나서 알아채기 어렵다. 글이 적은 개발 DB에서는 인덱스를 안 써 드러나지 않는다.
- **같은 쿼리에서 거르면서 `iterative_scan`을 안 켬**: 인덱스가 모은 후보가 조건에 많이 걸러지면 쪽이 덜 찬다. 이것도 오류 없이 결과만 줄어든다(3.20).
- **(두 DB일 때) `IN ()` 빈 목록, MySQL `IN` 결과 순서를 믿음**: 스텝 22의 함정. 범위가 비면 SQL 문법 오류였고, `id IN (12, 7, 31)`은 그 순서로 오지 않아 가까운 순서를 다시 맞춰야 했다. 한 쿼리가 되면서 없어졌다.
- **기준값 없이 보여 주기**: 의미 검색은 늘 1등이 있다. 관계없는 글이 결과처럼 보인다(3.16).
- **다른 모델로 검색어 임베딩**: 차원이 같아도 공간이 달라 거리가 뜻이 없다(3.14).
- **넣는 글자만 바꾸고 옛 임베딩을 그대로**: 새 글만 새 방식이라 같은 내용인데 거리가 달라진다. 버전 번호로 다시 만든다(3.22).
- **같은 클래스에서 `@Cacheable` 메서드를 부름**: 프록시를 거치지 않아 캐시가 안 걸린다(3.21).
- **페이지 번호 0부터·1부터 섞기**: 이 프로젝트 API는 1부터, Spring Data는 0부터다. `PageQuery.toPageable`을 거친다. 직접 `PageRequest.of(page.page(), …)`를 쓰면 한 쪽씩 밀린다(이번에 테스트가 잡음).
- **의미 검색 실패를 글자 검색으로 몰래 대신함**: 사용자는 다른 종류의 결과를 의미 검색으로 믿는다(3.23).
- **DB 오류까지 503으로 바꿈**: 주 DB가 죽었는데 "글자로 찾기를 이용해 주세요"라고 안내하게 된다. 503은 의미 검색만의 문제(추천 꺼짐, Ollama)일 때만 쓴다(5.18).

## 8. 확인 문제

1. 임베딩으로 비슷한 글을 찾으면 LIKE·태그로 찾을 때보다 나은 점은?
<details><summary>답 보기</summary>글자가 아니라 뜻이 가까운 글을 찾는다. "Spring Security"와 "스프링 시큐리티로 로그인 토큰 검증"처럼 겹치는 낱말이 없어도 가깝게 나온다.</details>

2. 코사인 유사도와 코사인 거리의 관계, pgvector에서 코사인 거리 연산자는?
<details><summary>답 보기</summary>코사인 거리 = 1 - 코사인 유사도. 작을수록 비슷하다. 연산자는 &lt;=&gt;.</details>

3. 벡터 길이를 1로 맞추면(정규화) 무엇이 좋은가?
<details><summary>답 보기</summary>코사인 유사도의 분모가 1이 되어 내적과 같아진다. 글 길이처럼 벡터 크기에 영향을 주는 요소가 비교를 흔들지 않는다.</details>

4. HNSW 인덱스가 하는 일과, "근사"라는 말의 뜻은?
<details><summary>답 보기</summary>가까운 벡터끼리 여러 층의 그래프로 이어 두어 모든 행과 거리를 재지 않고 가까운 것을 빨리 찾는다. 근사라서 아주 드물게 진짜 가장 가까운 것을 놓칠 수 있다. 추천에는 그 정도 오차가 괜찮다.</details>

5. 임베딩 표에 비공개 글도 넣어 두는데 추천에 나오지 않는 이유는?
<details><summary>답 보기</summary>가까운 글을 찾는 쿼리에 보는 사람이 볼 수 있는 글 조건(visibleTo)을 같이 걸기 때문이다(findNear). 글과 임베딩이 같은 DB에 있어 한 쿼리로 묶을 수 있다. 스텝 22까지는 두 DB라 PostgreSQL에서 후보를 뽑고 MySQL에서 거르는 두 번 읽기였다.</details>

6. 스텝 22까지는 추천 후보를 size(5)개가 아니라 30개 뽑았다. 그 이유와, 지금은 그럴 필요가 없는 이유는?
<details><summary>답 보기</summary>그때는 다른 DB에서 볼 수 없는 글을 걸러 내므로, 몇 개가 빠져도 size개를 채우려고 넉넉히 뽑았다. 지금은 가시성 조건을 건 뒤에 LIMIT size를 하므로 걸러진 다음의 size개가 바로 나온다.</details>

7. 원래 글을 볼 수 없으면 추천도 404인 이유는?
<details><summary>답 보기</summary>남의 비공개 글 번호로 비슷한 글을 물어 그 글의 주제를 짐작하는 길을 막는다. 글 상세와 같은 가시성 판단을 쓴다.</details>

8. 인기 글은 비회원 기준으로, 비슷한 글은 보는 사람 기준으로 거르는 이유는?
<details><summary>답 보기</summary>인기 글은 순위를 캐시해 모두에게 같은 "공개 글" 목록을 준다. 비슷한 글은 캐시하지 않고 요청마다 계산하므로 보는 사람에 맞춰(구독자 공개 글 등) 거를 수 있다.</details>

9. 테스트에 진짜 bge-m3 대신 가짜(낱말 주머니)를 쓰는 이유와, 그래도 확인되는 것은?
<details><summary>답 보기</summary>Ollama 없이 빠르고 결과가 늘 같다. 가까운 순 정렬, 비공개·자기 글 제외, 다른 블로그 포함, size 처리 같은 우리 코드의 규칙을 확인한다. 모델 품질은 따로 재 본다.</details>

10. 모델을 다른 것으로 바꾸면 무엇을 해야 하나?
<details><summary>답 보기</summary>모든 글의 임베딩을 새 모델로 다시 만든다. 다른 모델의 벡터끼리는 비교할 수 없다. 차원이 다르면 표의 vector(n)도 바꾼다.</details>

11. `docker ps`의 IMAGE 칸이 `pgvector/pgvector:pg17`이다. 이 컨테이너에서 도는 DB는 무엇이고, 왜 공식 `postgres:17` 이미지를 쓰지 않았나?
<details><summary>답 보기</summary>PostgreSQL 17이다. 이 이미지는 공식 PostgreSQL 17 이미지에 pgvector 확장을 설치해 둔 것이다. 공식 이미지에는 pgvector가 설치돼 있지 않아 CREATE EXTENSION vector가 실패한다. 설치는 이미지가, 켜기는 Flyway의 V1__init.sql이 한다.</details>

12. 운영 서버에 Ollama 컨테이너가 떠 있고 bge-m3도 pull해 두었다. 그런데 새 글의 임베딩이 생기려면 무엇이 더 일어나야 하나?
<details><summary>답 보기</summary>앱이 Ollama의 POST /api/embed를 불러야 한다. Ollama는 요청을 기다리는 서버라 스스로 계산하지 않는다. 이 프로젝트에서는 글 발행·수정이 커밋된 뒤 PostEmbeddingListener가 다른 스레드에서 PostEmbeddingService.refresh를 부르고, 그 안의 embeddingClient.embed가 그 호출이다.</details>

13. Ollama가 꺼져 있던 동안 쓴 글은 어떻게 되나? 따로 다시 만들어 줘야 하나?
<details><summary>답 보기</summary>그때는 refresh가 경고 로그만 남기고 넘어가 그 글은 임베딩이 없다(추천은 빈 배열, 글 저장은 성공). 따로 할 일은 없다. 다음에 서버가 뜰 때 onReady → sync()가 임베딩이 없는 발행 글을 찾아 만든다.</details>

14. 비슷한 글을 보여 줄 때(GET /api/posts/12/similar)도 Ollama를 부르나?
<details><summary>답 보기</summary>부르지 않는다. 12번 글을 저장할 때 만들어 둔 벡터를 DB에서 꺼내(findEmbedding) DB 안에서 거리만 잰다. Ollama를 부르는 것은 글 임베딩을 만들 때와 의미 검색의 검색어를 바꿀 때뿐이다.</details>

15. Spring AI나 pgai 같은 방법을 쓰면 "API를 부르지 않아도" 되나?
<details><summary>답 보기</summary>아니다. Spring AI는 라이브러리가 대신 같은 HTTP API를 부르고, pgai는 DB 쪽 작업자가 부른다. 누가 부르느냐가 바뀔 뿐 모델 서버에 요청이 가야 임베딩이 생기는 것은 같다. 앱 안에서 모델을 직접 돌리는 방법(ONNX Runtime 등)만 HTTP 호출이 없지만, 앱 메모리와 시작 시간이 크게 는다.</details>

16. DataSource 빈을 하나 더 평범하게 만들면 무슨 일이 생기나?
<details><summary>답 보기</summary>DataSourceAutoConfiguration이 "DataSource가 이미 있다"며 물러나 주 DB 자동 설정이 멈춘다. JPA·Flyway가 흔들린다.</details>

17. `@Bean(defaultCandidate = false)`가 이 문제를 푸는 방식은?
<details><summary>답 보기</summary>타입만으로 고를 때의 후보에서 빠져서, 자동 설정의 "있나?" 검사와 JPA·Flyway의 주입에 보이지 않는다. @Qualifier로 이름을 짚어야만 주입된다.</details>

18. 두 DB 사이에 외래 키와 한 트랜잭션이 없어서 이 프로젝트가 대신 한 것은?
<details><summary>답 보기</summary>글을 지우면 애플리케이션이 임베딩도 지우고, 글 저장이 커밋된 뒤에 임베딩을 쓰며, 어긋난 것은 서버 시작 때 sync로 맞춘다(최종 일관성).</details>

19. 글 쓰기 쪽이 추천 쪽을 직접 부르지 않고 이벤트를 내는 이유는?
<details><summary>답 보기</summary>post가 recommend를 모르게 해서, 추천을 통째로 빼도 글 쓰기 코드를 고치지 않게 한다. 의존 방향이 recommend → post 하나뿐이다.</details>

20. `@EventListener` 대신 `@TransactionalEventListener`를 쓰는 이유는?
<details><summary>답 보기</summary>커밋에 성공한 뒤에만 실행해서, 롤백된 글의 임베딩을 만들지 않고, 다른 스레드에서 읽어도 커밋된 새 내용이 보이게 하려고.</details>

21. `@TransactionalEventListener`가 아무 일도 하지 않는 경우는?
<details><summary>답 보기</summary>이벤트를 트랜잭션 밖에서 발행했을 때. 기다릴 커밋이 없어 실행되지 않는다(fallbackExecution = true면 실행).</details>

22. `@Async`가 비동기로 돌지 않는 경우 두 가지는?
<details><summary>답 보기</summary>@EnableAsync가 없을 때, 같은 클래스 안에서 this로 부를 때(프록시를 거치지 않음).</details>

23. 비동기 임베딩이 실패해도 예외를 던지지 않고 경고만 남기는 이유와, 그 대신 마련한 것은?
<details><summary>답 보기</summary>응답이 이미 나간 뒤라 예외가 아무에게도 가지 않고, 추천은 부가 기능이라 글 쓰기·서버를 막으면 안 된다. 서버 시작 때 sync가 빠진 임베딩을 다시 만든다.</details>

24. 테스트에서 PostgreSQL 컨테이너에 `@ServiceConnection`을 붙이지 않은 이유는?
<details><summary>답 보기</summary>붙이면 Spring Boot가 그것을 주 DB 연결로 써 버린다. 두 번째 DB라 DynamicPropertyRegistrar로 app.recommend.datasource.* 설정에 이어 준다.</details>

25. 비동기 결과를 기다릴 때 `Thread.sleep(2000)` 대신 조건을 돌며 기다리는 이유는?
<details><summary>답 보기</summary>빨리 끝나면 바로 넘어가고, 느린 환경에서도 최대 시간까지 기다려서 테스트가 덜 흔들리고 덜 느리다.</details>

26. "자바 공부"로 글자 검색은 0개인데 의미 검색은 "스프링 부트 입문기"를 찾는다. 왜 그런가?
<details><summary>답 보기</summary>글자 검색은 낱말이 들어 있어야 찾는다. 의미 검색은 검색어와 글을 같은 모델로 임베딩해 뜻이 가까운지(코사인 유사도) 본다. bge-m3는 "자바"와 "스프링"이 가까운 주제라는 것을 학습했다.</details>

27. 의미 검색에 기준값(0.40)이 없으면 "양자역학"으로 찾았을 때 무슨 일이 생기나?
<details><summary>답 보기</summary>의미 검색은 늘 가장 가까운 글이 있으므로, 관계없는 글들이 가까운 순으로 결과처럼 나온다. 기준값이 "충분히 가깝지 않은 글"을 뺀다.</details>

28. 의미 검색 쿼리에 가시성 조건(`visibleTo`/`listedIn`)을 거는 이유는? 거르지 않으면 무엇이 깨지나? 스텝 22에서는 이것을 어떻게 했나?
<details><summary>답 보기</summary>임베딩 표에는 비공개·숨긴 글도 있다. 거르지 않으면 볼 수 없는 글의 제목이 검색 결과로 샌다(헌법 II). 지금은 글과 임베딩을 묶은 쿼리 하나에 조건을 건다. 스텝 22에서는 두 DB라 PostgreSQL에서 가까운 100개를 뽑고 MySQL에서 볼 수 있는 글만 남긴 뒤 순서를 다시 맞춰 잘랐다.</details>

29. 블로그 안 검색을 "전체에서 가까운 100개를 뽑고 이 블로그 것만 거르기"로 하면 어떤 경우에 결과가 0개가 되나? 지금 코드는 왜 그런 일이 없나?
<details><summary>답 보기</summary>다른 블로그의 가까운 글이 100자리를 다 차지하면, 그 뒤 "이 블로그 것만" 거를 때 0개가 된다. 지금은 블로그 조건(<code>listedIn</code>)이 처음부터 같은 쿼리에 들어 있어 이 블로그 글 가운데서 가까운 순을 찾는다. (스텝 22에서는 MySQL에서 이 블로그의 볼 수 있는 글 번호를 먼저 읽어 <code>post_id IN (…)</code>으로 범위를 정했다.)</details>

30. `LIMIT 100`으로 물었는데 운영에서 결과가 40개를 넘지 않는다. 원인과 이 프로젝트의 해결은? 같은 쿼리에서 가시성까지 거르면서 하나 더 켠 설정은?
<details><summary>답 보기</summary>HNSW 인덱스가 한 번에 모으는 후보 수 <code>hnsw.ef_search</code>의 기본값이 40이다. 연결을 만들 때 <code>SET hnsw.ef_search = 200</code>(Hikari <code>connection-init-sql</code>). 같은 쿼리에서 거르면 후보가 걸러져 모자랄 수 있어 <code>SET hnsw.iterative_scan = strict_order</code>도 켠다(모자라면 인덱스를 더 읽되 가까운 순서는 지킴).</details>

31. `QueryEmbeddings`를 `SemanticSearchService` 안의 메서드로 두면 캐시가 왜 동작하지 않나?
<details><summary>답 보기</summary><code>@Cacheable</code>은 프록시가 메서드 호출을 가로채서 건다. 같은 클래스 안에서 <code>this.embed()</code>로 부르면 프록시를 거치지 않는다.</details>

32. 넣는 글자에 태그를 더한 뒤, 이미 있던 글의 임베딩은 어떻게 새 방식이 되나?
<details><summary>답 보기</summary>표에 <code>text_version</code>을 두고 지금 방식은 2다. 서버가 뜰 때 <code>sync()</code>가 <code>text_version</code>이 2가 아닌 발행 글을 다시 만든다. 기존 행은 칸을 더할 때 기본값 1이 되었다.</details>

33. 추천을 꺼 둔 서버에서 의미 검색은 왜 빈 목록이 아니라 503을 주나? 비슷한 글 추천은 왜 빈 목록을 주나?
<details><summary>답 보기</summary>의미 검색은 사용자가 직접 요청한 일이라, 결과가 없는 것("뜻이 가까운 글이 없습니다")과 못 찾은 것을 구분해 알려야 한다. 추천은 글 화면의 덧붙은 칸이라 비어 있어도 글을 읽는 데 지장이 없다.</details>

34. Ollama는 멀쩡한데 주 DB 쿼리가 실패했다. 의미 검색은 503인가 500인가? 왜 그렇게 나눴나?
<details><summary>답 보기</summary>500이다. 503("지금은 의미 검색을 쓸 수 없습니다. 글자로 찾기를 이용해 주세요")은 의미 검색만의 문제(추천 꺼짐, Ollama 실패)일 때 쓴다. 임베딩이 주 DB에 있으니 DB가 실패하면 글자 검색도 안 되어 그 안내가 맞지 않고, 다른 API와 같은 서버 오류로 다룬다. 코드에서는 Ollama 호출(<code>embed</code>)만 <code>try</code>로 감싸 503으로 바꾼다.</details>
