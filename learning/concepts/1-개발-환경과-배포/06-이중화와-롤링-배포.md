# 이중화와 롤링 배포: upstream, 헬스체크, 앱을 끄는 순서, 되돌리기

> 관련 스텝: [스텝 25](../../스텝-25.md) (T136~T139) · 관련 개념: [CI/CD 개념](./05-CI-CD.md)(배포 전략·헬스 체크·늘리기→옮기기→줄이기), [이 프로젝트의 CI/CD](./05-CI-CD.md), [서버와 Docker](./03-Docker와-서버.md), [동시 수정 막기](../2-데이터/05-트랜잭션과-동시성.md)(앱 두 대에서 같이 도는 작업), [커밋 뒤 비동기 처리](../2-데이터/11-임베딩과-의미-검색.md), [멱등성과 Redis](../2-데이터/13-멱등성과-Redis.md), [블로그 주소를 경로로](../4-웹과-프론트/05-블로그-주소-서브도메인에서-경로로.md)(학교 nginx)

## 1. 이 문서로 배우는 것

- **이중화**(redundancy)가 무엇이고, 이 프로젝트의 이중화가 어디까지인가(같은 서버 안의 앱 두 대)
- 배포 전략 가운데 **롤링**을 고른 이유(블루·그린, 우리 nginx를 두는 방법과 비교)
- 리버스 프록시의 **upstream**: 요청 나누기, 실패한 서버 빼기(`max_fails`·`fail_timeout`), 다른 서버로 다시 보내기(`proxy_next_upstream`), POST는 다시 보내지 않는 이유
- 앱을 여러 대로 늘리려면 갖춰야 할 것: 상태를 앱 밖에 두기(Redis·DB·업로드 폴더), 같이 도는 서버 작업
- **헬스체크**: liveness와 readiness, Spring Boot Actuator, 무엇을 넣고 무엇을 숨기나
- 앱을 **끄는 순서**: SIGTERM, graceful shutdown, Spring의 종료 단계와 비동기 작업, `docker stop -t`. 그리고 흔한 예제 `await-termination`이 오히려 나쁜 이유(실험)
- 배포하는 동안 **옛 버전과 새 버전이 함께** 떠 있을 때 생기는 일
- 롤링 배포 스크립트의 순서와 **되돌리기 규칙**("살아 있는 앱이 0대가 되는 순간이 없게")

## 2. 왜 필요한가

스텝 24까지 배포는 "옛 앱을 지우고 새 앱을 띄우기"였다([CI CD](./05-CI-CD.md) 5.4, [CI CD](./05-CI-CD.md)의 "다시 띄우기"). 새 앱이 뜨는 데 30초~1분이 걸리고, 그동안 사이트에 들어오면 nginx가 502를 보여 줬다. main에 병합할 때마다 그랬다.

앱을 **늘 두 대** 띄워 두고 **한 대씩** 바꾸면, 한 대를 바꾸는 동안 다른 한 대가 요청을 받는다. 지원은 이중화를 직접 설정해 보는 것도 목표로 했다.

## 3. 기본 개념

### 3.1 이중화와 그 범위

**이중화**는 같은 일을 하는 것을 둘 이상 두어, 하나가 멈춰도 서비스가 계속되게 하는 것이다. 무엇을 둘로 두느냐에 따라 버틸 수 있는 장애가 다르다.

| 범위 | 버티는 것 | 못 버티는 것 |
| --- | --- | --- |
| 같은 서버 안의 앱 프로세스 두 대(**이 프로젝트**) | 앱 하나의 배포·재시작·멈춤 | 서버 자체가 죽음, DB·Redis가 죽음(각각 한 대) |
| 서버 두 대 | 서버 하나가 죽음 | 데이터센터 장애 |
| 여러 지역(리전) | 지역 장애 | (비용이 아주 큼) |

그러니 이 프로젝트의 목표는 정확히 말하면 **"무중단 배포 + 앱 이중화 경험"**이다. 서버가 죽어도 버티는 고가용성은 아니다.

### 3.2 배포 전략 고르기

[CI CD](./05-CI-CD.md)에서 본 전략을 이 환경에 대 보면:

| 전략 | 평소 앱 | 배포 때 nginx | 이 환경에서 |
| --- | --- | --- | --- |
| 다시 띄우기(Recreate) | 한 대 | 그대로 | 배포마다 끊김(스텝 24까지) |
| 블루·그린 | 한 대(배포 때만 두 벌) | **보내는 곳을 바꾸고 reload** | 학교 nginx는 학생이 reload할 수 없고 서버가 10분마다 다시 읽음. 언제 바뀌는지 몰라 옛 앱을 끌 때를 정할 수 없음. 평소엔 한 대라 이중화도 아님 |
| **롤링** | **두 대** | 그대로(upstream을 처음 한 번만) | 맞음 |
| 카나리 | 여러 대 | 일부만 새 버전으로 보내는 비율 조절 | 앱 두 대에는 과함 |

롤링을 하는 방법도 둘이었다.

| 방법 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- |
| A. **학교 nginx 설정 파일에 upstream** | 설정 파일을 한 번만 고침(10분 안에 자동 반영). 컨테이너 하나 덜 운영. 다른 학생이 이미 같은 방식(upstream 두 대)을 써서 허용됨을 확인 | 배포 중에 nginx를 못 건드림 → 끄기 전에 미리 빼지 못하고, 꺼진 뒤 nginx가 알아채게 둠 |
| B. 우리 nginx 컨테이너를 앞에 | 학교 요청이 없음. 배포 중 reload로 "미리 빼고 → 끄고 → 넣기" | 컨테이너 하나 더, 그 nginx는 한 대 |

A를 골랐다(R-18).

### 3.3 리버스 프록시와 upstream

**리버스 프록시**는 서버 앞에서 요청을 대신 받아 뒤의 서버로 넘겨주는 문지기다. 사용자는 `now-log.java21.net`만 알고, 뒤에 앱이 몇 대인지·포트가 뭔지 모른다. 학교 nginx가 그 역할을 한다([블로그 주소 서브도메인에서 경로로](../4-웹과-프론트/05-블로그-주소-서브도메인에서-경로로.md)).

**upstream**은 넘겨줄 서버 목록에 이름을 붙인 것이다.

```nginx
upstream now_log_java21_net {
    server 127.0.0.1:8460 max_fails=1 fail_timeout=10s;
    server 127.0.0.1:8461 max_fails=1 fail_timeout=10s;
}
```

- 나누는 방식은 기본이 **라운드 로빈**(번갈아)이다. `least_conn`(연결이 적은 쪽), `ip_hash`(같은 IP는 같은 서버) 등으로 바꿀 수 있다.
- 이름은 공용 nginx 전체에서 겹치면 안 된다(설정이 모두 한 nginx에 모이므로). 도메인을 이름으로 쓰는 이유다.

**실패한 서버 빼기: 수동(passive) 헬스 판단**

무료 nginx는 주기적으로 `/health`를 찔러 보는 **능동** 헬스 체크(`health_check`)가 없다. 그건 상용 NGINX Plus 기능이다. 대신 **실제 요청이 실패한 것**으로 판단한다.

- `max_fails=1 fail_timeout=10s`: `fail_timeout`(10초) 안에 1번 실패하면 그 서버를 "사용 불가"로 표시하고 **10초 동안** 보내지 않는다. 10초가 지나면 다시 보내 보고, 성공하면 복귀한다.
- 그래서 nginx는 "앱이 지금 뜨는 중"인지 모른다. 연결이 거부되면 실패로 셀 뿐이다.

**다른 서버로 다시 보내기**

```nginx
proxy_next_upstream error timeout http_502 http_503;
proxy_next_upstream_tries 2;
proxy_connect_timeout 3s;
```

- `proxy_next_upstream`: 연결 실패·시간 초과·502·503이면 사용자에게 오류를 보이기 전에 **다음 서버로** 보낸다. 무중단 배포의 핵심 줄이다.
- `proxy_next_upstream_tries 2`: 두 대까지만 시도.
- `proxy_connect_timeout 3s`: 응답 없는 서버에 연결을 3초 안에 포기(기본 60초).
- **POST는?** nginx는 POST·PATCH 같은 멱등이 아닌 요청을 **이미 서버에 보낸 뒤에는** 다시 보내지 않는다(`non_idempotent`를 따로 켜지 않는 한). 연결 자체가 안 된 요청만 다른 서버로 간다. 그래서 글이 두 번 저장되지 않는다.

### 3.4 앱을 여러 대로 늘리려면

요청이 매번 다른 앱으로 갈 수 있으므로, **앱 안(메모리)에 상태를 두면 안 된다.**

| 상태 | 이 프로젝트 | 두 대에서 |
| --- | --- | --- |
| 로그인 | JWT 쿠키 + Refresh 토큰은 Redis | 어느 앱이든 같은 Redis를 봄 ✓ |
| 시도 횟수, 인증 코드, 연타 방지 키(Idempotency-Key), 캐시 | Redis | ✓ |
| 글·댓글·공감 수 | PostgreSQL, 수는 행 잠금·한 줄 UPDATE | ✓ |
| 업로드 이미지 | 서버의 `~/uploads`를 두 컨테이너가 같이 마운트(UUID 이름) | ✓ |
| 1분 자동 임시저장 | 타이머가 브라우저에 있고 매번 DB에 PUT | ✓ |
| 앱 메모리의 잠금·저장소(`synchronized`, `ConcurrentHashMap`) | 없음 | ✓ |
| **스케줄 작업**(예약 발행, 새벽 통계) | 앱마다 돈다 | **고쳐야 함** → [트랜잭션과 동시성](../2-데이터/05-트랜잭션과-동시성.md) |
| DB 연결 | 앱마다 Hikari 10개 | 합 20, PostgreSQL 기본 최대 100 ✓ |

스케줄 작업은 "한 앱에서만 켜기"로 피할 수도 있었지만, 그러면 그 앱이 배포로 꺼진 동안 작업이 멈추고 두 앱의 설정이 달라진다. 작업이 두 앱에서 돌아도 맞게 고쳤다(조건부 UPDATE, advisory lock).

### 3.5 헬스체크: liveness와 readiness

| 질문 | 이름 | 실패하면 보통 |
| --- | --- | --- |
| 살아 있나? (멈추거나 엉키지 않았나) | **liveness** | 재시작한다(쿠버네티스) |
| 요청을 받을 준비가 됐나? (다 떴고, 꼭 필요한 연결이 붙었나) | **readiness** | 요청을 보내지 않는다 |

뜨는 중인 앱, DB에 못 붙은 앱은 살아 있지만(liveness OK) 준비되지 않았다(readiness 실패). 배포 스크립트가 "새 앱이 됐으니 다음 앱을 꺼도 된다"고 판단하려면 **readiness**를 봐야 한다.

로그에서 `Started BlogApplication`을 찾는 방법(스텝 24까지)은 "다 떴다"까지는 알려 주지만, Redis 연결이 실제로 되는지는 모른다.

Spring Boot **Actuator**가 이 주소를 만들어 준다. readiness 그룹에 무엇을 넣을지 정할 수 있다. 넣는 것이 많을수록 엄격하지만, 잠깐 느린 외부 서비스 하나 때문에 "준비 안 됨"이 되기 쉽다.

### 3.6 앱을 끄는 순서

`docker stop`은 컨테이너에 **SIGTERM**을 보내고, 정해진 시간(`-t`, 기본 10초) 안에 안 꺼지면 **SIGKILL**로 강제 종료한다.

Spring Boot는 SIGTERM을 받으면 정해진 순서로 정리한다.

```
SIGTERM
├─ ① 종료 단계(lifecycle stop): SmartLifecycle 빈을 차례로 멈춤. 단계마다 최대 30초
│     (spring.lifecycle.timeout-per-shutdown-phase)
│     ├─ 웹 서버(graceful shutdown): 새 요청은 네트워크 단에서 안 받고, 처리 중인 HTTP 요청이 끝나길 기다림
│     └─ 비동기 스레드 풀: 새 작업은 안 받고, 돌고 있는 @Async 작업이 끝나길 기다림
└─ ② 빈 정리(destroy)
      ├─ JPA EntityManagerFactory, DB 연결 풀(Hikari) 닫음
      └─ 스레드 풀 종료(남은 작업이 있으면 인터럽트로 끊음)
```

- **graceful shutdown**은 Spring Boot 3.4부터 기본값이다. 설정이 없어도 SIGTERM에 `Commencing graceful shutdown. Waiting for active requests to complete` 로그가 찍힌다(이 프로젝트에서 확인).
- 비동기 작업(임베딩 만들기, 재설정 메일)은 대부분 마지막에 DB를 쓰므로 **②보다 먼저**, 즉 ①에서 끝나야 한다.
- ①의 두 기다림은 차례로 지나간다(실험 로그에서 웹 서버 정리가 끝난 뒤 스레드 풀을 기다렸다). 최악이면 30초 + 30초가 넘는다. 그래서 `docker stop -t 70`을 준다.

**`await-termination: true`는 넣지 않는다.** 이름만 보면 "끌 때 작업을 기다려라"라서 넣고 싶어지고, 인터넷 예제에도 많다. 실험해 보니 이 설정을 켜면 ①에서 기다리지 않고 DB부터 닫은 뒤 ②에서 기다렸다(5.4). 기다려도 DB를 못 쓴다. Spring Framework 6.1부터 스레드 풀이 ①에 참여하게 바뀐 것으로 알려져 있고, 그 전에는 이 설정이 유일한 방법이라 옛 예제에 많이 남아 있다(Spring 소스로 확인한 것은 아니고, 동작은 로그로 확인했다).

### 3.7 옛 버전과 새 버전이 함께 떠 있다

롤링 배포 중에는 몇십 초 동안 한 앱은 새 버전, 한 앱은 옛 버전이다.

| 무엇 | 일어날 수 있는 일 | 대응 |
| --- | --- | --- |
| DB 스키마 | 새 앱이 Flyway로 컬럼을 지웠는데 옛 앱이 그 컬럼을 씀 → 옛 앱 오류 | 컬럼 삭제·이름 바꾸기는 **늘리기 → 옮기기 → 줄이기**로 배포를 나눔([CI CD](./05-CI-CD.md) 3.9). 되돌리기도 이것을 전제로 함 |
| 화면 JS 파일 | 파일 이름에 해시가 있음(`index-3fa1.js`). 새 앱에서 받은 index.html이 새 JS를 요청했는데 그 요청이 옛 앱으로 가면 404 | 새로고침하면 풀림. 받아들임. 필요하면 `ip_hash`(같은 IP는 같은 앱, 대신 한쪽에 몰릴 수 있음) |
| API 모양 | 새 화면이 옛 API를 부름 | 칸을 지우지 않고 더하기만 하면 대부분 괜찮음 |

## 4. 동작 원리: 롤링 배포 한 번

```
시간 →
app-2(8461)  [옛]──stop──(꺼짐)──run 새──(뜨는 중)──UP──────────────────[새]
app  (8460)  [옛]──────────────────────────────────────12초──stop──(꺼짐)──run 새──UP──12초──[새]
nginx        두 대에 나눔 │ app-2 연결 거부 → 실패 표시, 10초 동안 app만 │ 다시 app-2에도 │ app 실패 표시 … │ 두 대
사용자       계속 200 (실패한 요청은 nginx가 다른 앱으로 다시 보냄)
```

1. app-2에 SIGTERM. 처리 중인 요청은 마치고, 새 연결은 거부된다. nginx로 오는 다음 요청이 연결 거부 → `proxy_next_upstream`이 app으로 다시 보냄 → app-2를 10초 동안 뺌.
2. 새 app-2가 뜨고 readiness가 UP이 될 때까지 기다린다(최대 3분).
3. **12초 기다린다.** nginx가 app-2를 "사용 불가"로 표시해 둔 10초가 지나야 app-2를 다시 쓴다. 그 전에 app을 끄면 nginx 입장에서 둘 다 못 쓰는 순간이 생긴다.
4. app도 같은 순서.

## 5. 이 프로젝트에서는

### 5.1 학교 nginx 설정 파일

지원 계정의 `~/nginx/now-log.java21.net.conf`(학교 nginx가 읽는 가상 호스트 설정 파일). 바꾼 곳만:

```nginx
# [추가] 보낼 곳 목록. server 블록 바깥
upstream now_log_java21_net {
    server 127.0.0.1:8460 max_fails=1 fail_timeout=10s;
    server 127.0.0.1:8461 max_fails=1 fail_timeout=10s;
}

server {
    server_name now-log.java21.net;
    …                                         # 로그, client_max_body_size 20M 그대로
    location / {
        proxy_pass http://now_log_java21_net;   # [바꿈] 원래 http://127.0.0.1:8460

        proxy_next_upstream error timeout http_502 http_503;   # [추가]
        proxy_next_upstream_tries 2;
        proxy_connect_timeout 3s;

        …                                     # proxy_set_header 줄들 그대로
    }
    …                                         # Certbot이 넣은 443·인증서 줄 그대로
}
```

- `127.0.0.1`: nginx와 앱이 같은 서버라서. 원래 `proxy_pass`에 적힌 주소 그대로다.
- `upstream`은 `server { }` 바깥(http 단계)에만 쓸 수 있다.
- 처음 고칠 때 `http_502 http_502`로 503을 빠뜨리는 오타가 있었다. nginx 문법 검사로는 안 걸릴 수 있어서 눈으로 봐야 한다.
- 파일 수정은 지원이 한다. **reload는 관리자 권한(sudo)이 필요해 학생은 못 하고, 대신 서버가 10분마다 설정을 자동으로 다시 읽는다.** 그래서 고친 뒤 최대 10분이 지나야 반영된다.
- 새 설정에 문법 오류가 있으면 nginx는 새 설정을 버리고 옛 설정으로 계속 돈다. 사이트는 멀쩡해 보이는데 변경이 반영되지 않는 것이다. 학생 모두가 같이 쓰는 nginx이므로 고칠 때 `;`, `{ }` 짝, upstream 이름과 `proxy_pass` 이름이 같은지를 눈으로 꼼꼼히 본다.

### 5.2 헬스체크: `application.yml`

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health
      discovery:
        enabled: false
  endpoint:
    health:
      show-details: never
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,db,redis
  health:
    mail:
      enabled: false
```

| 줄 | 뜻과 이유 |
| --- | --- |
| `exposure.include: health` | Actuator의 여러 주소 중 health만 연다. `/actuator/env`(설정값)·`/actuator/beans` 같은 건 열지 않는다 |
| `discovery.enabled: false` | `/actuator`(열린 주소 목록)도 닫는다. 쓸 일이 없다 |
| `show-details: never` | 무엇이 왜 DOWN인지(DB 이름·주소)는 보이지 않는다. 이 주소는 nginx를 통해 바깥에도 열린다 |
| `probes.enabled: true` | `/actuator/health/liveness`, `/actuator/health/readiness`를 만든다 |
| `readiness.include` | 준비 = 다 떴음(`readinessState`) + DB 연결 + Redis 연결. 둘이 없으면 글 읽기·로그인이 안 된다. 그룹에 없는 이름을 넣으면 앱이 뜰 때 실패하므로 `db`, `redis` 이름이 맞는지도 앱이 확인해 준다 |
| `health.mail.enabled: false` | 메일 서버 접속 검사를 끈다. 메일 비밀번호가 없는 설정에서 `/actuator/health` 전체가 DOWN이 되고, 메일이 잠깐 안 된다고 글 읽기까지 막을 이유도 없다 |

보안 설정은 따로 열 필요가 없었다(`SecurityConfig`가 `/api/admin/**`만 막고 나머지는 `permitAll`). `/actuator/env`를 브라우저로 열면 화면용 index.html이 나온다(SPA 폴백, [SPA와 서버 라우팅](../4-웹과-프론트/06-SPA와-서버-라우팅.md)). 설정 정보는 새지 않는다.

확인: 테스트(`HealthIntegrationTest`)는 세 주소가 200 `{"status":"UP"}`이고 `components`가 없는지, 다른 actuator 주소가 열리지 않는지 본다. 운영에서도 `https://now-log.java21.net/actuator/health/readiness` → `{"status":"UP"}`.

### 5.3 꺼질 때 비동기 작업: 실험

임시 클래스로 앱이 뜨면 비동기로 "N초 기다리고 → DB 조회"를 하게 해 두고, 중간에 SIGTERM을 보냈다(실험 뒤 지움).

| 경우 | 로그 | 결과 |
| --- | --- | --- |
| 기본값, 8초 작업 | SIGTERM → 6초 뒤 `PROBE 끝까지 완료, DB 조회 결과 1` → `Closing JPA EntityManagerFactory` | 끝까지 돌았고 DB는 그 뒤에 닫힘 |
| 기본값, 45초 작업 | SIGTERM → 30초 뒤 `Shutdown phase … ends with 1 bean still running after timeout of 30000ms: [applicationTaskExecutor]` → DB 닫음 → `sleep interrupted` | 30초 한도에서 끊김 |
| `await-termination: true`, 45초 작업 | SIGTERM과 **같은 초에** `HikariPool-1 - Shutdown initiated...` → 20초 뒤 `Timed out while waiting for executor` | DB를 먼저 닫고 기다림 |

우리 작업은 임베딩(수 초), 메일(수백 ms)이라 기본값으로 끝까지 돈다. 서버가 뜰 때 빠진 임베딩을 채우는 `sync`는 30초를 넘으면 끊기지만 다음에 뜰 때 다시 채운다. 이 결과는 `global/config/AsyncConfig` 주석에 남겼다.

### 5.4 배포 스크립트: `deploy/deploy.sh`

**설정값**

```bash
# 바꾸는 순서대로 "이름:서버 포트". 처음 배포에는 2번이 없으므로 2번을 먼저 띄워야 1번을 바꾸는 동안에도 끊기지 않는다
APPS=(aigj017-app-2:8461 aigj017-app:8460)
# docker stop이 기다리는 시간. Spring은 처리 중인 HTTP 요청(최대 30초)과 비동기 작업(최대 30초)을 차례로 기다린다(AsyncConfig)
STOP_TIMEOUT=70
# nginx upstream의 fail_timeout(10초)보다 길게. 다시 뜬 앱을 nginx가 쓰기 시작하기 전에 다음 앱을 끄지 않게
NGINX_SETTLE=12
```

포트 8460~8469가 지원에게 배정된 포트다. 두 앱 모두 컨테이너 안에서는 8460으로 듣고(`-p 8461:8460`), 서버 포트만 다르다.

**준비 확인**

```bash
wait_ready() {
  for _ in $(seq 1 90); do
    if [ "$(docker inspect --format '{{.State.Running}}' "$1" 2>/dev/null)" != "true" ]; then
      echo "   $1 컨테이너가 멈췄습니다" >&2
      return 1
    fi
    if curl -fs -o /dev/null "http://127.0.0.1:$2/actuator/health/readiness"; then
      return 0
    fi
    sleep 2
  done
  echo "   $1이 3분 안에 준비되지 않았습니다" >&2
  return 1
}
```

- 2초마다 최대 90번(3분). 컨테이너가 멈추면 3분을 다 기다리지 않는다.
- `curl -f`는 200이 아닌 응답(DOWN이면 503)을 실패로 본다. 서버(호스트)에서 부르므로 이미지에 curl이 없어도 된다.

**한 대 바꾸기**

```bash
replace() {
  if docker inspect "$1" >/dev/null 2>&1; then
    docker stop -t "$STOP_TIMEOUT" "$1" >/dev/null || true
    docker rm "$1" >/dev/null
  fi
  run_app "$1" "$2" "$3"
  wait_ready "$1" "$2"
}
```

예전의 `docker rm -f`는 SIGKILL이라 처리 중인 요청이 끊겼다. `docker stop`으로 graceful shutdown을 하게 했다.

**되돌리기**

```bash
rollback() {
  local before="${before_image[$1]:-}"
  if [ -z "$before" ]; then
    # 이번 배포에서 처음 만든 앱(처음의 2번)이면 지운다
    echo "   $1: 배포 전에 없던 앱이라 지웁니다" >&2
    docker rm -f "$1" >/dev/null 2>&1 || true
  elif replace "$1" "$2" "$before"; then
    echo "   $1: 옛 이미지로 되돌렸습니다" >&2
  else
    echo "   $1: 옛 이미지도 뜨지 않았습니다. docker logs $1 을 확인하세요" >&2
    return 1
  fi
}
```

- `before_image`는 배포 전에 각 앱이 쓰던 이미지 **ID**다(`docker inspect --format '{{.Image}}'`). `docker load`가 `latest` 태그를 새 이미지로 옮겨 가므로 태그로는 옛 이미지를 가리킬 수 없다.
- 옛 이미지는 **두 대 모두 바뀐 뒤에만** 지운다. 스텝 24까지는 성공하면 바로 지워서 되돌릴 이미지가 없었다([CI CD](./05-CI-CD.md) 5.7).

**본 흐름과 실패 처리**

```bash
for entry in "${APPS[@]}"; do
  name="${entry%%:*}"; port="${entry##*:}"
  echo "== $name (서버 포트 $port) 바꾸기"
  if ! replace "$name" "$port" "$new_image"; then
    …
    # 되돌리기가 실패하면 그 앱은 죽어 있다. 이때 남은 앱(새 버전)까지 되돌리려고 끄면 살아 있는 앱이 0대가 되므로 그대로 둔다
    if rollback "$name" "$port"; then
      for (( i=${#done_apps[@]}-1; i>=0; i-- )); do
        if ! rollback "${done_apps[$i]%%:*}" "${done_apps[$i]##*:}"; then
          break
        fi
      done
    else
      echo "   이미 새 버전으로 바꾼 앱(${done_apps[*]:-없음})은 요청을 받고 있으므로 건드리지 않습니다" >&2
    fi
    exit 1
  fi
  done_apps+=("$entry")
  echo "   준비됨. nginx가 다시 쓰기 시작할 때까지 ${NGINX_SETTLE}초"
  sleep "$NGINX_SETTLE"
done
```

규칙은 하나다. **살아 있는 앱이 0대가 되는 순간을 만들지 않는다.**

| 실패 | 처리 | 이유 |
| --- | --- | --- |
| 첫 앱(app-2) 새 버전 | app-2만 옛 버전으로 | app은 아직 옛 버전으로 요청을 받는 중 |
| 둘째 앱(app) 새 버전 | app을 옛 버전으로 → 그다음 app-2도 옛 버전으로 | 버전이 섞인 채 계속 돌면 3.7의 JS 404가 계속 생김. 꺼져 있는 쪽(app)을 먼저 살려야 app-2를 끌 때 0대가 아님 |
| 되돌린 옛 버전도 안 뜸 | 거기서 멈춤, 새 버전으로 살아 있는 앱은 그대로 | 그 앱을 끄면 0대 |
| 처음 만든 app-2 | 지움 | 되돌릴 옛 버전이 없음 |

어느 경우든 `exit 1`이라 GitHub Actions 배포 잡이 실패로 표시되고 메일이 간다. 되돌렸어도 "이번 배포는 실패"다.

**Redis를 다시 만들지 않기**

```bash
if ! REDISCLI_AUTH="$REDIS_PASSWORD" docker exec -e REDISCLI_AUTH "$REDIS" redis-cli ping 2>/dev/null | grep -q PONG; then
  docker rm -f "$REDIS" >/dev/null 2>&1 || true
  docker run -d --name "$REDIS" … redis-server --requirepass "$REDIS_PASSWORD" --appendonly yes >/dev/null
fi
```

스텝 24까지는 "비밀번호가 바뀌었을 수 있으니" 배포마다 Redis를 다시 만들었다. 앱이 한 대일 때는 앱도 어차피 다시 뜨니 상관없었지만, 롤링에서는 **바꾸지 않는 동안 요청을 받는 앱이 Redis를 잃는다**(로그인·캐시). 지금 비밀번호로 PING이 되면 그대로 둔다. 비밀번호는 `-e 이름`으로 넘겨 명령줄에 찍히지 않게 한다([Docker와 서버](./03-Docker와-서버.md)). `redis-cli`는 `REDISCLI_AUTH` 환경 변수를 비밀번호로 쓴다.

### 5.5 서버 없이 시험하기: 가짜 docker

배포 스크립트는 서버에서 돌려 보기 전에 실패 경우를 확인하기 어렵다. 그래서 **가짜 `docker`·`curl`**을 만들어 `PATH` 앞에 두고 bash 5.2 컨테이너에서 돌렸다(맥의 bash는 3.2라 연관 배열 `declare -A`가 없다).

- 가짜 `docker`: 컨테이너 상태를 파일로 기억하고(이미지·실행 중·포트), 받은 명령을 기록한다. `FAIL="이름=이미지"`면 그 조합은 뜨자마자 멈춘다.
- 가짜 `curl`: 그 포트에 실행 중인 컨테이너가 있으면 성공.
- 가짜 `sleep`: 바로 끝남.

| 경우 | 최종 상태 |
| --- | --- |
| 첫 배포(app-2 없음) | 둘 다 새 버전 |
| 평소 | 둘 다 새 버전 |
| app-2 새 버전 실패 | 둘 다 옛 버전(app은 손대지 않음) |
| app 새 버전 실패 | 둘 다 옛 버전 |
| 첫 배포에서 app-2 실패 | app-2 지움, app 옛 버전 |
| app의 새·옛 버전 모두 실패 | app-2(새 버전) 살려 둠 |

마지막 경우에서 **스크립트 버그**를 찾았다. 처음 버전은 되돌리기가 실패해도 다음 앱을 계속 되돌리려 해서, 유일하게 살아 있던 app-2를 껐다. 되돌리기가 실패하면 멈추게 고쳤다. 가짜 환경 쪽 버그도 두 개 있었다(이미지 ID `sha:old`의 `:`를 포트 구분자로 잘라 버림, 출력 필터가 `REDIS_HOST`가 든 `docker run` 줄까지 거름). 시험 도구도 의심해야 한다.

배포 완료: …
```

서버에서:

```
aigj017-app     81cc523876ca  Up About a minute  0.0.0.0:8460->8460/tcp
aigj017-app-2   81cc523876ca  Up 2 minutes       0.0.0.0:8461->8460/tcp
aigj017-redis   redis:7.4     Up About an hour   6379/tcp

- 두 앱이 같은 이미지, app-2가 먼저 떴다.
- **Redis가 1시간 전에 만들어진 그대로다.** 옛 스크립트로 배포한 PR #3 때 만들어졌고, 이번 배포에서는 PING이 통해 다시 만들지 않았다.
- 두 앱 readiness 모두 UP, 메모리는 앱당 600MiB대(`docker stats`의 `/ 125.5GiB`는 상한이 없어 서버 전체가 표시된 것).

nginx upstream 반영(T139) 전까지는 nginx가 8460만 보므로, app을 바꾸는 동안 예전처럼 잠깐 끊긴다. 반영 뒤부터 무중단이다.

**반영 뒤 무중단 확인(2026-10-15, T139)**: 노트북에서 0.5초마다 사이트에 요청을 보내 둔 채 GitHub Actions "Run workflow"로 배포했다.

```bash
while true; do curl -s -o /dev/null -m 5 -w '%{http_code}\n' https://now-log.java21.net/; sleep 0.5; done | uniq -c
```

| 시각 (KST) | 일 |
| --- | --- |
| 13:02:36 | 요청 기록 시작 |
| 13:06:21 | `aigj017-app-2`(8461) 바꾸기 시작 |
| 13:06:47 | `aigj017-app`(8460) 바꾸기 시작 |
| 13:07:13 | 배포 완료 |

기록한 요청 362번이 모두 200이었다. 두 앱을 바꾸는 동안(13:06:15~13:07:20)에도 94번 모두 200이었다. 반영 전이었다면 app을 바꾸는 동안 502가 나왔어야 한다.

- **서버 안에서 사이트 주소로 curl을 보내면 `000`이 나온다.** 서버가 자기 공인 주소로 다시 들어가는 연결이 막혀 있어서다. 사이트로 보내는 요청은 노트북에서 보내야 한다(서버에서 앱을 직접 보려면 `127.0.0.1:8460`, `:8461`).
- **요청이 두 앱에 나뉘는지**는 nginx 로그를 볼 권한이 없어서, 서버에서 `docker stats --no-stream --format '{{.Name}} {{.NetIO}}' aigj017-app aigj017-app-2`로 두 앱이 보낸 양이 같이 늘어나는지 봤다. app-2는 nginx가 요청을 보내지 않으면 DB·Redis에 짧은 질의만 보내므로 보낸 양이 거의 늘지 않는다.

## 6. 자주 하는 실수와 함정

| 실수 | 무슨 일이 생기나 | 이렇게 |
| --- | --- | --- |
| 다음 앱을 정해진 시간 뒤 바로 끔 | 새 앱이 아직 안 떴으면 0대 | readiness UP을 확인한 뒤 |
| UP 확인 직후 다음 앱을 끔 | nginx가 다시 뜬 앱을 아직 빼 둔 상태(fail_timeout)라 둘 다 못 씀 | fail_timeout보다 길게 기다림 |
| 로그 한 줄로 "떴다" 판단 | DB·Redis 연결은 모름 | readiness 주소 |
| readiness에 외부 서비스를 다 넣음 | 메일·Ollama가 잠깐 느려도 배포가 실패·되돌림 | 꼭 필요한 것만(DB, Redis) |
| health details를 바깥에 공개 | 내부 구성·주소가 보임 | `show-details: never`, health만 노출 |
| `docker rm -f`로 끔 | SIGKILL, 처리 중인 요청이 끊김 | `docker stop -t` 충분히 |
| 옛 예제의 `await-termination: true` | DB를 먼저 닫고 기다림 | Boot 3.2 이상은 기본값 |
| 공용 컨테이너(Redis)를 배포마다 다시 만듦 | 요청 받는 앱이 상태를 잃음 | 살아 있으면 그대로 |
| 성공하자마자 옛 이미지 삭제 | 둘째 앱 실패 때 되돌릴 이미지가 없음 | 모두 끝난 뒤 삭제, 이미지는 ID로 |
| 되돌리기가 실패해도 다음 앱을 계속 되돌림 | 살아 있는 앱까지 꺼서 0대 | 실패하면 멈춤 |
| 스케줄 작업을 그대로 둔 채 앱을 늘림 | 같은 일이 두 번 | [트랜잭션과 동시성](../2-데이터/05-트랜잭션과-동시성.md) |
| 컬럼 삭제와 코드를 한 배포에 | 옛 앱이 오류, 되돌리기도 안 됨 | 늘리기 → 옮기기 → 줄이기 |
| 컨테이너 메모리 상한 없음 | JVM이 서버 전체 메모리를 기준으로 힙을 잡을 수 있음(공용 서버) | 앱마다 `--memory` 상한(남은 일) |

## 7. 직접 해 보기

서버에서(지원 계정):

```bash
# 두 앱과 이미지
docker ps --filter name=aigj017-app --format '{{.Names}}  {{.Image}}  {{.Status}}  {{.Ports}}'
# 둘 다 준비됐나
curl -s http://127.0.0.1:8460/actuator/health/readiness; echo
curl -s http://127.0.0.1:8461/actuator/health/readiness; echo
```

nginx 반영 뒤 **무중단 확인**: 터미널 하나에서

```bash
while true; do curl -s -o /dev/null -w '%{http_code}\n' https://now-log.java21.net/; sleep 0.5; done | uniq -c
```

를 돌려 두고, GitHub Actions의 deploy 워크플로를 "Run workflow"로 돌린다. 200만 이어지면 성공이다. 같은 방법으로 반영 전에 돌려 보면 app을 바꾸는 동안 502가 몇 줄 나오는 것도 볼 수 있다.

**한 대 끄기 실험**(배포 없이): `docker stop -t 70 aigj017-app-2`를 하는 동안 위 반복이 200인지 본다. 끝나면 `docker start aigj017-app-2`로 같은 컨테이너를 다시 띄우고 readiness가 UP인지 본다.

노트북에서 graceful shutdown 보기: 개발 서버를 8081로 띄우고(`./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081`) 그 PID에만 `kill -TERM`을 보낸 뒤 로그에서 `Commencing graceful shutdown`을 찾는다. 8080(평소 개발 서버)은 건드리지 않는다.

## 8. 확인 문제

1. 이 프로젝트의 이중화가 버티는 장애와 못 버티는 장애를 하나씩 말하라.
<details><summary>답</summary>앱 하나의 배포·재시작·멈춤은 버틴다. 서버 자체가 죽거나 DB·Redis가 죽는 것은 못 버틴다(각각 한 대, 같은 서버).</details>

2. 블루·그린 대신 롤링을 고른 이유 두 가지는?
<details><summary>답</summary>블루·그린은 배포마다 nginx가 보내는 곳을 바꿔야 하는데 학교 nginx는 학생이 reload할 수 없고 서버가 10분마다 다시 읽어서, 언제 바뀌는지 알 수 없다. 그리고 평소엔 한 대라 이중화가 아니다. 롤링은 upstream을 한 번만 넣으면 되고 평소에 두 대다.</details>

3. 무료 nginx는 앱이 "뜨는 중"인 걸 어떻게 아나?
<details><summary>답</summary>모른다. 능동 헬스 체크는 NGINX Plus 기능이다. 실제 요청이 연결 거부·시간 초과로 실패하면 그 서버를 fail_timeout 동안 빼는 수동 판단만 한다.</details>

4. 앱 하나가 꺼지는 순간 들어온 POST 요청은 두 번 저장될 수 있나?
<details><summary>답</summary>아니다. nginx는 멱등이 아닌 요청을 이미 서버에 보낸 뒤에는 다른 서버로 다시 보내지 않는다. 연결 자체가 거부된 요청만 다음 서버로 간다. 이미 받은 요청은 graceful shutdown으로 끝까지 처리된다.</details>

5. readiness와 liveness의 차이는? 배포 스크립트는 왜 readiness를 보나?
<details><summary>답</summary>liveness는 살아 있나, readiness는 요청을 받을 준비가 됐나다. 뜨는 중이거나 DB·Redis에 못 붙은 앱은 살아 있지만 준비되지 않았다. 다음 앱을 꺼도 되는지는 새 앱이 요청을 받을 수 있는지로 판단해야 한다.</details>

6. readiness 그룹에 메일을 넣지 않은 이유는?
<details><summary>답</summary>메일 서버가 잠깐 안 된다고 글 읽기까지 막을 이유가 없다. 넣으면 메일 문제로 배포가 실패·되돌려질 수 있고, 메일 비밀번호가 없는 설정에서는 늘 DOWN이 된다.</details>

7. readiness가 UP이 된 직후 다음 앱을 끄면 어떤 문제가 생길 수 있나?
<details><summary>답</summary>nginx는 방금 꺼졌던 앱을 fail_timeout(10초) 동안 "사용 불가"로 표시해 둔다. 그 사이 다른 앱을 끄면 nginx가 쓸 수 있는 앱이 없다. 그래서 12초 기다린다.</details>

8. `docker stop -t 70`의 70초는 어떻게 정했나?
<details><summary>답</summary>Spring은 종료 단계에서 처리 중인 HTTP 요청(최대 30초)과 비동기 작업(최대 30초)을 차례로 기다린다. 둘을 합친 60초보다 길게 줘야 강제 종료(SIGKILL) 전에 정리가 끝난다.</details>

9. `spring.task.execution.shutdown.await-termination=true`를 켜면 무엇이 나빠지나?
<details><summary>답</summary>종료 단계에서 스레드 풀을 기다리지 않고 DB 연결부터 닫은 뒤, 빈 정리 때 기다린다. 작업이 끝까지 돌아도 DB를 쓸 수 없다. 기본값은 DB가 열려 있는 종료 단계에서 최대 30초 기다린다.</details>

10. 배포 스크립트가 Redis를 배포마다 다시 만들면 롤링에서 무슨 일이 생기나?
<details><summary>답</summary>한 앱을 바꾸는 동안 요청을 받고 있는 다른 앱이 Redis를 잃는다. 그 몇 초 동안 로그인·캐시·연타 방지가 깨진다.</details>

11. 옛 이미지를 태그가 아니라 ID로 기억하는 이유, 그리고 언제 지우나?
<details><summary>답</summary>`docker load`가 `latest` 태그를 새 이미지로 옮겨 가서 태그로는 옛 이미지를 가리킬 수 없다. 두 대가 모두 새 버전이 된 뒤에만 지운다. 그 전에 지우면 둘째 앱이 실패했을 때 되돌릴 이미지가 없다.</details>

12. 둘째 앱(app)의 새 버전이 실패했을 때 app을 먼저 되돌리고 app-2를 나중에 되돌리는 이유는?
<details><summary>답</summary>app은 꺼져 있고 app-2(새 버전)만 요청을 받는 중이다. app-2를 먼저 끄면 0대가 된다. 꺼진 app을 옛 버전으로 먼저 살린 뒤 app-2를 바꿔야 한다.</details>

13. 되돌린 옛 버전도 뜨지 않으면 왜 나머지 앱을 건드리지 않나?
<details><summary>답</summary>그 앱은 죽어 있고, 새 버전으로 살아 있는 앱이 유일하게 요청을 받는다. 그것까지 되돌리려고 끄면 0대가 된다. 새 버전이라도 살아 있는 쪽을 지킨다.</details>

14. 롤링 배포 중 화면 JS 404가 생길 수 있는 이유는?
<details><summary>답</summary>JS 파일 이름에 해시가 있다. 새 앱에서 받은 index.html이 새 JS를 요청했는데 그 요청이 아직 옛 버전인 다른 앱으로 가면 그 파일이 없다. 새로고침하면 풀린다.</details>

15. 가짜 docker로 시험하는 것의 한계는?
<details><summary>답</summary>순서와 분기는 확인되지만 실제 docker 동작(포트 충돌, 이미지 로드, 컨테이너 상태 전이), 실제 앱 기동 시간, nginx 동작은 확인되지 않는다. 시험 도구 자체에도 버그가 있을 수 있다. 그래서 첫 실제 배포를 지켜보고 서버에서 상태를 확인했다.</details>

## 9. 더 읽을거리

- nginx 문서 `ngx_http_upstream_module`(`server`의 `max_fails`·`fail_timeout`), `ngx_http_proxy_module`(`proxy_next_upstream`, `non_idempotent`, `proxy_next_upstream_tries`)
- Spring Boot 문서 "Graceful Shutdown", "Kubernetes Probes"(liveness·readiness), "Actuator Endpoints / Health Groups"
- Spring Framework 문서 "Task Execution and Scheduling"(`ThreadPoolTaskExecutor`의 종료)
- Docker 문서 `docker stop`(SIGTERM과 `--time`)
- 쿠버네티스 문서 "Configure Liveness, Readiness and Startup Probes"(같은 개념을 플랫폼이 해 주는 모습)
