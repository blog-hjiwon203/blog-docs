# 59. 시간 칸 스냅숏: 인기 블로거, 더보기 중 순위 고정, 추천

> 관련 스텝: [스텝 20](../스텝-20.md) (T078~T081 인기 블로거·랭킹 전체보기·추천 블로그) · 관련 개념: [35 캐시: Spring Cache와 Redis](./35-Spring-Cache와-Redis.md)(꼭 먼저), [36 집계 쿼리로 순위 매기기](./36-집계-쿼리로-순위-매기기.md), [52 예약 작업과 프록시 자기 호출](./52-예약-작업과-프록시.md), [58 방문 통계](./58-방문-통계와-새벽-집계.md)(조회 기록 정리), [08 페이지 처리](./08-페이지네이션.md), [16 인가와 가시성 판단](./16-인가와-가시성.md)

## 1. 이 문서로 배우는 것

- "1시간마다 갱신되는 순위"를 만드는 두 방법: 정해진 때 도는 작업 vs **시간 칸(bucket)을 키로 한 캐시**
- **결정적(deterministic) 계산**: 언제 다시 계산해도 같은 답이 나오게 기간의 끝을 고정하기
- 순위 목록을 20개씩 **더보기** 할 때, 중간에 순위가 바뀌면 생기는 중복·누락과 `snapshotAt`으로 막기(409)
- 블로그 단위 점수: 글 활동 + 새 구독자, 7일 창
- 캐시에는 번호와 점수만, 볼 수 있는지는 읽을 때
- 추천 블로그: 순위에서 "나와 이미 구독한 것" 빼기
- 테스트에서 캐시와 시간대 다루기

## 2. 왜 필요한가

명세:

- HOME-04: "홈에 인기 블로거 5명을 보여 준다. 최근 7일 블로그 점수 순, 1시간마다 갱신."
- HOME-05: "인기 글·인기 블로거 '랭킹 전체보기'는 100위까지 20개씩 더보기. 홈과 같은 기준, 같은 시점이다. 더보기 중 순위가 새로 계산되면 알리고 처음부터 다시 보여 준다."
- SUB-06: "구독 피드에 추천 블로그 5개(자기 블로그와 이미 구독한 블로그 제외)."

인기 글(스텝 8, [35](./35-Spring-Cache와-Redis.md))은 "최근 1시간 점수를 5분 캐시"였다. 인기 블로거는 기간이 **7일**이라 계산이 더 무겁고, "1시간마다"라는 갱신 주기와 "홈·전체보기·추천이 같은 시점"이라는 조건이 붙는다.

## 3. 기본 개념

### 3.1 "1시간마다 갱신"을 만드는 두 방법

| | 정해진 때 도는 작업 | 시간 칸 캐시(이 프로젝트) |
| --- | --- | --- |
| 방법 | `@Scheduled(cron = "0 0 * * * *")`가 매시 정각에 계산해 Redis에 저장 | 요청이 오면 "지금 칸"(예: 18:00)을 키로 캐시를 찾고, 없으면 계산 |
| 서버가 막 켜졌을 때 | 다음 정각까지 순위가 비어 있음(켜질 때 한 번 더 돌려야 함) | 첫 요청이 계산 |
| 서버가 여러 대일 때 | 매시 여러 대가 같이 돔(한 대만 돌게 하는 장치 필요) | 누가 계산해도 같은 값(3.2) |
| 아무도 안 볼 때 | 그래도 계산 | 계산하지 않음 |

R-13의 원래 결정은 "스케줄러가 계산해 Redis에 저장"이었다. 결과(1시간마다, 상위 100, 기준 시각)는 같고 위 단점이 없어 시간 칸 캐시로 만들었다(research.md R-13 구현 메모).

### 3.2 결정적 계산: 기간의 끝을 고정한다

"최근 7일"을 **지금부터** 7일로 잡으면, 18:05에 계산한 값과 18:40에 계산한 값이 다르다. 그 사이 조회·공감이 늘었기 때문이다. 캐시가 비워져(TTL, Redis 재시작) 다시 계산하면 같은 18시 칸 안에서 순위가 바뀐다.

그래서 기간을 **정시로 자른다**.

```
지금 18:37 → 칸 = 18:00
점수 기간 = [10/4 18:00, 10/11 18:00)      ← 끝이 지금이 아니라 정시
기준 시각(snapshotAt) = 18:00
```

18:00 이후에 생긴 활동은 이 칸의 점수에 들어가지 않는다. 그러니 18:00~18:59 사이 언제 계산해도 같은 답이다. 이렇게 **입력이 같으면 언제 몇 번 계산해도 같은 결과**인 계산을 결정적이라고 한다. 결정적이면 캐시는 "계산을 아끼는 장치"일 뿐이고, 캐시가 사라져도 결과가 바뀌지 않는다.

19:00이 되면 칸이 바뀌어 키가 달라지고, 새 기간으로 계산한다. 이것이 "1시간마다 갱신"이다.

(정확히는 지난 칸 안의 행이 **지워지면** 다시 계산한 값이 달라질 수 있다. 예: 구독 취소는 구독 행을 지운다. 6장 참고.)

### 3.3 더보기 중 순위가 바뀌면

100위를 20개씩 받는다고 하자. 1~20위를 받은 뒤 순위가 새로 계산되어 21위였던 블로그가 15위로 올랐다.

```
처음 받은 것:  1 … 15(B) … 20
새 순위:       1 … 15(X) … 20, 21(B) …    ← 실제로는 X가 올라 B가 밀린 경우
다음 20개:     21(B) … 40                   ← B가 두 번 보임(중복)
```

반대로 내려간 블로그는 영영 안 보일 수 있다(누락). 커서 목록([08](./08-페이지네이션.md))이 "마지막으로 받은 행 다음"으로 이어 가는 것과 달리, 순위는 **모든 행의 자리가 한꺼번에 바뀌므로** 커서로도 해결되지 않는다.

해결은 "같은 순위표에서만 이어 받기"다.

1. 첫 요청의 응답에 그 순위표의 이름표 `snapshotAt`(기준 시각)을 준다.
2. 더보기 요청은 `snapshotAt`을 함께 보낸다.
3. 서버의 지금 순위표가 그 이름표와 다르면 **409 `RANKING_UPDATED`**와 새 기준 시각을 준다.
4. 화면은 "순위가 새로 계산됐습니다"를 알리고 처음부터 다시 받는다.

명세 HOME-05가 정한 동작이다. 409 Conflict는 "요청이 서버의 지금 상태와 충돌"을 뜻해 맞는다.

### 3.4 블로그 점수

```
블로그 점수 = 기간 안에 그 블로그의 공개 글이 받은 (조회 × 1 + 공감 × 3 + 댓글 × 5) + 새 구독자 × 10
```

- 글 점수와 같은 가중치(설정값 `app.popular.*`)에 구독을 더했다. 구독은 블로그 자체에 대한 관심이라 무겁게 둔다(`app.ranking.subscribe-weight: 10`).
- 기간은 7일(`app.ranking.blog-window: 7d`). 1시간이면 글 하나가 조금만 떠도 순위가 출렁여, 블로그 단위로는 너무 짧다(R-13).
- 비공개 글·숨김 글의 활동은 세지 않는다. 남이 볼 수 없는 글로 쌓은 점수가 순위에 드러나면 안 된다.

### 3.5 캐시에는 번호와 점수만

캐시에는 `(블로그 번호, 점수)` 100개와 기준 시각만 둔다([35](./35-Spring-Cache와-Redis.md) 3.2와 같은 생각).

- 블로그 이름·사진·구독자 수는 읽을 때 DB에서 가져온다. 이름을 바꾸면 바로 보인다.
- **볼 수 있는지도 읽을 때** 다시 본다. 18:10에 블로그가 이용 제한되면, 18:00 칸 캐시에 그 블로그가 있어도 응답에서 빠진다. 그래서 100위 목록이 실제로는 100개보다 적을 수 있다.

## 4. 동작 원리

```
[홈] GET /api/home/bloggers  (18:37)
  → RankingService.bloggers()
      hourStart = 18:00
      BloggerRanking 프록시.snapshot(18:00)      ← @Cacheable(key = "2026-10-11T18:00")
          캐시에 있으면 그대로
          없으면 BlogScoreRepository.topScores([10/4 18:00, 10/11 18:00), 가중치, 100) → 캐시에 저장
      번호로 블로그·주인 한 번에 읽기 → 볼 수 있고 이사하지 않은 것만, 순위 순서대로
  → 위 5개를 카드로 (구독자 수는 한 번에 세기)
  ← { snapshotAt: "2026-10-11T18:00:00+09:00", items: [5], nextOffset: null }

[랭킹 전체보기 첫 20] GET /api/ranking/bloggers
  ← { snapshotAt: 18:00, items: [1~20위], nextOffset: 20 }

[더보기] GET /api/ranking/bloggers?snapshotAt=2026-10-11T18:00:00%2B09:00&offset=20
  → 지금 칸이 18:00이면 같은 순위표의 21~40위, nextOffset: 40
  → 19:00이 지났으면 409 { code: RANKING_UPDATED, detail: { snapshotAt: "…19:00…" } }
       → 화면: 안내 + 처음부터 다시

[추천] GET /api/recommend/blogs  (로그인한 을)
  → 같은 순위표에서 을의 블로그와 을이 구독한 블로그를 빼고 위에서 5개
  → 카드에 그 블로그의 최근 글 제목
```

## 5. 이 프로젝트에서는

### 5.1 점수 SQL: `ranking/domain/BlogScoreRepository`

```sql
SELECT s.blog_id, SUM(s.weight) AS score
FROM (
    SELECT p.blog_id, a.weight
    FROM (
        SELECT post_id, :viewWeight AS weight FROM view_log WHERE viewed_at >= :since AND viewed_at < :until
        UNION ALL
        SELECT post_id, :likeWeight FROM post_like WHERE created_at >= :since AND created_at < :until
        UNION ALL
        SELECT post_id, :commentWeight FROM comment
        WHERE created_at >= :since AND created_at < :until AND deleted_at IS NULL AND is_blinded = 0
    ) a
    JOIN post p ON p.id = a.post_id
    WHERE p.status = 'PUBLISHED' AND p.visibility = 'PUBLIC' AND p.deleted_at IS NULL AND p.is_blinded = 0
    UNION ALL
    SELECT blog_id, :subscribeWeight FROM subscription WHERE created_at >= :since AND created_at < :until
) s
JOIN blog b ON b.id = s.blog_id
JOIN member m ON m.id = b.member_id
WHERE b.deleted_at IS NULL AND b.is_restricted = 0 AND b.moved_to_blog_id IS NULL
  AND m.status <> 'WITHDRAWN'
  AND NOT (m.status = 'SUSPENDED' AND (m.suspended_until IS NULL OR m.suspended_until > :until))
  AND EXISTS (SELECT 1 FROM post p2 WHERE p2.blog_id = b.id AND p2.status = 'PUBLISHED'
              AND p2.visibility = 'PUBLIC' AND p2.deleted_at IS NULL AND p2.is_blinded = 0)
GROUP BY s.blog_id
ORDER BY score DESC, s.blog_id DESC
LIMIT :limit
```

줄별로:

- 안쪽 `UNION ALL` 세 개: 글 활동 한 건 = 한 줄(글 번호, 가중치). 인기 글 SQL([36](./36-집계-쿼리로-순위-매기기.md) 3.2)과 같은 모양이다.
- `JOIN post … WHERE … PUBLIC …`: 공개 발행 글의 활동만 남기고, 글 번호를 **블로그 번호**로 바꾼다.
- 바깥 `UNION ALL`: 구독은 글이 아니라 블로그에 바로 붙으므로 따로 더한다.
- `:since`, `:until`: 3.2의 `[정시 − 7일, 정시)`. `< :until`(포함하지 않음)이 결정적 계산의 핵심이다.
- 블로그·주인 조건: 지운·이용 제한·이사한 블로그, 탈퇴·정지 중인 주인은 뺀다. 정지는 "기간이 정해져 있고 기준 시각에 아직 안 끝남"까지 본다(스텝 18의 "읽을 때 판단하는 정지 기간", [53](./53-서비스-관리와-제재-이력.md)). 기준을 `NOW()`가 아니라 `:until`로 둔 것도 결정적이게 하려는 것이다.
- `EXISTS (공개 글)`: 공개 글이 하나도 없는 블로그는 순위에 올리지 않는다. 구독자만 많고 볼 글이 없는 블로그가 홈에 뜨는 것을 막는다.
- `ORDER BY score DESC, s.blog_id DESC`: 동점이면 번호가 큰(나중에 만든) 블로그가 위. 정렬을 완전히 정해야 같은 데이터에서 늘 같은 순서가 나온다([36](./36-집계-쿼리로-순위-매기기.md) 3.4).
- 여기서 미리 걸러 100자리를 아낀다. 읽을 때 한 번 더 보는 것은 칸 안에서 바뀐 상태 때문이다(3.5).

### 5.2 시간 칸 캐시: `ranking/application/BloggerRanking`

```java
@Cacheable(cacheNames = CACHE, key = "#hourStart.toString()", sync = true)
public BloggerSnapshot snapshot(LocalDateTime hourStart) {
    return new BloggerSnapshot(hourStart, blogScoreRepository.topScores(
            hourStart.minus(rankingProperties.blogWindow()), hourStart,
            new BlogScoreRepository.Weights(popularProperties.viewWeight(), popularProperties.likeWeight(),
                    popularProperties.commentWeight(), rankingProperties.subscribeWeight()),
            CANDIDATES));
}
```

- `key = "#hourStart.toString()"`: SpEL로 인자를 키로 쓴다. Redis 키는 `blog:popularBloggers::2026-10-11T18:00`이 된다(접두사 `blog:`는 application.yml). 칸마다 다른 키다.
- `sync = true`: 캐시가 빈 순간 요청 100개가 몰려도 한 요청만 계산하고 나머지는 기다린다(캐시 쇄도 막기, [35](./35-Spring-Cache와-Redis.md) 3.8). 7일치 집계라 특히 중요하다.
- **TTL은 다른 캐시와 같은 5분**이다. 18시 칸이 5분마다 사라져 다시 계산되지만, 결정적이라 같은 답이 나온다. 칸을 1시간 동안 붙잡아 둘 필요가 없다.
- 호출하는 쪽(`RankingService`)이 `LocalDateTime.now(clock).truncatedTo(ChronoUnit.HOURS)`로 칸을 정한다. `truncatedTo(HOURS)`는 분·초·나노초를 0으로 만든다.
- 이 메서드는 `RankingService`라는 **다른 빈**이 부른다. 같은 클래스 안에서 부르면 프록시를 거치지 않아 캐시가 동작하지 않는다([52](./52-예약-작업과-프록시.md) 3.4).
- `BloggerSnapshot`과 `BlogScore`는 `Serializable` 레코드다. 이 프로젝트의 Redis 캐시는 Java 직렬화로 값을 저장하기 때문이다([35](./35-Spring-Cache와-Redis.md) 3.7).

### 5.3 같은 순위표에서만 이어 받기: `RankingService`

```java
@Transactional(readOnly = true)
public RankedBlogs bloggerPage(String snapshotAt, Integer offset) {
    int start = offset(offset);
    RankedBlogs all = bloggers();
    requireSameSnapshot(snapshotAt, all.snapshotAt());
    return new RankedBlogs(all.snapshotAt(), slice(all.blogs(), start));
}

private static void requireSameSnapshot(String requested, LocalDateTime current) {
    if (requested == null || requested.isBlank()) {
        return;
    }
    OffsetDateTime parsed;
    try {
        parsed = OffsetDateTime.parse(requested);
    } catch (DateTimeParseException e) {
        throw BusinessException.invalidField("snapshotAt", "기준 시각 형식이 올바르지 않습니다.");
    }
    OffsetDateTime now = DateTimes.toOffset(current);
    if (!parsed.toInstant().equals(now.toInstant())) {
        throw new BusinessException(ErrorCode.RANKING_UPDATED, Map.of("snapshotAt", now));
    }
}
```

- `snapshotAt`이 없으면 첫 요청이라 비교하지 않는다.
- 비교는 `toInstant()`로 **같은 순간인지**를 본다. `2026-10-11T18:00+09:00`과 `2026-10-11T09:00Z`는 글자는 다르지만 같은 순간이다. 문자열로 비교하면 다른 시간대 표기로 보낸 클라이언트가 늘 409를 받는다.
- 409의 `detail`에 새 기준 시각을 담는다. 화면이 "19:00 기준으로 처음부터 다시 보여 드릴게요"라고 알릴 수 있다.
- `offset`은 0~99만 받는다(100위까지). 아니면 400 `offset`.
- 인기 글 전체보기(`postPage`)도 같은 방식이다. 인기 글 순위표는 홈과 같은 5분 캐시(스텝 8)이고, 그 캐시는 처음부터 상위 100개와 계산 시각을 담고 있었다. 이번에는 100위까지 읽는 `HomeService.popularRanking(limit)`만 더했다(T078).

컨트롤러는 다음 묶음의 시작을 정한다.

```java
/** 다음 묶음의 시작. 이번 묶음이 20개가 안 되거나 100위에 닿으면 끝(null). */
private static Integer next(int start, int size) {
    int next = start + size;
    return size == RankingService.PAGE_SIZE && next < RankingService.MAX_RANK ? next : null;
}
```

### 5.4 추천: 순위에서 빼기

```java
public RankedBlogs recommend(Long viewerId) {
    RankedBlogs all = bloggers();
    Set<Long> subscribed = viewerId == null ? Set.of() : Set.copyOf(subscriptionRepository.findBlogIdsByMemberId(viewerId));
    List<Blog> picked = all.blogs().stream()
            .filter(blog -> !blog.isOwnedBy(viewerId))
            .filter(blog -> !subscribed.contains(blog.getId()))
            .limit(HOME_SIZE)
            .toList();
    return new RankedBlogs(all.snapshotAt(), picked);
}
```

- 새 계산 없이 **같은 순위표**에서 고른다. 그래서 홈 인기 블로거와 추천이 같은 기준·같은 시점이다(R-13).
- 구독한 블로그 번호를 한 번에 읽어 `Set`으로 만든다. 블로그마다 "구독했나?"를 물으면 100번 쿼리가 나간다.
- 비회원은 빼는 것이 없어 인기 블로거와 같다.
- 추천 카드에는 그 블로그의 **최근 글 제목**을 붙인다. "어떤 글을 쓰는 블로그인지" 보고 구독을 정하라는 것이다. 홈 카드에는 붙이지 않는다(카드 5개마다 쿼리 하나라, 꼭 필요한 곳에만).

### 5.5 화면

- **홈**(`pages/home/HomePage.tsx`): 인기 글 아래 "인기 블로거 최근 7일 · 18:00 기준"과 카드 5개, 오른쪽에 "랭킹 전체보기".
- **랭킹 전체보기**(`pages/ranking/RankingPage.tsx`, `/ranking`, `/ranking?tab=bloggers`): 인기 글·인기 블로거 탭, 기준 시각과 계산 방식 설명, 더보기. 머리글에 "랭킹" 링크.
- **구독 피드**(`pages/feed/FeedPage.tsx`): 아래에 "추천 블로그" 5개와 줄마다 구독 버튼. 피드가 비어 있어도 보인다(처음 온 사람이 구독할 곳을 찾게).
- 카드 한 줄은 `components/BlogCardItem.tsx` 하나를 홈·랭킹·추천이 같이 쓴다. 확인 중에 이 카드가 순위 목록용 3칸 grid(`.rank`)를 빌려 써서 4칸(순위·사진·이름·버튼)이 밀리는 문제가 있었다. 사진이 넓은 칸을 차지해 이름이 오른쪽 끝으로 밀렸다. 카드 전용 `.blog-card`(flex, 이름 칸만 늘어남)로 바꿨다.

409 처리:

```tsx
} catch (caught) {
  if (caught instanceof ApiError && caught.code === 'RANKING_UPDATED') {
    const next = String(caught.detail?.snapshotAt ?? '')
    setNotice(`순위가 새로 계산됐습니다. ${next ? formatTime(next) + ' 기준으로 ' : ''}처음부터 다시 보여 드릴게요.`)
    apply(await fetchFirst(tab))
  } else {
    setError(errorMessage(caught))
  }
}
```

- `fetchFirst(tab)`은 첫 묶음을 받기만 하는 함수, `apply`는 받은 것을 화면 상태로 바꾸는 함수다. 둘을 나눈 이유: `useEffect` 안에서 바로 `setState`를 부르면 린트 규칙(oxlint `set-state-in-effect`)에 걸린다. 받기는 effect에서, 바꾸기는 응답이 온 뒤에 하도록 나눴다. 409 뒤 다시 받을 때도 같은 두 함수를 쓴다.

Thymeleaf로 치면, 서버가 첫 페이지를 그릴 때 `<input type="hidden" name="snapshotAt">`을 심어 두고 "더보기" 폼이 그 값을 함께 보내는 것과 같다. 서버가 "그 순위표는 이제 없다"고 하면 첫 페이지로 다시 보내는 것이다.

### 5.6 테스트: `RankingIntegrationTest`

```java
@BeforeEach
void clearCaches() {
    cacheManager.getCache(BloggerRanking.CACHE).clear();
    cacheManager.getCache(PopularRanking.CACHE).clear();
}
```

- 테스트들은 같은 Redis를 쓴다. 앞 테스트가 만든 18시 칸 캐시가 남아 있으면 이 테스트에서 넣은 활동이 반영되지 않는다. 시작할 때 비운다.

`bloggersAreRankedBySevenDayScoreAndHiddenBlogsAreLeftOut`:

- 블로그 A(조회 200 + 새 구독자 1), B(조회 301), C를 만들고 활동 시각을 **2시간 전**으로 넣는다. 지금 칸(정시)보다 앞이어야 이번 칸 점수에 들어간다(3.2). 1분 전으로 넣으면 다음 칸에 들어가 이번 순위에 안 보인다.
- B를 이용 제한 → 점수는 가장 높아도 순위에 없다. `snapshotAt`은 `:00:00+09:00`으로 끝난다(정시).
- 추천: A를 구독한 독자에게 A가 없고, A의 주인에게도 A가 없다.
- 같은 `snapshotAt`으로 더보기 200, 다른 값이면 409와 `detail.snapshotAt` = 지금 기준 시각, `offset=100`은 400.
- **"1위가 A"를 확인하지 않는다.** 처음에는 그렇게 썼다가 전체 테스트를 돌리니 실패했다. 다른 테스트가 같은 DB에 만든 블로그가 더 높은 점수를 가질 수 있어서다. "순위 안에 A가 있고 B는 없다"로 바꿨다.

`rankingPostsUseTheHomeSnapshot`:

- 인기 글 전체보기와 홈 인기 글의 `snapshotAt`이 같은지 본다(같은 캐시).
- 조회 시각을 **자바에서 한국 시간으로** 만들어 넣는다. 처음에는 SQL의 `NOW() - INTERVAL 1 MINUTE`으로 넣었는데 실패했다. 테스트 DB 컨테이너의 `NOW()`는 UTC라 한국 시간보다 9시간 앞선 시각이 들어가고, "최근 1시간"에서 빠졌다. 블로거 테스트의 `NOW() - INTERVAL 2 HOUR`는 7일 창이라 9시간이 어긋나도 창 안이었을 뿐이다.

## 6. 자주 하는 실수와 함정

- **기간의 끝을 "지금"으로**: 캐시가 다시 계산될 때마다 같은 칸에서 순위가 바뀐다. 끝을 정시로 고정한다.
- **결정적이라고 믿고 끝냄**: 지난 칸 안의 행이 **지워지면**(구독 취소는 행 삭제, 탈퇴 정리) 다시 계산한 값이 조금 달라질 수 있다. 같은 칸에서 순위가 살짝 바뀌어도 `snapshotAt`은 같아 409가 나지 않는다. 지금 규모에서는 받아들였다. 정확히 하려면 칸이 처음 계산될 때 결과를 TTL 1시간 이상으로 고정하거나, 지우는 대신 "취소 시각"을 남긴다.
- **더보기를 offset만으로**: 중간에 순위가 바뀌면 중복·누락. 기준 시각을 함께 보내고 다르면 409.
- **기준 시각을 문자열로 비교**: 같은 순간의 다른 표기가 다르다고 나온다. `Instant`로 비교.
- **캐시에 블로그 이름·가시성까지 저장**: 이름 변경·이용 제한이 한 시간 늦게 반영된다. 번호와 점수만 두고 나머지는 읽을 때.
- **같은 클래스에서 `@Cacheable` 메서드 호출**: 캐시가 안 걸린다. 다른 빈에서 부른다.
- **비공개 글 활동까지 점수에**: 남이 못 보는 글이 순위로 드러난다.
- **테스트에서 캐시를 안 비움**: 앞 테스트의 칸이 남아 새 데이터가 안 보인다.
- **테스트에서 "1위는 X"**: 같은 DB를 쓰는 다른 테스트 데이터와 섞인다. 포함 여부나 상대 순서를 본다.
- **DB `NOW()`로 테스트 시각**: 컨테이너는 UTC, 앱은 한국 시간.
- **조회 기록을 1시간만 남김**: 블로거 점수가 7일을 본다. 7일 + 1시간 남긴다([58](./58-방문-통계와-새벽-집계.md) 5.4).

## 8. 확인 문제

1. 정해진 때 도는 작업 대신 시간 칸을 키로 한 캐시를 쓴 장점 세 가지는?
<details><summary>답</summary>서버가 막 켜져도 첫 요청이 계산해 비지 않는다. 서버가 여러 대여도 같은 값을 계산해 "한 대만 돌기" 장치가 필요 없다. 아무도 보지 않는 시간에는 계산하지 않는다.</details>

2. 점수 기간의 끝을 "지금"이 아니라 "정시"로 둔 이유는?
<details><summary>답</summary>그래야 같은 시간 칸 안에서 언제 다시 계산해도 같은 답이다(결정적). 캐시가 5분마다 사라지거나 Redis가 재시작해도 홈·전체보기·추천의 순위가 바뀌지 않는다.</details>

3. TTL이 5분인데 "1시간마다 갱신"이 되는 이유는?
<details><summary>답</summary>5분마다 캐시가 사라져 다시 계산해도 같은 칸이면 같은 기간이라 결과가 같다. 정시가 바뀌어야 키와 기간이 바뀌어 순위가 바뀐다.</details>

4. 랭킹 더보기를 offset만으로 하면 생기는 문제와, 커서로도 해결되지 않는 이유는?
<details><summary>답</summary>받는 사이 순위가 바뀌면 같은 블로그가 두 번 보이거나 어떤 블로그는 안 보인다. 순위는 모든 행의 자리가 한꺼번에 바뀌어 "마지막 행 다음"이라는 커서의 기준도 무의미해진다. 같은 순위표(snapshotAt)에서만 이어 받고, 바뀌면 409로 처음부터.</details>

5. 기준 시각 비교를 문자열이 아니라 Instant로 하는 이유는?
<details><summary>답</summary>18:00+09:00과 09:00Z는 같은 순간이지만 문자열은 다르다. 다른 시간대로 표기하는 클라이언트가 늘 409를 받게 된다.</details>

6. 캐시에 블로그 이름이나 "볼 수 있음"을 넣지 않은 이유는?
<details><summary>답</summary>이름 변경이나 이용 제한이 칸이 바뀔 때까지 반영되지 않는다. 번호와 점수만 캐시하고 나머지는 읽을 때 DB와 가시성 판단으로 본다.</details>

7. 테스트에서 활동 시각을 "1분 전"이 아니라 "2시간 전"으로 넣은 이유는?
<details><summary>답</summary>이번 칸의 점수 기간은 정시에서 끝난다. 1분 전 활동은 대개 정시 뒤라 다음 칸에 들어가 이번 순위에 안 보인다. 2시간 전이면 확실히 이번 칸 기간 안이다.</details>

8. 추천 블로그를 따로 계산하지 않고 인기 블로거 순위표에서 고르는 이유는?
<details><summary>답</summary>명세가 홈·전체보기·추천을 같은 기준·같은 시점으로 정했다(R-13). 같은 순위표에서 나와 구독한 블로그만 빼면 그 조건이 지켜지고 계산도 한 번이다.</details>

9. 같은 칸 안에서 순위가 조금 바뀔 수 있는 경우 하나는?
<details><summary>답</summary>칸 기간 안에 생긴 구독이 취소되면(구독 행 삭제) 그 뒤 다시 계산한 점수가 줄어든다. 탈퇴 정리로 행이 지워질 때도 마찬가지다.</details>
