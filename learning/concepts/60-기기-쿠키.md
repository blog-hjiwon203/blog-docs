# 60. 기기 쿠키: 남이 내 계정을 잠가도 내 브라우저는 들어오게

> 관련 스텝: [스텝 20](../스텝-20.md) (T055b) · 관련 개념: [40 시도 횟수 제한](./40-시도-횟수-제한.md)(꼭 먼저), [10 HTTP 쿠키](./10-HTTP-쿠키와-로그인-상태.md), [11 JWT](./11-JWT-로그인-토큰.md)(서명), [21 가입과 로그인](./21-가입-로그인-로그아웃.md), [55 모듈 경계](./55-모듈-경계와-ArchUnit.md)

## 1. 이 문서로 배우는 것

- 계정 잠금의 약점 **잠금 악용(lockout abuse)**과, OWASP가 권하는 **기기 쿠키(device cookie)** 방식
- 서버가 값을 저장하지 않고도 "내가 준 값"인지 확인하는 법: **HMAC 서명**
- 서명 비교를 **고정 시간**으로 해야 하는 이유
- 한 비밀 키를 여러 용도에 쓰지 않기(용도별 키 만들기)
- 시도 횟수의 **키를 바꾸는 것**으로 기능을 더하기: `login:{이메일}` → `login-device:{기기}`
- 이 방식이 막지 못하는 것

## 2. 왜 필요한가

스텝 9(T055a, [40](./40-시도-횟수-제한.md))에서 로그인 비밀번호를 **이메일마다 15분에 5번** 틀리면 15분 동안 막았다. 무차별 대입은 막혔지만 새 약점이 생겼다.

> 내 이메일을 아는 사람은 누구나, 일부러 5번 틀려서 나를 15분 동안 못 들어오게 할 수 있다. 15분마다 반복하면 계속.

이것이 잠금 악용이다. R-17은 이것을 두 겹으로 줄이기로 했다(2026-10-09 지원 결정).

1. **전에 로그인한 브라우저는 잠그지 않는다**(T055b, 이 문서).
2. 새 기기에서 잠긴 주인은 메일 링크로 푼다(T088, 메일 발송이 필요해 뒤로).

## 3. 기본 개념

### 3.1 잠금 악용과 기기 쿠키

OWASP의 "Slow Down Online Guessing Attacks with Device Cookies"가 제안하는 방식은 이렇다.

- 로그인에 **성공한** 브라우저에 "이 회원이 여기서 로그인했었다"는 쿠키를 준다.
- 로그인 시도가 이 쿠키를 가지고 오면, 실패 횟수를 이메일이 아니라 **그 기기**로 센다.
- 쿠키가 없는 시도(공격자, 처음 쓰는 기기)는 지금처럼 이메일로 센다.

```
공격자(쿠키 없음): 틀림×5 → "login:gap@x.com" 5회 → 이메일 잠김
나(기기 쿠키 있음): 맞는 비밀번호 → 키가 "login-device:Q3x…" → 0회 → 들어감
```

공격자는 내 브라우저의 쿠키를 가질 수 없으니 내 기기 키를 올릴 수 없다. 나는 평소 쓰던 브라우저로 계속 들어온다.

반대로 **기기 쿠키를 가진 사람이 틀리면** 그 기기 키가 오른다. 내 노트북을 잠깐 쓴 누군가가 5번 틀리면 그 노트북만 15분 막히고, 이메일은 막히지 않는다.

### 3.2 서버가 저장하지 않는 확인: HMAC 서명

기기 쿠키의 값이 그냥 `회원 번호`라면 누구나 `7`이라고 지어 보내 회원 7의 기기인 척할 수 있다. 값을 **서버만 만들 수 있게** 해야 한다. 방법은 두 가지다.

| 방법 | 어떻게 | 대가 |
| --- | --- | --- |
| 서버에 저장 | 임의 값을 만들어 DB·Redis에 "이 값 = 회원 7의 기기"로 저장, 올 때 찾아봄 | 저장소와 정리 작업이 필요 |
| **서명** | 값 뒤에 서버 비밀 키로 만든 서명을 붙임. 올 때 다시 계산해 같은지 봄 | 저장할 것이 없음. 대신 하나만 골라 무효로 만들기 어려움 |

**HMAC**(Hash-based Message Authentication Code)은 "비밀 키 + 메시지"로 만든 해시다.

```
서명 = HMAC-SHA256(비밀 키, "7.Q3xR…")
쿠키 = "7.Q3xR….서명"
```

- 비밀 키를 모르면 다른 메시지(`8.Q3xR…`)의 서명을 만들 수 없다. 메시지를 한 글자만 바꿔도 서명이 완전히 달라진다.
- 서버는 받은 메시지로 서명을 **다시 계산**해 붙어 온 서명과 같은지만 본다.
- JWT의 HS256 서명([11](./11-JWT-로그인-토큰.md))이 바로 HMAC-SHA256이다. 기기 쿠키는 JWT보다 단순한 형식(점 두 개로 나눈 세 칸)을 쓸 뿐 원리는 같다.

서명은 **암호화가 아니다**. 쿠키를 열면 회원 번호가 그대로 보인다. 숨길 필요가 없는 값이라 괜찮다(HttpOnly라 자바스크립트로는 읽지도 못한다).

### 3.3 임의 값(nonce)을 넣는 이유

`회원 번호.서명`만 쓰면 회원 7의 기기 쿠키는 **언제나 같은 값**이다. 한 번 새면 모든 기기에서 통한다. 그리고 "기기마다" 셀 수가 없다.

그래서 로그인할 때마다 128비트 임의 값(nonce, "한 번 쓰는 수")을 만들어 넣는다.

- 기기마다 다른 쿠키 → 시도 횟수 키도 기기마다 다르다(`login-device:{nonce}`).
- `SecureRandom`: 예측할 수 없는 난수. `java.util.Random`은 몇 개의 출력으로 다음 값을 맞힐 수 있어 보안 용도에 쓰면 안 된다.

### 3.4 고정 시간 비교

서명이 맞는지 `String.equals`로 비교하면, 앞 글자부터 비교하다 **다른 글자를 만나는 순간 멈춘다**. 첫 글자가 맞으면 아주 조금 더 오래 걸린다. 이 시간 차를 수없이 재면 서명을 한 글자씩 맞혀 갈 수 있다(타이밍 공격). 네트워크 너머에서는 어렵지만, 막는 비용이 거의 없으니 막는다.

`MessageDigest.isEqual(a, b)`는 길이가 같으면 **끝까지 다 비교**한다. 걸린 시간으로 몇 글자가 맞았는지 알 수 없다.

### 3.5 한 비밀 키를 두 용도에 쓰지 않기

서버에는 이미 JWT 서명용 비밀 키가 있다. 그 키를 그대로 기기 쿠키에도 쓰면, 어느 한쪽에서 만든 서명이 다른 쪽에서 통할 수 있는 길이 생긴다(지금 형식으로는 어렵지만 형식이 바뀌면 모른다). 그래서 **용도 이름을 붙여 다른 키를 만든다**.

```
기기 쿠키 키 = "device-cookie:" + JWT 비밀 키
```

설정할 비밀 값은 하나로 두면서 용도마다 다른 키가 된다. 정석은 HKDF 같은 키 유도 함수로 만드는 것이고, 이 프로젝트는 "용도 접두어 + 비밀"을 HMAC의 키로 쓰는 단순한 방식이다.

### 3.6 쿠키의 성질

| 속성 | 값 | 이유 |
| --- | --- | --- |
| 이름 | `device` | |
| 수명 | 1년(`Max-Age`) | "전에 로그인한 브라우저"라는 표시는 오래 유지돼야 쓸모 있다 |
| HttpOnly | 예 | 자바스크립트(XSS)로 훔쳐 가지 못하게 |
| 도메인 | 로그인 쿠키와 같음(`.blog.com`) | 로그인 API를 어느 주소에서 불러도 같은 쿠키 |
| 로그아웃 | 지우지 않음 | 로그아웃해도 "이 브라우저는 전에 로그인했었다"는 사실은 그대로 |

로그인할 때마다 새 값을 준다(nonce가 바뀜). 오래된 쿠키는 브라우저가 덮어쓴다.

## 4. 동작 원리

```
[로그인] POST /api/auth/login { email, password }  (Cookie: device=7.Q3x….sig 가 있을 수도)
  → AuthController.login
      deviceToken = 쿠키 "device"의 값(없으면 null)
      AuthService.login(email, password, deviceToken)
        attemptKey:
          DeviceTokens.verify(deviceToken) → 서명 맞음? → Device(7, "Q3x…")
            → 이 이메일의 회원 번호가 7인가?  맞으면 "login-device:Q3x…"
          아니면(없음, 서명 틀림, 다른 회원 것) "login:gap@x.com"
        AttemptLimiter.attempt(그 키, 비밀번호 확인)      ← IP별 20회 제한은 여기서 늘 함께
      성공 → 로그인 쿠키 + 새 기기 쿠키 device=7.Zk9….sig2 (1년)
```

## 5. 이 프로젝트에서는

### 5.1 만들기와 확인: `auth/application/DeviceTokens`

```java
@Component
public class DeviceTokens {

    private static final String PURPOSE = "device-cookie:";
    private static final Base64.Encoder ENCODER = Base64.getUrlEncoder().withoutPadding();

    private final SecureRandom random = new SecureRandom();
    private final byte[] key;

    public DeviceTokens(AuthProperties properties) {
        this.key = (PURPOSE + properties.jwtSecret()).getBytes(StandardCharsets.UTF_8);
    }

    /** 새 기기 값. */
    public String issue(Long memberId) {
        byte[] nonce = new byte[16];
        random.nextBytes(nonce);
        String body = memberId + "." + ENCODER.encodeToString(nonce);
        return body + "." + sign(body);
    }
```

- `PURPOSE + jwtSecret`: 3.5의 용도별 키.
- `new byte[16]` + `SecureRandom`: 128비트 임의 값(3.3).
- `Base64.getUrlEncoder().withoutPadding()`: 바이트를 쿠키에 넣을 수 있는 글자로. 일반 Base64의 `+`, `/`, `=`는 쿠키·주소에서 문제가 될 수 있어 URL용(`-`, `_`)에 패딩 없이 쓴다.

```java
    public Optional<Device> verify(String token) {
        if (token == null) {
            return Optional.empty();
        }
        String[] parts = token.split("\\.", -1);
        if (parts.length != 3) {
            return Optional.empty();
        }
        String body = parts[0] + "." + parts[1];
        // 서명 비교는 걸린 시간으로 몇 글자가 맞았는지 알 수 없게 고정 시간 비교를 쓴다
        if (!MessageDigest.isEqual(sign(body).getBytes(StandardCharsets.UTF_8), parts[2].getBytes(StandardCharsets.UTF_8))) {
            return Optional.empty();
        }
        try {
            return Optional.of(new Device(Long.parseLong(parts[0]), parts[1]));
        } catch (NumberFormatException e) {
            return Optional.empty();
        }
    }

    private String sign(String body) {
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(key, "HmacSHA256"));
            return ENCODER.encodeToString(mac.doFinal(body.getBytes(StandardCharsets.UTF_8)));
        } catch (NoSuchAlgorithmException | InvalidKeyException e) {
            throw new IllegalStateException(e);
        }
    }
```

- `split("\\.", -1)`: 점으로 나눈다(`.`은 정규식에서 "아무 글자"라 `\\.`로). `-1`은 끝의 빈 칸도 남기라는 뜻이다. `"7.abc."`를 기본 `split`은 2칸으로 줄이지만 `-1`이면 3칸(마지막이 빈 값)이 되어 형식 검사가 정확하다.
- 형식이 틀리거나 서명이 다르면 **예외 대신 빈 값**이다. 쿠키는 사용자가 마음대로 바꿀 수 있는 입력이라, 이상한 값은 "기기 쿠키 없음"으로 보고 지금처럼 이메일로 센다. 로그인 자체를 실패시키지 않는다.
- 서명을 확인한 **뒤에** 숫자로 바꾼다. 서명이 맞으면 서버가 만든 값이라 숫자가 맞다. `try`는 만일을 위한 것이다.
- `Mac.getInstance`는 호출마다 만든다. `Mac` 객체는 스레드에 안전하지 않아 여러 요청이 하나를 같이 쓰면 안 된다.

### 5.2 키 바꾸기: `AuthService.attemptKey`

```java
public Member login(String rawEmail, String password, String deviceToken) {
    String email = Emails.normalize(rawEmail);
    Member member = attemptLimiter.attempt(attemptKey(email, deviceToken), () -> { … 비밀번호 확인 … });
    …
}

/** 믿을 수 있는 기기(이 이메일 회원의 기기 쿠키)면 기기별, 아니면 이메일별 횟수. */
private String attemptKey(String email, String deviceToken) {
    return deviceTokens.verify(deviceToken)
            .filter(device -> memberRepository.findByEmail(email)
                    .map(member -> member.getId().equals(device.memberId()))
                    .orElse(false))
            .map(device -> "login-device:" + device.nonce())
            .orElse("login:" + email);
}
```

- **기능 전체가 "키 하나를 고르는 일"이다.** 시도 횟수 제한 장치(`AttemptLimiter`, [40](./40-시도-횟수-제한.md))는 그대로 두고, 무엇을 세는지만 바꾼다. 막힘·15분·429·성공 시 지우기가 모두 그대로 기기 키에도 적용된다.
- `filter(… 이 이메일의 회원 번호와 같은가)`: **다른 회원의 기기 쿠키로는 안 된다.** 공격자가 자기 계정으로 로그인해 받은 진짜 기기 쿠키를 들고 내 이메일로 시도하면, 서명은 맞지만 회원 번호가 달라 이메일 키로 센다. 이 조건이 없으면 공격자는 자기 기기 쿠키로 내 이메일을 무제한(기기 쿠키를 계속 새로 받아서) 시도할 수 있다.
- 가입하지 않은 이메일이면 `findByEmail`이 비어 `false` → 이메일 키. 가입 여부를 숨기는 기존 동작([40](./40-시도-횟수-제한.md))과 같다.
- **IP별 제한은 그대로**다. `AttemptLimiter.attempt`가 어떤 키든 IP 키(`attempt:ip:…`)를 함께 올린다.

### 5.3 쿠키 읽고 주기: `AuthCookieManager`, `AuthController`

```java
public MeResponse login(@Valid @RequestBody LoginRequest request, HttpServletRequest httpRequest,
                        HttpServletResponse response) {
    Member member = authService.login(request.email(), request.password(), cookieManager.deviceToken(httpRequest));
    cookieManager.login(response, member, request.keepLoggedIn());
    cookieManager.issueDevice(response, member.getId());
    …
}
```

- 쿠키를 다루는 일은 presentation 계층(`AuthCookieManager`)이, 판단은 application 계층(`AuthService`, `DeviceTokens`)이 한다. 서비스는 HTTP를 모르고 문자열 하나만 받는다([24](./24-계층-구조와-DTO.md)).
- `issueDevice`는 로그인 쿠키와 같은 도우미(`addCookie`)로 같은 도메인·HttpOnly·SameSite를 쓰고, 수명만 365일이다.
- 모두 `auth` 기능 안이다. 스텝 19b에서 인증의 속을 `auth`로 모았기 때문에([55](./55-모듈-경계와-ArchUnit.md)) 다른 기능을 건드리지 않고 더할 수 있었다.

### 5.4 테스트: `DeviceCookieIntegrationTest`

`ownerWithDeviceCookieStillLogsInWhenOthersLockTheEmail`:

1. 주인이 로그인 → 응답에 `device` 쿠키, HttpOnly.
2. 쿠키 없이 5번 틀림 → 쿠키 없이 맞는 비밀번호도 429(이메일 잠김).
3. **기기 쿠키를 들고** 맞는 비밀번호 → 200.
4. 다른 회원의 진짜 기기 쿠키 → 429. 지어낸 값(`{주인 번호}.abc.forged`) → 429.

`deviceItselfIsLockedAfterFiveFailures`:

1. 기기 쿠키를 들고 5번 틀림 → 기기 쿠키로 맞는 비밀번호도 429.
2. 쿠키 없이(다른 브라우저) 맞는 비밀번호 → 200. 기기 쪽만 셌으니 이메일은 안 막혔다.

이 기능 때문에 **기존 테스트가 깨졌다**. 로그인 응답의 쿠키를 "정확히 이 셋"으로 확인하던 `LoginIntegrationTest`, "브라우저를 다시 켜면 남는 쿠키"를 세던 `KeepLoggedInIntegrationTest`가 새 `device` 쿠키 때문에 실패했다. 두 테스트가 로그인 쿠키만 골라 보도록 고쳤다. 응답에 무언가를 더하면 "정확히 같다"로 확인하던 테스트가 깨진다. 그 테스트가 정말 확인하려던 것이 무엇인지(로그인 쿠키의 성질) 다시 보고 그것만 확인하게 고친다.

## 6. 자주 하는 실수와 함정

- **값을 서명 없이**: `7`만 넣으면 누구나 회원 7의 기기인 척한다.
- **서명만 확인하고 회원은 안 봄**: 공격자가 자기 계정의 진짜 기기 쿠키로 남의 이메일을 무제한 시도한다.
- **`equals`로 서명 비교**: 타이밍 공격. `MessageDigest.isEqual`.
- **`java.util.Random`으로 임의 값**: 예측 가능. `SecureRandom`.
- **JWT 키를 그대로 공유**: 용도별로 다른 키를 만든다.
- **이상한 쿠키에 예외**: 사용자가 쿠키를 바꾸면 로그인이 500. "쿠키 없음"으로 처리.
- **로그아웃 때 기기 쿠키도 지움**: 로그아웃 → 남이 잠금 → 나도 못 들어옴. 기기 표시는 남긴다.
- **기기 쿠키를 가진 시도는 아예 안 셈**: 내 노트북을 쓴 사람이 무제한으로 맞혀 볼 수 있다. 기기도 15분 5번.
- **이것으로 끝났다고 생각함**: 막지 못하는 것이 있다(아래).

막지 못하는 것:

- **새 기기의 주인**: 새 휴대폰, 쿠키를 지운 브라우저는 기기 쿠키가 없어 이메일 잠금에 걸린다. 메일 링크로 풀기(T088)가 두 번째 겹이다.
- **기기 쿠키를 훔친 사람**: 그 브라우저의 쿠키를 가져가면 그 기기로 15분 5번씩 시도할 수 있다. 하나만 골라 무효로 만드는 목록이 없다(서명 방식의 대가, 3.2). 비밀번호를 바꿔도 기기 쿠키는 그대로다. 막으려면 기기 값을 서버에 저장해 "이 회원의 기기 모두 무효" 같은 기능을 만든다.
- **비밀 키가 바뀌면**: JWT 비밀 키를 바꾸면 모든 기기 쿠키의 서명이 맞지 않아 "처음 쓰는 기기"가 된다. 로그인은 되고 다음 로그인에 새 쿠키를 받는다.

## 7. 직접 해 보기

1. 브라우저 A로 로그인 → 개발자 도구 → Application → Cookies에 `device`가 있다(HttpOnly 표시). 로그아웃해도 남아 있다.
2. 다른 브라우저(또는 curl)로 같은 이메일에 틀린 비밀번호 5번.

   ```bash
   for i in 1 2 3 4 5; do
     curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: blog.test' -H 'X-Requested-With: XMLHttpRequest' \
       -H 'Content-Type: application/json' -d '{"email":"gap@example.com","password":"wrong-pass"}' \
       http://localhost:8080/api/auth/login
   done
   ```

   마지막에 맞는 비밀번호로 한 번 더 → 429.
3. 브라우저 A에서 로그인 → 들어간다.
4. Redis에서 키를 본다.

   ```bash
   docker compose exec redis redis-cli --scan --pattern 'attempt:*'
   ```

   `attempt:login:gap@example.com`(이메일), `attempt:ip:…`가 보이고, A에서 틀려 보면 `attempt:login-device:…`가 생긴다.
5. `device` 쿠키 값의 마지막 글자 하나를 바꿔(개발자 도구에서 편집) 로그인해 보면, 서명이 틀려 이메일 키로 센다(이메일이 잠겨 있으면 429).

```bash
./mvnw test -Dtest=DeviceCookieIntegrationTest
```

## 8. 확인 문제

1. 이메일별 잠금만 있을 때 생기는 "잠금 악용"이란?
<details><summary>답</summary>내 이메일을 아는 누구나 일부러 5번 틀려 나를 15분 동안 못 들어오게 할 수 있고, 반복하면 계속 막을 수 있다.</details>

2. 서버에 아무것도 저장하지 않고 "내가 준 기기 쿠키"인지 확인하는 방법은?
<details><summary>답</summary>값 뒤에 서버 비밀 키로 만든 HMAC 서명을 붙인다. 받으면 값으로 서명을 다시 계산해 같은지 본다. 키를 모르면 맞는 서명을 만들 수 없다.</details>

3. 서명이 맞는 기기 쿠키인데도 이메일 키로 세는 경우는? 그 조건이 없으면 생기는 일은?
<details><summary>답</summary>쿠키의 회원 번호가 로그인하려는 이메일의 회원이 아닐 때. 없으면 공격자가 자기 계정으로 받은 진짜 기기 쿠키로 남의 이메일을 기기 키로 시도해 이메일 잠금을 피한다.</details>

4. 기기 쿠키에 임의 값(nonce)을 넣는 이유 두 가지는?
<details><summary>답</summary>기기마다 다른 값이라 기기별로 횟수를 셀 수 있다. 그리고 회원마다 늘 같은 값이 아니라서 하나가 새도 다른 기기 값이 되지 않는다.</details>

5. 서명 비교에 `String.equals` 대신 `MessageDigest.isEqual`을 쓰는 이유는?
<details><summary>답</summary>equals는 다른 글자를 만나면 멈춰 맞은 글자 수에 따라 시간이 달라진다(타이밍 공격). isEqual은 끝까지 비교해 시간으로 정보를 주지 않는다.</details>

6. 로그아웃해도 기기 쿠키를 지우지 않는 이유는?
<details><summary>답</summary>기기 쿠키는 "로그인 상태"가 아니라 "이 브라우저에서 전에 로그인했었다"는 표시다. 지우면 로그아웃한 뒤 남이 이메일을 잠갔을 때 나도 못 들어온다.</details>

7. 기기 쿠키를 가진 사람의 실패는 왜 세나?
<details><summary>답</summary>세지 않으면 내 기기를 잠깐 쓴 사람이 무제한으로 비밀번호를 맞혀 볼 수 있다. 기기도 15분 5번이면 막히고, 이메일 쪽은 세지 않아 다른 브라우저는 들어온다.</details>

8. 이 방식이 막지 못하는 경우 하나와, 그것을 위한 다음 작업은?
<details><summary>답</summary>새 기기나 쿠키를 지운 브라우저의 주인은 이메일 잠금에 걸린다. 메일 링크로 잠금을 푸는 T088(비밀번호 재설정과 함께)이 두 번째 겹이다.</details>
