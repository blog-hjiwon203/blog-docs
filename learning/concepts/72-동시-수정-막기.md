# 72. 동시 수정 막기: 갱신 손실, 조건부 UPDATE, 비관적·낙관적 잠금, advisory lock

> 관련 스텝: [스텝 25](../스텝-25.md) (T133~T135 이중화 준비) · 관련 개념: [23 트랜잭션과 동시성](./23-트랜잭션과-잠금.md)(비관적 잠금 처음), [33 격리 수준, 스냅샷, 데드락](./33-격리-수준과-데드락.md), [52 예약 작업과 프록시](./52-예약-작업과-프록시.md)(예약 발행), [58 방문 통계](./58-방문-통계와-새벽-집계.md)(새벽 모으기), [27 소프트 삭제와 일괄 수정](./27-소프트-삭제와-일괄-수정.md)(벌크 UPDATE와 수정 시각), [42 커밋 뒤 비동기 처리](./42-두-번째-DB와-비동기-처리.md), [73 이중화와 롤링 배포](./73-이중화와-롤링-배포.md)

## 1. 이 문서로 배우는 것

- **읽고 → 판단하고 → 쓰기**(read-modify-write) 코드에 왜 틈이 생기는지, 그 틈에서 생기는 **갱신 손실**(lost update)
- PostgreSQL 기본 격리 수준(READ COMMITTED)에서 **같은 행을 두 트랜잭션이 UPDATE하면** DB가 실제로 하는 일: 행 잠금, 기다림, WHERE 다시 확인. 그리고 DB가 **해 주지 않는** 일("읽은 뒤에 바뀌었나" 확인)
- JPA 변경 감지 UPDATE가 **모든 칸**을 `WHERE id = ?`로 쓰는 것이 왜 위험한가
- 틈을 막는 네 가지 도구와 고르는 기준
  - **조건부 UPDATE**(한 문장으로 확인하고 바꾸기, compare-and-set)
  - **비관적 잠금**(읽기 전에 `SELECT … FOR UPDATE`)
  - **낙관적 잠금**(`@Version`)
  - **advisory lock**(행이 아니라 번호에 거는 잠금)
- 틈의 길이로 도구 고르기: 한 요청 안의 짧은 틈과, 화면을 연 뒤 몇 분의 긴 틈
- 이 프로젝트에서 지원이 리뷰로 찾은 버그: 예약 발행 직전의 취소가 발행을 덮어쓰던 것

## 2. 왜 필요한가

스텝 25에서 앱을 두 대로 늘리기로 했다([73](./73-이중화와-롤링-배포.md)). 앱이 한 대일 때는 "이 서버 안에서 한 번만 돈다"고 믿던 코드가 두 대에서 동시에 돈다.

- 1분마다 도는 **예약 발행**이 두 앱에서 같은 글을 같이 발행한다. 글은 멀쩡해 보이지만 발행 이벤트(임베딩 만들기)가 두 번 나간다. 나중에 "구독자에게 새 글 알림"이 붙으면 알림이 두 번 간다.
- 매일 0시 10분의 **새벽 통계**가 두 앱에서 같이 "지우고 다시 넣기"를 한다. 한쪽이 UNIQUE 위반으로 실패한다.

그런데 고치다 보니 **앱이 한 대여도 있던 문제**가 함께 드러났다. 예약 발행 작업과 글쓴이의 요청은 원래 다른 스레드에서 동시에 돌 수 있었다. 작업이 글을 읽은 뒤 저장하기 전에 글쓴이가 제목을 고치면, 작업이 옛 제목으로 덮어썼다. 반대로 작업이 발행한 직후 글쓴이의 예약 취소가 발행을 덮어쓰기도 했다(5.4, 지원이 리뷰로 찾음).

동시성 버그는 테스트를 한 줄씩 돌려서는 드러나지 않는다. 그래서 **틈이 어디 있는지 읽어 내는 눈**과 **그 순간을 일부러 만드는 테스트**가 필요하다.

## 3. 기본 개념

### 3.1 읽고 → 판단하고 → 쓰기, 그리고 갱신 손실

글 수정 요청을 처리하는 코드는 대개 세 단계다.

```java
Post post = postRepository.findById(id);     // ① 읽기
if (post.isPublished()) throw ...;           // ② 판단: ①에서 읽은 값으로
post.changeTitle(newTitle);                  // ③ 쓰기: 트랜잭션 끝에 UPDATE
```

①과 ③ 사이에는 시간이 있다(몇 밀리초라도). 그 사이에 다른 트랜잭션이 같은 행을 바꾸고 커밋하면 이렇게 된다.

```
트랜잭션 A                         트랜잭션 B
① 읽기: title='옛', status=SCHEDULED
                                   ① 읽기: 같은 값
                                   ③ status=PUBLISHED로 쓰고 커밋
② 판단: (옛 값으로) 통과
③ 쓰기: title='새', status=SCHEDULED  ← B가 바꾼 status를 옛 값으로 되돌림
```

B의 수정이 흔적 없이 사라졌다. 이것이 **갱신 손실**(lost update)이다. 오류도 나지 않고 둘 다 "성공"한다는 점이 무섭다.

### 3.2 READ COMMITTED에서 UPDATE가 하는 일

PostgreSQL 기본 격리 수준은 READ COMMITTED다([33](./33-격리-수준과-데드락.md)). 여기서 두 가지를 정확히 알아야 한다.

**(1) 평범한 SELECT는 잠금에 막히지 않는다.** 다른 트랜잭션이 행을 UPDATE하고 아직 커밋하지 않았으면, SELECT는 기다리지 않고 **커밋된 옛 값**을 본다(MVCC). 그래서 위 ①은 B가 진행 중이어도 옛 값을 읽는다.

**(2) UPDATE는 행을 잠그고, 늦게 온 UPDATE는 기다렸다가 WHERE를 다시 본다.**

```
① 그 행을 다른 트랜잭션이 잠그고 있으면 커밋·롤백될 때까지 기다린다
② 풀리면 커밋된 최신 행으로 WHERE 조건을 다시 확인한다
③ 맞으면 그 행을 바꾸고, 안 맞으면 건너뛴다(0행)
```

여기서 흔한 오해가 있다. "내가 읽은 뒤 누가 바꿨으면 DB가 내 UPDATE를 취소해 주겠지." **아니다.** READ COMMITTED의 DB는 WHERE 조건만 다시 본다. "이 트랜잭션이 아까 읽은 값과 지금 값이 다른가"는 보지 않는다.

| UPDATE | 앞 트랜잭션이 status를 PUBLISHED로 커밋한 뒤 다시 보면 | 결과 |
| --- | --- | --- |
| `… WHERE id = 10 AND status = 'SCHEDULED'` | status가 조건에 안 맞음 | **0행**(덮어쓰지 않음) |
| `… WHERE id = 10` | id는 여전히 맞음 | **실행**(덮어씀) |

첫 줄이 "취소된 것처럼" 보이는 건 DB가 알아서 막아서가 아니라 **우리가 WHERE에 조건을 적었기 때문**이다.

"읽은 뒤 바뀌었으면 실패"를 DB가 해 주게 하려면 격리 수준을 REPEATABLE READ 이상으로 올린다. 그러면 PostgreSQL은 그런 UPDATE를 `could not serialize access due to concurrent update` 오류로 롤백한다. 대신 그 오류를 받아 다시 시도하는 코드가 필요하다. 이 프로젝트는 기본값(READ COMMITTED)을 쓴다.

### 3.3 변경 감지 UPDATE는 모든 칸을 `WHERE id = ?`로 쓴다

JPA는 트랜잭션이 끝날 때 영속성 컨텍스트의 엔티티를 처음 읽은 값과 비교해, 바뀐 것이 있으면 UPDATE를 보낸다(변경 감지, [06](./06-JPA와-엔티티-매핑.md)). Hibernate는 기본으로 **바뀐 칸만이 아니라 모든 칸**을 UPDATE 문에 넣는다(`@DynamicUpdate`를 붙이면 바뀐 칸만 쓴다. 이 프로젝트 엔티티에는 없다).

```sql
UPDATE post SET title=?, content_html=?, status=?, published_at=?, visibility=?, … WHERE id=?
```

그래서 제목만 고친 요청도 **처음 읽었던 status·published_at을 함께 다시 쓴다.** 3.1의 갱신 손실이 바로 이렇게 일어난다. 조건이 `WHERE id = ?`뿐이라 3.2의 다시 확인에도 걸리지 않는다.

### 3.4 틈을 막는 네 가지 도구

| 도구 | 어떻게 | 충돌하면 | 잘 맞는 곳 |
| --- | --- | --- | --- |
| **한 문장 UPDATE**(조건부 UPDATE, 원자적 증가) | 판단을 WHERE에 넣거나(`AND status='SCHEDULED'`), 계산을 SET에 넣어(`count = count + 1`) 읽기 없이 한 문장으로 | 0행(조용히 할 일 없음) | 판단이 단순하고 바꿀 칸이 정해진 일: 상태 바꾸기, 수 올리기 |
| **비관적 잠금** | 읽기 전에 `SELECT … FOR UPDATE`로 행을 잠금. 다른 쪽은 기다림 | 기다렸다가 최신 값으로 처리 | 읽고 복잡하게 판단한 뒤 여러 칸을 쓰는 일, 충돌해도 둘 다 반영돼야 하는 일 |
| **낙관적 잠금**(`@Version`) | 버전 칸을 두고 `UPDATE … WHERE id=? AND version=읽은값` | 0행 → `OptimisticLockException` → 사용자에게 다시 시도 | 충돌이 드물고, 기다리게 하기보다 알려 주는 게 나은 일. **요청이 여러 번에 걸치는 긴 틈** |
| **advisory lock** | 행이 아니라 우리가 정한 **번호**에 거는 잠금 | 못 잡으면 기다리거나(`pg_advisory_lock`) 바로 false(`pg_try_…`) | 여러 표를 건드리는 작업 전체를 한 곳에서만 돌리기 |

이름 때문에 헷갈리기 쉬운 점: **조건부 UPDATE는 "낙관적 잠금"과 닮았지만 같지 않다.** 둘 다 미리 잠그지 않고 쓰는 순간 WHERE로 확인한다. 하지만

- 낙관적 잠금은 "읽은 뒤 **아무 칸이든** 바뀌었나"(version)를 보고, 조건부 UPDATE는 "**이 일을 해도 되는 상태인가**"(status)만 본다.
- 낙관적 잠금은 읽기 → (시간) → 쓰기이고, 조건부 UPDATE는 **읽기 없이 한 문장**이라 틈 자체가 없다.

그리고 조건부 UPDATE도 "잠금이 없다"는 뜻은 아니다. DB는 UPDATE하는 행을 **언제나** 잠그고 커밋까지 쥔다. 다만 미리 잠그지 않을 뿐이다.

### 3.5 틈의 길이로 고르기

| 틈 | 예 | 맞는 도구 |
| --- | --- | --- |
| **짧다**: 한 요청(트랜잭션) 안, 밀리초 | 예약 발행 작업과 글쓴이 요청이 동시에 | 한 문장 UPDATE, 비관적 잠금 |
| **길다**: 화면을 연 뒤 저장할 때까지, 몇 분, 요청 여러 번 | 노트북과 휴대폰에서 같은 글을 열어 두고 각자 저장 | 낙관적 잠금 + 화면이 version을 들고 다니기 |

긴 틈은 비관적 잠금으로 막을 수 없다. 두 저장 요청이 시간상 겹치지 않기 때문이다. 화면을 열 때 받은 version을 저장할 때 같이 보내고, 서버가 비교해 "다른 곳에서 수정됐습니다"라고 알려 줘야 한다.

## 4. 동작 원리

### 4.1 조건부 UPDATE: 두 트랜잭션이 같은 글을 발행하려 할 때

```
앱1                                           앱2
SELECT id … WHERE status='SCHEDULED' → [10]   SELECT id … → [10]
UPDATE post SET status='PUBLISHED' …
 WHERE id=10 AND status='SCHEDULED'
 → 행 10 잠금, 1행
                                              UPDATE … WHERE id=10 AND status='SCHEDULED'
                                               → 행 10 잠금을 기다림
COMMIT → 이벤트 보냄
                                               → 풀림. 최신 행으로 WHERE 다시 확인
                                               → status='PUBLISHED'라 0행 → 이벤트 안 보냄
```

판단(SCHEDULED인가)과 쓰기가 한 문장 안에서 일어나서, 그 사이에 끼어들 틈이 없다. "1을 받은 쪽은 하나"를 DB가 보장한다.

### 4.2 비관적 잠금: 읽기 전에 잠그면

```
요청(예약 취소)                               작업
                                              UPDATE … → 행 10 잠금(커밋 전)
SELECT id FROM post WHERE id=10 FOR UPDATE
 → 잠금을 기다림
                                              COMMIT
 → 잠금을 얻음
SELECT … (엔티티 읽기) → status=PUBLISHED      ← 최신 값
판단: "발행한 글은 되돌릴 수 없다" → 400
```

순서가 반대면(요청이 먼저 잠금) 작업의 조건부 UPDATE가 기다렸다가 WHERE를 다시 보고 0행이 된다. **누가 먼저든 뒤쪽이 앞쪽 커밋을 보고 판단한다.** 두 일이 한 줄로 선다.

잠금은 반드시 **엔티티를 읽기 전에** 걸어야 한다. 먼저 읽고 나서 잠그면 이미 옛 값을 들고 있다. READ COMMITTED는 문장마다 최신 커밋을 보므로, 잠근 뒤의 SELECT는 최신 값을 읽는다.

### 4.3 낙관적 잠금: `@Version`

```java
@Version
private Long version;
```

Hibernate가 UPDATE에 버전 조건을 붙이고 버전을 올린다.

```sql
UPDATE post SET …, version = 4 WHERE id = 10 AND version = 3
```

0행이면 그사이 누가 바꾼 것이라 `OptimisticLockException`을 던지고 트랜잭션이 롤백된다. 받는 쪽(컨트롤러·화면)이 처리해야 한다. 벌크 UPDATE(`@Modifying @Query`)는 기본으로 버전을 올리지 않는다는 점도 알아 둔다.

### 4.4 advisory lock

행이나 표가 아니라 **64비트 번호**에 거는 잠금이다. 번호의 뜻은 앱이 정한다("1 = 새벽 통계").

| 함수 | 못 잡으면 | 풀리는 때 |
| --- | --- | --- |
| `pg_advisory_lock(n)` | 기다림 | `pg_advisory_unlock(n)` 또는 **연결**이 끊길 때 |
| `pg_try_advisory_lock(n)` | 바로 false | 위와 같음 |
| `pg_advisory_xact_lock(n)` | 기다림 | **트랜잭션**이 끝날 때 |
| `pg_try_advisory_xact_lock(n)` | 바로 false | 트랜잭션이 끝날 때 |

연결 단위(`xact`가 없는 것) 잠금은 커넥션 풀과 같이 쓰면 위험하다. 풀은 연결을 닫지 않고 돌려쓰므로, 푸는 것을 잊으면 그 연결을 받은 다른 요청이 잠금을 쥔 채가 된다. 트랜잭션 단위(`xact`)는 커밋·롤백 때 저절로 풀려 이런 실수가 없다.

여러 앱에서 예약 작업을 하나만 돌리게 해 주는 라이브러리 **ShedLock**도 같은 일을 한다(잠금 표를 만들어 씀). DB가 PostgreSQL 하나라면 advisory lock으로 충분하다.

## 5. 이 프로젝트에서는

### 5.1 예약 발행: 엔티티 저장 → 조건부 UPDATE

**바꾸기 전**(스텝 17, [52](./52-예약-작업과-프록시.md) 5.3)은 예약 글을 엔티티로 읽고 고쳐 저장했다.

```java
List<Post> due = postRepository.findAll(/* SCHEDULED, 시각 지남 */);
for (Post post : due) {
    post.publishScheduled();            // 엔티티 필드를 바꿈 → 트랜잭션 끝에 모든 칸 UPDATE
    events.publishEvent(new PostContentChangedEvent(post.getId()));
}
```

두 앱이 같은 글을 읽으면 둘 다 이벤트를 보내고(4.1의 반대), 읽은 뒤 글쓴이가 고친 제목을 옛 값으로 덮어썼다(3.1).

**바꾼 뒤**: `post/domain/PostRepository.java`

```java
/** 예약 시각이 지금이거나 지난 예약 글 번호 (POST-13). 지운 글은 뺀다. 발행은 글마다 publishIfDue로 한다. */
@Query("select p.id from Post p where p.status = com.nhnacademy.blog.post.domain.PostStatus.SCHEDULED"
        + " and p.deletedAt is null and p.scheduledAt <= :now")
List<Long> findDueScheduledIds(@Param("now") LocalDateTime now);

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Post p set p.status = com.nhnacademy.blog.post.domain.PostStatus.PUBLISHED,"
        + " p.publishedAt = p.scheduledAt, p.visibility = com.nhnacademy.blog.post.domain.Visibility.PUBLIC,"
        + " p.scheduledAt = null"
        + " where p.id = :id and p.status = com.nhnacademy.blog.post.domain.PostStatus.SCHEDULED"
        + " and p.deletedAt is null and p.scheduledAt <= :now")
int publishIfDue(@Param("id") Long id, @Param("now") LocalDateTime now);
```

- `findDueScheduledIds`: 엔티티가 아니라 **번호만** 읽는다. 제목을 손에 들지 않으니 옛 제목으로 덮어쓸 수도 없다.
- `publishIfDue`의 WHERE: `status = SCHEDULED`(아직 예약인가), `deletedAt is null`(지우지 않았나), `scheduledAt <= now`(시각을 미루지 않았나). 번호를 읽은 뒤 이 중 하나라도 바뀌면 0행이다.
- SET은 **발행에 필요한 칸만** 바꾼다. 제목·본문은 건드리지 않는다.
- `p.publishedAt = p.scheduledAt, …, p.scheduledAt = null`: SQL의 SET 오른쪽은 **바꾸기 전 행 값**을 본다. 그래서 publishedAt에는 지우기 전의 예약 시각이 들어간다.
- 반환값 `int`: 바뀐 행 수(0 또는 1).
- 벌크 UPDATE라 JPA Auditing(`@LastModifiedDate`)을 거치지 않아 **`updated_at`이 바뀌지 않는다**([27](./27-소프트-삭제와-일괄-수정.md)). 예전에는 발행 순간이 수정 시각으로 남아 예약 발행 글에 "수정 …"이 붙을 수 있었는데 그것도 없어졌다.
- `clearAutomatically`·`flushAutomatically`: 벌크 UPDATE는 영속성 컨텍스트를 거치지 않으므로, 전에 고친 엔티티를 먼저 내보내고(flush) 끝난 뒤 컨텍스트를 비운다(clear). 같은 트랜잭션에서 옛 값을 든 엔티티를 쓰지 않게 하려는 것이다.

`post/application/ScheduledPublisher.java`

```java
@Transactional
public int publishDue() {
    LocalDateTime now = LocalDateTime.now(clock);
    int published = 0;
    for (Long id : postRepository.findDueScheduledIds(now)) {
        // 0이면 다른 앱이 먼저 발행했거나, 그사이 예약이 바뀌었다
        if (postRepository.publishIfDue(id, now) == 1) {
            events.publishEvent(new PostContentChangedEvent(id));
            published++;
        }
    }
    return published;
}
```

**1을 받은 쪽만** 이벤트를 보낸다. 이벤트에는 **번호만** 싣는다(`PostContentChangedEvent(Long postId)`). 받는 쪽 `PostEmbeddingListener`는 `@TransactionalEventListener`(기본 AFTER_COMMIT)라서 이 트랜잭션이 커밋된 뒤에 돌고, `PostEmbeddingService.refresh`가 DB에서 글을 **다시 읽어** 임베딩을 만든다. 그래서 "이벤트에 옛 제목이 실린다"는 일은 생기지 않는다([42](./42-두-번째-DB와-비동기-처리.md)).

### 5.3 새벽 통계: advisory lock

`manage/domain/BlogStatsRepository.java`

```java
/** 새벽 모으기 잠금 번호. advisory lock은 번호에 거는 잠금이고 번호의 뜻은 앱이 정한다(이 앱에서 쓰는 번호는 이것 하나). */
private static final long AGGREGATION_LOCK = 1L;

public boolean tryLockAggregation() {
    return Boolean.TRUE.equals(jdbc.queryForObject("SELECT pg_try_advisory_xact_lock(?)", Boolean.class,
            AGGREGATION_LOCK));
}
```

`manage/application/StatsAggregator.java`

```java
@Scheduled(cron = "${app.scheduling.stats-cron:0 10 0 * * *}")
@Transactional
public void run() {
    if (!blogStatsRepository.tryLockAggregation()) {
        log.info("통계 모으기 건너뜀: 다른 앱이 모으는 중");
        return;
    }
    …  // 지난 7일 지우고 다시 넣기, 누적 다시 계산, 오래된 기록 지우기
}
```

- 왜 조건부 UPDATE가 아니라 advisory lock인가: 이 작업은 여러 표를 지우고 넣는 **묶음**이다. 행 하나의 조건으로 "누가 할지"를 표현할 수 없다.
- 왜 동시 실행이 문제인가: 앱1이 `DELETE stat_date = D` → `INSERT`(커밋 전), 앱2가 `DELETE`를 하면 앱1이 새로 넣은 행은 앱2의 DELETE가 시작할 때 없던 행이라 지우지 못하고 지나간다. 이어서 앱2의 `INSERT`가 UNIQUE `(blog_id, stat_date)`에 걸린다.
- `try`: 진 앱은 기다리지 않고 끝난다. `xact`: `run()`의 트랜잭션이 끝나면 저절로 풀린다. `JdbcTemplate`도 같은 트랜잭션(같은 연결)을 쓰므로 모으기 내내 잠금이 유지된다.
- 앱1이 끝난 **뒤에** 앱2가 실행돼 또 모으는 것은 괜찮다. 지우고 다시 넣는 작업이라 결과가 같다([58](./58-방문-통계와-새벽-집계.md)의 "몇 번 돌려도 같다"). 막아야 하는 것은 **겹치는 것**뿐이다.
- 덕분에 스케줄 작업을 "앱1에서만 켜기"로 하지 않고 **두 앱 모두 켠다.** 앱1이 배포로 꺼져 있어도 앱2가 한다.

테스트(`StatsIntegrationTest.onlyOneAppAggregatesAtATime`)는 다른 스레드가 트랜잭션 안에서 잠금을 쥔 채 기다리게 해 두고 `run()`을 불러 아무것도 모으지 않는지, 잠금이 풀린 뒤에는 모으는지 본다. 잠금 없는 코드로 돌리면 `Expecting empty but was: [1]`로 실패한다.

### 5.4 지원 리뷰로 찾은 버그: 발행 직전의 예약 취소

조건부 UPDATE로 "작업이 글쓴이 수정을 덮어쓰는 것"은 막혔다. 지원이 PR #3 리뷰에서 반대 방향을 짚었다.

> 1. 예약 발행 작업이 조건부 UPDATE(`WHERE status = 'SCHEDULED'`)로 글을 PUBLISHED로 바꿨지만, 아직 커밋하기 전이다.
> 2. 이때 사용자가 예약 취소·수정을 요청한다. 요청은 글을 읽을 때 커밋된 값만 보므로 아직 SCHEDULED로 읽는다.
> 3. 그래서 "발행한 글은 임시저장으로 되돌릴 수 없다" 검사를 통과하고, 해당 글의 상태를 DRAFT/SCHEDULED로 바꾼다.
> 4. 1의 작업이 커밋하고 발행 이벤트(임베딩)가 나간다.
> 5. 이어서 2의 요청이 실행되어 글이 발행 전 상태로 덮어써진다.

3.2와 3.3을 겹치면 정확히 이렇게 된다. 요청의 ①읽기는 잠금에 막히지 않아 옛 값(SCHEDULED)을 보고(3.2의 1), 판단은 옛 값으로 통과하고, ③쓰기는 `WHERE id = ?`뿐인 모든 칸 UPDATE라 작업의 잠금이 풀린 뒤 그대로 덮어쓴다(3.2의 2, 3.3).

- 결과: 발행 이벤트는 나갔는데 글은 조용히 DRAFT로 돌아가고, "발행한 글은 되돌릴 수 없다"는 규칙이 뚫린다.
- 앱이 한 대여도 생긴다(작업 스레드와 요청 스레드).
- 같은 패턴을 찾아보니 **관리 화면 일괄 공개 범위 변경**도 같았다. 공개 범위만 바꿨는데 발행이 SCHEDULED로 되돌아갔다(테스트로 재현).

**고친 것**: 글을 고치는 요청이 엔티티를 **읽기 전에** 행을 잠근다. `post/application/PostService.java`

```java
@Transactional
public Post edit(Blog blog, Long postId, LoginMember member, PostCommand command) {
    lockForChange(postId);
    Post post = findEditable(blog, postId, member);
    …
}

private void lockForChange(Long postId) {
    postRepository.lockById(postId);
}
```

`changeVisibility`, `delete`도 첫 줄이 `lockForChange(postId)`다. `lockById`는 공감·댓글이 이미 쓰던 잠금이다([23](./23-트랜잭션과-잠금.md)).

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p.id from Post p where p.id = :postId")
Optional<Long> lockById(@Param("postId") Long postId);
```

여러 글을 한 번에 고치는 곳(`ManagePostService.changeVisibility`, `BlogMoveService.movePosts`)은 `lockAllById`를 쓴다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p.id from Post p where p.id in :ids order by p.id")
List<Long> lockAllById(@Param("ids") Collection<Long> ids);
```

`order by p.id`가 중요하다. 두 요청이 [3, 7]과 [7, 3] 순서로 잠그면 각자 하나씩 쥐고 상대를 기다리는 **데드락**이 생긴다. 늘 번호 순서로 잠그면 이 순환이 생기지 않는다([33](./33-격리-수준과-데드락.md)).

### 5.5 그 순간을 테스트로 만들기

"작업이 UPDATE는 했고 아직 커밋하기 전"은 아주 짧은 순간이라 그냥 돌려서는 거의 안 걸린다. 테스트가 그 순간을 고정한다.

```java
private int whilePublishing(long post, Callable<ResultActions> request) throws Exception {
    CountDownLatch published = new CountDownLatch(1);
    CountDownLatch commit = new CountDownLatch(1);
    ExecutorService pool = Executors.newFixedThreadPool(2);
    try {
        Future<Integer> job = pool.submit(() -> transactions.execute(tx -> {
            int changed = postRepository.publishIfDue(post, LocalDateTime.now());
            published.countDown();   // UPDATE 했다고 알리고
            await(commit);           // 커밋하지 않고 멈춤
            return changed;
        }));
        assertThat(published.await(10, TimeUnit.SECONDS)).isTrue();

        Future<Integer> response = pool.submit(() -> request.call().andReturn().getResponse().getStatus());
        waitUntilSomeoneWaitsForALock();   // 요청이 잠금을 기다리기 시작할 때까지
        commit.countDown();                // 이제 작업 커밋

        assertThat(job.get(10, TimeUnit.SECONDS)).isEqualTo(1);
        return response.get(10, TimeUnit.SECONDS);
    } finally {
        commit.countDown();
        pool.shutdown();
    }
}
```

- `TransactionTemplate`(`transactions.execute`)으로 트랜잭션을 직접 열고, 그 안에서 멈춰 "커밋 전"을 붙잡는다.
- `waitUntilSomeoneWaitsForALock()`은 `pg_stat_activity`에서 `wait_event_type = 'Lock'`인 연결이 생길 때까지 100ms씩 본다. "요청이 잠금에 막혔다"를 확인하고 나서 커밋해야 순서가 매번 같다. `Thread.sleep`으로 "아마 막혔겠지" 하고 기다리면 느린 PC에서 순서가 바뀐다.

| 테스트 | 잠금 없는 코드 | 고친 코드 |
| --- | --- | --- |
| 발행 직전 예약 취소 | 200, DRAFT로 덮어씀 | **400**, PUBLISHED 유지 |
| 발행 직전 일괄 공개 범위 변경 | **SCHEDULED로 되돌아감** | PUBLISHED 유지, 공개 범위만 바뀜 |

### 5.6 이제 순서는 어떻게 되나

| 경우 | 결과 |
| --- | --- |
| 발행 전에 제목 수정(예약 시각 그대로) | 요청이 저장 → 작업이 기다렸다가 WHERE 확인 → **고친 내용으로 발행** |
| 발행 전에 예약 시각 미룸 | 작업은 `scheduledAt <= now`에 안 맞아 0행 |
| 발행 전에 예약 취소 | 작업은 status가 DRAFT라 0행 |
| 발행 직후 "지금 발행"(예약 체크 끔) + 내용 수정 | 요청이 PUBLISHED를 보고 `publish()`는 아무것도 안 바꾸고 내용만 저장 → **둘 다 반영** |
| 발행 직후 예약 유지한 채 저장, 임시저장 | **400**("이미 발행한 글은 예약할 수 없습니다", "발행한 글은 임시저장으로 되돌릴 수 없습니다"). 덮어쓰지 않고 알려 준다 |

### 5.7 왜 `@Version`이 아니라 비관적 잠금인가

`@Version`으로도 5.4는 막힌다(요청의 UPDATE가 0행 → 예외 → 롤백). 그래도 비관적 잠금을 고른 이유(PR #3 지원 댓글로 남김):

1. **충돌해도 둘 다 반영된다.** 기다렸다가 최신 상태로 처리하므로, 발행 직후 내용만 고친 요청은 200이다. `@Version`이면 409로 거절되고 사용자가 다시 저장해야 한다.
2. **추가로 처리할 것이 없다.** `@Version`이면 409 응답·화면 안내·재시도, 그리고 작업 쪽도 한 글의 충돌이 같은 트랜잭션의 다른 글까지 롤백시키므로 글마다 트랜잭션을 나눠야 한다. version 칸 마이그레이션도 필요하다.
3. **기다리는 시간이 짧다.** 틈이 작업 트랜잭션 한 번(밀리초)이다.
4. **기존 방식과 같다.** 공감·댓글이 이미 `lockById`로 줄을 선다.

다만 3.5의 **긴 틈**(두 기기에서 동시 편집)은 이 방법으로 못 막는다. 그건 `@Version` + 화면이 version을 들고 다니는 방식으로 따로 다룰 일이다(이번 범위 밖).

## 6. 자주 하는 실수와 함정

| 실수 | 무슨 일이 생기나 | 이렇게 |
| --- | --- | --- |
| "DB가 바뀐 걸 알아서 막아 주겠지" | READ COMMITTED는 WHERE만 다시 본다. `WHERE id = ?`는 그대로 덮어쓴다 | 조건을 WHERE에 넣거나, 읽기 전에 잠그거나, `@Version` |
| 엔티티를 읽은 **뒤에** 잠금 | 이미 옛 값을 들고 있어서 소용없다. 같은 엔티티는 영속성 컨텍스트가 돌려줘서 다시 읽어도 옛 값이다 | 잠금을 트랜잭션 첫 문장으로 |
| 여러 행을 아무 순서로 잠금 | 데드락 | 번호 순서(`order by id`) |
| 조건부 UPDATE의 반환값을 안 봄 | 0행인데 "발행했다"며 이벤트를 보냄 | `== 1`일 때만 다음 일 |
| 이벤트에 엔티티 값을 실음 | 커밋 전·옛 값이 퍼짐 | 번호만 싣고, 받는 쪽이 커밋 뒤 다시 읽기 |
| advisory lock을 연결 단위로 쓰고 안 풂 | 풀이 그 연결을 돌려쓰면 다른 요청이 잠금을 쥔 채가 됨 | `pg_try_advisory_xact_lock`(트랜잭션 끝에 풀림) |
| `xact` 잠금을 트랜잭션 밖에서 | 문장이 끝나자마자 풀려 뜻이 없다 | `@Transactional` 메서드 안에서. 프록시 자기 호출도 조심([52](./52-예약-작업과-프록시.md)) |
| 앱 한 대만 켜서 해결 | 그 앱이 꺼진 동안 작업이 멈추고, 앱마다 설정이 달라짐 | 작업이 여러 번 돌아도 맞게(DB가 가르기) |
| 동시성 테스트를 `sleep`으로 | PC 속도에 따라 순서가 바뀌어 가끔만 실패 | 래치·배리어, `pg_stat_activity`로 상태 확인 |
| 고친 코드만 돌려 보고 끝 | 테스트가 버그를 못 잡는지도 모름 | 고치기 전 코드로 한 번 실패를 확인 |

## 7. 직접 해 보기

### 7.1 psql 두 창으로 3.2를 눈으로 보기

개발 DB에 두 창으로 접속한다(`docker exec -it blog-postgres psql -U blog -d blog`). 시험용 글 번호를 하나 정한다(예: 예약 글을 만들어 두고 그 번호).

```sql
-- 창 1
BEGIN;
UPDATE post SET status = 'PUBLISHED' WHERE id = 10 AND status = 'SCHEDULED';   -- UPDATE 1

-- 창 2
SELECT status FROM post WHERE id = 10;          -- 기다리지 않고 SCHEDULED (커밋 전 옛 값)
UPDATE post SET status = 'DRAFT' WHERE id = 10; -- 여기서 멈춤(창 1의 잠금)

-- 창 1
COMMIT;

-- 창 2: UPDATE 1 로 끝난다 → 조건이 없어서 PUBLISHED를 DRAFT로 덮어씀
```

창 2의 UPDATE를 `… WHERE id = 10 AND status = 'SCHEDULED'`로 바꿔 다시 해 보면 `UPDATE 0`이 나온다. 창 2에서 맨 처음 `SELECT id FROM post WHERE id = 10 FOR UPDATE;`를 하면 그 SELECT가 기다리는 것도 본다. 끝나면 글 상태를 원래대로 돌린다.

### 7.2 테스트가 버그를 잡는지

## 8. 확인 문제

1. 갱신 손실이 "오류 없이" 일어난다는 게 왜 위험한가?
<details><summary>답</summary>두 요청 모두 성공 응답을 받아서 아무도 문제를 모른다. 한쪽의 수정이 흔적 없이 사라지고, 로그에도 남지 않는다. 오류가 나는 버그보다 찾기 어렵다.</details>

2. READ COMMITTED에서 다른 트랜잭션이 UPDATE하고 커밋하지 않은 행을 평범한 SELECT로 읽으면? UPDATE하려 하면?
<details><summary>답</summary>SELECT는 기다리지 않고 커밋된 옛 값을 본다(MVCC). UPDATE는 그 행의 잠금이 풀릴 때까지 기다렸다가, 커밋된 최신 행으로 WHERE를 다시 확인해 맞으면 바꾸고 안 맞으면 0행이다.</details>

3. `UPDATE … WHERE id = ? AND status = 'SCHEDULED'`가 늦게 온 쪽에서 0행이 되는 건 DB가 "바뀐 걸 알아채서"인가?
<details><summary>답</summary>아니다. 우리가 WHERE에 status 조건을 적었기 때문이다. DB는 최신 행으로 WHERE만 다시 본다. `WHERE id = ?`만 있으면 그대로 덮어쓴다.</details>

4. JPA 변경 감지로 제목만 바꿨는데 status가 옛 값으로 돌아갈 수 있는 이유는?
<details><summary>답</summary>Hibernate는 기본으로 바뀐 칸만이 아니라 엔티티의 모든 칸을 UPDATE한다. 처음 읽은 status도 같이 쓰므로, 그사이 다른 트랜잭션이 바꾼 status를 옛 값으로 되돌린다.</details>

5. 예약 발행 작업에 조건부 UPDATE를 쓰면 왜 "두 앱 중 한쪽만 이벤트를 보낸다"가 보장되나?
<details><summary>답</summary>판단과 쓰기가 한 문장이라 사이에 틈이 없다. 먼저 UPDATE한 쪽이 행을 잠그고, 늦은 쪽은 기다렸다가 커밋된 PUBLISHED로 WHERE를 다시 봐서 0행이 된다. 반환값이 1일 때만 이벤트를 보낸다.</details>

6. 지원이 찾은 버그에서, 작업 쪽에 조건부 UPDATE가 있는데도 덮어쓰기가 일어난 이유를 두 가지로 말하라.
<details><summary>답</summary>① 요청은 작업 커밋 전의 옛 값(SCHEDULED)을 읽어 "되돌릴 수 없다" 검사를 통과했다. ② 요청의 UPDATE는 조건 없이(`WHERE id = ?`) 모든 칸을 써서, 작업의 잠금이 풀린 뒤 발행 상태를 덮어썼다.</details>

7. `lockForChange`를 엔티티를 읽은 뒤에 부르면 왜 소용없나?
<details><summary>답</summary>이미 옛 값을 영속성 컨텍스트에 들고 있다. 잠금을 얻은 뒤 같은 엔티티를 다시 찾아도 컨텍스트가 같은 객체를 돌려줘 옛 값 그대로다. 잠금을 먼저 걸어야 그 뒤의 SELECT가 최신 커밋을 읽는다.</details>

8. `lockAllById`에 `order by p.id`가 없으면 무슨 일이 생길 수 있나?
<details><summary>답</summary>두 요청이 같은 글들을 서로 다른 순서로 잠그면 각자 하나씩 쥐고 상대의 것을 기다리는 데드락이 생긴다. 모두 같은 순서로 잠그면 순환이 생기지 않는다.</details>

9. 새벽 통계에 조건부 UPDATE 대신 advisory lock을 쓴 이유는? 왜 `try`와 `xact`인가?
<details><summary>답</summary>여러 표를 지우고 넣는 묶음이라 행 하나의 조건으로 "누가 할지"를 정할 수 없다. try는 진 앱이 기다리지 않고 바로 끝나게, xact는 트랜잭션이 끝날 때 저절로 풀려 푸는 걸 잊을 일이 없게 하려는 것이다(커넥션 풀에서 연결 단위 잠금은 위험).</details>

10. 한 앱이 새벽 통계를 끝낸 뒤 다른 앱이 또 모으는 건 왜 괜찮은가?
<details><summary>답</summary>지난 7일을 지우고 다시 넣고 누적도 다시 계산하는 작업이라 몇 번 돌려도 결과가 같다. 막아야 하는 것은 겹쳐서 도는 것뿐이다.</details>

11. 이 프로젝트가 `@Version` 대신 비관적 잠금을 고른 이유를 둘 이상 말하라. `@Version`이 필요한 경우는?
<details><summary>답</summary>충돌해도 기다렸다가 최신 상태로 처리해 대부분 둘 다 반영된다(409 재시도가 없다). 409 처리·작업 트랜잭션 쪼개기·마이그레이션이 필요 없다. 틈이 밀리초라 대기 비용이 작고, 공감·댓글이 이미 같은 방식이다. 두 기기에서 화면을 열어 두고 저장하는 긴 틈은 요청이 겹치지 않아 행 잠금으로 못 막으므로 그때 `@Version`이 필요하다.</details>

12. 동시성 테스트에서 `pg_stat_activity`를 보는 이유는? `Thread.sleep(500)`과 무엇이 다른가?
<details><summary>답</summary>요청이 실제로 잠금을 기다리기 시작한 것을 확인한 뒤에 작업을 커밋해야 순서가 매번 같다. sleep은 "아마 그쯤 막혔겠지"라는 추측이라 느린 환경에서 순서가 바뀌어 가끔만 실패한다.</details>
