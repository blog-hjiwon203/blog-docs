# 스텝 26. RSS 피드

> 작업: T141, T142, T143, T144 · 코드 브랜치: `step-26-rss` · 날짜: 2026-11-12 · 결정: research.md R-19, spec.md 2026-11-12 지원 결정(SUB-07)

## 한눈에 보기

지원이 만드는 다른 앱(LOLog)이 여러 블로그의 글을 RSS로 가져가려고 한다. now-log에는 피드가 없어서, 블로그마다 **RSS 2.0 피드** `/@{주소}/rss`를 만들었다. 블로그 주소만 받아도 피드를 찾을 수 있게 블로그 화면 HTML에 **자동 찾기 태그**를 넣고, 머리글에 RSS 링크를 달았다. v1.1.0 마무리 뒤 처음 다시 연 스텝이라 버전을 1.2.0-SNAPSHOT으로 올렸다.

가장 중요한 결정은 **"읽는 쪽에 맞추지 않고 표준대로"**다. LOLog 명세 초안은 `description`만 읽는다. 하지만 RSS 2.0에서 `description`은 요약 칸이고 전체 본문은 Content 모듈의 `content:encoded`가 맡는다. 어느 칸을 읽을지는 읽는 쪽이 정하므로, now-log는 칸을 뜻대로 채우고 LOLog가 `content:encoded`를 먼저 읽도록 맞추기로 했다(지원 결정).

## 요청 흐름

```
[리더] GET /@my-daily                     ← 사람이 준 블로그 주소
   → SpaForwardController: 블로그 확인 → index.html
     head에 <link rel="alternate" type="application/rss+xml" title="소소한 하루" href="http(s)://{플랫폼}/@my-daily/rss">
[리더] GET /@my-daily/rss
   → RssFeedController(/@{address}/rss가 화면 패턴 /{s1}/{s2}보다 구체적)
   → RssFeedService.find: 주소 규칙·DB → 없음 404 / 이사 301 /@새주소/rss / isOpenToOthers 아님 404
       inBlog + visibleTo(null, now) → 최신 20개(카테고리 함께) → RssFeed record로
   → RssFeedWriter: <rss><channel>… <item> title·link·guid·pubDate·category·description·content:encoded
   ← 200 application/rss+xml;charset=UTF-8, Cache-Control: max-age=300
```

## 막혔던 점

- **"RSS 2.0이면 다 맞겠지"**: 처음에는 LOLog 명세(PR #62)를 보며 거기 맞춰 만들려고 했다. 따져 보니 RSS 2.0의 `item` 칸은 모두 선택이라, 본문 전체를 어디 넣을지, `category`에 무엇을 넣을지, 피드를 어떻게 찾는지는 표준이 정하지 않는다. 그 빈칸은 Content 모듈·Autodiscovery·Atom 같은 다른 표준이 메운다. 그래도 "어느 칸을 읽을지"는 읽는 쪽 몫으로 남는다. 지원이 "앱 쪽 방식은 상관없다"고 정해서 now-log는 표준대로 칸을 채웠다. 대신 LOLog 명세의 "`description`만 쓴다"는 "`content:encoded` 먼저"로 고쳐야 now-log 글이 요약 300자로 잘리지 않는다(LOLog 쪽 일, 이 저장소에서는 고치지 않음).
- **태그를 `category`에 넣을까**: 흔히 그렇게 하지만, RSS 2.0에는 태그 칸이 없어서 섞으면 읽는 쪽이 다시 나눌 수 없다. 카테고리 하나만 넣고, 테스트에서 태그를 단 글로 확인했다(지원도 "카테고리에 태그 넣지 마"로 확인).
- **개발 DB의 집밥 글**: 실제 서버로 피드를 받아 보니 `맛집·요리/집밥` 글 3개가 나왔다. 운영에서는 이 카테고리가 비공개라 404인 글들이라 피드가 새는 줄 알았다. 개발 DB를 보니 집밥 카테고리가 공개(`is_private = false`)였고, 글 API도 200이었다. 피드가 목록과 같은 조건(`visibleTo`)을 쓰므로 둘이 같은 답을 내는 것이 맞다.
- **`/@주소/rss`가 화면 패턴에 먹히지 않을까**: 화면 주소 `/{s1}/{s2}`도 이 주소에 맞는다. Spring MVC는 더 구체적인 패턴을 고르므로 `/@{address}/rss`가 이긴다. 테스트가 이 주소에서 XML을 받는 것으로 확인한다.

## 명세와 다르거나 아직 채우지 않은 것

- 조건부 요청(`ETag`·`Last-Modified` → 304)은 넣지 않았다. 피드가 글 20개라 작다(R-19 남은 것).
- Atom 피드는 내지 않는다. 필요하면 `/@{주소}/atom`으로 더한다.
- 이용 제한 블로그를 주인이 볼 때도 머리글에 RSS 링크는 보인다(눌러 보면 404). 블로그 응답에 이용 제한 여부가 없어서다. 자동 찾기 태그는 넣지 않는다.
- 다른 블로그로 옮긴 글은 `guid`(글 주소)가 바뀌어 리더가 새 글로 볼 수 있다.

## 직접 해 보기

```bash
docker compose up -d && ./mvnw spring-boot:run
curl -i http://localhost:8080/@my-daily/rss | head -12                     # 200, application/rss+xml, max-age=300
curl -s http://localhost:8080/@my-daily/rss | xmllint --noout - && echo ok  # 올바른 XML
curl -s http://localhost:8080/@my-daily | grep -o '<link rel="alternate"[^>]*>'
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/@nobody-zz/rss   # 404
./mvnw test -Dtest=RssFeedIntegrationTest
```

블로그 화면(`http://blog.test:5173/@my-daily`) 머리글의 RSS를 눌러 피드가 열리는지 보고, 글 하나를 비공개로 바꾼 뒤 피드에서 빠지는지 본다. 운영 배포 뒤에는 피드 주소를 [W3C Feed Validation Service](https://validator.w3.org/feed/)에 넣어 본다.
