# 스텝 27. 조회 중복 판정을 Redis로

> 작업: T141~T142 · 날짜: 2026-11-26 · 결정: research.md R-02 "조회 중복 표시" · 이 스텝은 tasks 표 없이 대화로 진행했고 끝난 뒤 문서에 옮겼다

## 한눈에 보기

Redis 발표("Redis 캐싱 및 활용")를 준비하며 이 프로젝트에서 Redis를 쓰는 곳과 발표 주제(Cache-Aside, TTL, 캐시 무효화, 조회수 집계, 로그인 토큰 관리)를 맞대 봤다. 지원이 정한 기준은 **"Redis를 쓰는 것이 지금 구현보다 나은 경우만 반영하고, 아니면 보고"**였다. 후보를 하나씩 따져서 하나만 바꿨다.

| 후보 | 결과 | 이유 |
| --- | --- | --- |
| 조회 5분 중복 판정 | **바꿈** (T141) | 글 행 잠금이 조회자가 아니라 글 단위라 같은 글을 보는 모든 사람과 공감·댓글이 줄을 섰다. Redis `SET NX EX 300` 한 명령이 같은 일을 잠금 없이 한다 |
| 조회수를 Redis `INCR`로 모아 스케줄러로 DB 반영(Write-Behind) | 안 바꿈 | 반영 전에 죽으면 조회수를 잃고, 인기 점수·통계가 쓰는 `view_log`도 늦어지며, 앱 두 대의 중복 반영 장치가 더 필요하다. 지금 트래픽에서 얻는 것이 작다 |
| Refresh 토큰 로테이션 | 안 바꿈 | 토큰은 이미 Redis에 있다(Redis를 더 쓰는 일이 아니다). 쿠키가 HttpOnly·Secure·host-only라 훔치기 어렵고, 로테이션을 하면 Access가 끝난 순간 화면이 동시에 보내는 API 요청들이 같은 Refresh 토큰을 쓰다 서로를 로그아웃시키는 경합을 따로 막아야 한다 |
| 글 상세 Cache-Aside + 수정 시 삭제 | 안 바꿈 (지원 결정) | 상세는 보는 사람마다 권한을 DB에서 확인해야 해서 캐시해도 줄어드는 DB 일이 거의 없다. 인기 글 `@Cacheable`(TTL 5분)이 이미 Cache-Aside다 |

| 작업 | 만든 것 | 핵심 파일 |
| --- | --- | --- |
| T141 조회 중복 판정 | `lockById` + `existsBy…ViewedAtAfter` → `setIfAbsent("view:seen:{글}:{조회자}", "1", 5분)`. 센 조회만 DB(`view_log` 한 행 + `view_count + 1`). DB가 실패하면 표시를 지움. 안 쓰게 된 `existsBy…` 메서드 삭제 | `post/application/ViewService`, `post/domain/ViewLogRepository` |
| T142 문서 | research R-02, tasks, 개념 [조회수](./concepts/5-기능-설계/06-조회수.md) 4.5·5.4·5.8·6·7·8 보강, [캐시와 저장소 고르기](./concepts/2-데이터/12-캐시와-저장소-고르기.md) 5.11 표, 이 노트 | `blog-docs/…` |

API·응답·화면은 그대로다. 5분 판정 결과도 같다(전에는 "마지막으로 센 기록 시각 + 5분", 지금은 "센 때 건 TTL 5분"이라 같은 순간에 끝난다).

## 요청 흐름

```
POST /api/posts/8/views
  PostController.view
    ① postReadService.readable(...)      볼 수 있는 글인가? 아니면 404·403    [읽기 전용 트랜잭션]
    ② visitorKeys.resolve(...)           "m:42" 또는 "a:<uuid>"
    ③ viewService.record(8, key)
         Redis: SET view:seen:8:m:42 1 NX EX 300
           ├ nil (5분 안에 셌음) → 끝, DB에 안 감
           └ OK  → [트랜잭션] INSERT view_log, UPDATE post SET view_count = view_count + 1, COMMIT
                    (예외면 Redis DEL view:seen:8:m:42 후 다시 던짐)
  ← 204
```

## 막혔던 점

- **Redis는 DB 트랜잭션에 묶이지 않는다.** `@Transactional`이 되돌리는 것은 DB뿐이라, `SET NX`가 성공한 뒤 DB 쓰기가 실패하면 표시만 남아 5분 동안 그 사람의 조회가 안 세진다. 예외에서 키를 지우게 했다. 커밋 순간의 실패는 이 `catch`가 보지 못하는데, 조회 하나를 덜 세는 것이라 받아들였다.
- **테스트에서 "5분 뒤".** 전에는 `view_log.viewed_at`을 6분 앞으로 옮겼지만 이제 판정이 Redis라 소용없다. TTL이 290~300초인지 확인한 뒤 키를 지워서 흉내 낸다.

## 직접 해 보기

```bash
docker compose up -d && ./mvnw spring-boot:run
# 글 하나를 브라우저로 연 뒤
docker exec -it blog-redis redis-cli --scan --pattern 'view:seen:*'
docker exec -it blog-redis redis-cli TTL 'view:seen:<글 번호>:<조회자 키>'   # 300에서 줄어든다
./mvnw test -Dtest=ViewCountIntegrationTest
```

[조회수](./concepts/5-기능-설계/06-조회수.md) 7.4에 `SET NX`를 `hasKey` + `set` 두 명령으로 바꿔 동시 테스트를 깨 보는 실습이 있다.
