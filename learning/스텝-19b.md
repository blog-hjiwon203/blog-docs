# 스텝 19b. 인증 경계 정리

> 작업: T114, T115 · 코드 브랜치: `step-19b-auth-boundary` · 날짜: 2026-10-11 · 스텝 20 앞의 구조 정리(2026-10-11 지원 결정)

## 한눈에 보기

기능은 그대로 두고 인증 코드의 경계를 정리했다. 지원이 처음 생각한 것은 인증 서버와 게이트웨이로 서비스를 나누는 것이었다. 이야기를 나눈 끝에 "이 프로젝트에서는 서비스 분리의 득이 없고 비용만 크다"고 보고, **실행은 하나로 두고 경계만 분명히 하는 모듈러 모놀리스**로 정했다. 이유와 비교는 [55](./concepts/55-모듈-경계와-ArchUnit.md) 3절에 있다.

| 작업 | 만든 것 | 핵심 파일 |
| --- | --- | --- |
| T114 경계 정리 | 인증의 속 11개 클래스(토큰 발급·검증, 토큰 저장소, 로그인 쿠키, 인증·CSRF 필터, 시도 횟수 제한과 설정, 인증 설정)를 `global/auth/`에서 `auth/`의 세 계층으로 옮김. 본인 확인·비밀번호 바꾸기를 `CredentialService`로, 로그인 끝내기를 `LoginSessions`로 모음. 회원 기능(`MeService`, `WithdrawalService`, `MeController`)과 방문자 키(`VisitorKeys`)가 속을 직접 쓰지 않게 함. `global/auth/`에는 입구만 남음 | `auth/application/CredentialService`, `auth/presentation/LoginSessions`, `auth/{domain,application,presentation}/…`, `member/…`, `global/web/VisitorKeys` |
| T115 경계 테스트 | ArchUnit 규칙 4개: 인증의 속, 비밀번호 해시 도구는 `auth`·보안 설정 밖에서 쓰지 않음, domain은 위 계층을 모름, application은 presentation을 모름 | `src/test/.../ArchitectureTest`, `pom.xml`(archunit-junit5 1.4.1) |

## 요청 흐름 (바뀐 곳만)

```
[비밀번호 변경] PUT /api/me/password → MeController → MeService.changePassword
        → CredentialService.changePassword: 이메일 가입 회원? → verifyCurrentPassword(횟수 제한 "password-change:{id}")
          → PasswordRule → 해시 저장

[탈퇴] DELETE /api/me → MeController → WithdrawalService.withdraw
        → CredentialService.verifyCurrentPassword(같은 횟수 제한, 틀리면 401 LOGIN_FAILED) → 블로그·흔적 정리
        → LoginSessions.end: Access 토큰 막기, Refresh 토큰 지우기, 쿠키 지우기   ← 전에는 쿠키만

[빌드] ./mvnw test → ArchitectureTest가 바이트코드를 읽어 경계·계층 규칙 검사 (1초 남짓)
```

## 막혔던 점

- **서비스 분리를 할까 말까**: 지원이 "인증 쪽 모듈을 분리하고 게이트웨이도 넣고 싶다"고 했다. 그래서 인증 서버 + 게이트웨이 구조와 정해야 할 것(토큰 서명 방식, 정지 즉시 차단, DB 나누기)을 정리해 보였다. 지원이 "서비스 분리를 흉내 낸 건데 굳이인가 싶다"고 되물었고, 이 프로젝트에는 나눌 이유가 없다는 데 뜻이 모였다. 서비스나 멀티 모듈 대신 인증 경계 정리만 하기로 했다(plan.md "인증 경계"에 적음).
- **규칙이 정말 잡나**: 규칙이 늘 통과하면 아무것도 안 잡는 규칙일 수도 있다. `MeService`에 인증의 속을 가리키는 코드를 일부러 넣어 실패를 확인했다. 처음에 쿠키 이름 **문자열 상수**로 시험했더니 통과해 버렸다. 컴파일러가 상수 값을 복사해 넣어 바이트코드에 참조가 남지 않기 때문이다. `.class` 참조로 다시 시험해 두 규칙(인증의 속, 계층 방향)이 실패하는 것을 봤다([55](./concepts/55-모듈-경계와-ArchUnit.md) 5.5).
- **테스트 수가 392로 나옴**: 전체 테스트 뒤 보고 파일을 합쳤더니 392개였다. 옮긴 테스트 셋의 옛 보고 파일(`global.auth.…`)이 `target/surefire-reports`에 남아 있었다. 이번 실행분만 세면 367개(363 + 경계 4)다.
- **탈퇴 뒤 토큰**: 로그인 끝내기를 입구 하나로 모으면서, 탈퇴가 쿠키만 지우던 것이 로그아웃처럼 토큰까지 막게 됐다. 이번 스텝에서 동작이 바뀐 유일한 곳이고, 더 안전한 쪽이다(T108 "쿠키·토큰 무효화"에 맞음).
- **확인**: 8081 서버에서 확인용 회원으로 차례로 시험해 모두 스텝 19와 같았다.
  - 로그인 200, 내 정보 200
  - 비밀번호 변경: 틀리면 400 `currentPassword`, 맞으면 204
  - 로그아웃 204 뒤 옛 쿠키로 내 정보 401
  - 새 비밀번호로 로그인 200
  - 탈퇴: 틀리면 401 `LOGIN_FAILED`, 맞으면 204, 그 뒤 옛 쿠키로 401
  - 개발 DB에는 탈퇴한 확인용 회원(경계확인19b)이 남아 있다.
