# 스텝 25. 이중화·무중단 배포

> 작업: T133~T140 · 코드 PR: [#3](https://github.com/blog-hjiwon203/now-log/pull/3)(앱 코드 준비), [#4](https://github.com/blog-hjiwon203/now-log/pull/4)(롤링 배포 스크립트) · 날짜: 2026-10-14~15 · 결정: research.md R-18 · 이 스텝은 tasks 표 없이 대화로 진행했고 끝난 뒤 문서에 옮겼다

## 한눈에 보기

배포할 때마다 수십 초 끊기던 것을 없애려고, 앱을 **두 대 늘 띄우고 한 대씩 바꾸는 롤링 배포**로 바꿨다. 순서는 이랬다.

1. **앱 코드부터**: 두 대에서 같이 돌면 문제가 되는 서버 작업을 고쳤다. 그러다 앱이 한 대여도 있던 경합이 드러났고, 지원이 리뷰로 반대 방향의 경합을 하나 더 찾았다.
2. **헬스체크**: 배포 스크립트가 "새 앱이 요청을 받을 수 있나"를 물을 주소를 만들었다.
3. **배포 스크립트**: 한 대씩 끄고 → 띄우고 → 준비를 확인하고 → 다음 앱으로. 실패하면 옛 이미지로 되돌린다.
4. **학교 nginx**: 설정 파일에 upstream을 넣으면 서버가 10분 안에 자동으로 다시 읽는다. 배포 중에도 200만 나오는 것을 확인했다(T139).

## 요청 흐름

```
[배포] main 병합 → Actions: test → 이미지 → scp → ssh: deploy.sh
[deploy.sh]
  이미지 load(new_image = ID) → 네트워크 → Redis(PING 되면 그대로) → PostgreSQL·Ollama(그대로)
  → 배포 전 이미지 ID 기억(before_image)
  → app-2: stop -t 70 → rm → run 새 → readiness UP? ─아니오→ 되돌리기, exit 1
                                     └예→ 12초
  → app:   stop -t 70 → rm → run 새 → readiness UP? ─아니오→ app 되돌리기 → app-2 되돌리기, exit 1
                                     └예→ 12초
  → 옛 이미지 삭제, "배포 완료"

[사용자 요청, nginx 반영 뒤]
  https://now-log.java21.net → 학교 nginx upstream now_log_java21_net
    → 8460 또는 8461(번갈아). 꺼진 쪽이면 연결 거부 → 다른 쪽으로 다시 보냄, 10초 동안 뺌

[예약 발행, 두 앱에서 1분마다]
  findDueScheduledIds → 글마다 publishIfDue(조건부 UPDATE)
    1행 → 커밋 뒤 이벤트(번호만) → 임베딩 리스너가 DB에서 다시 읽음
    0행 → 다른 앱이 했거나 그사이 예약이 바뀜
[글쓴이 수정·취소]
  lockById(FOR UPDATE) → 읽기 → 판단 → 저장   (작업과 한 줄로 섬)
[새벽 통계, 두 앱에서 0:10]
  try_advisory_xact_lock(1) → true면 모으기, false면 건너뜀
```

## 막혔던 점

- **처음 정리가 사실과 달랐다**: 다른 AI와 나눈 대화를 정리한 문서에 "브랜치 `deploy-two-apps`에 변경을 만들어 뒀다"고 적혀 있었는데, 그런 브랜치는 없었다. 정리 문서도 코드로 확인하고 시작했다.
- **조건부 UPDATE만으로는 반쪽이었다 (지원 리뷰)**: 작업 쪽에 조건을 달아 "작업이 글쓴이 수정을 덮어쓰기"는 막았는데, 지원이 PR #3 리뷰에서 반대 방향을 짚었다. 작업이 UPDATE하고 커밋하기 전에 예약 취소가 옛 상태를 읽고 검사를 통과해, 작업 커밋 뒤 발행을 DRAFT로 덮어쓴다. 재현 테스트로 확인했고(200·DRAFT), 같은 패턴을 찾다 일괄 공개 범위 변경도 발견했다(공개 범위만 바꿨는데 SCHEDULED로 되돌아감). 리뷰 → 수정 커밋 순서가 보이게, 이미 만들어 둔 수정 커밋을 맨 끝으로 옮겨 리뷰 뒤에 올렸다.
- **"DB가 바뀐 걸 알아서 막지 않나?"**: 지원이 물었다. READ COMMITTED는 WHERE만 다시 본다. 작업 쪽이 0행이 되는 건 우리가 `status` 조건을 적었기 때문이다([72](./concepts/72-동시-수정-막기.md) 3.2).
- **낙관적 잠금이면 되지 않나?**: `@Version`으로도 막히지만, 충돌하면 409로 거절되고 작업 쪽 트랜잭션도 쪼개야 한다. 기다렸다가 둘 다 반영하는 비관적 잠금을 골랐다. 이유는 PR #3에 지원 댓글로 남겼다([72](./concepts/72-동시-수정-막기.md) 5.7).
- **틀린 설명을 실험으로 바로잡음**: 처음에 "기본값은 꺼질 때 비동기 작업을 기다리지 않으니 `await-termination: true`를 넣자"고 했다. 설정 메타데이터의 기본값(false)만 보고 판단한 것이었다. 실험해 보니 기본값이 이미 종료 단계에서 30초까지 기다렸고, 그 설정을 켜면 DB를 먼저 닫아 오히려 나빴다. 코드는 그대로 두고 주석으로 남겼다([73](./concepts/73-이중화와-롤링-배포.md) 5.3).
- **Redis를 배포마다 다시 만들고 있었다**: `deploy.sh`를 읽다 발견했다. 앱 한 대일 때는 문제가 없었지만 롤링에서는 살아 있는 앱이 Redis를 잃는다.
- **가짜 docker 시험에서 스크립트 버그**: 되돌리기가 실패해도 다음 앱을 계속 되돌리려다 유일하게 살아 있는 앱을 껐다. 시험 도구 쪽 버그 두 개(이미지 ID의 `:`, 출력 필터)도 고쳤다.
- **그 순간을 테스트로 고정하기**: "작업 UPDATE 후 커밋 전"은 너무 짧아 그냥 돌려서는 안 걸린다. `TransactionTemplate` 안에서 래치로 멈추고, `pg_stat_activity`로 요청이 잠금을 기다리는 걸 본 뒤 커밋했다.
- **nginx는 내가 reload할 수 없다**: 설정 파일은 지원 계정에 있지만 reload는 sudo가 필요하다. 처음에는 고칠 때마다 강사님께 말씀드려야 하는 줄 알았는데, 서버가 10분마다 설정을 자동으로 다시 읽는다고 안내받았다. 다른 학생 설정에서 upstream 두 대를 쓰는 것을 보고 이 방식이 허용됨을 확인했다.
- **서버에서 사이트로 curl하면 `000`**: 반영됐는지 보려고 서버에서 사이트 주소로 요청을 보냈더니 두 앱 모두 받은 흔적이 없었다. 서버는 자기 공인 주소로 다시 들어갈 수 없었다. 사이트 요청은 노트북에서 보내고, 서버에서는 `docker stats`로 두 앱이 보낸 양만 봤다.
- **처음 고친 nginx 설정의 오타**: `proxy_next_upstream … http_502 http_502`로 503이 빠져 있었다.

## 명세와 다르거나 아직 채우지 않은 것

- **서버 한 대 안의 이중화**: 서버·DB·Redis가 죽으면 못 버틴다.
- **두 기기 동시 편집**: 화면을 열어 둔 사이 다른 기기에서 고친 내용을 덮어쓰는 긴 틈은 행 잠금으로 못 막는다(`@Version` + 화면이 version을 들고 다니기, 범위 밖).
- **배포 중 JS 404**: 옛·새 버전이 섞인 몇십 초 동안 생길 수 있다(새로고침하면 풀림).
- **작은 남은 일**: 앱 컨테이너 메모리 상한(`--memory`), 배포 로그의 Ollama 진행 표시 숨기기, 발행 직후 400을 받은 편집 화면이 글 상태를 다시 읽기.
- **앱 이름**: `aigj017-app-1`로 바꿀까 했다가 그대로 두기로 했다(바꾸면 다음 배포에서 옛 컨테이너가 8460을 쥐고 있어 이름 넘기기 처리가 필요하다).
