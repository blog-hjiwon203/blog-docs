# 티스토리형 블로그 Constitution (1팀 공통)

지원, 민주, 서현 세 사람은 각자 다른 언어·프레임워크로 각자의 블로그 서비스를 만든다. 이 헌법은 세 서비스가 모두 "티스토리 같은 블로그"가 되도록 지켜야 할 변하지 않는 원칙을 정한다. 모든 spec, plan, tasks는 이 원칙을 어기면 안 된다.

## Core Principles

### I. What은 함께, How는 각자 (NON-NEGOTIABLE)

- 공통 명세(spec.md)에는 **서비스 밖에서 사용자로서 확인할 수 있는 동작**만 적는다.
- 언어, 프레임워크, DB, 인증 구현, 화면 구성, 디자인, 문구, 구현 수치는 각자의 plan.md에 둔다.
- 요구사항은 세 단계로 나눈다.
  - **공통**: 세 서비스가 같은 규칙으로 구현한다.
  - **선택**: spec.md의 "선택 항목(Variation Points)" 중 하나를 고르고, 고른 방식을 plan.md에 밝힌다.
  - **자율**: 각자 정하며 spec.md에 적지 않는다.

**Rationale**: 세 서비스를 같은 체크리스트로 테스트·비교하려면 관찰 가능한 동작은 같아야 하고, 구현 자유는 보장돼야 한다.

### II. 비공개는 존재 자체를 숨긴다

- 볼 권한이 없는 글·블로그(남의 비공개 글, 관리자가 숨긴 글, 이용 제한된 블로그)는 403이 아니라 **404**로 응답한다.
- 볼 수 없는 글은 목록, 카테고리·태그, 검색, 홈, 인기 글, 피드, 사이드바, 이전·다음 글, **글 개수**에서 모두 빠진다.
- 목록과 개수는 항상 "보는 사람이 볼 수 있는 글"만 센다.

**Rationale**: 글이 있다는 사실만으로도 정보가 샌다.

### III. 공유된 주소는 깨지지 않는다

- 블로그 주소는 개설 후 바꿀 수 없고, 블로그가 삭제돼도 **영구 예약**된다.
- 글 주소는 처음 발행할 때 정해지고, 수정해도 바뀌지 않는다.
- 블로그 이사로 옮긴 글은 옛 주소에서 새 주소로 연결된다.

**Rationale**: 이미 공유된 링크가 깨지거나 남의 블로그로 연결되면 안 된다.

### IV. 권한은 서버가 지킨다

- 모든 행동은 spec.md의 권한표를 따른다.
- 버튼을 숨기는 것만으로는 부족하다. 주소를 직접 입력하거나 요청을 직접 보내도 같은 결과(로그인 안내 / 403 / 404)가 나와야 한다.
- 사용자 입력에 든 스크립트는 어디에 보여도 실행되지 않는다. 다른 사이트가 로그인한 사용자 대신 행동할 수 없다.
- 내부 정보(오류 위치, 서버 구성, 비밀번호, 로그인 정보)는 어디에도 드러나지 않는다.

### V. 제재는 숨김이며 되돌릴 수 있다

- 서비스 관리자는 남의 글·댓글·블로그 **내용을 수정하거나 삭제하지 않는다**. 숨김·제한만 한다.
- 해제하면 위치, 수치, 주소까지 원래대로 돌아간다.
- 제재에는 사유가 반드시 남고, 제재받은 사람은 그 사유를 볼 수 있다.
- 서비스 관리자는 가입이나 화면으로 될 수 없고, 다른 서비스 관리자를 제재할 수 없다.

### VI. 사용자의 입력과 숫자는 잃거나 틀리지 않는다

- 같은 요청을 연달아 보내도 한 번만 처리한다(발행, 댓글, 공감, 구독).
- 공감 수, 댓글 수, 구독자 수, 글 수는 새로고침하면 언제나 실제 값과 같다.
- 저장에 실패하거나 로그인이 만료돼도 쓰던 제목·본문·댓글을 잃지 않는다.
- 여러 단계 작업(글 삭제, 카테고리 삭제, 블로그 이사)은 일부만 처리된 상태로 남지 않는다.
- 되돌릴 수 없는 작업은 실행 전에 한 번 더 확인한다.

### VII. 추적 가능한 ID와 우선순위

- 모든 기능은 `영역코드-두 자리 번호`(예: `POST-03`)의 통합 ID를 가진다. 삭제된 번호는 다시 쓰지 않는다.
- 각자의 plan.md, tasks.md, 커밋, PR은 이 통합 ID를 그대로 쓴다.
- 등급: **P0** 필수(세 사람 모두 구현), **P1** 권장, **P2** 확장. 시기(1차·2차)는 정하지 않는다.
- P0만으로 "가입 → 블로그 개설 → 글 발행 → 다른 사람이 홈에서 발견 → 읽기·댓글·공감" 한 바퀴가 돌아야 한다.

## 범위 제약

- **포함**: 회원·인증, 블로그, 글, 카테고리, 태그, 댓글·방명록, 반응, 구독·피드·알림, 검색, 홈·탐색, 블로그 관리, 서비스 관리, 공통 정책(13개 영역)
- **제외**: 광고·수익화·결제, 모바일 앱, 이메일·푸시 알림, 개인 도메인 연결, 스킨 HTML·CSS 직접 편집, 비회원 댓글
- 날짜·시각은 한국 시간(KST)으로 보여 준다.
- 휴대폰 화면 폭에서 모든 P0 기능을 가로 스크롤 없이 쓸 수 있다.
- 최신 크롬, 사파리, 엣지에서 같은 기능이 동작한다.

## 개발 워크플로

1. 공통 명세 변경은 `specs/001-tistory-blog/spec.md`에서 한다. 선택 항목을 바꾸면 해당 FR과 "선택 항목" 표를 함께 고친다.
2. 미결정 사항(`[NEEDS CLARIFICATION]`)은 세 사람이 합의한 뒤 `/speckit.clarify` 결과로 spec.md의 Clarifications에 옮긴다.
3. 각자 저장소에서 `/speckit.plan`을 실행할 때, 고른 선택 항목 8개와 자율 값(업로드 상한, 로그인 유지 기간, 인기 글 기준 등)을 plan.md에 표로 밝힌다.
4. plan.md의 Constitution Check는 이 문서의 원칙 I~VII을 하나씩 확인한다.
5. 서로의 서비스는 spec.md의 Acceptance Scenarios와 Success Criteria로 교차 테스트한다.

## Governance

- 이 헌법은 다른 모든 문서보다 우선한다. 개인 plan이 원칙과 다르면 그 이유를 plan.md의 Complexity Tracking에 적는다.
- 개정은 세 사람 모두의 동의가 필요하고, 상단 Sync Impact Report와 버전을 함께 고친다.
- 버전 규칙: 원칙 삭제·재정의는 MAJOR, 원칙·절 추가나 실질적 확장은 MINOR, 문구 정리는 PATCH.
